## 一、项目总览与路线图

### 产品定位

面向零基础投资者的 ETF 学习助手。用户用自然语言提问（如"ETF 和股票有什么区别"、"南方标普 ETF 管理费多少"），系统从知识库中检索相关内容，经过重排序后生成准确、易懂的回答。

### 四阶段路线图

| 阶段 | 目标 | 状态 |
|------|------|------|
| P0 | 基础 RAG：混合检索 + 重排序 + 评测框架 | ✅ 已完成 |
| P1 | 内容丰富化：新手文档 + 文档类型标签 + 费率提取优化 | ✅ 已完成 |
| P2 | 事实准确：接入 AkShare 金融 API，费率/净值/规模走 API 直达 | ✅ 已完成 |
| P2.5 | 幻觉防御：阈值拒识 + 防幻觉 Prompt + 知识库扩充 | ✅ 已完成 |
| P3 | 智能决策：LLM 驱动的 Query Rewriter + 智能路由 | ⬜ 未开始 |

### 关键设计决策

1. **用 AkShare 而非爬虫获取金融数据** — AkShare 是国内成熟的开源金融数据接口，覆盖 ETF 费率、净值、规模等结构化数据，比从 PDF 正则提取更可靠
2. **Markdown 优先于 PDF 作为知识源** — Markdown 解析无损耗，PDF（尤其扫描版）需要 OCR，质量不可控
3. **API 路由优先于 RAG** — 事实类问题（费率、净值）直接调 API，不经过向量检索和正则提取，既快又准
4. **规则引擎优先于 LLM** — 意图识别和查询改写先用关键词规则实现，LLM 作为后续优化方向

## 二、P0 阶段：基础 RAG 搭建

> 时间线：2026-03-25 ~ 2026-04-14

### 2.1 知识库初始化

**做了什么：** 处理 5 篇文档（2 份 ETF 招募书 PDF、1 份交易所知识 PDF、2 篇 Markdown 文章），切分为 739 条文本块，存入 Supabase 向量数据库。（截至 P2.5 累计 10 篇文档、1115 条切片）

**踩过的坑：**
1. Supabase 外键约束顺序问题 — 需先创建被引用表
2. HuggingFace 模型下载超时 — 通过设置 `HF_ENDPOINT=https://hf-mirror.com` 国内镜像解决
3. Supabase RLS 权限错误 — 改用 `service_role` 密钥
4. 向量维度不匹配（1536 vs 768）— 通过 `ALTER TABLE` 修改列维度
5. Supabase Storage 文件名无效 — 修正文件名格式

### 2.2 混合检索架构

**做了什么：** 实现 Dense + Sparse + RRF 融合检索：
- Dense：`text2vec-base-chinese` 模型生成 768 维向量，Supabase `match_chunks` RPC 检索
- Sparse：Supabase `match_chunks_fts` RPC 全文检索
- RRF（Reciprocal Rank Fusion）：融合两路检索结果

**为什么：** 单一向量检索对精确实体（基金代码、费率数字）匹配能力不足，全文检索可以补充关键词精确匹配能力。

### 2.3 CrossEncoder 重排序

**做了什么：** 引入 `BAAI/bge-reranker-v2-m3` 模型，对候选 chunk 做交叉注意力重排序。

**为什么：** 向量检索的相似度分数不够精确，CrossEncoder 对 query-document pair 做精细化打分，能显著提升 Top 结果的相关性。

### 2.4 评测框架

**做了什么：** 创建 `test_qa.py`，支持单题测试和批量评测，指标包括：
- Hit@5：Top 5 结果中是否包含相关片段
- MRR（Mean Reciprocal Rank）：首个相关片段的排名倒数
- nDCG@5：归一化折损累积增益
- 费率字段准确率：提取的费率数字是否与预期匹配

### 2.5 基线指标

| 指标 | 结果 |
|------|------|
| Hit@5 | 5/5 (100%) |
| MRR | 1.0 |
| 费率准确率 | 4/5 (80%) |

## 三、P1 阶段：内容丰富化

> 时间线：2026-05-15 ~ 2026-05-18

### 3.1 新增新手入门评测用例

**做了什么：** 在 `eval_cases.json` 中新增 5 道面向 ETF 新手的测试题：
- ETF 和股票有什么区别？
- 新手如何开户买 ETF？
- 红利低波 ETF 适合现在买入吗？
- ETF 有什么优势？
- 该怎么挑选一只好的 ETF？

**为什么：** 原评测只有 5 道费率题，无法评估新手常见问题的检索效果。产品定位是"辅助小白学习"，必须验证入门类问题。

### 3.2 新增 Markdown 文档入库

**做了什么：** 将 3 个 Markdown 文件加入 `data_pipeline.py` 的 `target_files`：
- `ETF新手快速入门.md` — 从零基础到开户实操
- `etf_basic_knowledge.md` — ETF 基础概念
- `dividend_low_volatility_strategy_2026.md` — 红利低波投资策略

**为什么：** 原来只有两只 ETF 的招募书 PDF，内容过于专业。新手问"ETF 和股票有什么区别"时检索不到合适内容。

### 3.3 文档类型标签（doc_type）

**做了什么：** 给每篇文档打上类型标签，全链路透传：

| 修改文件 | 改动内容 |
|---------|---------|
| `data_pipeline.py` | 入库时写入 `document_type` 字段 |
| `embedding_repo.py` | 查询时返回 `doc_type` 字段 |
| `retriever.py` | 透传 `doc_type` 到检索结果 |
| `match_chunks_fts.sql` | SQL 函数返回 `document_type` 列 |
| `qa_service.py` | 新增 `_boost_by_doc_type()` 方法 |

**为什么：** 费率问题需要从招募书提取精确数字，但新手指南里有"管理费通常 0.15%~0.5%/年"这种笼统描述，会干扰提取。打标签后，`prospectus` 类型权重 ×1.5，`guide` 类型权重 ×0.7。

### 3.4 费率提取优先级优化

**做了什么：** 新增 `_is_specific_fee_chunk()` 方法，区分：
- 具体描述（含"年费率计提"、"基金资产净值"）→ 优先提取
- 通用描述（含"通常"、"一般"、"大约"）→ 兜底提取

**为什么：** 入库新手指南后，费率准确率从 80% 降到 40%。正则从"管理费通常 0.15%~0.5%/年"提取出 0.15%，而非招募书中的真实费率 0.50%。

### 3.5 项目结构调整

**做了什么：** 将 `test_qa.py` 从 `ai_etf/` 移到项目根目录。

**为什么：** 原位置导致 `sys.path` 指向错误，`from server.services.qa_service import QAService` 找不到 `server` 包。

### 3.6 Supabase SQL 函数修复

**做了什么：** 重建函数前先执行 `DROP FUNCTION IF EXISTS`。

**为什么：** PostgreSQL 不允许在返回类型不同时直接 `CREATE OR REPLACE FUNCTION`。新增 `document_type` 列后旧函数返回类型冲突。

## 四、P2 阶段：金融 API 集成

> 时间线：2026-05-19

### 4.1 新建 FinanceApiService

**做了什么：** 创建 `server/services/finance_api_service.py`，封装 AkShare 接口：

| 方法 | 功能 |
|------|------|
| `query(question)` | 从问题提取基金名称，自动判断查什么数据 |
| `_query_fees(code)` | 查管理费、托管费、申购费、赎回费 |
| `_query_nav(code)` | 查最新净值 |
| `_query_overview(code)` | 查概览（费率+规模+管理人） |
| `_resolve_fund_code(name)` | 基金名称→代码（快捷映射+模糊匹配） |
| `_extract_fund_name(q)` | 从问题中提取基金名称 |

**为什么：** 之前费率靠正则从文档提取，准确率 80%，容易被科普文干扰。API 返回结构化数据，精确可靠。

### 4.2 QuestionAgent 新增 factual_query 意图

**做了什么：** 在 `question_agent.py` 新增意图识别规则，匹配关键词：净值、规模、收益率、涨跌幅、多少钱、价格。

**为什么：** 这类问题答案是精确数字，不需要从文档检索，应直接调 API。

### 4.3 QAService 新增 API 路由

**做了什么：** `handle_question()` 中意图识别后增加分支：

```
if 意图 == factual_query 或是费率问题:
    调 FinanceApiService.query()
    成功 → 用 API 数据构建 prompt，跳过 RAG
    失败 → 降级到 RAG 流程
```

新增 `_build_api_prompt()` 将 API 数据格式化为 LLM prompt。

**为什么：** 事实类问题走 API 直达，比 RAG 更快更准。保留 RAG 作为降级方案。

### 4.4 评测脚本适配

**做了什么：** `test_qa.py` 中 `source == "api"` 时跳过 chunk 评分，直接标记为通过。

**为什么：** API 路由的题目 `top_chunks` 为空，按 RAG 标准评分会得 0 分，但 API 数据实际是正确的。

### 4.5 pyproject.toml 清理

**做了什么：** 项目名改为 `ai-etf`，删除无用依赖，补充缺失依赖（akshare、fastapi、uvicorn 等）。

**为什么：** 原文件从测试项目复制而来，依赖列表与实际代码不一致。

## 五、P2.5 阶段：幻觉防御与知识库扩充

> 时间线：2026-05-19

### 5.1 幻觉问题

用户问知识库中不存在的内容（如"比特币怎么买"）时，系统仍会检索出"最相似"的文本块，LLM 基于无关上下文编造答案。

### 5.2 第一道防线：Rerank 分数阈值拒识

**做了什么：** 在 `qa_service.py` 中：
- 新增 `RERANK_THRESHOLD = 0.2` 常量
- 新增 `_check_rejection()` 方法：Top1 分数 < 阈值或检索结果为空时触发分层拒识
- 新增 `_handle_no_results()` 方法：ETF 相关问题给引导提示，非 ETF 直接拒识
- 新增 `_is_etf_related()` 方法：60+ 个关键词判断问题是否与 ETF/投资相关
- 新增 `_rerank_and_select()` 方法：拆出重排序逻辑，降低 `handle_question` 复杂度

**分层拒识逻辑：**

| 场景 | source | 行为 |
|------|--------|------|
| 检索到相关内容且分数 ≥ 0.2 | rag | 正常 RAG 流程 |
| ETF 相关但知识库无匹配 | fallback | 通用知识引导 + 免责声明 |
| 非 ETF 问题 | rejected | 直接拒识，prompt 为 None |

### 5.3 第二道防线：Prompt 防幻觉护栏

**做了什么：** 在 `prompt_builder.py` 的 Instructions 区域前置三条强制规则：

1. **事实隔离**：先评估 Context 是否包含回答所需信息
2. **拒绝幻觉**：Context 不足时必须输出"知识库中未找到相关事实"，禁止调用内部知识
3. **格式对齐**：有答案时按格式要求输出

### 5.4 评测脚本适配

**做了什么：** `test_qa.py` 支持三种 source 的评分：
- `source == "api"` → 跳过 chunk 评分，直接通过
- `source == "fallback"` → ETF 相关兜底，视为通过
- `source == "rejected"` → 非 ETF 拒识，与 `expect_reject` 字段对比判断

新增 `_compute_retrieval_metrics()`、`_collect_relevances()`、`_evaluate_fee_fields()` 辅助函数，降低 `_evaluate_case` 复杂度。

### 5.5 知识库扩充

**做了什么：** 新增 4 份 Markdown 知识文档：

| 文件 | 主题 | 切片数 |
|------|------|--------|
| etf_qdii_cross_border.md | QDII ETF 与跨境投资 | 8 |
| etf_tax_rules.md | ETF 税收规则 | 9 |
| etf_trading_rules.md | ETF 交易规则详解 | 14 |
| etf_vs_other_funds.md | ETF vs 其他基金类型 | 8 |

**为什么选这几个主题：**
1. QDII/跨境 ETF — "比特币怎么买"暴露了跨境 ETF 知识缺失
2. 税收规则 — 新手常问"ETF 要交税吗"
3. 交易规则 — T+0/T+1、涨跌停、最小单位等实操问题
4. 基金类型对比 — ETF vs LOF vs 联接基金 vs 货币基金

### 5.6 关键词规则强化（_is_etf_related）

**做了什么：** 将 `_is_etf_related()` 从扁平元组（~60 个关键词）重构为分类字典 `_ETF_KEYWORDS`，共 11 个类别、140+ 个关键词。

| 类别 | 说明 | 示例关键词 |
|------|------|-----------|
| product | 基金产品术语 | etf、基金、指数、qdii、lof、联接 |
| action | 交易行为 | 申购、赎回、定投、买入、卖出、建仓 |
| metric | 收益与风险指标 | 净值、分红、收益率、涨跌、回撤 |
| account | 账户与持仓 | 持仓、份额、仓位、重仓、满仓 |
| market | 市场与交易所 | 证券、交易所、场内、场外 |
| asset | 资产类别 | 股票、债券、黄金、比特币、加密 |
| index | 指数名称 | 纳斯达克、标普、恒生、沪深、中证 |
| sector | 行业板块 | 消费、医药、科技、新能源、半导体 |
| strategy | 投资目标与策略 | 红利、高股息、低波、配置、定投 |
| colloquial | 口语化/暗喻表达 | 标的、品种、敞口、上车、能买吗 |
| fee | 费用相关 | 费率、管理费、托管费、手续费 |

**为什么：** 用户说"想配点美股敞口"、"稳一点的标的"这类暗喻/行业用语时，原关键词无法命中，会误判为非 ETF 问题并触发拒识。扩充后覆盖面显著提升。

**设计原则：**
1. 分类组织便于后续维护和扩展
2. 每个类别独立可读，新增关键词时不会破坏已有结构
3. 覆盖产品术语、交易行为、口语化表达等多个维度，降低误拒率

## 六、Bug 修复记录

### 6.1 模糊匹配返回联接基金（严重）

**问题：** `_resolve_fund_code()` 的匹配算法偏向联接基金。联接基金名字更长（如"嘉实中证500ETF联接A"），字符重叠得分更高。ETF 过滤条件 `"ETF" in name` 也让联接基金通过。

**修复：**
1. 先过滤联接基金（名字/类型含"联接"）
2. 匹配算法改为子串匹配优先
3. ETF 识别改为代码前缀判断（51/15/16/58）

### 6.2 费率准确率降至 40%

**问题：** 入库新手指南后，正则从"管理费通常 0.15%~0.5%/年"提取出 0.15%。

**修复：** 新增 `_is_specific_fee_chunk()` 区分具体/通用描述，优先从具体文档提取。

### 6.3 Supabase SQL 函数返回类型冲突

**问题：** 新增 `document_type` 列后，`CREATE OR REPLACE FUNCTION` 报错"cannot change return type"。

**修复：** 加 `DROP FUNCTION IF EXISTS` 后再创建。

### 6.4 test_qa.py 模块导入失败

**问题：** 文件在 `ai_etf/` 子目录内，`sys.path` 指向错误。

**修复：** 移到项目根目录。

### 6.5 检索结果为空时未触发拒识

**问题：** "比特币怎么买"在知识库扩充后检索返回 0 条结果，绕过了拒识检查。

**修复：** `_check_rejection()` 增加对 `top` 为空的处理，调用 `_handle_no_results()` 做分层拒识。

## 九、已知待改进项与 P3 规划

### 已知问题

1. **模糊匹配不保证选到最主流的 ETF** — 同一指数有多只 ETF 时，匹配结果取决于列表顺序
2. **评测用例覆盖面有限** — 12 道题，缺乏多基金对比、边界条件等测试
3. **`_extract_fund_name` 提取能力有限** — 不支持带空格的名称（"沪深 300"）或英文缩写
4. ~~暗喻/行业用语识别不足~~ — 已通过 11 类 140+ 关键词扩充解决（P2.5）
5. **LLM 调用不在后端** — 当前后端只构建 prompt，实际 LLM 调用在前端/API 层

### P3 规划：Agent 智能决策

| 功能 | 方案 | 优先级 |
|------|------|--------|
| Query Rewriter | 关键词快筛 + LLM 兜底，把暗喻翻译为标准术语 | 高 |
| 智能路由 | 根据问题复杂度决定走 RAG / API / 多轮对话 | 中 |
| 回答质量自评估 | LLM 对自己的回答做可信度评分 | 低 |

**Query Rewriter 方案：**
```
用户提问 → 关键词快筛（_is_etf_related，0 延迟）
  ├─ 命中 → 直接走 RAG
  └─ 未命中 → LLM 轻量判断（~0.5s）
      ├─ ETF 相关 → 输出标准化关键词 → 重新检索
      └─ 非 ETF → 拒识
```
