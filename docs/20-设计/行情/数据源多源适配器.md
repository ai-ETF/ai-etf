## 1. 背景与术语

### 1.1 要解决的问题

需求方原话：

> 当前多处向外请求数据没有设计多源方案（交易日历请求、白名单请求、基金净值曲线请求），采用单一源，如果数据源拒绝了我们的请求，则出现没有数据的情况。

有一次真实事故作证：2026-07-28 ~ 2026-10-13，东财 `push2*` 被拒，`K线/实时/分时/榜单` 全部空掉（`2026-10-数据获取现状.md` §1）。当时的处理是「整体从东财切到新浪」（commit `e711ecb`）—— **一刀切**。本设计要解决的正是「一刀切」这件事。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **源（source）** | 一个具体的数据接口，如「东财 pingzhongdata」。是**取数**的单位 |
| **域名（domain）** | 源所在的服务器地址，如 `fund.eastmoney.com`。是**故障隔离**的单位 |
| **能力（capability）** | 源能提供什么，如 `history` / `latest` / `batch` / `calendar` / `fund_catalog` |
| **调用侧** | 使用数据的业务代码（缓存服务、组合服务、API 层）。**必须对换源无感** |
| **熔断（open）** | 某域名连续失败达到阈值后进入的「暂停使用」状态 |
| **半开（half_open）** | 冷却结束后放行**少量**请求试探，成功即恢复、失败则继续熔断 |
| **域级失败** | 连接层失败：403 / 超时 / 连接被拒 → 整个域名可疑 |
| **接口级失败** | 连接成功但内容不对：`200 + 空数据` / 解析失败 / 字段漂移 → **只有这一个源可疑** |

**域级 / 接口级这条区分是整个设计的地基。** 见 §5.2。

### 1.3 为什么「按域名隔离」而不是「按源隔离」

需求方原话：

> 我希望这个换源可以很灵活，可以只把拒绝我的源换掉，而不是一旦换源，全部都一起从东财换成新浪，可以只把拒绝的哪些域名换掉。

这句话里的「源」和「域名」是同一个东西 —— 上游拒绝我们时，拒的是**出口/域名**，不是某一个接口。所以：

- **故障域 = 域名**。`fund.eastmoney.com` 被拒时，它下面的 pingzhongdata、Fund_JJJZ_Data.aspx、fundcode_search.js **会一起挂**；
- 反之，`api.fund.eastmoney.com` 被拒时，`fund.eastmoney.com` 上的一切**毫发无伤**。

**⚠️ 一个必须先认清的事实**（实测，见 §6.1）：净值线上「看起来有 4 个源」，但其中 2 个同属 `fund.eastmoney.com`。**对「域名被拒」这类故障，它们不构成互备。** 不认清这一点，会高估系统的容错能力。

### 1.4 与缓存文档的边界

本文只回答「数据从哪来、怎么取、坏了怎么办」，不描述「数据存到哪、什么时候更新、业务怎么用」。三篇文档的分工固定为：

| 文档 | 独占内容 |
|---|---|
| 本文 | 源清单、域名/能力、字段映射、失败分类、熔断、超时、日志、契约测试 |
| [`../基金与交易/场外净值缓存.md`](../基金与交易/场外净值缓存.md) | 净值表结构、缓存分层、预热、合并规则、更新调度、订单确认口径 |
| [`../基金与交易/交易日历缓存.md`](../基金与交易/交易日历缓存.md) | 交易日历表、全量拉取、刷新、降级、T 日语义 |

`SourceMeta` / `Source` / `NavPoint` / `CalendarData` 的定义只在本文 §4.2 出现一次；缓存文档引用，不重复定义。

## 2. 现状：三条单源线

### 2.1 净值曲线

| 项 | 现状 |
|---|---|
| 源 | `ak.fund_open_fund_info_em` → `fund.eastmoney.com/pingzhongdata/{code}.js` |
| 调用点 | `finance_api_service.py:215, 659, 691`、`portfolio_service.py:257`（4 处，全部无缓存） |
| 备选 | **无**。且东财还有两条更轻的路径完全没用（`api.fund.eastmoney.com/f10/lsjz`、`fundmobapi`） |
| 失败表现 | 异常被 `except` 吞掉，返回 `{}` / `[]` / `None`（如 `finance_api_service.py:683-685`）→ **页面静默变空，没有可查的痕迹** |

### 2.2 交易日历

| 项 | 现状 |
|---|---|
| 源 | `ak.tool_trade_date_hist_sina()` → `finance.sina.com.cn/realstock/company/klc_td_sh.txt` |

| 失败降级 | 沿用上一次成功的副本，且**不更新日期**（`:76-79`）；**从未成功过**则退化为「周一至周五即交易日」（`:92-95`） |
| 备选 | **无** |
| 特别之处 | 接口本身只是一段 **508 字节的混淆文本**（`对外数据源请求与返回.md` A2）—— **格式一变，解码全废** |

### 2.3 白名单目录

| 环节 | 源 | 域名 | 备注 |
|---|---|---|---|
| 候选发现 | `ak.fund_name_em()` | `fund.eastmoney.com` | 全量 28049 行 / 3.0 MB / 14.54s（实测） |
| 费率分档 | `fund_fee_source.fetch_jjfl()`（**项目自己用 requests 抓**） | `fundf10.eastmoney.com` | 纯 HTML 表格解析，**改版即断** |
| 基础信息 | `fund_fee_source.fetch_basic_info()`（自抓） | `fundmobapi.eastmoney.com` | JSON，字段名是无分隔大写缩写 |

调度：每天 02:17 全量重抓（`spot_cache_scheduler.py:141`），约 4580 请求 / 20–30 分钟。

**这一条线已经是「两个独立域名」了**（`fundf10` 与 `fundmobapi`），但**没有统一的失败/健康概念** —— 每只基金各自 `try/except`，失败只写一行日志（`fund_catalog_sync.py:283`）。

### 2.4 已有的一份「反面教材」

`finance_api_service.py:45-47`：

```python
_consecutive_failures = 0     # 类属性
_next_retry_at = 0            # 类属性
```

这两个是**类属性、全项目一份**，不区分端点。目前只有 spot 用了它们。

**这意味着**：如果直接照搬这套状态给净值、日历、目录各补一份冷却，**任意一个端点的失败会把其它端点一起拖进冷却**。`2026-10-数据获取现状.md` 的 P10 记的就是这件事。新设计必须**按域名分表**，这是硬要求。

## 3. 设计目标

需求方列的条件，逐条落成可检验的设计约束：

| # | 需求 | 设计落点 | 怎么算达标 |
|---|---|---|---|
| **G1** | 新增一源**边际成本低** | 新源 = 实现一个 `Source` 协议 + 注册一行 + 写一个字段映射。**不改调用侧，不改状态机** | 加一个源的 diff 只含一个文件 |
| **G2** | 对调用侧**换源无感** | 调用侧只拿归一化模型，永远不知道数据从哪来 | 调用侧代码里出现不了源名 |
| **G3** | **自由切换**，不做「主/备」硬绑定 | 候选源按 `能力` 检索 + 偏好排序，**逐一尝试直到成功**。偏好是排序，不是绑定 | 首选挂掉后能自动用次选，无需改配置 |
| **G4** | **自动换源策略** | 域名级健康状态机（关闭 / 熔断 / 半开）+ 失败分类 | 故障注入测试：切断某域名，观察是否自动切走 |
| **G5** | 只取**白名单内**的基金 | 源不做过滤，**筛选在调用侧**（缓存服务按白名单筛） | 源接口无「白名单」参数 |
| **G6** | 换源**灵活**，只换被拒的那个域名 | 熔断单位 = 域名；失败分域级 / 接口级 | 切断域名 A，域名 B 不受影响（单测） |
| **G7** | **日志便于日后调整策略** | 结构化事件日志（§7），每次换源 / 熔断 / 恢复都有可解析的一行 | 能用 grep 统计「哪个源最常失败」 |

## 4. 架构

### 4.1 分层

```
   业务层（NavCacheService / trading_calendar / fund_catalog_sync）
        │  只说出「我要什么能力」，说「不要」什么源
        ▼
   ┌────────────────────────────────────────────────────┐
   │  SourceRouter                                      │
   │   pick(capability) -> [源1, 源2, ...]  （按偏好排序、    │
   │                                        已过滤不可用的） │
   │   调用方按顺序尝试，第一个成功即返回                    │
   └───────┬────────────────────────────┬───────────────┘
           │                            │
   ┌───────▼─────────┐          ┌───────▼──────────────┐
   │  Registry        │          │  HealthTracker        │
   │  源名 → Source   │          │  域名 → 健康状态       │
   │  能力 → [源]     │          │  （熔断单位 = 域名）    │
   └───────┬─────────┘          └───────────────────────┘
           │
   ┌───────▼────────────────────────────────────────────┐
   │  Source 实现（每个源一个文件）                        │
   │   · em_pingzhongdata   （history）                   │
   │   · em_fund_jjjz       （batch）                     │
   │   · em_lsjz            （history≤20 / latest）       │
   │   · em_mobile          （latest）                    │
   │   · sina_trade_date    （calendar）                  │
   └───────┬────────────────────────────────────────────┘
           │  只在这里出现 HTTP / akshare / 解析
           ▼
       上游域名
```

**边界很硬**：`HTTP`、`akshare`、`HTML/JS 解析`、`字段名` **只允许出现在 `Source` 实现里**。其它所有层看到的都是归一化模型。

### 4.2 源协议

```python
@dataclass(frozen=True)
class SourceMeta:
    name: str                      # "em_pingzhongdata"，全局唯一，写进数据行的 source 列
    domain: str                    # "fund.eastmoney.com"，熔断单位
    capabilities: frozenset[str]   # history / history_recent / latest / batch / calendar
    priority: int = 100            # 同能力下的默认偏好序（小者优先），可被配置覆盖
    timeout: float = 15.0          # 强制超时（见 §4.5）
    description: str = ""          # 给运维看的：这个源是什么、有什么坑


@dataclass(frozen=True)
class CalendarData:
    """交易日历源的归一化输出。"""
    trading_days: frozenset[date]   # 交易日集合
    coverage_start: date            # 源声明的最早日期
    coverage_end: date              # 源声明的最晚日期
    source: str                     # 源名


class Source(Protocol):
    """源实现接口。HTTP / akshare / 解析只允许出现在这一层。"""

    meta: SourceMeta

    def fetch_history(self, code: str, limit: Optional[int] = None) -> list[NavPoint]:
        """history / history_recent / latest 三种能力共用。

        - limit=None：全量历史，只有声明 history 的源可以接受；
        - limit=N：最近 N 条，history / history_recent / latest 都可以接受；
        - latest 源在 limit=N 时返回最新一条（N 必须 >= 1）。
        """

    def fetch_latest_batch(self, codes: list[str]) -> dict[str, list[NavPoint]]:
        """batch 能力。每个代码返回该源在批量窗口内的全部点（通常是最近两天）。

        返回 list 而不是单个 NavPoint：批量源同时给出「最新一天 + 前一天」，
        缓存服务的合并规则需要前一天来发现更正（场外净值缓存 §4.6）。
        """

    def fetch_calendar(self) -> CalendarData:
        """calendar 能力。"""

    # 按能力实现对应方法；未实现的方法 raise NotImplementedError（不静默返回空）
```

**消费者接口（冻结）**：缓存层只依赖 `SourceRouter`，不直接接触 `Source`：

```python
class SourceRouter:
    def fetch_history(self, code: str) -> list[NavPoint]: ...                       # history
    def fetch_history_recent(self, code: str, limit: int) -> list[NavPoint]: ...    # history / history_recent
    def fetch_latest(self, code: str) -> NavPoint: ...                              # latest / history_recent / history
    def fetch_latest_batch(self, codes: list[str]) -> dict[str, list[NavPoint]]: ...# batch
    def fetch_calendar(self) -> CalendarData: ...                                   # calendar
```

**错误模型（冻结）**：

```python
class FailureKind(str, Enum):
    TIMEOUT = "TIMEOUT"
    HTTP_403 = "HTTP_403"
    HTTP_5XX = "HTTP_5XX"
    HTTP_429 = "HTTP_429"
    CONNECTION_ERROR = "CONNECTION_ERROR"
    EMPTY_PAYLOAD = "EMPTY_PAYLOAD"
    PARSE_ERROR = "PARSE_ERROR"
    SCHEMA_DRIFT = "SCHEMA_DRIFT"
    INVALID_REQUEST = "INVALID_REQUEST"

class SourceError(Exception):
    source: str          # 源名
    kind: FailureKind
    message: str

class AllSourcesFailed(Exception):
    capability: str
    tried: list[dict]    # [{"source": ..., "kind": ..., "error": ...}]
```

**归一化模型**（与净值缓存文档 §4.10 共用）：

```python
@dataclass(frozen=True)
class NavPoint:
    fund_code: str
    nav_date: date                  # 净值归属日 —— 不是拉取日
    unit_nav: Optional[Decimal]
    accumulated_nav: Optional[Decimal]
    daily_growth: Optional[Decimal]
    source: str                     # 哪个源产出的
```

**新增一个源要做的事**（对应 G1）：

1. 写一个类，声明 `SourceMeta`，实现对应能力的方法；
2. 在 `server/sources/registry.py` 的 `default_sources()` 里注册一行；
3. 写一个字段映射函数 + 一条契约测试。

调用侧、状态机、日志、配置**一行都不用改**。

### 4.3 注册表与偏好

```python
# 默认偏好（越小越优先）。可以用环境变量覆盖，语义是「排序」，不是「主/备绑定」。
SOURCE_PRIORITY_OVERRIDE = "NAV_SOURCE_PRIORITY"   # 例：em_lsjz,em_pingzhongdata
```

**为什么用「偏好排序」而不是「主源 + 备源」**（G3）：主/备是硬编码的两级结构，加第三个源时要么升级成三级、要么退化成链式降级。排序列表天然支持 N 个源，且「切换」只是重排。

### 4.4 健康跟踪

```python
@dataclass
class DomainHealth:
    domain: str
    state: str = "closed"              # closed | open | half_open
    consecutive_failures: int = 0
    cooldown_until: float = 0.0        # monotonic 时间戳
    last_success_at: float | None = None
    last_failure_at: float | None = None
    last_failure_kind: str | None = None   # 见 §5.2
    last_error: str | None = None
```

**存储位置**：进程内内存（`dict[str, DomainHealth]` + `threading.Lock`）。

- **为什么不做跨进程/持久化**：熔断状态是**短期**状态（分钟级），重启后重新学习成本很低；持久化反而要处理「重启后旧状态把好域名锁死」的问题。
- **多个 worker 的情况**：若将来跑多进程，每个进程各自熔断（可能重复试探，但不会出错）。**当前部署是单进程**（uvicorn 单 worker，`spot_cache_scheduler` 是进程内 apscheduler），够用。这一点记在 §10 Q5。

**实现补充（2026-10-18）：接口级降级的载体**

原设计只有 `DomainHealth`，「接口级失败只降级该源」缺少落点。实现时增加了一个按**源名**记的短冷却：

```python
@dataclass
class SourceHealth:
    name: str
    degraded_until: float = 0.0   # monotonic；接口级失败的软降级截止时间
```

规则（`server/sources/health.py`）：

- 接口级失败（`EMPTY_PAYLOAD` / `PARSE_ERROR` / `SCHEMA_DRIFT` / `INVALID_REQUEST`）只写 `SourceHealth.degraded_until = now + interface_degrade_cooldown(60s)`，**不触碰域名状态**；
- `pick()` 在**存在其它可用候选**时跳过被软降级的源；若它是**唯一候选**，仍然尝试 —— 否则接口级失败会被放大成「该能力完全不可用」；
- 该源任意一次成功即清除软降级。

**半开试探额度的补充修正**：当 `half_open_probes=1`、`recovery_confirm=2` 且该域名只有一个源时，第一次试探成功后会耗尽额度、永远凑不齐第二次成功确认。实现上在**每次半开试探成功后重置该域的试探额度**（`record_success` 里清空 `probe_used`），使单源域名也能在两次成功后被确认恢复（单测 `test_半开试探连续成功两次才恢复` 覆盖）。

### 4.5 取数方式与超时（对 P4 / `2026-10-数据获取现状.md` P4 的正面处理）

需求方要求「**不要掩盖错误，要将错误暴露出来**」。上游函数无 timeout 意味着「错误」会表现为「整个服务卡住」，这是最糟的暴露方式。

简单格式（JSON / 单个 JS 变量）自解析；复杂格式（HTML 表格、混淆串）继续用 akshare + A 的超时包装 | 两种取数方式并存，需要清晰的边界注释 |

**决策（2026-10-18）：采用 C，并把范围写死。**

| 范围 | 做法 |
|---|---|
| 净值线：`em_pingzhongdata` / `em_fund_jjjz` / `em_lsjz` / `em_mobile` | **自解析直连**，`requests.Session` + 显式 `timeout`，不再经过 akshare |
| 费率页 HTML（`fundf10/jjfl`）、交易日历混淆串、全市场目录 | **继续用 akshare**，外面包超时；不重复造 HTML / 混淆文本解析 |
| 场内行情（`fund_etf_*` / `stock_zh_a_minute`） | 本轮暂缓；恢复时按同一 `Source` 协议接入，优先自解析简单格式 |

**四条硬约束：**

1. **不 fork、不改 `site-packages`、不全局 monkeypatch `requests`。** 只把用到的少数取数/解析逻辑收进 `Source` 实现；复制 akshare 代码时保留 MIT 来源声明。
2. **akshare 精确锁版本**：`pyproject.toml` 从 `^1.12.0` 改为当前验证过的精确版本（落地时为 `1.18.64`）；升级走独立分支，先跑 §8.2 的契约测试。
3. **超时分两种**：自解析源用真 `timeout`；仍走 akshare 的调用用 `ThreadPoolExecutor + future.result(timeout)` 兜底，并明确它**不能杀死底层线程**，只是过渡。
4. **每个实际使用的源一条契约测试**（§8.2），akshare 升级前必须全绿；不铺测试体系。

## 5. 换源策略

### 5.1 选源流程

```python
def pick(capability: str) -> list[Source]:
    """返回按偏好排序、且当前可用的候选源。调用方按顺序尝试。"""
    cands = registry.by_capability(capability)
    now = monotonic()
    usable = []
    for s in cands:
        h = health(s.meta.domain)
        if h.state == "open" and now < h.cooldown_until:
            continue                        # 域名在冷静期，跳过它下面所有源
        if h.state == "open":
            h.state = "half_open"           # 冷静期已过，允许试探
        usable.append(s)
    return sorted(usable, key=lambda s: preference(s))

# 调用方（例如 NavCacheService 取某只基金的历史）
for src in router.pick("history"):
    try:
        points = src.fetch_history(code)
        router.record_success(src)
        return points
    except SourceError as e:
        router.record_failure(src, e)       # 分类、累计、可能触发熔断、写日志
        continue
raise AllSourcesFailed("history", tried=[s.meta.name for s in tried])
```

**关键点**：

- **逐个尝试**，不是「选一个就完事」。所以偏好排序只影响顺序，不影响正确性；
- **全部失败时抛 `AllSourcesFailed`**，带上试过哪些源、各自什么错。**绝不静默返回空**（需求方要求 2）。

### 5.2 失败分类（「域级 vs 接口级」是核心）

| 失败形态 | 分类 | 依据 | 对健康状态的影响 |
|---|---|---|---|
| `HTTP 403`（如新浪 D1 不带 Referer，实测 403） | **域级** | 连接层被拒 | 该**域名**记一次失败 |
| `HTTP 5xx` / `429` | **域级** | 服务端问题 / 限速 | 该**域名**记一次失败 |
| `TIMEOUT` | **域级** | 可能被限速 | 该**域名**记一次失败 |
| `CONNECTION_ERROR`（`RemoteDisconnected` 等） | **域级** | 实测出现过（东财 `index_zh_a_hist` 5.91s 后 `RemoteDisconnected`） | 该**域名**记一次失败 |
| `EMPTY_PAYLOAD`：`200` 但内容是错误对象 | **接口级** | 实例：A7 返回 `{"Data":null,"ErrCode":4}` | **只**让该**源**降级，域名不动 |
| `PARSE_ERROR`：HTML 表格错位 / 混淆串解不开 | **接口级** | 实例：akshare `Length mismatch: Expected axis has 14 elements, new values have 13 elements` | **只**让该**源**降级 |
| `SCHEMA_DRIFT`：列名/列数变了 | **接口级** | 批量接口的列名带日期，**每天都在变**（正常）vs 列数变了（异常） | **只**让该**源**降级 |

**为什么必须分开**：`fund.eastmoney.com` 上的 A7（`pinzhong/LJSYLZS`）实测「200 + 空 Data」。如果这被判成域级失败，**整个 `fund.eastmoney.com` 会被熔断** —— 而 pingzhongdata、fundcode_search.js 全在这个域名上，等于把净值线和白名单线一起打死。**这正是需求方最担心的「一旦换源，全部都一起换」的反面。**

> 这条区分同时也是 G6 的检验点：**切断域名 A 时，域名 B 必须毫发无伤**（测试见 §8）。

### 5.3 状态机

```
                    ┌──────────────────────────────────────┐
                    │                                      │
   ┌────────┐  连续 N 次失败   ┌──────┐   冷却 T 秒   ┌───────────┐
   │ closed │ ───────────────► │ open │ ────────────► │ half_open │
   └────┬───┘                  └──▲───┘               └─────┬─────┘
        │                         │                         │
        │                         │ 试探失败（T 翻倍）        │ 试探成功
        └─────────────────────────┴─────────────────────────┘
                        恢复为 closed（失败计数清零，T 复位）
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `SOURCE_FAILURE_THRESHOLD` | **3** | 连续失败几次进入 open |
| `SOURCE_COOLDOWN_BASE` | **60s** | 首次冷却时长 |
| `SOURCE_COOLDOWN_MAX` | **1800s** | 翻倍上限（与现有 spot 退避 `min(30·2^(n-1), 1800)` 的封顶一致，见 `finance_api_service.py:47` `MAX_BACKOFF`） |
| `SOURCE_HALF_OPEN_PROBES` | **1** | 半开状态每个源放行几次试探 |
| `SOURCE_RECOVERY_CONFIRM` | **2** | 半开连续成功几次才恢复 `closed` |
| `SOURCE_INTERFACE_DEGRADE_COOLDOWN` | **60s** | 接口级失败后该源被软降级的时长（§4.4 实现补充） |

以上参数在 `server/sources/config.py` 的 `AdapterConfig` 中，均可用同名环境变量覆盖。

**「连续」的定义**：域名下任意源的一次**成功**即清零该域名的计数。理由 —— 域名是故障单位，它恢复了就是恢复了。

**半开的粒度**：半开时**每个源各放行 1 次**试探，而不是整个域名只放 1 次。这样能分辨「域名恢复了但某个接口还坏着」。

### 5.4 防抖（避免抖动式切换）

上游抖动时，源会在 closed / open 之间来回跳，导致「同一份数据一半来自 A 一半来自 B」，口径混乱。

| 机制 | 设计 |
|---|---|
| **最短冷却** | 进入 open 后至少 `SOURCE_COOLDOWN_BASE`（60s）内不试 |
| **指数退避** | 每次半开失败，冷却翻倍，上限 1800s |
| **恢复确认** | 半开试探成功后，先累计 `SOURCE_RECOVERY_CONFIRM`（默认 **2**）次连续成功，才标 `closed` |
| **不回切** | 一旦切到次选源，**不主动切回**首选（除非首选被显式重排或进程重启）—— 避免首选半死不活时反复横跳。见 §10 Q2 |

### 5.5 手动换源（对应 Ubuntu 的 `sources.list`）

| 手段 | 载体 | 生效方式 |
|---|---|---|
| 调整偏好顺序 | 环境变量 `NAV_SOURCE_PRIORITY` / `CALENDAR_SOURCE_PRIORITY` / … | 重启生效 |
| 强制停用某域名 | 环境变量 `SOURCE_DENYLIST`（逗号分隔域名，如 `push2delay.eastmoney.com`） | 重启生效 |
| 紧急全量切换 | 同 `SOURCE_DENYLIST` + `*_SOURCE_PRIORITY` 一起改 | 重启生效 |

**为什么不做热更新**：换源是低频运维动作，重启一次的成本远低于「运行时改配置导致状态不一致」的风险。这与项目现有约定一致 —— `server/config/settings.py` 全部是环境变量 + 默认值，没有热加载机制。

| 归一化字段 | `em_pingzhongdata` | `em_fund_jjjz` | `em_lsjz` | `em_mobile` |

**⚠️ 三个必须写进代码注释的坑**：

1. `em_fund_jjjz` 的**日期来自 `showday` 数组**，不要按下标臆造日期，也不要依赖 akshare 拼出来的列名（`2026-10-13-单位净值`）。它的「当日」= **最新已公布日**，不是日历今天（2026-10-14 白天实测，`showday` 仍是 `2026-10-13`）。

## 7. 日志与可观测

需求方原话：「**需要写好日志，方便日后读取日志调整策略**」。

### 7.1 结构化事件日志

每次状态变化产生**一行可解析的 JSON**（用现成的 `logging`，message 就是 JSON 串）：

```json
{"event":"source_result","ts":"2026-10-14T20:03:11+08:00","capability":"history",
 "source":"em_pingzhongdata","domain":"fund.eastmoney.com","ok":false,
 "kind":"TIMEOUT","elapsed_ms":15000,"error":"ReadTimeout(...)"}

{"event":"domain_state","ts":"...","domain":"fund.eastmoney.com",
 "from":"closed","to":"open","consecutive_failures":3,"cooldown_until":"...","trigger":"TIMEOUT"}

{"event":"source_switch","ts":"...","capability":"history",
 "from":"em_pingzhongdata","to":"em_lsjz","reason":"TIMEOUT",
 "tried":["em_pingzhongdata"],"code":"110020"}

{"event":"domain_state","ts":"...","domain":"fund.eastmoney.com",
 "from":"open","to":"half_open","probe_source":"em_pingzhongdata"}

{"event":"all_sources_failed","ts":"...","capability":"history","code":"110020",
 "tried":[{"source":"em_pingzhongdata","kind":"TIMEOUT"},
          {"source":"em_lsjz","kind":"EMPTY_PAYLOAD"}]}
```

### 7.2 为什么这组字段

| 事件 | 用来回答什么问题 |
|---|---|
| `source_result` | 「哪个源最常失败？」「失败都是哪一类？」 |
| `domain_state` | 「熔断发生过几次？是抖动还是持续故障？」（`cooldown_until` 是 `time.monotonic()` 的秒数，不是绝对时间） |
| `source_switch` | 「一天换了多少次源？」（换太频繁 = 参数要调） |
| `all_sources_failed` | **最高优先级告警**：这一刻这个能力**完全没数据** |
| `tried` 字段 | 「换源顺序对不对？」「该不该调整偏好」 |

### 7.3 日志级别约定

| 事件 | 级别 |
|---|---|
| 成功 | `DEBUG`（高频，默认不输出） |
| 单次失败、切换 | `WARNING` |
| 域名熔断、`all_sources_failed` | `ERROR` |
| 首次启动未取到日历 / 净值为空 | `ERROR`（**不要用默认值兜底掩盖** —— 这是需求方「不要掩盖错误」的直接落点） |

### 7.4 区分「正常变化」与「异常」

- `em_fund_jjjz` 的列名**每天变**是**正常**的 → 不记 `SCHEMA_DRIFT`；
- 列**数量**变了（14 → 13）才是**异常** → 记 `SCHEMA_DRIFT`。

**这条区分要靠契约测试来兜**（§8.2），否则「每天变」会把日志刷爆。

## 8. 测试策略

> 用户非测试岗，修 bug 以恢复产品行为为先，**不堆测试体系**（记忆 `user-not-a-tester-minimal-tests`）。下面只列**必须**的。

### 8.1 状态机单测（这是核心逻辑，必须覆盖）

| 用例 | 断言 |
|---|---|
| 连续 3 次失败 | 域名状态 `closed → open`，且记录了 `consecutive_failures=3` |
| 冷却期内取源 | 该源**不在**候选列表里 |
| 冷却结束后取源 | 状态变 `half_open`，放行 1 次试探 |
| 半开试探成功 ×2 | 状态 → `closed`，失败计数清零 |
| 半开试探失败 | 状态 → `open`，冷却**翻倍** |
| **接口级失败（`EMPTY_PAYLOAD`）** | **域名仍为 `closed`**，只有该源被降级 |
| **域级失败（`TIMEOUT`）** | 该域名下**所有**源都被跳过 |
| **切断域名 A** | 域名 B 的源**完全不受影响**（G6 的检验点） |
| 全部源失败 | 抛 `AllSourcesFailed`，**且异常里带上了试过哪些源**（不是静默空） |

### 8.2 契约测试（应对「上游改版」）

沿用 `tests/integration/server/services/test_upstream_contract.py` 的既有模式，**每个源一条**：

- 断言真实返回能被解析成 `NavPoint`（不是「应该能」）；
- 断言**字段结构**（如 `em_fund_jjjz` 的 `datas` 列数 / `showday` 是否可解析，而不是具体日期）；
