# 【暂缓】场内基金行情数据源设计文档

> **状态更新（2026-10-26）：本设计的实施对象已下线，文档仅作历史留存。**
>
> 产品只做场外基金交易，**常规基金不需要实时行情**。因此：
>
> - 删除每 30 秒一次的场内全量行情轮询（`refresh_etf_spot` 任务）与内存哈希表 `_spot_dict`；
> - 一并删除只靠该缓存提供数据的接口：`/market/spot`、`/market/spot/name`、`/market/ranking`、
>   `/market/filter`、`/market/categories`、`/market/category/{cat}`、
>   `/market/money-flow`、`/market/money-flow/name`、`/market/money-flow/ranking`；
> - 详情页不再返回 `realtime`；自选/持仓的行情字段改读最新净值（`fund_nav_state`）；
> - `/market/search` 改查本地目录（`fund_catalog`）：搜场内代码无结果，搜名称出场外基金；
> - 目录外代码（场内 ETF）的净值/详情查询一律 404「不在支持目录内」，不再回退上游 akshare。
>
> 仍保留的场内上游调用：K 线（`/market/kline`）、分时（`/market/intraday`）——它们不依赖
> 上述缓存，是否一并下线留给下一轮决策（见接入方案 §7 Q3 的更新）。
>
> **实施记录见文末 §11**（删除清单、按新语义重写的模块、测试结果、已知残留）。

> **原方案（历史）**：行情取数实现为**两个地位对等的源适配器**（东财 / 新浪）；**每个端点各启用一个源**（配置决定），该端点的源不可用时自动逃生到另一个，也可**随时改配置手动切换（整体或单端点）**。新浪取不到的字段**暂不需要**。（设计灵感：Ubuntu的软件源）
>
> **本期分配**：
>
> | 端点 | 生效源 | 为什么这么分 |
> |---|---|---|
> | 列表 / 快照 | **东财** | 榜单、筛选、资金流向依赖它独有的换手率/量比/委比/内外盘/主力净流入/份额/市值 |
> | K线 | **东财** | 低频（被 1 天文件缓存吸收），东财扛得住；能拿到换手率。周/月线**仍统一由日线重采样**，不用东财原生接口（为让两源产出逐字段一致，§6.2-9） |
> | **分时** | **新浪** | **它是唯一没有缓存、会被前端轮询线性放大的端点**，放到请求最便宜的源上 |
>
> **两条策略原则（关键，勿混淆）**：**实现层完全对等**（同一套接口、同一套归一化、同一套契约测试，没有「只有某某源才走」的分支），降低边际成本；**策略层按端点单活、由配置决定**（不逐请求竞速、不按「谁快」自动择优）——理由见 §5.1。
> **代码状态**：当前分支 `fix/market-source-sina` 上是**「全新浪」实现**（commit `e711ecb`），**与本文目标方案不一致，尚未改造**（差距清单见 §6）。
> **部署状态**：**未部署**（用户 2026-10-13 明确「暂不部署」）。
> **本文所有上游结论均为实测**，标注了时间与原始输出；未实测的一律标「待验证」。

## 1. 术语与背景

### 1.1 我们要解决的问题

前端反馈：**K 线 / 实时行情 / 分时 / 榜单全空**（13 个行情端点里 11 个失效）。根因见 §4：生产服务器出口被东财 push2 集群拒绝。

**对应的实际问题**：过度依赖单一数据源，如果该数据源请求失败，则面临无数据的情况。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **全市场快照** | 一次调用拿到全部场内 ETF 的实时行情（东财 `fund_etf_spot_em`，实测 1643 只；新浪 `fund_etf_category_sina`，实测 1696 只） |
| **`_spot_dict`** | `FinanceApiService` 的**类级内存缓存**，`{"512890": {行情dict}, ...}`，键是**不带市场前缀的 6 位代码**，是全项目行情数据的唯一底座 |
| **行情缓存刷新** | 定时任务每 30 秒调 `refresh_spot_cache()`；交易时段真正拉数，非交易时段跳过（跳过条件的缺陷见 §4.3） |
| **源适配器** | 把某个上游（东财 / 新浪）的取数结果归一化成**规范列名**的一段代码。两个适配器**地位对等**：同一套接口、同一套归一化、同一套契约测试，没有任何「只有某某源才走」的分支 |
| **当前源（active）/ 逃生源** | **策略层**概念：**每个端点**同一时刻只有一个 active 源，由配置决定（§5.7）。这不是「主/次」的代码关系，而是**配置关系**——随时可改，无需改代码 |
| **逃生切换（failover）** | active 源不可用时自动改用另一个。只做「逃生」（当前源明确挂了），**不做「择优」**（谁快用谁）——理由见 §5.1 |
| **push2 系** | 东财行情集群域名族：`push2delay.eastmoney.com`（实时列表）/ `push2his.eastmoney.com`（历史与分钟）/ `push2.eastmoney.com` 等 |
| **冷却（熔断）** | 某源连续失败后，在一段时间内**不再尝试该源**，直接走另一源；避免失败源继续承受全量压力 |
| **交易时段** | 交易日 09:30–15:00（北京时间），唯一来源 `server/services/trading_calendar.py` |

### 1.3 约束（不可违反）

- **接口契约不变**：所有 `/api/market/*` 的 URL、请求参数、响应字段名与结构保持不变。
- **非 Optional float**：`server/models/schemas.py` 的行情字段是非 Optional 的 `float` → 取不到的字段**必须填 `0.0`，不能填 `null`**。
- 不引入付费数据源（个人团队成本不合适）。

## 2. 什么是 akshare

### 2.1 一句话

**akshare 是一个开源的 Python 财经数据库，它自己不生产、不存储、不售卖行情数据**，而是把各家网站**给网页用的公开接口**「翻译」成 pandas DataFrame。

### 2.2 它具体做的三件事

以本项目最核心的调用 `ak.fund_etf_spot_em()`（东财全市场快照）为例，它内部做的是：

1. **拼请求**：硬编码 URL `https://push2delay.eastmoney.com/api/qt/clist/get` 与一串参数，其中包含东财网页端的公开 token `ut=bd1d9ddb04089700cf9c27f6f7426281`、板块过滤 `fs=b:MK0021,...`、字段编号 `fields=f1,f2,f3,...`；
2. **发 HTTP**：用 `requests` 请求，**按 `pz=100` 分页**，直到取完全部 1643 只（实测 **17 个 HTTP 请求**一次快照）；
3. **解析**：把返回 JSON 里的 `f12/f14/f2/f3/...` 字段编号**重命名成中文列名**（`代码/名称/最新价/涨跌幅/...`），并把字符串转成数值、把 `数据日期`/`更新时间` 转成时间戳，最后返回一张 37 列的大表。

**所以 akshare 是「解析器」，不是「供应商」**。数据从哪来、什么时候变、允不允许你取，都不由它控制。

> 本项目用法：**直接调用 akshare 函数，不自己发 HTTP**（例外的两处是 `fund_fee_source.py`、`portfolio_service.py`，它们为费率/持仓页面自建请求头）。
> 版本：本地与生产均为 **akshare 1.18.64**（实测确认）。这个版本号很重要——列名与实现随版本变化，见 §2.4。

### 2.3 三层脆弱性（本设计的出发点）

```
上游页面/接口改版  ──→  akshare 更新适配  ──→  我们升级 akshare 才恢复
上游风控收紧/拒绝  ──→  请求直接失败      ──→  换源 or 降低压力（本次事故）
我们调用不当      ──→  把上游打死        ──→  限速、退避、缓存、多源分流
```

| 层 | 表现 | 已知实例 |
|---|---|---|
| 上游改版 | 列名/字段编号变化 → 解析报错或列对不上 | 本项目既有的 `fund_etf_fund_info_em` 在 akshare 1.18.64 上抛 `Length mismatch` |
| 上游风控 | 请求被拒（TCP/TLS 通但 HTTP 立即断开） | 2026-07-28 ~ 10-13 东财 push2 拒绝生产出口（§4） |
| 我们调用不当 | 把免费接口当自家 API 高频压 | 失败后 24h 每 30 秒无退避重试，近两周 3.1 万次无效日志（§4.3） |

**关键含义**：akshare 没有 SLA、没有配额协商、没有客服，且它封装的都是**别人家的免费公开接口**。「能用」是默认状态，**「被拒绝」是必须预先设计的正常风险**——这就是本方案要「两个源适配器 + 逃生切换 + 退避」而不是「单源直连」的根本原因。

### 2.4 版本管理的硬要求

- **锁版本**（现状：`poetry.lock` 固定 1.18.64）；
- **升级 akshare 前必须先跑真实上游契约测试**（`-m integration_net`，§7），因为它会把列名写死在代码里；
- 升级后要核对本项目的字段映射表（§5.2/§5.3），列名一变，`row.get('最新价')` 会静默变 `0.0`——**这是最危险的失败模式：不报错，只是全变 0**。

## 3. 反爬（风控）与应对

### 3.1 先明确立场

本章的目标是**「不触发对方风控、不滥用免费接口」**，不是「伪装身份绕过检测」。理由很实际：

- 我们没有任何绕过手段能长期有效，也没有对抗的资源；
- 对方封的是**出口 IP**，一被封就是整个产品的地基塌掉（本次已发生 3 周）；
- 因此唯一可持续的策略是：**降低请求量、留退避余量、多源分流**。

### 3.2 对方看到的我们（我们的请求特征，实测）

| 特征 | 东财适配器 | 新浪适配器 |
|---|---|---|
| 域名 | `push2delay.eastmoney.com`（列表）、`push2his.eastmoney.com`（K线/分钟） | `vip.stock.finance.sina.com.cn`（列表）、`quotes.sina.cn` / `finance.sina.com.cn`（分钟、日K） |
| **User-Agent** | **`python-requests/2.32.5`**（requests 默认值，akshare 未显式设置） | 同左 |
| 连接方式 | **每条请求新建 Session 并禁用连接池**（`pool_connections=1, pool_maxsize=1`）→ 无 keep-alive | 裸 `requests.get`（同样无复用） |
| 分页节流 | `time.sleep(random.uniform(0.5, 1.5))`（分页之间，**akshare 内置**） | 单请求，无分页 |
| 超时 | `timeout=15`（东财路径） | **无超时**（`requests.get` 未传 timeout）⚠️ |
| 重试 | `max_retries=3`，退避 `1.0×2^n + U(0.5,1.5)`（**akshare 内置**） | **无重试** |
| 请求数/次快照 | **17 个 HTTP 请求**（`pz=100`，1643 只分 17 页） | **1 个 HTTP 请求** |

> UA 实测：`requests.utils.default_headers()['User-Agent']` → `python-requests/2.32.5`；akshare 这两个函数源码里**没有** `User-Agent`/`Referer` 设置，即它明确告诉对方「我是脚本」。项目里自建请求头的地方见 `server/services/fund_fee_source.py:41-42`（UA + Referer），那是走网页的路径，与行情无关。

**结论**：akshare 已经帮我们做了**分页延迟**和**有限重试**（这两点值得感谢），但它**不做限速、不伪装 UA、不复用连接**——**请求频率与总负载的责任完全在调用方（我们）**。

### 3.3 我们实际的请求量（算账）

轮询间隔 30 秒、交易时段 09:30–11:30 + 13:00–15:00 共 4 小时：

| 方案 | 调用次数/交易日 | HTTP 请求数/交易日 | 说明 |
|---|---|---|---|
| **现状（东财快照，30s）** | 480 | **≈ 8160** | 每次快照 17 个请求；若因故障变成全天候轮询 → 2880 × 17 ≈ **48960/天** |
| **新浪快照（30s）** | 480 | **480** | 单请求，一次拿全 1696 只 |
| 事故期间（东财，失败 + 无退避） | 2880/天（含国庆休市） | ≈ 3 × 失败次数 | 首次分页即失败 → 每次调用触发 akshare 内部 3 次重试（约 1–3 个请求） |

两个必须记住的数字：

1. **东财的一次「全量快照」不是 1 个请求，而是 17 个**（`pz=100` 分页 + 页间 0.5–1.5s 随机延迟）。单次实测 18.8s（生产）/ 24.2s（本地），其中约 16s 是分页之间的 sleep 累加——**这个接口天生就慢，且慢的原因是它自己在自我保护**。
2. **新浪源便宜 17 倍**（480 vs 8160 请求/交易日）。所以「失败时自动逃生到新浪」不仅救可用性，也在给东财减压。

**配置 C 下的分摊**（这就是分源要解决的问题）：

| 端点 | 生效源 | 请求量 | 备注 |
|---|---|---|---|
| 列表/快照 | 东财 | ≈ 8160/交易日 | **固定、必然发生**，是唯一的重负载；东财承受它、并因此能提供全部字段 |
| K线 | 东财 | 每只每天 ≤1 次 | 被 1 天文件缓存吸收，可忽略 |
| 分时 | 新浪 | **无上界**（随用户数 × 轮询频率） | 放在单请求的新浪上；**再给它加 30–60s 缓存**才能真正封顶（措施 11） |

要点：**重负载给字段最全的源，不可控负载给最便宜的源，K线给谁都不痛**。

### 3.4 应对措施清单

#### 已实现（在 `e711ecb` 中）

| # | 措施 | 位置/状态 |
|---|---|---|
| 1 | **只在交易时段拉全量** | `trading_calendar.is_trading_time()`；但**跳过条件有缺陷**：只有缓存非空时才在非交易时段跳过 → 缓存为空则全天候轮询（§4.3）。**必须修** |
| 2 | **失败指数退避** | `refresh_spot_cache()`：失败 `min(30 × 2^(n-1), 1800)` 秒，写入 `_next_retry_at`，冷却期内直接返回不发请求；成功清零 |
| 3 | **多层缓存** | 内存 `_spot_dict`（TTL 30s）、基金列表（TTL 1h）、K 线文件缓存（`/tmp/etf_kline_cache`，TTL 1 天，文件名带源标识）。K 线历史只增不改，1 天缓存把「每个用户点开 K 线」变成「每天最多 1 次上游请求」。**唯一没有缓存的是分时**（→ 措施 11） |
| 4 | **依赖 akshare 内置节流/重试** | 分页 0.5–1.5s 随机延迟 + 3 次带抖动的指数退避重试（§3.2，被动获得） |

#### 待实现（本方案要求）

| # | 措施 | 说明 |
|---|---|---|
| 5 | **多源（适配器 + 逃生切换，按端点）** | 本方案核心：**每个端点**各有一个生效源（配置决定，本期：列表/K线＝东财，分时＝新浪），该源的冷却期内请求改由另一个源服务。既保可用，又把负载分散到两个不同厂商；冷却状态**按端点分开**，一个端点抖动不牵连另一个 |
| 6 | **新浪适配器必须自包超时** | 新浪路径**无 timeout**（§3.2）：上游连接半开时会永久挂住调度任务。必须用 `concurrent.futures` + 超时或包装 requests 超时来兜住 |
| 7 | **K线/分时也要退避** | 现状只有 spot 有退避；`query_kline` / `query_intraday` 失败即返回空，无计数无冷却。改造成多源后，这两个端点**各自**需要一套计数与冷却 |
| 8 | **请求伪装（评估后决定，不是必须）** | 用 `requests.Session` + 浏览器 UA + `Referer`（对齐 `fund_fee_source.py` 的做法），或给 akshare 打补丁注入 header。**代价**：需自行维护请求层、脱离 akshare 升级路径。**建议**：先做 1–7、9–11，观察东财稳定性后再评估；UA 是「降低被误判概率」，不是「绕过」 |
| 9 | **健康可观测** | `/api/market/health` 目前只返回 `{"status":"ok"}`——行情挂了 3 周它照样 ok。应暴露 `spot_count` / `last_success_at` / `consecutive_failures` / **每个端点的当前生效源**（Q7）。分源之后「现在列表用的是哪个源、分时用的是哪个源」必须一眼可见 |
| 10 | **不要把间隔改小** | 30s 已接近「每次快照 18.8s」的占空比极限（63%）。若要提高实时性，应先减少请求数（换单请求源、只拉关注列表），**不是**缩短间隔。本期把**分时**（唯一随用户放大的端点）放到新浪，也是在减少东财的请求压力 |
| 11 | **分时补短缓存** | 分时是唯一**没有缓存**的端点，请求量随「打开分时页的用户数 × 前端轮询频率」线性放大；配置 C 下它走新浪，更不能无缓存。本期加 30–60s 内存缓存（键含端点+代码+生效源）。**这一项的收益可能比换源本身更大** |

#### 明确不做（红线）

- ❌ 不并发打同一端点、不做多线程抓取；
- ❌ 不用多出口 IP / 代理池去分摊规避；
- ❌ 不在非交易时段拉全量（除已有的白名单同步等本来就在凌晨的任务）；
- ❌ 不用「加频率试探」的方式验证对方是否恢复（本次复核只用了个位数请求）。

## 4. 事故根因分析

> 环境：生产服务器，部署目录 `/root/ai-etf`，服务 `fastapi.service`。诊断全程只读，未重启、未改代码。

### 4.1 现象：13 个行情端点逐个实测

```

spot/512890                     → {"data":null,"error":"未找到基金代码: 512890"}
```

**11/13 端点失效，唯一存活的是 `/detail`——它走的是 `fund.eastmoney.com`（另一套域名）。**

### 4.2 上游可达性：东财 push2 出口曾被拒

事故期间的实测（东财侧）：

| 上游 | 结果 |
|---|---|
| `push2delay` / `push2his` / `push2` / `82.push2.*` 等（6 个子域、6 个不同 IP 段） | 全部 `http_code=000`（Empty reply from server） |
| `openssl s_client -connect push2delay.eastmoney.com:443` | `CONNECTED`，证书 `CN=*.eastmoney.com`，`Verify return code: 0 (ok)` |
| 明文 HTTP（80 端口） | 同样 `000` |
| `fund.eastmoney.com` / `datacenter-web.eastmoney.com` / `quote.eastmoney.com` | ✅ 200 |
| 同一时刻从**其它网络**访问同一接口 | ✅ 正常返回真实 JSON |

**当时的结论**：TCP 通、TLS 握手成功，但 HTTP 请求一发出即被立即断开（0.08–0.13s）→ 这是**针对本服务器出口的应用层拒绝**，不是接口下线，不是 akshare 版本问题，代码侧无法绕过。

> 时间线：最后一次成功刷新为 **2026-07-28**（Jul 27/28），此后连续失败约 3 周。

### 4.3 自伤式的重试：为什么事故会持续 3 周

```
journalctl -u fastapi | grep -c 刷新成功  → 25204
journalctl -u fastapi | grep -c 刷新失败  → 36409      ← 近两周每天 2500–2880 次
```

近两周每日失败次数：`09-29: 533 → 10-01: 2070 → 10-02~10-07: 2880/天 → 10-12: 2532`。

**2880 = 24h × 120 次/h**，即交易日与非交易日、甚至国庆休市（10-01~10-08）**都在打**。

**机制（代码缺陷）**：`refresh_spot_cache()` 的跳过条件是

```
if not is_trading_time(...) and cls._spot_dict is not None:   # 缓存非空才跳过
```

一旦持续失败，`_spot_dict` **永远是 `None`**，跳过条件永不成立 → 变成全天候 30 秒一次的失败循环，且**没有任何退避**。

> 无法确证「是这 6 万次请求导致（或加剧）了封禁」，但这是典型会被风控命中的形态，**必须消除**——这也是本次「退避」被并入范围的理由（无论当前源是东财还是新浪，退避都不能没有）。

### 4.4 2026-10-13 复核：**东财出口已自行恢复**

实现完成后复核生产出口（同一天、同一台机器、同一出口，`akshare 1.18.64`）：

| 上游 | 结果 |
|---|---|
| `push2delay` / `push2his` / `push2` | **全部 HTTP 200**（不再是 `000`） |
| `ak.fund_etf_spot_em()` | ✅ **1643 行**，18.8s |
| `ak.fund_etf_hist_em(512890, daily)` | ✅ 185 行，0.1s |
| `ak.fund_etf_hist_min_em(512890, 1min)` | ✅ 1085 行，0.2s |
| `ak.fund_etf_category_sina("ETF基金")` | ✅ 1696 行，5.1s |

**结论与含义**：

1. 「东财封禁」**不是永久状态**，在 2026-07-28 ~ 2026-10-13 期间持续，之后**自行解除**。成因无法从服务器侧确证（§3.3 的高频请求是最大嫌疑，属推断）；
2. 因此「换源」不是**唯一活路**，而是**权衡选择**；
3. 正因如此，本次决策改为 **两个对等源适配器 + 按端点单活源 + 可随时切换**：日常列表/K线用东财（字段完整）、分时用新浪（无缓存、负载不可控），某个端点的源不可用时自动逃生到另一个（可用性不依赖单源），同时用退避防止再次把任一源打死；
4. **但「已恢复」不等于「可靠」**：它拒绝过我们一次且持续 3 周，必须假设还会发生 → 多源与退避不是可选项。

### 4.5 为什么恰好是「K线/实时/分时/榜单」全空

这四类恰好是走 **push2 系域名**的那几类；`/detail` 走 `fund.eastmoney.com` 所以活着——这也解释了「为什么详情页正常、其它全空」的现象。

## 5. 目标方案：对等源适配器 + 单活源 + 可随时切换

### 5.1 总览

**一句话**：两个源在**实现上对等**，在**策略上按端点单活、由配置决定**——「随时能切」靠的是实现对称，「不来回跳」靠的是配置 + 冷却 + 防抖，而不是运行时打分。

```
   /api/market/*  ──→  FinanceApiService.query_xxx（端点已知：spot / kline / intraday）
                                │
                                │ ① 缓存命中？ → 直接返回（列表 30s / K线 1天 / 分时 30–60s）
                                ↓
                    ┌───────────────────────────────────────┐
                    │ 取该端点的 active 源（配置，§5.7）      │
                    │ 例：spot→eastmoney  kline→eastmoney    │
                    │     intraday→sina                      │
                    └───────────────┬───────────────────────┘
                                    │ active 在冷却期？→ 换另一个源（逃生）
                                    ↓
                 ┌──────────────────────┐   ┌──────────────────────┐
                 │  EastmoneySource     │   │  SinaSource          │
                 │  (适配器, 对等)       │   │  (适配器, 对等)       │
                 └──────────┬───────────┘   └──────────┬───────────┘
                            │ 成功                     │ 成功
                            ↓                          ↓
         ┌────────────────────────────────────────────────────────┐
         │  归一化层（共用，与源无关）                              │
         │  规范列名 · 单位统一 · 剔当日未收盘K线 · 缺失→0 · 日期格式 │
         └────────────────────────┬───────────────────────────────┘
                                  ↓
                    缓存 → 返回（响应结构与生效源无关）
              失败 → 计失败 + 进冷却（**每端点、每源各一份计数**）
```

**本期分配**（配置 C，理由见 §5.7）：

| 端点 | 生效源 | 逃生源 | 选择依据 |
|---|---|---|---|
| 列表 / 快照 | 东财 | 新浪 | 字段完整度（榜单/筛选/资金流向必需） |
| K线 | 东财 | 新浪 | 低频，用慢但字段全的源；有文件缓存吸收 |
| 分时 | 新浪 | 东财 | **无缓存、会随用户/轮询线性放大** → 用请求最便宜的源 |

**五条设计原则**：

1. **实现层完全对等**（两个适配器同一接口、同一归一化、同一套契约测试）。这是「随时切换」能成立的前提：切换只改配置，不改代码。也让将来加第三个源（腾讯）只是再写一个适配器。
2. **按端点单活，源由配置决定；不逐请求竞速、不按「谁快」自动择优**。理由是本方案最重要的一条：**两个源在实现上可以等价，在输出上不等价**——东财快照 37 列（含换手率/量比/委比/内外盘/主力净流入/份额/市值），新浪只有 13 列；成交量单位还差 100 倍。若「无差别对待」到逐请求选源，同一个页面会出现「今天有换手率、明天变 0」「成交量在 100 倍上下跳」——**稳定地少几个字段，远比数字自己会变好**。
3. **自动切换只做「逃生」，不做「择优」**。两个源都返回 200 时，任何健康度/延迟打分都判断不出**谁的数据更新、谁的口径对**（实测就存在两源都「正常」但口径不同的情况：盘中东财日K含当日未收盘K线、新浪不含）。**健康的源 ≠ 正确的源**，这个判断只能由人给配置。另：两源延迟差 3.7 倍，按延迟择优必然抖动（flapping）。
4. **端点内不混源，端点之间允许不同源**。同一份响应只来自一个源（字段级混源会让同一响应里出现「价格来自新浪、换手率来自东财、时间来自第三个时刻」）。但列表用东财、分时用新浪是允许的——**代价是引入了跨端点的少量不一致**，且有一条**跨端点数据依赖**要守住（分时的昨收基准，按 §5.5-4 优先取自 K 线）。
5. **冷却期不再打该源**：失败源在冷却期内完全不接收请求，否则「多源」只是把失败源的负载照旧压上去，等于没兜；且同一份请求量摊到两个源上，正好与 §3 反爬的目标相反（东财一次快照 17 个请求，均摊毫无收益）。

**本期分配（配置 C）下的净结论**：列表与 K线都走东财 → **这两个端点在正常态下没有字段损失**（换手率、量比、外盘内盘、委比、资金流向、份额、市值全部可用）。两处已知取舍：①**周/月线**不用东财原生接口、统一重采样（换来两源逐字段一致，见上）；②**分时**走新浪，没有原生 `均价`，由 `amount/volume` 计算（东财有原生均价，两者算法略有差异，属可接受），且分时成交量需换算（§5.5-1）。**上表中的字段损失只在「逃生到新浪」期间发生**——不再是常态。

### 5.5 必须在归一化层统一的两源差异（**最重要的实现细节**）

> 不处理这几处，「换源对前端透明」就是假的——数据会静默错，不报错。**其中第 1 条（成交量单位）在配置 C 分源后从「换源时才痛」变成「常态就痛」**。

**1. 成交量单位：东财是「手」，新浪是「份」，相差约 100 倍** ⚠️

实测同一只、同一时刻（`512890`，2026-10-13）：

| 源 | 字段 | 值 | 单位 |
|---|---|---|---|
| 东财 spot | `成交量` | `3608627.0` | **手**（取整） |
| 新浪 spot | `成交量` | `360862713` | **份** |
| 东财分钟 | `成交量` | `9458` | 手 |
| 新浪分钟 | `volume` | `945700` | 份 |

`成交额` 两源一致（元）：`442962540`。

**这就是为什么必须归一化**：本项目旧实现（东财）直接把 `成交量` 塞进 `volume`，所以契约里的 `volume` 历史单位是**手**；若切到新浪时直接透出新值，前端成交量显示与排序会瞬间放大 100 倍，且**用户看到的是同一只基金的两次不同数字**。
→ **决策（2026-10-13 用户已定）：统一为「份」**。理由：本产品**主要做场外交易**，成交/申赎不涉及「手」这个单位，展示口径取更直观的**份额**即可；「份」也是绝大多数行情软件的展示单位。换算在**适配器出口**完成——东财的「手」×100 转为「份」后，两源、两缓存、两适配器只剩一个单位。代价：相对历史契约（手）会变一次，属**一次性的、可接受的**口径切换（本次一并把它写进验收清单，§8）。

**⚠️ 本期分源后新增的陷阱（必须处理）**：配置 C 下**列表走东财（成交量＝手）、分时走新浪（＝份）**，而 `IntradayResponse` 里

- `total_volume` 取自**列表快照**（东财 → 手）
- `items[].volume` 取自**分时接口**（新浪 → 份）

→ **同一份响应里两个成交量字段会差 100 倍**。这不是假设，是分源后的必然结果：现分支（全新浪）两处都是「份」所以看不出来，一旦按配置 C 分源就会暴露。**归一化层必须把分时的点位成交量与其汇总值换算到同一口径**（**统一为「份」，已定**），并在 §8 验收里逐字段比对。

**2. 日 K 是否含当日未收盘的 K 线：东财含、新浪不含**

| 源 | 盘中（2026-10-13 上午）日K 最后一根 |
|---|---|
| 东财 `fund_etf_hist_em` | `2026-10-13`（含当日，未收盘） |
| 新浪 `fund_etf_hist_sina` | `2026-10-12`（不含当日） |

若不统一，K 线图的最后一根会「同一个页面刷新两次，时而有时而无」，切换源时更会跳变。
→ **建议统一为「剔除当日未收盘 K 线」**：盘中当日走势由 `/spot`（实时价）与 `/intraday`（分时）承担，K 线只画已收盘的完整 K 线，职责更清晰，也更符合「K 线是历史」的语义。

**3. 分钟窗口都跨多日，必须按「今天（北京日期）」过滤**

东财 1085 根（5 天）、新浪 1970 根（9 天）——**两源实测都是滚动窗口**，不过滤会把十几天画成一天。

**4. 分时涨跌幅口径**：统一为**相对昨收**（旧实现是「相对当日首点」，与行情页对不上，属既有缺陷，本次一并对齐）。

昨收的取法在分源后要**明确顺序**（不能只依赖快照）：

```
① 本端点（当日）K 线的前一日收盘   ← 首选：与 /kline 口径天然一致，与分时同属「行情序列」
② 列表快照的 prev_close            ← 回落：K 线取不到时用（注意跨端点依赖，见 §5.7）
③ 再取不到 → 该点 change_pct = 0.0，不抛错
```

为什么把顺序倒过来（原设计是快照优先）：配置 C 下**列表走东财、分时走新浪**，若昨收取自东财快照，则**分时这一路的正确性依赖列表那一路的可用性**，列表逃生到新浪时昨收口径还会跟着变。改成「K 线优先」后，分时（新浪）只依赖 K 线（东财）的日线序列，基准更稳定，也与 `/kline` 最后一根的涨跌幅**天然对得上**（验收项见 §8）。

**5. 缺失字段一律 `0.0`**（不是 `null`）：契约是非 Optional float，§1.3。

### 5.6 缓存与职责边界

| 层 | 载体 | TTL | 职责 |
|---|---|---|---|
| 内存行情 | `_spot_dict`（类级） | 30s | 全项目行情底座；定时任务刷新，接口只读 |
| 基金列表 | `_fund_list_cache` | 1h | 名称 ↔ 代码解析 |
| K 线 | `/tmp/etf_kline_cache/*.json` | 1 天 | 历史只增不改；**文件名带源标识**（如 `512890_daily_sina.json`），避免换源后命中旧列名缓存 |
| 分时 | **当前无缓存**（本期补：内存 30–60s） | — | 键含**端点 + 基金代码 + 生效源**；不加这张缓存，分时请求量随用户数线性放大 |
| 失败冷却 | `_fail_streak` / `_next_retry_at` | 30s → 30min | **按端点独立**，不进文件 |

**缓存必须存「归一化后」的数据**（统一列名、统一单位、统一日期格式），不存上游原始表——否则换源/升级后缓存与新解析器串味（这是旧实现踩过的坑：缓存里是东财列名，新代码按 `df['date']` 取值直接 KeyError）。

**缓存与「切换源」的相互作用**（对称模型的直接后果；切换机制本身见 §5.7）：

| 缓存 | 切换源时会发生什么 | 处理 |
|---|---|---|
| 内存行情 `_spot_dict`（30s） | 最长 30s 内还挂着旧源的字段（如从新浪切到东财，`turnover_rate` 要等下一次刷新才非 0） | 可接受，不自愈以外的动作。**不必**清缓存——30s 内自动重建 |
| K 线文件缓存（1 天，路径带源标识） | 切换后**自然走另一个源自己的缓存**，不会串味；代价是可能读到另一个源 1 天内的旧数据 | 可接受（历史 K 线只增不改）。若要求切换后立即可信，清一次 `/tmp/etf_kline_cache` 即可 |
| 分时短缓存（本期新增，30–60s） | 切换后最长 1 分钟内仍返回旧源数据 | 可接受。**键里带上生效源**，切换后立即换键，实际不会串味 |

**切换动作 = 改配置 + 等一个刷新周期**（内存 30s / 分时 30–60s / K线 1 天）。**不做「切换时清空全部缓存」的复杂流程**——分源缓存路径已经把串味问题挡在外面。

**按端点切源时，缓存影响面也是按端点的**：把 `/intraday` 切到另一个源，只影响分时那张短缓存；列表的内存快照与 K 线文件缓存**完全不动**。

### 5.7 源适配器接口、切换与防抖

**适配器接口（两个实现都满足，无主次）**：

```
class MarketSource(Protocol):
    name: str                                   # "eastmoney" / "sina"
    def fetch_spot(self) -> DataFrame           # → 规范列名（含 code 用裸 6 位码）
    def fetch_daily_kline(self, code) -> DataFrame   # → date/open/high/low/close/volume/amount
    def fetch_intraday(self, code) -> DataFrame      # → day/open/high/low/close/volume/amount
```

两边都**只管取数 + 把上游列名翻译成规范列名**；单位换算、剔当日K线、缺失填 0、重采样这些**放在共用的归一化层**（否则两个适配器会各写一遍，早晚不一致）。

**配置形态：默认值 + 按端点覆盖**（用户 2026-10-13 选定）：

```
default_source: "eastmoney"                 # 兜底：没被 override 的端点都走它
source_overrides:                           # 只写需要偏离默认的端点
  intraday: "sina"                          # ← 本期分时走新浪
                                            # spot / kline 不写 = 跟随 default = 东财

解析规则：来源 = source_overrides.get(endpoint) or default_source
运维含义：① 一句话整体切（改 default_source，同时清空 overrides）；
         ② 单独调某一类（只改对应的 override 项）；
         ③ 改完即生效，无需改代码、无需重启。
```

**选源与冷却（每**端点**各持一份状态）**：

```
每端点每源状态 : _fail_streak[src][endpoint] / _next_retry_at[src][endpoint]

选源逻辑（endpoint 已知：spot / kline / intraday）：
  primary = source_overrides.get(endpoint) or default_source    # 配置给的
  backup  = "sina" if primary == "eastmoney" else "eastmoney"

  if now >= _next_retry_at[primary][endpoint]:   # primary 不在冷却期
      用 primary
  else:                                          # primary 明确挂了 → 逃生
      用 backup（日志与健康指标标注「降级中」）
  两个都不可用 → 返回空 + 健康指标暴露（§3.4-9）
```

**为什么状态要按端点分开**：一个端点的失败不该牵连另一个。实例——东财列表失败进入冷却的 10 分钟里，**K线仍然可以正常走东财**（它们是不同的上游路径：`push2delay` vs `push2his`，实测可达性也确实可以不同）。若共用一个计数，列表的抖动会把 K线一起拖下水。

**切换的两条路径**：

| 路径 | 触发 | 特点 |
|---|---|---|
| **自动逃生** | 该端点的生效源（primary）连续失败（进入冷却） | 快（下一次请求即生效）、无需人工；**只救可用性，不做择优**（原则 3）；**只影响该端点** |
| **手动切换** | 改配置（整体或单端点） | 用于对方风控公告、数据可疑、例行演练；**改完即生效，无需改代码、无需重启** |

**本期分配的理由（为什么是「列表+K线走东财、分时走新浪」）**：

三类端点的负载特征完全不同，这才是分源的意义（§3.3 有完整算账）：

| 端点 | 触发方式 | 频次 | 东财成本 | 新浪成本 |
|---|---|---|---|---|
| 列表 / 快照 | **定时任务** | 480 次/交易日，**固定必然发生** | 17 请求 · 18.8s | 1 请求 · 5.1s |
| K线 | 用户 | 每只每周期 ≈1 次（**被 1 天文件缓存吸收**） | 1 请求 · 0.1s | 1 请求 |
| 分时 | 用户 | **无缓存 → 每次请求都打上游**（前端若轮询则随用户数线性放大） | 1 请求 · 0.2s（原生均价） | ≤2 请求 · 0.6s |

- **列表选东财，是因为字段**：换手率/量比/委比/内外盘/主力净流入/份额/市值**只有东财有**，而 `/ranking`、`/filter`、`/money-flow`、`/categories`、`/spot` 全建在快照上。代价明确：东财要承受 **8160 请求/交易日 + 18.8s/30s（63% 占空比）**，这是**已知并接受**的成本，缓解手段见 Q12。
- **K线选东财，是因为它便宜得可以忽略**：被 1 天文件缓存吸收后，每只每天最多 1 次请求，东财的「慢」在这里没有代价；换来换手率与原生周/月线（不必重采样）。
- **分时选新浪，是因为它最不可控**：它是三类里**唯一没有缓存**的，请求量随「打开分时页的用户数 × 前端轮询频率」放大。把它放在**请求最便宜、实测对 30 秒轮询最宽容**的源上，风险最小。

> ⚠️ **顺带发现（与选源无关，但收益更大）**：分时当前**完全没有缓存**（每次请求都打上游）。建议加一个短缓存（如 60s）——若前端在轮询，这一项的请求量可能比定时任务还大。**这比换源更直接地砍请求量。**

**跨端点数据依赖（混源后必须守住的一条）**：分时的涨跌幅基准是昨收，原设计取自列表快照，于是「分时（新浪）」会依赖「列表（东财）」的可用性，列表逃生时分时的基准还会跟着变。**按 §5.5-4 的修订**：昨收改为**优先取本端点当日 K 线的前一日收盘**，快照只作为回落 → 分时只依赖**K线**这一路（本期同在东财），依赖面收窄。但**只要端点间还共享任何数据，就要显式写进验收清单**（§8），不能靠「碰巧一致」。

**防抖（必须有，否则会来回跳）**：

- 切换后给**原源一个最小保持期**（建议 10 分钟）：期间即使原源恢复也不回切；
- 冷却时间沿用指数退避（`30s × 2^(n-1)`，上限 30 分钟），避免「恢复→立刻失败→再切」的死循环；
- 手动切换**不受保持期限制**（人工优先）。

**「随时切换」的护栏＝两源一致性测试**：能在任何时候切的前提是「切了以后前端看不出区别」。因此**两个适配器必须跑同一组契约测试并断言产出逐字段一致**（§7），这条测试比实现本身更重要——它是「对等」这个说法的唯一证据。
