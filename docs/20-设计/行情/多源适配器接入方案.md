## 1. 背景与术语

### 1.1 为什么需要这次接入

`server/sources/` 的多源适配器已经把「净值线 4 个源 + 日历线 1 个源 + 路由 / 熔断 / 降级 / 结构化事件」实现完毕，但生产环境里**只有交易日历消费它**：

- 日历：`TradingCalendarCache` 通过 `SourceRouter.fetch_calendar()` 取数，链路完整；
- 净值：`FinanceApiService`、`PortfolioService` 仍然直接 `import akshare as ak`，适配器没有任何业务消费方。

这不是「再写一个源」的问题，而是**接入口缺失**：如果没有一个统一的消费方，业务会各自处理选源、超时、失败分类、白名单过滤，适配器的语义会被绕过，最终又长出一条新旧并存的旁路。

本方案的目标是建立**唯一消费方**，并把它拆成方向相反的两条边：

```
业务读：业务服务 → FundNavService → Supabase(fund_nav*)
数据写：调度器/脚本 → FundNavSyncService → SourceRouter → 各 Source → Supabase
```

读路径不触网、写路径不出现在请求线程里（唯一例外是详情页首次查看某个基金的历史，见 §4.6）。这样「选源 / 超时 / 熔断」只存在于写侧，业务读侧只有一次带索引的 SQL。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **适配器层** | `server/sources/`：源协议、注册表、路由、健康状态、事件日志 |
| **消费方（写）** | 唯一调用适配器的服务；净值线是 `FundNavSyncService`，日历线是 `TradingCalendarCache` |
| **消费方（读）** | 业务唯一允许依赖的净值读入口 `FundNavService`；它只读 DB，只 import `server.sources.models` 的数据类型，不 import `router` / `registry` |
| **`fund_nav` / `fund_nav_state` / `fund_nav_revision`** | 净值明细 / 每只基金的同步状态 / 数值更正日志；唯一真相源 |
| **`fund`** | 基金主数据：公司、经理、类型描述、跟踪标的、成立日、规模、风险等级、QDII 标识、生命周期 |
| **`fund_trade_rule`** | 交易规则（原白名单表）：行存在 = 可交易；申购状态、费率、份额类别、T+N |
| **`NOT_YET_PUBLISHED`** | 指定日期的净值尚未公布，属于「数据还没到」，不是错误 |
| **`FETCH_FAILED`** | 该日应有净值但库中没有，且同步尚未补齐；属于「数据取不到」，不得用 T-1 顶替 |
| **`NO_NAV`** | 历史已完整，但该日期早于最早净值日（基金成立前）；重试也不会出现，需要人工核查 |
| **确认日** | `trade_orders.confirm_date`，订单应当按这一天的净值成交 |
| **读穿透（read-through）** | 详情页首次读取某只基金全量历史时，读入口同步触发一次补数后返回；此后只读 DB（§4.6） |

基金域表（`fund` / `fund_trade_rule` / `fund_nav*`）的字段、约束、索引、合并函数与状态机，以《[场外净值与基金元数据存储设计](../基金与交易/场外净值与基金元数据存储设计.md)》为准；本文只描述谁在什么时候读写它们。

### 1.3 范围与边界

**本轮做：**

- 新建 `fund` / `fund_trade_rule` 与 `fund_nav` / `fund_nav_state` / `fund_nav_revision`；`fund_risk_profiles` 补外键；
- 新建读入口 `FundNavService`、写入口 `FundNavSyncService`，以及元数据读入口 `FundMetaService`；
- 全量最新净值每日落库、持仓历史预热、详情页首次读取时按需补历史；
- 白名单同步时顺带落 `fund` + `fund_trade_rule` + `fund_risk_profiles`（公司 / 经理 / 类型 / 跟踪标的 / 成立日 / 规模 / 风险等级 / QDII 推导结果 / 费率与申购状态）；
- 切换所有净值读取点与订单确认点；
- 删除净值线的直连 akshare 代码、未使用的适配器代码、重复逻辑。

**本轮不做：**

- 场内行情、K 线、分时、白名单目录、货基万份收益、文档下载；
- ~~删除场内 30 秒轮询~~（已于 2026-10-26 单独完成，不属于本轮净值线范围，见 Q3）；
- 给适配器增加 `metadata` 能力（元数据仍由目录同步的 `fetch_basic_info` 提供，理由见 §4.4）；
- 修改已有 API 响应字段语义、金额/费率/份额计算规则；
- 引入依赖注入容器、消息队列、分布式锁；
- 多进程 / 多 worker 的熔断状态共享（读侧已无进程内状态，该问题只剩路由层）。

### 1.4 存储层只有 DB 一层

原稿设计是「L1 最新净值字典 + L2 历史 LRU + DB 真相源」。放弃场内基金后，净值每个交易日只公布一次，没有实时性需求；而 L1/L2 会引入进程内副本与 DB 的失效、多 worker 不一致等新问题。因此只保留 **DB 一层**：调度器写入，读路径只读。

为什么不做缓存、容量如何估算、将来何时才考虑补缓存，统一见存储设计 §1.6；本文只负责把「写多少、何时写、谁来读」接上。

### 2.3 订单确认现状

`confirm_pending_orders()`（`portfolio_service.py:1045`）在交易日 15:37 由调度器触发（`spot_cache_scheduler.py:125-133`），选出 `confirm_date <= today` 的 pending 订单，逐笔调用 `_confirm_one_order()`。

确认时取净值的方式是：

```python
# portfolio_service.py:1246（申购）、:1377（赎回）
nav = self._get_nav(fund_code)          # ← 取「最新一条净值」
if nav is None or nav <= 0:
    raise RuntimeError(f"无法获取基金 {fund_code} 的确认日净值，拒绝确认")
```

三个后果：

1. **取最新而不是 `confirm_date` 当日**：`_get_nav` 内部是 `df.iloc[-1]`，完全不看订单确认日；
2. **15:37 时，场外当日净值通常尚未公布**：主路径每天都在用 T-1 净值确认 T 日订单；
3. **取不到净值就抛错**：`confirm_pending_orders` 把订单落 `rejected` 并退回本金，把「数据还没到」当成「数据错了」。

### 2.4 服务构造与依赖

项目没有依赖注入容器，路由层在 18+ 处直接 `FinanceApiService()` / `PortfolioService()`。原稿的 L1/L2 是进程级可变状态，才需要「进程内唯一实例 + 组合根」；改成 DB 直读后，服务本身不持有任何跨请求状态，按请求构造一次没有代价。

需要共享的只剩两样，且都已存在专用入口：

| 共享物 | 入口 | 状态 |
|---|---|---|
| Supabase 客户端 | `server.storage.supabase_client.get_supabase()` | 进程级 |
| `SourceRouter`（含熔断/健康状态） | `server.sources.get_router()` | 进程级 |

因此 `FundNavService` / `FundNavSyncService` / `FundMetaService` 沿用 `TradingCalendarCache` 的构造方式（`trading_calendar_cache.py:127-160`）：

- 构造函数接受 `client` / `router`，测试可完全注入；
- 属性懒加载：读服务只加载 `get_supabase()`；只有 `FundNavSyncService` 加载 `get_router()`；
- **不再提供 `get_nav_cache()` 之类的全局单例**：没有状态就没有唯一性要求，多一个全局变量只会多一条隐式依赖。

## 4. 接入方案

### 4.1 核心原则

1. **唯一消费方**：业务服务不 import `server.sources`，只依赖 `FundNavService` / `FundMetaService`。
2. **依赖方向单向**：读 `API/Service → FundNavService → Supabase`；写 `调度器/读服务 → FundNavSyncService → SourceRouter → Source`。选源只发生在同步服务内部，`FundNavService` 不直接接触 `SourceRouter`；它只 import `server.sources.models` 里的纯数据类型（`NavPoint`），不 import `router` / `registry`。
3. **契约先行**：`FundNavService` / `FundNavSyncService` 的方法签名先冻结，再改调用侧。
4. **失败不掩盖**：
   - 「没有数据」是合法读结果（`None`）；
   - 「数据库不可用」「上游全失败」必须抛异常或返回显式状态；
   - 不得用 `0`、`1.0`、T-1 净值、空列表冒充成功。
5. **幂等**：批量更新、历史补齐、单只修复可重复执行；更正只写一次 `fund_nav_revision`。
6. **单一职责**：适配器管选源/超时/熔断；同步服务管合并/落库；读服务管查询与状态判定；业务管展示与交易语义。
7. **读写分离**：请求线程只读；唯一的写例外是详情页首次查看触发的历史补齐（§4.6），且该写入幂等。

### 4.2 目标架构

```
读（请求线程）                              写（调度器 / 管理脚本）
server/api/*   portfolio_service.py         spot_cache_scheduler.py
        │                  │                          │
        ▼                  ▼                          ▼
  FundNavService     FundMetaService         FundNavSyncService
        └─────────┬─────────┘                          │
                  ▼                                    ▼
        Supabase: fund_nav / fund_nav_state      SourceRouter
                  fund_nav_revision / fund(主数据)      │
                  ▲                     em_fund_jjjz  em_mobile
                  │                     em_lsjz       em_pingzhongdata
                  └───────── merge_fund_nav ───────────┘
```

注：`FundNavService.get_history` 首次读穿透时委托 `FundNavSyncService.ensure_history`（§4.6.2），这是读服务唯一依赖同步服务的地方。

元数据不经过适配器：`FundCatalogSync` 在现有 02:17 同步中调用 `fetch_basic_info`，与 jjfl 结果一起通过 `upsert_fund_catalog` 写 `fund` / `fund_trade_rule` / `fund_risk_profiles`（§4.4）。

### 4.3 对外契约

```python
class NavLookupStatus(str, Enum):
    OK = "ok"
    NOT_YET_PUBLISHED = "not_yet_published"
    FETCH_FAILED = "fetch_failed"
    NO_NAV = "no_nav"          # 该日期本身没有净值（非净值日 / 基金成立前），重试也不会出现


@dataclass(frozen=True)
class NavLookup:
    status: NavLookupStatus
    point: NavPoint | None
    reason: str | None = None


@dataclass(frozen=True)
class LatestNav:
    """最新净值的最小投影：只含持仓 / 下单预估 / 问答实际用到的字段。"""
    fund_code: str
    nav_date: date
    unit_nav: Decimal


class FundNavService:
    """净值唯一读入口。业务不得直接访问 SourceRouter、akshare 或 fund_nav* 表。"""

    def get_latest(self, code: str) -> LatestNav | None:
        """读 fund_nav_state.latest_*；库中无该基金时返回 None。"""

    def get_latest_batch(self, codes: list[str]) -> dict[str, LatestNav]:
        """持仓页一次批量读取；缺失的代码不出现在返回字典里。"""

    def get_history(self, code: str, limit: int | None = None) -> list[NavPoint]:
        """读 DB；历史未补齐时先做一次读穿透补数（§4.6）。"""

    def get_nav_on(self, code: str, on_date: date) -> NavLookup:
        """指定日期净值。四态必须可区分；只读 DB，不触网。"""


class FundNavSyncService:
    """净值唯一写入口。只由调度器 / 管理脚本 / 读穿透调用。"""

    def update_batch(self, codes: list[str] | None = None) -> UpdateResult: ...
    def ensure_history(self, code: str) -> HistoryFillResult: ...
    def repair(self, code: str, on_date: date) -> NavLookup: ...
    def describe(self) -> dict: ...


class FundMetaService:
    """基金元数据读入口。业务不得为经理/公司/QDII 再出一趟网。"""

    def get(self, code: str) -> FundMeta | None: ...
    def get_batch(self, codes: list[str]) -> dict[str, FundMeta]: ...
```

契约细节：

- `get_latest_batch` 只查 `fund_nav_state`（一行一只基金），不查可能上千行的 `fund_nav` 主表；返回字典缺 key 表示库中无该基金，不返回 `None` 占位或 0。
- `LatestNav` 只投影 `unit_nav` + `nav_date`：持仓、下单预估、问答都不需要累计净值与日增长率。需要完整点时用 `get_nav_on` 或 `get_history`，不要给 `LatestNav` 加可选字段把两种模型混在一起。
- `get_history(limit)` 返回按 `nav_date` 升序排列的点；`limit` 只影响返回条数（DB 用 `ORDER BY nav_date DESC LIMIT` 再反转），不影响补齐范围。
- `get_history` 的读穿透规则（唯一一处读时写）：
  1. `fund_nav_state.history_status = 'ready'` → 直接读 DB；
  2. 否则调用 `FundNavSyncService.ensure_history(code)`，成功后读 DB；
  3. 同一进程内按 `fund_code` 加锁，并发首次访问只触发一次上游请求；
  4. 补数失败 → 抛 `FundNavUnavailable(code, ...)`，由 API 映射为 503；**不得返回已有片段冒充完整历史**。
- `get_nav_on` 的判定顺序（纯 DB、五步）见存储设计 §2.5；四个状态的语义见上表 `NavLookupStatus`。这里只强调：**历史未完整时不得判定为「已公布但没有」**，必须返回 `FETCH_FAILED(reason="history_not_complete")`。
- 对货基（`MONEY_FUND_CODE`）**不在读服务内特判**；`PortfolioService` 继续直接返回 `1.0000`，读服务只处理普通净值基金。
- 元数据缺失时 `get` 返回 `None`，由调用方显式处理（例如详情页展示为空）；**不提供 `is_qdii()` 这类缺失即 `False` 的便捷方法**，避免把「不知道」伪装成「不是 QDII」。

### 4.4 数据模型（见存储设计）

基金域表（`fund` / `fund_trade_rule` / `fund_risk_profiles` / `fund_nav` / `fund_nav_state` / `fund_nav_revision`）与 `fund_catalog` 视图的完整定义、约束、索引与容量，统一放在《[场外净值与基金元数据存储设计](../基金与交易/场外净值与基金元数据存储设计.md)》§4。接入侧只需守住六条边界：

1. **写入走合并函数，不自己拼 `upsert`**：新日期插入；同日数值变化写更正记录并累加 `revision_count`；同日数值不变不写主表。调用存储设计的 `merge_fund_nav(rows)`，让「改值 + 更正」在同一事务内完成（存储设计 §3.6.1）。
2. **状态单独更新**：合并成功后由 `FundNavSyncService` 更新 `fund_nav_state`；失败只写 `last_error`，不动 `latest_*`。
3. **元数据复用目录同步请求**：`fund_fee_source.fetch_basic_info()` 已经在调 `FundMNBasicInformation`，本轮只扩展返回字段（`JJGS` / `JJJL` / `ESTABDATE` / `ENDNAV` / `RISKLEVEL`），不新增上游请求。字段映射与 QDII 推导见存储设计 §8。
4. **主数据、规则、画像一起写**：`FundCatalogSync` 把三组行交给 `upsert_fund_catalog(funds, trade_rules, risk_profiles)`，同一事务提交。jjfl 失败时仍可写 `fund` 与画像，但不写规则——该基金随后不可交易（存储设计 §3.6.3）。
5. **准入看规则行，不看主数据行**：`fund_catalog` 是 `fund JOIN fund_trade_rule` 且 `lifecycle_status='active'` 的视图；`FundFeeService` 的 `is_supported` / 目录查询只改表名，语义不变（存储设计 §3.5 Q7/Q8）。
6. **净值不建外键**：基金被下架后历史净值仍要保留；`fund_nav*` 只由写入方保证「只写目录内代码」（存储设计 §2.2）。

### 4.5 更新与合并

`FundNavSyncService.update_batch(codes)` 的流程：

1. 从白名单取 `codes`（不传则取全部启用代码）；
2. `router.fetch_latest_batch(codes)`；
3. 对返回的 `{code: [NavPoint, ...]}` **按每个点**执行合并（通常是「最新一天 + 前一天」，不能只取第一个点）；
4. 对批量未命中的代码，走单只兜底 `router.fetch_latest(code)`（约 148 只/日）；
5. 更新 `fund_nav_state`；
6. 返回 `UpdateResult`（请求数、命中数、未命中数、失败数、耗时）。

合并语义（新日期 / 数值变化 / 未变化 / 更早日期）由存储设计的 `merge_fund_nav` 定义，这里不重复。接入侧只额外守两条规则：

- **失败不覆盖**：基金缺失、数值为空、上游异常时保留库中原值，只写 `last_error` / `last_error_at`；同步侧不自行判断「值看起来不对就改写」。
- **最新日不回退**：`latest_nav_date` 只能前进。批量源返回的「最新日」是上游已公布日，不是日历今天；不得据此判断「今天没数据 = 异常」。

`ensure_history(code)` 用于补齐单只基金的全量历史（详情页读穿透、持仓预热、`repair` 共用）：

1. `router.fetch_history(code)`（`em_pingzhongdata` 单次响应同时给出单位与累计净值）；
2. 全量合并（`merge_fund_nav`，按 `(fund_code, nav_date)` 去重），`history_status='ready'`，`history_start_date` 取最早点；
3. 若上游返回空或失败：未写入任何点 → `history_status='failed'`；已写入部分点 → `history_status='partial'`；两种情况都写 `last_error` / `last_error_at`，已写入的数据保留；
4. 重复调用幂等：`ready` 状态直接返回，不重复下载。

`repair(code, on_date)` 只补一个日期：先 `router.fetch_history_recent(code, 20)`，命中则返回 `OK`，未命中再用 `fetch_history` 兜底；两次都没有才返回 `FETCH_FAILED`。

### 4.6 读取与补齐策略

#### 4.6.1 读：谁触网、谁不触网

| 场景 | 调用 | 触网 |
|---|---|---|
| 持仓 / 账户 / 收益 | `get_latest_batch(codes)` | 否 |
| 下单预估价 | `get_latest(code)` | 否 |
| 详情页历史 | `get_history(code, limit)` | 仅首次补齐时 |
| 订单确认 | `get_nav_on(code, date)` | **从不** |
| 元数据展示 | `FundMetaService.get / get_batch` | 否 |

具体 SQL、索引与执行次数见存储设计 §3.5 与 §4.2。持仓页固定 1 次 `IN` 查询，与持仓只数无关。

#### 4.6.2 补齐：持仓 + 按需

不做全量历史预热（约 900 万行 / 1 GB / 2300 次请求）。历史按四条路径进入 DB：

1. **全量最新（每轮必跑）**：`update_batch()` 覆盖白名单全部代码，批量源命中后再对未命中代码单只兜底；这一步只写「最新一两个点」，让全站最新净值可用。
2. **持仓预热（每轮 `update_batch` 后）**：取 `portfolio_positions` 中 `quantity > 0` 的去重 `fund_code`，对 `history_status != 'ready'` 的逐只 `ensure_history()`。串行执行并限速，避免对上游形成突发流量；单只失败不阻塞其余基金。`ready` 的基金直接跳过，所以重复执行没有额外请求。
3. **详情按需**：用户首次打开某只基金详情时，`get_history` 读穿透触发一次 `ensure_history()`；此后该基金的历史留在 DB，后续请求不再触网。
4. **缺口修复**：确认时遇到 `FETCH_FAILED`，用 `fund_nav_admin repair <code> <date>` 或 `ensure_history` 补历史；`update_batch` 只写最新一两个点，补不了历史缺口。确认路径本身不触网，避免把上游延迟带进批量确认。

幂等与并发：`merge_fund_nav` 天然幂等（相同值重放不写）；`ensure_history` 按 `fund_code` 加进程内锁，防止并发的首次访问重复下载。当前单进程部署，不引入分布式锁；若将来多 worker，重复下载仍只会产生幂等写入，可接受。

失败处理：本只基金本轮失败后不原地重试，等下一轮 `update_batch` 再补；连续失败由 `last_error` / `last_error_at` 记录，用于运维判断是否上游长期缺数。

新增任务注册在现有 `spot_cache_scheduler.py`（沿用同一 `AsyncIOScheduler`），不新建第二个 scheduler：

### 4.8 订单确认语义

确认路径改为：

```python
# 申购、赎回共用（2026-10-30 起取成交净值日 accepted_date；此前是 confirm_date）
lookup = self._fund_nav.get_nav_on(fund_code, order["accepted_date"])
if lookup.status == NavLookupStatus.NOT_YET_PUBLISHED:
    logger.info("确认日净值尚未公布，保持 pending: order=%s, date=%s",
                order["id"], order["confirm_date"])
    skipped += 1
    continue
if lookup.status == NavLookupStatus.FETCH_FAILED:
    logger.error("确认日净值获取失败，保持 pending: order=%s, date=%s, reason=%s",
                 order["id"], order["confirm_date"], lookup.reason)
    skipped += 1
    continue
if lookup.status == NavLookupStatus.NO_NAV:
    # 重试也不会出现，必须人工判断（可能 confirm_date 早于基金成立日）
    logger.error("确认日不是有效净值日，保持 pending 待人工处理: order=%s, date=%s",
                 order["id"], order["confirm_date"])
    skipped += 1
    continue
nav = Decimal(str(lookup.point.unit_nav))
```

规则：

- `NOT_YET_PUBLISHED`、`FETCH_FAILED` **都不落 `rejected`、都不退款**；订单留在 pending，下个窗口重试；
- `NO_NAV` 同样不拒单、不退款，但**不自动重试**：它表示日期本身没有净值，重试无意义；日志 ERROR，等人工核查（正常情况不应出现，因为 `confirm_date` 来自交易日历）；
- 只有确定性错误（持仓不存在、费率规则缺失、金额非法）才落 `rejected`；
- 货基仍走 `MONEY_FUND_CODE → 1.0000` 特判，不查读服务；
- 确认路径**不触网**：`get_nav_on` 只读 DB。`FETCH_FAILED` 的修复交给人工 `repair` 或 `ensure_history`（`update_batch` 只补最新，补不了历史缺口），避免把上游超时带进批量确认；
- `confirm_pending_orders` 的返回值增加 `skipped` 计数，便于日志与运维判断；
- 15:37 任务保留，但只处理 `confirm_date < today` 的历史遗漏；当日订单一律等 20:05 之后。

#### 4.8.1 实现补充（2026-10-26，写代码时发现原方案未覆盖）

**① 买单的净值查询必须排在解冻之前。** 原 `_confirm_one_order` 的第一步是解冻资金
（`frozen_cash -= amount`），第二步才取净值。旧语义下取不到净值就抛错→拒单→退款，
解冻与退款配套，不会出错。新语义下取不到净值只是「保持 pending」，若解冻已经发生，
这笔钱既不在冻结、也没被扣走，用户可自由支配；下个窗口再次确认时会二次解冻，
把同一账户里**其他挂单**的冻结额扣掉。

因此实现把净值判定提到方法最前面（`get_nav_on` 只读、无副作用），
**任何写操作之前**先确定这笔订单本轮到底确不确认。解冻、扣份额等写操作的位置不变。

**② 参数改为显式的截止日。** 原 `skip_trading_day_check: bool` 用「今天是否交易日」
隐式推导截止日（交易日 → `confirm_date <= today`，非交易日 → `< today`），
而现在截止日由**调用方场景**决定（15:37 只补历史遗漏，20:05 之后才确认当日），
与是否交易日无关。故签名改为：

```python
def confirm_pending_orders(self, before_today: bool = False) -> dict:
    # before_today=True  → confirm_date <  today（15:37 历史遗漏任务）
    # before_today=False → confirm_date <= today（晚间/08:05/启动补偿/手动触发）
```

日历不可用时既不报错也不放行：截止日不再依赖日历，确认路径本身也就不再需要
`_is_trading_day`（下单路径仍需要，未改动）。调用点改动：
`spot_cache_scheduler.py` 的 15:37 任务传 `before_today=True`，
启动补偿与 `POST /api/portfolio/confirm-pending` 不传。

**③ 跳过计数与拒单的分界。** `_confirm_one_order` 在净值不可用时抛
`NavUnavailableForConfirm(order_id, nav_date, status, reason)`，
`confirm_pending_orders` 捕获后 `skipped += 1` 并 `continue`，**不落 rejected、不退款、不写流水**；
其余异常仍走原路径（落 `rejected` + 买单退款）。返回值增加 `skipped` 字段。

`_query_detail_overview` 的其余字段继续来自 `fund_overview_em`：托管人、业绩比较基准、分红都不在 `fund` 内；费率档位虽已存入 `fund_trade_rule`，本轮仍沿用 `fund_overview_em` 的实时值，整体换源会改变详情页口径（Q16）。`is_qdii` 是唯一新增字段，给 `FundMetaService` 一个真实消费者，也让用户要求的「QDII 标识入库」真正可用，而不是只写不读。

落点：`schemas.py` 的 `EtfDetailResponse` 增加 `is_qdii: Optional[bool] = None`（纯加法，缺省 `None` 表示未知）。

`is_qdii` 字段只做展示与后续筛选依据；**不参与份额、费率、确认延迟计算**——延迟仍由目录同步时的 `classify_fund → resolve_delays` 决定，避免同一口径两处计算。

**S3 只切只读路径**，交易确认仍走旧逻辑；S4 与调度改点同批上线，避免「15:37 已切新口径但没有晚间任务」导致订单卡住。

### 4.10 依赖注入与构造

服务全部**无状态**，因此不需要组合根单例；只保留与 `TradingCalendarCache` 相同的可注入构造：

```python
# server/services/fund_nav_service.py
class FundNavService:
    def __init__(self, client=None, sync: FundNavSyncService | None = None):
        self._client = client
        self._sync = sync

    @property
    def client(self):
        if self._client is None:
            from server.storage.supabase_client import get_supabase
            self._client = get_supabase()
        return self._client
```

业务服务构造参数注入：

```python
class PortfolioService:
    def __init__(self, fund_nav: FundNavService | None = None,
                 fund_meta: FundMetaService | None = None):
        self._fund_nav = fund_nav or FundNavService()
        self._fund_meta = fund_meta or FundMetaService()
```

这样既不引入容器，也保证：

- 测试可完全绕开 DB / 网络（注入假 `FundNavService`）；
- 每次请求 new 一个服务不会重建任何缓存，因为没有缓存；
- 依赖方向仍然单向：`FundNavService` 不 import `server.sources.router`；只有 `FundNavSyncService` 依赖 `get_router()`。

**实现补充（2026-10-26）**：`PortfolioService` 与 `FinanceApiService` 的注入改成
**惰性属性**（`self._fund_nav = fund_nav`，首次访问 `self.fund_nav` 时才 `FundNavService()`），
而不是上面写的 `fund_nav or FundNavService()`。原因：`FinanceApiService` 有大量纯上游
的用法（行情、榜单、搜索），这些路径不该因为构造实例就拉起净值读服务的依赖链；
惰性属性让「注入了假对象」与「完全不用」都成立，测试语义不变。

### 4.12 失败处理与可观测

| 场景 | 行为 |
|---|---|
| 批量源全失败 | `AllSourcesFailed` 上抛；调度器记录 ERROR；**库中旧值原样保留**，不写 0 |
| 批量零命中 | 视为成功但记 WARNING（适配器已有 `batch_empty` 事件）；单只兜底 |
| 单只兜底失败 | 更新 `last_error` / `last_error_at`；旧值保留；下轮重试 |
| DB 写失败 | 上抛；本轮更新标记失败。`merge_fund_nav` 在单个 RPC 事务内，整批回滚，不留半写 |
| 读路径 DB 不可用 | 抛异常；API 返回 5xx；**不返回空列表冒充无数据** |
| 历史未补齐、补数失败 | `get_history` 抛 `FundNavUnavailable` → API 503；不返回片段冒充完整历史 |
| 历史未补齐、补数成功 | 正常返回，日志 INFO 记录首次补齐耗时与点数 |
| 元数据抓取失败 | **不写 `fund`**，保留旧行；记 WARNING（code + 原因）；下次同步重试 |
| 费率解析失败 | **不写 `fund_trade_rule`**，保留旧规则；元数据照常写入；该基金本轮不新增/不更新交易资格 |
| 元数据从未成功过 | `FundMetaService.get` 返回 `None`；调用方按缺失处理，不伪造空字符串 |
| 净值更正 | 写 `fund_nav_revision`；日志 INFO；每周复核发现 |

结构化日志字段沿用适配器事件：`event` / `capability` / `source` / `domain` / `code` / `latency_ms` / `failure_kind` / `requested` / `returned`。同步服务补充：`batch_hit` / `single_fallback` / `updated` / `unchanged` / `revisions` / `history_filled` / `history_status`。

### 4.13 部署与回滚
