## 1. 背景与术语

### 1.1 要解决的问题

来自需求方的原话：

1. 基金净值曲线在**访问时**拉取，等待时间长、速度慢；
2. 多处对外请求没有多源方案，单一源被拒就全盘没数据；
3. 交易时段每 30s 拉一次场内行情，是弱需求却高频，多次被上游拒绝 —— **放弃场内高频部分，先保住场外**。

本文处理第 1 条。第 2 条见 `数据源多源适配器.md`，第 3 条见本文 §5（已实现）。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **支持目录 / 白名单** | `fund_catalog` 视图 = `fund` JOIN `fund_trade_rule` 且 `lifecycle_status='active'`。它同时是**交易准入**的唯一依据（视图里查不到即拒绝交易）。原 `fund_fee_rules` 表已被取代 |
| **场外基金** | 通过场外渠道（申购/赎回）交易的开放式基金。本项目口径 = **名称含「联接」且（名称含 ETF 或类型为指数型）**（`fund_catalog_sync.py:109-119`） |
| **单位净值** | 每份基金份额的净值，交易确认价（`positions.cost_price` 的来源） |
| **累计净值** | 单位净值 + 历史分红。**只用于展示**，不参与交易 |
| **净值日期** | 净值**所属**的交易日，**不是**我们拉取它的日期。上游返回的每个净值点自带这个日期，是全部口径的基准 |
| **历史补齐** | 某只基金的历史净值未完整时（`fund_nav_state.history_status != 'ready'`），按需或按持仓逐只拉全量。原设计叫「预热（preheat）」，语义已变：**不再全量预热全市场** |
| **T 日 / confirm_date** | 订单被受理的交易日 / 订单实际确认日 |
| **NavPoint** | 源层归一化后的净值点，定义见 `数据源多源适配器.md` |

### 1.3 不可违反的约束

- **净值数值影响订单确认**：确认价取错 → 用户份额算错 → 资产错。这是本设计里唯一「不允许降级」的地方。
- **不能假设「今天拉的 = 今天的净值」**：不同源的「今天」定义不同（`对外数据源请求与返回.md` §5.7）。数据自带日期才是准绳。
- **不掩盖错误**：上游失败必须留下可查痕迹，不允许静默兜底成 `0` 或旧值。
- 项目跑在 Linux + poetry；数据库结构唯一权威来源是 `supabase/migrations/`。

## 2. 修复前的实现（2026-10-14 快照）

> 本节**已失效**，保留它是为了说明「问题是怎么来的」。文中 `文件:行号` 都是 2026-10-14 的位置，
> 现在大面积对不上，不要按它去读代码。

### 2.1 净值只有一个来源

`ak.fund_open_fund_info_em(symbol=code, indicator=…)` → 底层打在 **`fund.eastmoney.com/pingzhongdata/{code}.js`**，解析那块 JS 变量。

**关键代价**（本机实测，2026-10-14）：

| 项 | 实测 |
|---|---|
| 单只响应体积 | `512890` 293 KB、`161725` 423 KB、`000008` 503 KB、`110020` 589 KB → **均值 ≈ 452 KB** |
| 单只耗时 | `000008` 0.16s、`110020` 0.26s |
| 返回内容 | **该基金全量历史**（`110020` 4160 行、`000008` 3278 行），不是增量 |
| 单位净值与累计净值 | **必须分两次请求** |

即：**取一只基金近 500 个点，要下载它的全部 4160 个点、452 KB。**

### 2.2 四个调用点，全部无缓存

| # | 位置 | 出网次数 | 触发路径 |
|---|---|---|---|
| 1 | `_query_nav` | 1 | 问答服务 |
| 2 | `_query_nav_history` | 1 | `GET /api/market/detail/{code}` |
| 3 | `_query_accumulated_nav` | 1 | 同上（由 #2 内部调用） |
| 4 | `portfolio_service._get_nav` | 1 | 持仓列表 / 下单预估 / 订单确认 |

`_get_nav` 是放大最严重的一处：`list_positions()` 在**持仓循环内**调用，**每个持仓出网 1 次**。

### 2.3 请求放大（当时的账）

| 用户动作 | 出网请求 | 流量 |
|---|---|---|
| 打开一次基金详情页 | 3 次（概览 + 单位净值 + 累计净值） | ≈ 500 KB |
| 刷新一次持仓列表（3 只持仓） | 3 次 | ≈ 1.4 MB |
| 刷新一次账户概况（3 只持仓） | 3 次 | ≈ 1.4 MB |

**请求量随「用户数 × 持仓数 × 刷新次数」线性增长，且每次几百 KB。** 这是「慢」的直接来源。

### 2.4 当时的调度

只有 4 个任务，其中 `refresh_etf_spot` 是场内 30 秒轮询（已删，见 §5），15:37 的确认任务会触发净值出网。

### 2.5 订单确认当时的做法（本设计最重要的修正点）

15:37 选出 `confirm_date <= today` 的 pending 订单，逐笔取**最新一条净值**确认：

```python
nav = self._get_nav(fund_code)          # ← 「最新一条」，不看 confirm_date
if nav is None or nav <= 0:
    raise RuntimeError(f"无法获取基金 {fund_code} 的确认日净值，拒绝确认")
```

三个问题：

1. **取「最新」而不是「confirm_date 当日」**。当日净值尚未公布时，会**用前一日的净值确认当日申购** —— 份额算错，无任何提示。
2. 15:37 这个时点，场外当日净值通常还没公布 → **「T 日 15:00 前下单、T 日确认」这条主路径每天都在踩问题 1**。
3. 取不到净值 → 订单落 `rejected` 并**退回本金**。「数据还没到」被当成了「数据错了」。

## 3. 当时发现的问题与现状

| # | 当时的现象 | 后果 | 现状（2026-10-27） |
|---|---|---|---|
| **P1** | 净值线无缓存、无落库；持仓/账户/收益按持仓数逐只出网 | 页面慢，请求量随用户线性放大 | ✅ **已解决**：`get_latest_batch` 一次 `IN` 查询 |
| **P2** | 确认取「最新净值」而非 `confirm_date` 当日净值 | 确认价可能取到 T-1，份额算错 | ✅ **已解决**：`get_nav_on(code, date)` 按日期取 |
| **P3** | 确认任务在 15:37，当日净值当晚才公布 | P2 每天都在发生 | ✅ **已解决**：确认挪到 18:00 之后多轮，15:37 只补历史遗漏（§4.5） |
| **P4** | 「尚未公布」与「上游错误」混为一谈，一律抛错 | 订单被拒 + 退款 | ✅ **已解决**：四态区分，未公布保持 pending（存储设计 §2.5） |
| **P5** | 每次请求下载全量历史再 `tail(limit)` | 取 500 点传 452 KB | ✅ **已解决**：读 DB，`LIMIT` 下推到 SQL |
| **P6** | akshare 裸 `requests.get`，无 timeout、无重试 | 上游抖动挂住调用线程 | ✅ **部分解决**：净值线走自解析源并设真 timeout；K 线/分时仍无 timeout（残留） |
| **P7** | 下单时 `price` 可由客户端传入 | 落库的预估值口径不清 | ⏸ **未处理**：确认时会重算，风险有限（§9 Q7） |
| **P8** | 白名单同步不记录「新增了哪些基金」 | 预热队列无从生成 | ✅ **已解决**：`FundCatalogSync.run()` 返回 `new_codes` |

## 4. 设计决策与现状

### 4.1 架构：从 `NavCacheService` 到「读、写两个服务」

**原设计**：一个 `NavCacheService` 作为全项目唯一净值入口，内部含「内存 L1 恒驻 + 内存 L2 LRU + Supabase」三层，调用侧只认它。

**现状（2026-10-27）**：没有缓存服务，拆成读写两端，都直接对着 DB：

```
定时调度（§4.5）──► FundNavSyncService  ──写──►  fund_nav / fund_nav_state
                     update_batch / ensure_history / repair     （3 个 RPC）

详情页 / 持仓 / 账户 / 下单 / 订单确认
        │
        └──────► FundNavService ──读──► fund_nav_state / fund_nav / fund_catalog
                 get_latest / get_latest_batch / get_history / get_nav_on / in_catalog
```

- `FundNavService` 无状态，实例每次请求新建；写路径的并发靠 `flock`（批量更新单飞）+ 模块级
  `code_lock(code)`（同一只基金串行补齐），**没有内存锁**；
- 目录外代码不进入这条链：`in_catalog()` 为假直接抛 `FundNotSupported`，API 映射 404。

### 4.2 表结构（已移交）

三张净值表的 DDL、键、约束、索引、迁移与回滚**全部在
[存储设计](场外净值与基金元数据存储设计.md) §3–§4**，本文不再重复。

> 早期版本在这里贴过一版 schema（`fund_nav` / `fund_nav_state` / `fund_nav_revision`），
> 其中 `fund_nav_state.preheat_status` 等列名**与最终实现不一致**（实际是 `history_status`）。
> 以迁移 `supabase/migrations/20261026120000_create_fund_master_and_trade_rule.sql` 为准。

### 4.3 历史补齐：从「L3 分级预热」到「持仓预热 + 详情按需」

**原设计（2026-10-18 决策 L3）**：白名单同步后先跑一次全市场批量更新让全站可用，再后台按优先级
逐只补全量历史（≈2328 请求 / ≈1000 MB / 串行 30–60 分钟）。

**为什么改**：全量预热 900 万行 / 1 GB，而绝大多数基金无人查看。2026-10-24 改为：

| 触发 | 范围 | 实现 |
|---|---|---|
| 每天净值更新后 | 只补**有持仓且 `history_status != 'ready'`** 的基金 | 调度器 `_warm_positions_job` → `warm_positions()` |
| 用户首次打开详情页 | 该基金单只全量 | `get_history()` 发现状态非 `ready` 时读穿透 `ensure_history()` |
| 确认日净值取不到 | 该基金该日 | `repair(code, on_date)`：先取近 20 条，未命中再全量 |

**状态机与完整性判据**（`history_status` 的 pending/ready/partial/failed）在存储设计 §2.4，此处不重复。

**现状**：已实现；补齐失败时 `get_history` 抛 `FundNavUnavailable`（API 503），**不返回已有片段**冒充完整历史。

### 4.5 日常更新调度

**核心手段**：单次调用**全市场场外净值批量接口**一次拿到约 2.4 万行的「最新一天 + 前一天」，
**在本地筛出白名单**。源名与列名结构见适配器文档；这里只保留调度口径。

- ⚠️ 批量接口的「当日」= **最新已公布日**，不是日历今天。2026-10-14 白天采样，列名仍是 `2026-10-13-*`。
  任何「今天拉到了今天的净值」的假设都是错的。
- **为什么多轮**：公布时间分散（QDII / 海外更晚），单轮必然漏；每轮都是幂等的「能更就更」。

**具体时刻、任务名与「看今天还是看前一天」的判断，唯一出处是
[接入方案](../行情/多源适配器接入方案.md) §4.7**，本文不重复。

**为什么坚持「按上一天是否交易日」**：`CronTrigger(day_of_week=…)` 只看星期几。国庆假期里的周四、
调休上班的周六都会判错 —— 这正是 `trading_calendar.py` 模块头注释记录过的历史 bug。午夜任务同理。

> 这些时刻**是经验初值，不是上游公布时间的保证**，需按 §7 采样校准（Q2）。

#### 每日请求量

| 项 | 次数 | 流量 |
|---|---|---|
| 批量更新（6 个窗口） | 6 | ≈ 26 MB |
| 未覆盖/缺当日净值的单只兜底 | ≈ 148 | ≈ 0.6 MB |
| **合计** | **≈ 155 / 日** | **≈ 27 MB / 日** |

对比修复前：一个用户刷一次持仓页就是 1.4 MB，且**随用户数无限增长**。

#### 批量接口覆盖不全（实测坐实，必须兜底）

实测 2026-10-14：白名单候选 **2328 只** → 批量命中 **2260 只（97.1%）**，未命中 **68 只**；
命中但当日净值为空 **80 只**（暂停申购 / 封闭期 / 新发未成立）。未命中的 68 只**不在**场内批量接口里
（实测交集为空），所以兜底只能走单只接口 → **批量为主 + 单只兜底**，约 `68 + 80 ≈ 148 只/日`。

### 4.6 合并规则（已落成数据库函数）

**为什么这样合并**：批量接口每天返回同一批「最新 + 前一天」，若不加判断地覆盖，会产生三类问题：
把更早的日期写回去（最新净值回退）、把没变化的数据反复重写（写放大）、数值被上游修正后无痕迹。

六种情况的处理（新日期追加 / 数值变化写更正 / 数值未变只更新时间 / 缺失保留旧值 /
更早日期不回退 / 历史缺口入补齐队列）**以存储设计 §2.3 的 R1–R5 与 §3.6.1 为准**，本文不重复。

**现状**：由 `merge_fund_nav(rows jsonb)` 在**一个事务**内完成（应用层「先查再改」无法保证
「改值 + 更正」原子）。状态更新另走 `upsert_fund_nav_state`，两段式：`latest_*` 只前进、
`last_checked_at` 每轮刷新。

### 4.7 订单确认口径

需求方原话：**「订单确认要根据指定的日期，而不是直接拉取最新一条的数据，万一没更新呢？」**

**决策（2026-10-18，选项 A）**：确认挪到净值公布之后，每次都是「能确认的就确认，不能的留着」的
幂等扫描；保留 15:37 但退化为「只处理 `confirm_date < today` 的历史遗漏」。具体时刻见接入方案 §4.7。

**已接受的业务语义变化**：用户会看到确认**推迟几小时**（从 15:37 变成当晚）。这是「数值正确」
与「确认及时」的取舍，由需求方拍板：宁可确认晚几小时，也不用 T-1 净值确认 T 日订单。

> **2026-10-30 补充（方案 A）**：这里的「确认日」在订单确认重写后拆成两个字段——
> 取价用 `trade_orders.accepted_date`（受理日 T，成交净值日），扫描门槛用 `confirm_date`（份额到账日）。
> 即确认仍然发生在上面的窗口里，只是取价日期从「T+confirm_delay」改回「T」。见[订单确认：业务规则](订单确认-业务规则.md) §1.2/§3.2。

**语义定义**（`get_nav_on` 的四态判定：OK / NOT_YET_PUBLISHED / FETCH_FAILED / NO_NAV）在
存储设计 §2.5；每条状态对应确认动作（未公布保持 pending、不落 rejected、不退款）在接入方案 §4.8。
两处都是唯一出处，本文不重复。

**下单预估是例外**：`apply_purchase` 取最新净值只是预估，确认时会按 `confirm_date` 重算，
所以那里**允许**用「最新」而不是「当日」。

### 4.8 失败与补齐

单飞（`flock`，拿不到锁视为本轮跳过而非失败）与「上游失败保留旧数据、绝不用 `0` 填充」
的实现见接入方案 §4.6–§4.7 与存储设计 §2.3；补齐入口（`ensure_history` / `repair`）见本文 §4.4。

> 这里只补一条**设计上的取舍记录**：原计划的「5 → 15 → 30 分钟重试退避」**没有实现**。
> 净值场景下「多轮固定窗口」（§4.5）本身就在做重试，再加一套退避只会让失败溯源更难；
