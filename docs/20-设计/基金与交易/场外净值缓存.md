## 1. 背景与术语

### 1.1 要解决的问题

来自需求方的原话：

1. 基金净值曲线在**访问时**拉取，等待时间长、速度慢；
2. 多处对外请求没有多源方案，单一源被拒就全盘没数据；
3. 交易时段每 30s 拉一次场内行情，是弱需求却高频，多次被上游拒绝 —— **放弃场内高频部分，先保住场外**。

本文只处理第 1 条与「场外净值」这一块。第 2 条见 `数据源多源适配器.md`，第 3 条见本文 §5。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **白名单** | `fund_fee_rules` 表里的全部基金代码。它同时是**交易准入**的唯一依据（查不到费率即拒绝交易，`portfolio_service.py:550`）。截至 2026-10-14 实测算出的候选口径约 **2328 只** |
| **场外基金** | 通过场外渠道（申购/赎回）交易的开放式基金。本项目白名单口径 = 名称含「联接」且是 ETF/指数型（`fund_catalog_sync.py:105`） |
| **单位净值** | 每份基金份额的净值，交易确认价（`positions.cost_price` 的来源） |
| **累计净值** | 单位净值 + 历史分红。**只用于展示**，不参与交易 |
| **净值日期** | 净值**所属**的交易日，**不是**我们拉取它的日期。上游返回的每个净值点自带这个日期，是本文全部口径的基准 |
| **预热（preheat）** | 白名单同步完成后，后台**离线**把每只基金的完整净值历史灌进缓存，使页面请求不再等待下载 |
| **T 日 / confirm_date** | 订单被受理的交易日 / 订单实际确认日。`apply_purchase` 在 `portfolio_service.py:582-591` 计算 |
| **归一化模型** | 把不同上游源的返回统一成 `NavPoint`（见 §4.10） |

### 1.3 不可违反的约束

- **净值数值影响订单确认**：确认价取错 → 用户份额算错 → 资产错。这是本设计里唯一「不允许降级」的地方。
- **不能假设「今天拉的 = 今天的净值」**：不同源的「今天」定义不同（`对外数据源请求与返回.md` §5.7）。数据自带日期才是准绳。
- **不掩盖错误**：上游失败必须留下可查痕迹，不允许静默兜底成 `0` 或旧值。
- 项目跑在 Linux + poetry；数据库结构唯一权威来源是 `supabase/migrations/`。

### 1.4 与适配器文档的边界

本文只回答「净值存到哪、什么时候更新、业务怎么用」；「数据从哪来、怎么取、坏了怎么办」见 [`数据源多源适配器.md`](../行情/数据源多源适配器.md)。

| 文档 | 独占内容 |
|---|---|
| [`数据源多源适配器.md`](../行情/数据源多源适配器.md) | 源清单、域名/能力、字段映射、失败分类、熔断、超时、更新日志、契约测试；`Source` / `NavPoint` 的唯一定义处 |
| 本文 | 三张净值表的 schema、L1/L2 缓存、预热、合并规则、更新调度、订单确认口径 |
| [`交易日历缓存.md`](交易日历缓存.md) | 日历表、全量拉取、刷新、降级、T 日语义 |

## 2. 当前实现

### 2.1 净值只有一个来源

`ak.fund_open_fund_info_em(symbol=code, indicator=…)` → 底层打在 **`fund.eastmoney.com/pingzhongdata/{code}.js`**，解析那块 JS 变量。

选型理由记录在 `finance_api_service.py:642-647`：旧接口 `fund_etf_fund_info_em` 已因上游表结构变更弃用；现接口**场内场外共用**（110020 / 512890 实测均可）。

**关键代价**（本机实测，2026-10-14）：

| 项 | 实测 |
|---|---|
| 单只响应体积 | `512890` 293 KB、`161725` 423 KB、`000008` 503 KB、`110020` 589 KB → **均值 ≈ 452 KB** |
| 单只耗时 | `000008` 0.16s、`110020` 0.26s |
| 返回内容 | **该基金全量历史**（`110020` 4160 行、`000008` 3278 行），不是增量 |
| 单位净值与累计净值 | **必须分两次请求**（`finance_api_service.py:665`） |

即：**取一只基金近 500 个点，要下载它的全部 4160 个点、452 KB。**

### 2.2 四个调用点，全部无缓存

| # | 位置 | 接口 | 出网次数 | 触发路径 |
|---|---|---|---|---|
| 1 | `finance_api_service.py:215` `_query_nav` | 单位净值 | 1 | 问答服务 |
| 2 | `finance_api_service.py:659` `_query_nav_history` | 单位净值 | 1 | `GET /api/market/detail/{code}` |
| 3 | `finance_api_service.py:691` `_query_accumulated_nav` | 累计净值 | 1 | 同上（由 #2 内部调用） |
| 4 | `portfolio_service.py:257` `_get_nav` | 单位净值 | 1 | 见下表 |
| 5 | `portfolio_service.py:628`（`apply_purchase` 内部）| 同 #4 | 1 | 下单 |

`_get_nav` 的调用点（这是放大最严重的一处）：

| 位置 | 场景 | 出网次数 |
|---|---|---|
| `portfolio_service.py:941` | `list_positions()` **持仓循环内** | **每个持仓 1 次** |
| `portfolio_service.py:1216` | `_confirm_one_order()` 申购确认 | 每笔订单 1 次 |
| `portfolio_service.py:1347` | `_confirm_one_order()` 赎回确认 | 每笔订单 1 次 |
| `portfolio_service.py:628` | `apply_purchase()` 下单预估值 | 每笔订单 1 次 |

### 2.3 请求放大（现状的账）

| 用户动作 | 出网请求 | 流量 |
|---|---|---|
| 打开一次基金详情页 | 3 次（概览 + 单位净值 + 累计净值） | ≈ 500 KB |
| 刷新一次持仓列表（3 只持仓） | 3 次 | ≈ 1.4 MB |
| 刷新一次账户概况（3 只持仓） | 3 次 | ≈ 1.4 MB |
| 刷新一次每日收益（3 只持仓） | 3 次 | ≈ 1.4 MB |

**这四个接口的请求量随「用户数 × 持仓数 × 刷新次数」线性增长，且每次都是几百 KB。** 这是「慢」的直接来源，也是「多次被上游拒绝」的成因之一。

### 2.4 调度现状

`server/services/spot_cache_scheduler.py`：

| 任务 | 触发 | 与净值的关系 |
|---|---|---|
| `refresh_etf_spot`（`:105`） | `IntervalTrigger(seconds=30)` | 无关（场内行情） |
| `confirm_pending_orders`（`:117`） | `CronTrigger(15:37, mon-fri)` | **确认订单 → 触发净值出网** |
| `credit_money_fund_income`（`:128`） | `CronTrigger(00:05)` | 货基万份收益，另一条线 |
| `fund_catalog_sync`（`:141`） | `CronTrigger(02:17)` | **白名单同步，不抓净值** |
| `_warmup_cache` / `_startup_pending_compensation`（`:154-156`） | 启动时 | 行情预热 + 订单补偿（会触发净值出网） |

### 2.5 订单确认现状（本设计最重要的修正点）

`confirm_pending_orders()` 在**交易日 15:37** 运行（`spot_cache_scheduler.py:117`），选出 `confirm_date <= today` 的 pending 订单，逐笔调 `_confirm_one_order()`。确认时：

```python
# portfolio_service.py:1216（申购）、:1347（赎回）
nav = self._get_nav(fund_code)          # ← 取的是「最新一条净值」
if nav is None or nav <= 0:
    raise RuntimeError(f"无法获取基金 {fund_code} 的确认日净值，拒绝确认")
```

**两个问题：**

1. **取「最新」而不是「confirm_date 当日」**。`_get_nav` 里是 `df.iloc[-1]`（`portfolio_service.py:259`），完全不看订单的 `confirm_date`。若当日净值尚未公布，会**用前一日的净值去确认当日申购** —— 份额算错，且无任何提示。
2. **15:37 这个时点，场外当日净值通常还没公布**（实测见 §10：2026-10-14 白天，上游最新净值日期仍是 2026-10-13）。也就是说**「T 日 15:00 前下单、T 日确认」这条主路径，每天都在踩问题 1**。
3. 取不到净值时抛错 → `confirm_pending_orders` 把订单落 `rejected` 并**退回本金**（`portfolio_service.py:1089-1091`）。「数据还没到」被当成了「数据错了」。

## 3. 发现的问题

| # | 位置 | 现象 | 后果 |
|---|---|---|---|
| **P1** | `portfolio_service.py:941` + `finance_api_service.py:659,691` | 净值线**无缓存、无落库**；`/positions`、`/account`、`/daily-returns` 按持仓数逐只出网 | 页面慢，请求量随用户线性放大 |
| **P2** | `portfolio_service.py:1216,1347` | 确认取「最新净值」而非 `confirm_date` 当日净值 | **确认价可能取到 T-1**，份额算错 |
| **P3** | `spot_cache_scheduler.py:117` | 确认任务在 15:37，而场外当日净值当晚才公布 | P2 每天都在发生，不是边缘情况 |
| **P4** | `portfolio_service.py:1217-1218` | 净值「尚未公布」与「上游错误」被混为一谈，一律抛错 | 订单被 `rejected` + 退款，用户需重新下单 |
| **P5** | `finance_api_service.py:659` | 每次请求下载**全量历史**再 `tail(limit)`（`finance_api_service.py:668`） | 取 500 点要传 452 KB |
| **P6** | akshare 东财/新浪系函数 | 裸 `requests.get`，**无 timeout、无重试**（`2026-10-数据获取现状.md` P4） | 上游延迟抖动时（实测 C1 出现过 1.2s ↔ 31.5s）会挂住调用线程 |
| **P7** | `portfolio_service.py:627-630` | 下单时 `price` 可由**客户端传入**（`schemas.py:491`），不传才自动取 | 订单落库的 price/fee/quantity 可能是客户端给的（确认时会重算，风险有限，但口径不清） |
| **P8** | `fund_catalog_sync.py:326` | 白名单同步**不抓净值**，「新增了哪些基金需要预热」这件事目前没有任何记录 | 预热队列无从生成 |

## 4. 设计方案

### 4.1 架构总览

```
                     ┌──────────────────────────────────────────┐
   定时调度 ────────► │  ① 批量更新（白名单 ∩ 全市场批量接口）    │
   (见 §4.5)         │     每次 1 请求 → 就地 diff → upsert      │
                     └──────────────┬───────────────────────────┘
                                    │
   白名单同步完成 ──► ┌─────────────▼───────────────────────────┐
                     │  ② 历史预热 / 缺口补齐（单只独立队列）    │ ──► 多源适配器
                     └─────────────┬───────────────────────────┘      (§4.10)
                                    │
                     ┌─────────────▼───────────────────────────┐
                     │  ③ NavCacheService   ← 全项目唯一净值入口 │
                     │     ├ 内存：latest_nav（全量常驻）        │
                     │     ├ 内存：history LRU（按访问加载）     │
                     │     └ 持久：Supabase fund_nav / _state    │
                     └─────────────┬───────────────────────────┘
                                   │ 调用侧只认这一个入口
        ┌──────────────┬───────────┼───────────┬──────────────┐
        ▼              ▼           ▼           ▼              ▼
   /detail        /positions   /account   /daily-returns   订单确认
  (§4.9-1)        (§4.9-2)   (§4.9-2)     (§4.9-2)       (§4.7)
```

**设计原则**：调用侧（API 层、组合服务）**不再直接接触上游**，只问 `NavCacheService`。换源、补齐、重试全部发生在缓存服务内部。

### 4.2 数据库设计

新增三张表（迁移文件建议 `supabase/migrations/20261014XXXXXX_create_fund_nav_cache.sql`，沿用现有 `时间戳_描述.sql` 命名与头部注释块风格）。

#### 4.2.1 `fund_nav` —— 净值主表

```sql
CREATE TABLE IF NOT EXISTS "public"."fund_nav" (
    "fund_code"       character varying(10) NOT NULL,
    "nav_date"        date NOT NULL,
    "unit_nav"        numeric(18,6),          -- 可空：累计净值先到、单位净值后到时不留空行
    "accumulated_nav" numeric(18,6),          -- 可空：累计净值取不到不阻塞单位净值
    "daily_growth"    numeric(10,4),          -- 日增长率（%）
    "source"          text NOT NULL,          -- 写这行的源名（见多源文档）
    "first_seen_at"   timestamptz NOT NULL DEFAULT now(),
    "updated_at"      timestamptz NOT NULL DEFAULT now(),
    "revision_count"  integer NOT NULL DEFAULT 0,  -- 该日净值被更正的次数
    PRIMARY KEY ("fund_code", "nav_date")
);

-- 取最近 N 条（详情页曲线）走这个索引
CREATE INDEX IF NOT EXISTS "idx_fund_nav_code_date_desc"
    ON "public"."fund_nav" ("fund_code", "nav_date" DESC);
```

**为什么用 `(fund_code, nav_date)` 做主键**：用户提的合并规则全部以「基金代码 + 净值日期」为键（追加 / 更正 / 不回退），复合主键让这三条规则直接落成 `upsert(on_conflict=…)`，不需要额外的去重逻辑。

**为什么 `unit_nav` 允许 NULL**：用户明确要求「累计净值失败不阻塞已有单位净值的展示和估值」。反向亦然 —— 两个字段各自可空，一行只有一边有值时仍然可读。

#### 4.2.2 `fund_nav_state` —— 每只基金的缓存状态（一行/只）

```sql
CREATE TABLE IF NOT EXISTS "public"."fund_nav_state" (
    "fund_code"          character varying(10) PRIMARY KEY,
    "preheat_status"     text NOT NULL DEFAULT 'pending',  -- pending|ready|partial|failed
    "latest_nav_date"    date,          -- 缓存里的最新净值日期（= 回退保护的基准）
    "latest_unit_nav"    numeric(18,6), -- 冗余存一份，估值时免去 join 主表
    "history_start_date" date,          -- 已缓存历史的最早日期（缺口判断用）
    "is_history_complete" boolean NOT NULL DEFAULT false, -- 是否确认拉到过成立以来全量
    "last_checked_at"    timestamptz,   -- 最后一次「成功检查」（数值未变也算）
    "last_success_at"    timestamptz,   -- 最后一次真正拿到数据
    "last_error"         text,          -- 最近一次失败原因（不掩盖错误）
    "last_error_at"      timestamptz,
    "updated_at"         timestamptz NOT NULL DEFAULT now()
);

-- 给「哪些基金还不健康」的运维查询
CREATE INDEX IF NOT EXISTS "idx_fund_nav_state_health"
    ON "public"."fund_nav_state" ("preheat_status", "last_error_at");
```

**为什么 `latest_unit_nav` 要冗余**：`/positions`、`/account` 只需要最新价，冗余在这张表可以一次 `SELECT … WHERE fund_code IN (…)` 拿全，不必碰可能上千行的 `fund_nav`。这是把「持仓循环逐只出网」（P1）变成「一次批量查库」的关键。

**`last_checked_at` vs `last_success_at` 分开**：用户提的合并规则里有「数值未变化 → 只更新成功检查时间」。这两个时间语义不同，混用会看不出「到底是没检查，还是检查了但没数据」。

#### 4.2.3 `fund_nav_revision` —— 更正日志（只追加）

```sql
CREATE TABLE IF NOT EXISTS "public"."fund_nav_revision" (
    "id"                  bigserial PRIMARY KEY,
    "fund_code"           character varying(10) NOT NULL,
    "nav_date"            date NOT NULL,
    "old_unit_nav"        numeric(18,6),
    "new_unit_nav"        numeric(18,6),
    "old_accumulated_nav" numeric(18,6),
    "new_accumulated_nav" numeric(18,6),
    "source"              text NOT NULL,
    "detected_at"         timestamptz NOT NULL DEFAULT now()
);
```

用户要求「已有日期数值变化 → 更新该日记录，记录更正日志」。这张表就是那个日志：**净值更正是真实存在的（分红、拆分、上游修正）**，不做记录的话只能看到「数字变了」却不知道什么时候变的。

#### 4.2.4 是否要走迁移

必须走。`fund_fee_rules` 等表全部由 `supabase/migrations/` 管理，且规则明确「库结构唯一权威来源收敛到 migrations」（commit `26a35d3`）。**本轮不执行迁移**，只登记设计。

### 4.3 内存缓存设计

**先算内存账**（决定能缓存什么）：

- 单只基金一个净值点 ≈ `(date, unit_nav, accumulated_nav, daily_growth)` 4 个对象 ≈ 200 B
- `110020` 有 4160 点 → 单只历史 ≈ 830 KB
- 2300 只全部常驻 ≈ **1.9 GB** → **不可接受**

因此内存缓存分两层：

| 层 | 内容 | 容量 | 说明 |
|---|---|---|---|
| **L1 恒驻** | `latest: dict[str, NavPoint]` | 白名单 ≈ 2328 条 ≈ **0.5 MB** | 服务启动时从 `fund_nav_state` 一次性载入。`/positions`、`/account`、订单确认全部命中这一层 |
| **L2 LRU** | `history: OrderedDict[str, list[NavPoint]]` | 上限 `NAV_HISTORY_CACHE_MAX_FUNDS`（默认 **200** 只）≈ 166 MB | 详情页曲线用。未命中时从 `fund_nav` 读（SQL 毫秒级），读入后进 LRU |
| **DB** | 全量历史 | — | 唯一真相源 |

**为什么 L2 用 LRU 而不是「全部常驻」**：详情页的访问是长尾分布（少数基金被反复看），LRU 用 166 MB 换掉 1.9 GB 的常驻，命中率损失很小。上限做成配置项，将来内存宽裕了可以调大。

**并发安全**：调度器（apscheduler 线程池）与请求处理（asyncio 事件循环）会同时读写。用 `threading.RLock` 保护 L1/L2；DB 写用 upsert 天然幂等，不做分布式锁。

### 4.4 首次预热

触发时机：**白名单同步完成后**（`fund_catalog_sync` 任务末尾，或 `merge_candidates` 返回新增代码时）。当前同步不记录「新增了哪些基金」（P8），本设计要补这个返回值。

#### 成本取舍（已决策：L3）

| 方案 | 做法 | 成本 | 拿到什么 |
|---|---|---|---|
| **L1 只预热最新净值** | 一次调用全市场批量接口（见 §4.5），筛出白名单写入 `fund_nav_state` | **1 请求 / ≈29s / 4.3 MB** | 估值、订单确认、持仓页立即可用；**详情页曲线仍为空** |
| **L2 全量历史预热** | 逐只调单只全量历史接口 | **≈2328 请求 / ≈1000 MB / 串行约 30–60 分钟** | 详情页曲线也可用 |
| **L3 分级预热（已采用）** | 先跑 L1（秒级让全站可用），再后台按优先级逐只补历史 | L1 成本 + L2 成本，但**错峰**且可中断 | 同上，且**服务立即可用**，历史慢慢长齐 |

**决策（2026-10-18）：采用 L3。** 理由：

1. L1 用 **1 个请求**就让「估值、订单确认、持仓页」这三件影响钱的事全部落地，性价比极高；
2. L2 的 1000 MB 是真实成本（实测 4 只平均 452 KB × 2328），一次性可接受但不能放在启动路径上；
3. L3 天然符合需求方说的「未经成功预热的基金返回『数据准备中』，不在页面请求里等待下载」。

**L3 的优先级排序**（预热队列的服务顺序）：

1. **已有持仓的基金** —— 直接关系用户看到的盈亏；
2. **最近 30 天被访问过的基金** —— 用 `fund_nav_state.last_checked_at` 或新增访问计数；
3. 其余按代码顺序。

**「数据准备中」的语义**（调用侧契约不变，只是数据为空）：

- `fund_nav_state.preheat_status = 'pending'` 且无任何 L1 数据 → `/detail` 的 `nav_history` 返回 `[]`，`realtime` 照常；
- **不返回 0、不返回假数据、不阻塞请求**。

### 4.5 日常更新调度

**核心手段**：单次调用**全市场场外净值批量接口**（`对外数据源请求与返回.md` 的 C1），一次拿到全市场约 2.4 万行的「最新一天 + 前一天」，**在本地筛出白名单**。

- 源名、列名结构与字段映射见适配器文档 §6.1（`em_fund_jjjz`）；本文只保留请求量测算所需的数据
- ⚠️ **它的「当日」= 最新已公布日，不是日历今天**。2026-10-14 白天采样，列名仍是 `2026-10-13-*`。任何「今天拉到了今天的净值」的假设都是错的

#### 调度表（北京时间）

沿用需求方给的初始配置，补上判断依据：

| 时间 | 任务 | 判断依据 |
|---|---|---|
| 场外目录同步完成后 | 新增基金入预热队列；跑一次 L1 批量更新 | 同步返回的新增代码（当前缺失，见 P8） |
| 每天 **08:00** | 批量检查最新净值，补收晚公布的（海外/QDII 类） | 每天执行，不看交易日 |
| **交易日 18:00–23:00，每小时** | 批量更新当日陆续公布的净值 | `is_trading_day(当日)` |
| **次日 00:00、01:00** | 延续上一交易日晚间的更新 | **按「上一天是否交易日」判断，不按星期几** |
| 服务启动时 | 恢复缓存；若错过计划检查则补执行一次 | 与 `last_checked_at` 比对 |

> **这些时刻是初始配置，不是上游公布时间的保证**（需求方原话）。真实的公布节奏必须实测（见 §7.3），实测后按数据调整。

**为什么坚持「按上一天是否交易日」**：`CronTrigger(day_of_week=…)` 只看星期几。国庆假期里的周四、调休上班的周六都会判错 —— 这正是 `trading_calendar.py` 模块头注释里记录过的一个历史 bug（当时行情缓存在休市日仍每 30s 刷）。午夜任务同理。

#### 每日请求量

| 项 | 次数 | 流量 |
|---|---|---|
| 批量更新（18–23 六次 + 00/01 两次 + 08:00 一次） | 9 | ≈ 39 MB |
| 未覆盖/缺当日净值的单只补齐 | 见 §4.5.1，约 150 | ≈ 0.6 MB |
| **合计** | **≈ 160 / 日** | **≈ 40 MB / 日** |

对比现状：一个用户刷一次持仓页就是 1.4 MB，且**随用户数无限增长**。

#### 4.5.1 批量接口覆盖不全（实测坐实，必须兜底）

实测 2026-10-14：

| 项 | 结果 |
|---|---|
| 白名单候选 | **2328 只** |
| 批量接口命中 | **2260 只（97.1%）** |
| **未命中** | **68 只** |
| 命中但当日净值为空 | **80 只**（暂停申购 / 封闭期 / 新发未成立） |
| 白名单内申购状态分布 | 开放申购 2027 / 限大额 162 / 暂停申购 71 |

未命中的 68 只**不是异常数据**，是正常的 ETF 联接基金：

```
000076 华夏恒生ETF联接现钞
000164 富国上证指数ETF联接A(后端)     ← 后端收费份额
016917 南方中证上海环交所碳中和ETF联接A
019167 易方达中证物联网主题ETF联接发起式A
027395 鹏华恒生科技ETF发起式联接A
...
```

**已排除的猜想**：它们**不在**场内批量接口（C2，1683 行 / 0.70s）里 —— 实测交集为空。所以兜底只能走单只接口。

**结论**：**批量为主 + 单只兜底**是必需的，不能只靠批量。兜底规模约 `68 + 80 ≈ 148 只/日`。

### 4.6 每次更新的合并规则

批量返回的数据，按「**基金代码 + 净值日期**」合并（需求方原表，落成可执行规则）：

| 情况 | 处理 | 落库动作 |
|---|---|---|
| 出现新日期 | 追加记录 | `upsert` 新行；更新 `fund_nav_state.latest_nav_date` |
| 已有日期数值变化 | 更新该日记录 + 记录更正日志 | `upsert` 覆盖 + 写 `fund_nav_revision` + `revision_count += 1` |
| 数值未变化 | 只更新成功检查时间 | 只更新 `fund_nav_state.last_checked_at`（**不写 fund_nav**） |
| 基金缺失 / 数值为空 / 异常 | 保留原缓存，标记待检查 | 写 `last_error` / `last_error_at`，**绝不覆盖已有值** |
| 返回日期比缓存更早 | **不回退最新净值** | 丢弃该点（`nav_date <= latest_nav_date` 且非更正） |
| 缓存存在历史缺口 | 加入单只历史补齐队列 | 标 `is_history_complete = false` |

**「数值未变化只更新时间」是省流的关键**：9 次批量更新里绝大多数基金当天只有一个新点，其余全是「没变化」，不应对主表产生任何写入。

**「返回日期比缓存更早不回退」的实现**：以 `fund_nav_state.latest_nav_date` 为基准，只接受 `nav_date > latest_nav_date` 的点（或日期相同但数值变更的更正）。

**缺口判断的边界**（需求方特别提到）：

- 批量接口**只覆盖最近两天**。服务停机较久时，不能只追加最新两条而留下中间空白；
- 判断「有没有缺口」要**结合基金成立日期**（`fund_fee_rules` 无此列，需从 `fund_overview_em` 的「成立日期/规模」取，或从首次拉到的历史起点推）与**不同市场的公布节奏**（QDII / 港股通类与 A 股不同）；
- 判定有缺口 → 进单只补齐队列，**不阻塞批量更新**。

### 4.7 订单确认口径（本设计的核心修正）

需求方原话：**「订单确认要根据指定的日期，而不是直接拉取最新一条的数据，万一没更新呢？」**

#### 新口径

```python
# 取代 portfolio_service.py:1216 与 :1347 的 self._get_nav(fund_code)
nav = nav_cache.get_nav_on(fund_code, order["confirm_date"])   # 指定日期，不是最新
```

`get_nav_on(code, d)` 语义：

| 情况 | 返回 | 确认动作 |
|---|---|---|
| `d` 日的净值已缓存 | `Decimal` | 正常确认 |
| `d` 日净值**尚未公布** | `None` + 明确原因 `NOT_YET_PUBLISHED` | **跳过该订单，留在 pending，下个窗口重试**。不落 `rejected`、不退款 |
| `d` 日净值**上游多次取不到** | `None` + `FETCH_FAILED` | 记录错误、**仍然跳过**（不确认）。由运维介入；**绝不用 T-1 顶替** |

**这是对 P4 的修正**：把「数据还没到」和「数据错了」分开。现状把两者都当成失败 → 订单被拒 + 退款，用户得重新下单。

#### 调度时点（已决策：A）

现状 15:37 确认「`confirm_date <= today`」的订单，而 T 日净值当晚才有 → 主路径必然踩到「未公布」。**决策（2026-10-18）：采用 A。**

- **确认任务挪到净值公布之后**：**20:00、21:00、22:00、23:00**（每次都是「能确认的就确认，不能的留着」的幂等扫描）+ **次日 08:00** 补漏；
- 保留现有 15:37 那次，但让它的作用退化为「处理 `confirm_date < today` 的历史遗漏」，不再期望能确认当日的；
- 启动补偿（`spot_cache_scheduler.py:88`）逻辑不变，同样走新口径；
- **未公布一律留在 pending**，不落 `rejected`、不退款；下一轮继续重试。

#### 已接受的业务语义变化

现状文档写的是「15:00 前提交：立即成交，按当日净值确认」（`server/api/portfolio.py:70`）。改成净值公布后确认后，**用户会看到确认推迟几小时**（从 15:37 变成当晚 20:00–23:00）。

这是「数值正确」与「确认及时」的取舍，**已由需求方拍板选 A**：宁可确认晚几小时，也不用 T-1 净值确认 T 日订单。

> 附带事实：下单路径 `apply_purchase`（`portfolio_service.py:628`）也调 `_get_nav` 取最新净值算预估值。改为缓存后它读 L1，**毫秒级**，且不再出网。它算出的只是**预估值**，真正的 price 在确认时按 §4.7 重算，所以这里**允许**用最新净值。

### 4.8 失败与补齐

| 机制 | 设计 |
|---|---|
| **单飞（合并并发）** | 批量更新同一时刻只跑一个。用与 `fund_catalog_sync.sync_lock()`（`fund_catalog_sync.py:88`）**同一套 flock 模式**，锁文件独立（`/tmp/fund_nav_update.lock`）。拿不到锁 = 已有更新在跑，本轮跳过，**不算失败** |
| **重试退避** | 失败后 **5 分钟 → 15 分钟 → 30 分钟**。重试任务与新一轮计划任务**合并**（同一把锁 + 检查 `last_checked_at`），避免重复执行 |
| **上游失败保留旧数据** | 始终保留最后一次成功的数据。**首次获取失败则保持「尚无数据」**，绝不用 `0` 填充 |
| **单只补齐队列** | 独立、低并发，不阻塞批量更新。优先级见 §4.4 |
| **每周一次分批历史复核** | 用来发现「最近两天之外」的净值更正（分红、拆分、上游修正）。按代码分段，一周内覆盖全部白名单，错峰在非更新时间 |
| **超时** | 适配器层统一强制 timeout（P6）。akshare 东财/新浪函数**无 timeout**，见多源文档 §4 |

### 4.9 调用侧切换（逐个改造点）

原则：**API 响应契约不变**，只改数据来源。前端（不在本仓库）不需要配合改动，未预热时看到的是「空序列」而不是报错。

| # | 改造点 | 现状 | 改为 |
|---|---|---|---|
| 1 | `finance_api_service.py:659` `_query_nav_history` | 直接调 akshare，全量下载后 `tail(limit)` | 读 `NavCacheService.get_history(code, limit)`；L2 → DB → 未预热则 `[]` |
| 2 | `finance_api_service.py:691` `_query_accumulated_nav` | 单独一次出网 | 从缓存历史的同一条记录取 `accumulated_nav`（**省掉一次 452 KB 请求**） |
| 3 | `finance_api_service.py:215` `_query_nav` | 直接调 akshare | 读 L1 |
| 4 | `portfolio_service.py:257` `_get_nav` | 直接调 akshare | **拆成两个方法**：`get_nav_latest(code)`（下单预估值用）与 `get_nav_on(code, date)`（确认用，§4.7） |
| 5 | `portfolio_service.py:941` 持仓循环 | 每只持仓出网一次 | 循环外一次批量 `SELECT … IN (fund_codes)`，循环内只查内存 |
| 6 | `portfolio_service.py:1216` / `:1347` | `_get_nav` 最新值 | `get_nav_on(code, confirm_date)`，未公布则跳过 |
| 7 | `portfolio_service.py:628` | `_get_nav` | `get_nav_latest` |

**为什么 #2 能省一次请求**：现状单位净值和累计净值是**两次独立请求**（`finance_api_service.py:665`）。批量接口和中国大陆单只历史接口（`api.fund.eastmoney.com/f10/lsjz`，实测 `DWJZ` + `LJJZ` 在同一行）都是一次返回两者。归一化后同属一个 `NavPoint`，天然只需一次。

### 4.10 与多源适配器的接缝

`NavCacheService` **不直接调任何上游**，只通过适配器取数。`Source` / `NavPoint` 的定义、源清单、域名与能力编排见 [`数据源多源适配器.md`](../行情/数据源多源适配器.md) §4.2、§6.1；本文不重复。

缓存服务只声明它需要的能力，不关心由哪个源提供：

| 能力 | 用途 |
|---|---|
| `batch` | §4.5 日常批量更新（一次拿全市场最新一天 + 前一天） |
| `history` | §4.4 预热、§4.8 缺口补齐（单只全量历史） |
| `latest` | §4.5.1 单只兜底（约 148 只/日） |

**责任划分**：

- **适配器**负责按能力选源、域名级熔断、超时、失败分类、重试与 `AllSourcesFailed`；
- **缓存服务**负责按白名单筛选（源不做过滤）、把 `NavPoint` 落成 `fund_nav` 行、合并规则（§4.6）、缓存分层（§4.3）；
- 取数失败必须让异常向上抛，**缓存服务不得把 `AllSourcesFailed` 静默改成空列表**。

`NavCacheService` 对适配器的调用入口：`fetch_history(code)`、`fetch_history_recent(code, limit)`、`fetch_latest(code)`、`fetch_latest_batch(codes)`。其中 `fetch_latest_batch` 返回 `dict[str, list[NavPoint]]`，缓存服务按 §4.6 合并窗口内的所有点（通常是最新一天 + 前一天），不能只取第一个点。能力名一旦变化，两边同时改，以适配器文档为准。

## 7. 测试策略

> 项目约定：用户非测试岗，修 bug 以恢复产品行为为先，**不堆测试体系**（记忆 `user-not-a-tester-minimal-tests`）。因此下面只列**必须**的几处。

### 7.1 单元测试（改哪些就测哪些）

| 目标 | 用例要点 |
|---|---|
| 合并规则（§4.6） | 六种情况各一例：新日期 / 数值变更（断言写 `fund_nav_revision`）/ 未变化（**断言不写主表**）/ 缺失 / 更早日期（断言不回退）/ 缺口标记 |
| `get_nav_on`（§4.7） | 已公布 / 未公布 / 抓取失败三种返回必须**可区分**（不是都返回 `None`） |
