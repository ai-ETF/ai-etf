## 1. 需求分析

### 1.1 业务场景

产品只做场外基金，不做场内实时交易。由此产生的存储约束：

1. **净值每天只公布一次**，通常在交易日 20:00 后陆续更新。没有秒级读取需求，不需要进程内缓存层。
2. **订单按 `confirm_date` 当日净值成交**。确认必须能回答「这一天到底有没有净值」，而不是拿最新一条顶替。
3. **净值会更正**。上游偶尔修正历史值，需要可追溯，不能静默覆盖。
4. **持仓页按用户持仓批量取最新净值**。读取次数应固定为 1 次，不随持仓只数增加。
5. **基金静态信息（公司、经理、类型、跟踪标的、成立日、规模、QDII）目前每次现抓、不落库**；`fund_fee_rules` 里只有名称，且它同时承担「白名单准入」职责。需要把身份/描述与交易规则拆开，并保留 QDII 判定依据。

### 1.2 数据需求

| 数据域 | 关键属性 | 来源 | 更新时机 | 保留 |
|---|---|---|---|---|
| 净值明细 | 基金代码、净值日、单位净值、累计净值、日增长率、写入源 | 适配器 4 个净值源 | 每轮同步只写最新 1–2 个点；首次查看补全量 | 永久 |
| 最新净值投影 | 基金代码、最新净值日、最新单位净值 | 由净值明细派生 | 每轮同步后更新 | 每基金 1 行 |
| 同步状态 | 历史完整性、历史起点、最后检查/成功/失败 | 同步服务 | 每轮同步、每次历史补齐 | 每基金 1 行 |
| 更正记录 | 基金代码、净值日、旧值、新值、来源、发现时间 | 合并时自动产生 | 仅在数值变化时追加 | 永久（量很小） |
| 基金主数据 | 代码、名称、`FTYPE`、公司、经理、跟踪标的、成立日、规模、风险等级、QDII 标识与依据、生命周期 | 移动端 `FundMNBasicInformation` | 每日白名单同步 | 每基金 1 行 |
| 交易规则 | 费率、份额类别、申购起点/上限、申购状态、T+N | 天天基金 jjfl + 移动端 | 每日白名单同步 | 每基金 1 行 |

明确不存：

- 场内行情、K 线、分时；
- 货基万份收益（仍由现有逻辑处理，`MONEY_FUND_CODE` 在读服务外特判）；
- 费率**计算过程**（申购费/赎回费算法仍在业务层；档位数据存在 `fund_trade_rule`）；
- 上游原始响应报文（只存归一化结果与源名，便于审计而不膨胀）。

### 1.3 访问需求

| 场景 | 操作 | 频次 | 单次数据量 | 说明 |
|---|---|---|---|---|
| 持仓 / 账户 / 收益 | 批量读最新 | 每次请求 | 行数 = 持仓数（十级） | 必须 1 条 SQL 完成 |
| 下单预估 | 单只读最新 | 每笔下单 | 1 行 | 失败要明确拒绝下单，不能猜 |
| 详情页历史 | 按基金读最近 N 条 | 每次查看 | 默认 500 行，`limit=None` 时可达约 4000 行 | 首次可能触发补数 |
| 订单确认 | 按（基金, 日期）读单点 | 每笔订单 | 1 行 | 只读 DB，不触网 |
| 每日全量最新 | 批量写 | 每天 6–9 轮 | 约 2300 只 × 1–2 点 | 未变化的行不写 |
| 持仓历史预热 | 单只写全量 | 每轮同步后 | 约 4000 行/只 | 仅 `history_status != 'ready'` 的持仓基金 |
| 基金目录 / 详情 | 读 `fund_catalog` | 每次请求 | 20 行/页；1 行详情 | 出现在目录 = 可交易 |
| 元数据展示 | 读 `fund` | 每次请求 | 数十行 | 与净值读互不依赖 |
| 主数据与规则同步 | 单只写 3 行（fund / 规则 / 风险） | 每天 1 次 | 约 2300 组 | 同一事务写入 |

延迟目标：单次读取的 DB 耗时在**几十毫秒内**（Q-D6 待上线实测）。没有硬性 SLA，但不能出现「页面等上游」的路径。

### 1.4 一致性与可用性需求

| 需求 | 落地 |
|---|---|
| 一只基金一天最多一个净值点 | 主键 `(fund_code, nav_date)` |
| 更正必须留痕 | 数值变化时写 `fund_nav_revision`，并在主表累加 `revision_count` |
| 最新净值不能回退 | 只在 `nav_date > latest_nav_date` 时推进状态表 |
| 写入可重复执行 | `upsert` / 合并函数幂等；相同值不产生写与更正记录 |
| 缺失不能伪装成 0 或 T-1 | 读服务返回显式状态（`NOT_YET_PUBLISHED` / `FETCH_FAILED` / `NO_NAV`） |
| DB 不可用时不能返回空列表 | 读异常上抛，API 返回 5xx |
| 多进程安全 | 读路径无进程内状态；写入用数据库事务 + 咨询锁串行化 |
| 历史不完整必须可判定 | `fund_nav_state.history_status` 是唯一判据 |
| 准入只由交易规则决定 | `lifecycle_status='active'` 且 `fund_trade_rule` 行存在；`fund` 行存在不代表可交易 |
| 主数据与交易规则一起写 | `upsert_fund_catalog` RPC 同一事务；外键阻止「规则孤儿」 |
| 下架不删数据 | `fund.lifecycle_status='removed'`；净值、订单、历史规则保留 |

### 1.5 容量估算

已知量级（来自既有实测，非本轮重跑）：

- 场外白名单约 **2328** 只；
- 单只老基金全量约 **4160** 个净值点（`110020`）；
- 单只全量响应约 452 KB。

估算：

| 表 | 行数量级 | 估算依据 |
|---|---|---|
| `fund_nav` | 按需增长；**全量补满的上限约 900 万行** | 2328 × 约 4000 点 |
| `fund_nav_state` | 2328 | 每基金 1 行 |
| `fund_nav_revision` | 极少（预计每年百行以内） | 只在更正时产生 |
| `fund` | 2328 | 每基金 1 行 |
| `fund_trade_rule` | 2328 | 每基金 1 行 |
| `fund_risk_profiles` | 2328 | 每基金 1 行 |

存储粗估：`fund_nav` 单行约 100–140 字节（含行头、数值变长、时间戳），900 万行约 **1.0–1.5 GB**（含主键索引）。实际值会明显低于上限，因为历史是按持仓与访问逐步补齐的。

日增量：每只基金每天最多新增 1 行，约 **2300 行/交易日**；未变化的历史行不重写。

**分区的触发条件**：`fund_nav` 超过约 2000 万行、或单表超过 5 GB 时，再按 `nav_date` 年/月分区；当前不做（Q-D2）。

### 1.6 非目标

- **不做进程内 L1/L2 缓存**。原稿的「L1 最新净值字典 + L2 历史 LRU + DB」在放弃场内基金后不再成立：

  | 判断 | 依据 |
  |---|---|
  | 场外净值没有实时性需求 | 每个交易日只公布一次，通常 20:00 后才陆续更新；同一只基金一天内不会变（除极少数更正） |
  | 读的瓶颈不在内存 | 持仓页是一次 `IN (codes)` 查 `fund_nav_state`，行数 = 持仓数；详情页走 `(fund_code, nav_date)` 主键扫描。两者都不随用户数放大 |
  | 缓存会引入新的一致性问题 | 进程内副本要处理失效、原子替换、多 worker 不一致，换来的只是毫秒级差异 |
  | DB 本身就是持久化真相源 | 重启不用重建、多进程天然一致、运维可直接查库核对 |

  若将来实测读延迟不达标，按「先看执行计划 → 补覆盖索引 → 最后才考虑进程内只读缓存」的顺序处理（Q-D6），不预置两层。
- 不做全市场基金目录：非白名单基金不落库，等有真实需求再扩（Q-D14）；
- 不做全量历史预热；
- 不做跨库同步、读写分离、物化视图；
- 不做多租户隔离；
- 不把费率**计算**、交易流水并入本文；`fund_trade_rule` 是费率数据的存储结构，不等同于费率业务逻辑。

## 2. 概念设计

### 2.1 实体

| 实体 | 说明 | 标识 |
|---|---|---|
| **基金（Fund）** | 基金主体：名称、`FTYPE`、公司、经理、跟踪标的、成立日、规模、风险等级、QDII 与生命周期 | `fund_code` |
| **交易规则（FundTradeRule）** | 准入与费率：行存在即可交易，`subscribe_status` 决定能否申购 | `fund_code` |
| **风险画像（FundRiskProfile）** | 四维评分与风险等级，由规则推导 | `fund_code` |
| **净值点（NavPoint）** | 某只基金在某个净值归属日的净值 | `fund_code` + `nav_date` |
| **同步状态（NavSyncState）** | 某只基金的历史完整性与最近同步结果 | `fund_code` |
| **更正记录（NavRevision）** | 某个净值点被修改的历史痕迹 | 自增 `id` |

### 2.2 联系

```
Fund (PK fund_code)
 ├─1:1─ FundTradeRule (PK fund_code, FK)    ← 行存在 = 可交易
 ├─1:1─ FundRiskProfile (FK)
 ├─1:1─ NavSyncState
 └─1:N─ NavPoint (PK fund_code + nav_date) ─1:N─ NavRevision
```

联系说明：

- Fund 1 : 1 FundTradeRule —— 一只基金至多一条交易规则；规则缺失 = 不可交易；
- Fund 1 : 1 FundRiskProfile —— 推导出的风险画像；
- Fund 1 : 1 NavSyncState —— 同步状态快照；
- Fund 1 : N NavPoint —— 净值明细；NavPoint 1 : N NavRevision —— 一个点可被更正多次；
- `fund_catalog` 是 Fund JOIN FundTradeRule（且 `lifecycle_status='active'`）的**只读视图**，承接原 `fund_fee_rules` 的读取形状。

**关于外键**：

| 关系 | 外键 | 理由 |
|---|---|---|
| `fund_trade_rule` → `fund` | **建**，`ON DELETE RESTRICT` | 规则不能脱离主数据存在；基金也不允许被物理删除 |
| `fund_risk_profiles` → `fund` | **建**，`ON DELETE RESTRICT` | 风险画像不能是孤儿 |
| `fund_nav*` → `fund` | **不建** | 基金下架或主数据被清理后，历史净值仍要对账；净值写入是批量合并，外键会放大写入成本 |
| `fund_nav_state` → `fund` | **不建** | 同上；状态可以重建 |

下架用 `fund.lifecycle_status='removed'`，不执行 `DELETE`。`fund_catalog` 过滤 `active`，因此下架后即使规则行还在，也不会重新出现在可交易目录里。

净值不建外键是有意取舍，不是遗漏（Q-D4）。

### 2.3 业务规则

| 编号 | 规则 | 落地位置 |
|---|---|---|
| R0 | 可交易 = `lifecycle_status='active'` 且交易规则行存在；`subscribe_status` 不在可申购集合时只能赎回 | `fund_catalog` 视图 + 业务判定 |
| R1 | 一只基金一个净值日只有一行 | 主键 |
| R2 | 同一日期数值变化必须留旧值 | 合并函数写 `fund_nav_revision` |
| R3 | 同一日期数值不变不写主表、不留更正 | 合并函数先比较 |
| R4 | `latest_nav_date` 只能前进 | 状态更新时比较 |
| R5 | 上游返回更早日期只补历史，不回退最新 | 状态更新时比较 |
| R6 | 取数失败保留原值，只写错误字段 | 同步服务 |
| R7 | 历史完整性只有 `history_status` 一个判据 | 状态表 |
| R8 | QDII 是推导值，必须同时保存推导依据 | `fund.is_qdii` + `fund.qdii_reason` |
| R9 | 元数据抓取失败不覆盖旧行；`is_qdii` 未知时存 NULL，不伪造 `false` | 同步服务 + CHECK |
| R10 | 不写 0 净值 | 物理约束 + 同步前校验 |
| R11 | 下架只改 `lifecycle_status`，不删除主数据、净值、订单 | `fund.lifecycle_status` |
| R12 | 主数据与交易规则在同一事务写入 | `upsert_fund_catalog` RPC |
| R13 | 用户业务表（持仓/自选/订单）里的 `fund_name` 是下单时快照，基金改名不回填 | `positions` / `watchlist` / `trade_orders` 各自持有 |

### 2.4 状态模型

`fund_nav_state.history_status`：

```
新基金/新代码 ──▶ pending
pending  --补齐成功──────────▶ ready
pending  --补齐失败/部分成功──▶ partial
partial  --补齐成功──────────▶ ready
partial  --补齐失败──────────▶ failed
failed   --再次补齐成功──────▶ ready
failed   --再次补齐失败──────▶ failed
ready    （不再触发补齐）
```

约束：

- `ready` 表示历史已完整，可以参与「缺口」判定；
- `partial` 表示只写了一部分，读 `get_nav_on` 时必须返回 `FETCH_FAILED(history_not_complete)`，不能断言「该日没有净值」；
- `failed` 与 `pending` 都不能参与缺口判定；
- `ready` 是终态：后续 `update_batch` 只写最新点，不会把状态打回 `partial`。

### 2.5 单点查询（`get_nav_on`）的四态判定

纯 DB 判定，顺序不能调换：

1. DB 有 `(fund_code, on_date)` 记录 → `OK`；
2. 无记录，且 `on_date` 晚于 `fund_nav_state.latest_nav_date` → `NOT_YET_PUBLISHED`；
3. 无记录，`history_status = 'ready'`，且 `history_start_date <= on_date <= latest_nav_date` → `FETCH_FAILED`（真实缺口，需 `repair`）；
4. 无记录，`history_status != 'ready'` → `FETCH_FAILED(reason="history_not_complete")`，不得判定为「已公布但没有」；
5. 无记录，`history_status = 'ready'`，且 `on_date < history_start_date` → `NO_NAV`（早于已知最早净值日），重试不会出现，需人工核查订单日期。

`NO_NAV` 不等于「基金成立前」：成立日来自 `fund.establish_date`，但判定只看净值覆盖区间。若成立日已同步且 `on_date < establish_date`，可在 `reason` 中补充 `before_establishment` 便于排查，不改变状态本身。

## 3. 逻辑设计

### 3.1 关系模式

```
fund(fund_code, fund_name, ftype, manager_company, fund_manager,
     tracking_index, tracking_index_code, establish_date, net_asset_scale,
     risk_level_code, is_qdii, qdii_reason, metadata_source,
     lifecycle_status, first_seen_at, synced_at, updated_at)
    主键: fund_code

fund_trade_rule(fund_code, fund_type, share_class, management_fee_rate,
                custody_fee_rate, sales_service_fee_rate, commission_rate,
                min_purchase_amount, max_purchase_amount, subscribe_status,
                purchase_fee_tiers, redemption_fee_tiers, confirm_delay,
                redeem_settle_delay, created_at, updated_at)
    主键: fund_code
    外键: fund_code → fund(fund_code)
    语义: 行存在 = 进入白名单

fund_risk_profiles(id, fund_code, equity_score, bond_score, commodity_score,
                   market_score, risk_level, risk_label, ...)
    主键: id    唯一: fund_code    外键: fund_code → fund(fund_code)

fund_catalog = fund ⨝ fund_trade_rule（USING fund_code）
               WHERE fund.lifecycle_status = 'active'
    只读视图，不占存储

fund_nav(fund_code, nav_date, unit_nav, accumulated_nav, daily_growth,
         source, first_seen_at, updated_at, revision_count)
    主键: (fund_code, nav_date)

fund_nav_state(fund_code, history_status, latest_nav_date, latest_unit_nav,
               history_start_date, last_checked_at, last_success_at,
               last_error, last_error_at, updated_at)
    主键: fund_code

fund_nav_revision(id, fund_code, nav_date, old_unit_nav, new_unit_nav,
                  old_accumulated_nav, new_accumulated_nav, source, detected_at)
    主键: id
```

### 3.2 键的设计

| 表 | 主键 | 理由 |
|---|---|---|
| `fund_nav` | `(fund_code, nav_date)` | 业务唯一键；同时是历史查询与单点查询的入口，一个索引覆盖两种模式 |
| `fund_nav_state` | `fund_code` | 一对一状态；持仓页按代码 `IN` 查询直接走主键 |
| `fund_nav_revision` | `id` | 只追加；业务上不要求唯一 |
| `fund` | `fund_code` | 自然业务键；对外接口、订单、净值都用它 |
| `fund_trade_rule` | `fund_code` | 一对一；与 `fund` 同键，JOIN 无需额外索引 |
| `fund_catalog` | 无 | 视图继承基表键 |

`fund_trade_rule` 不再保留代理主键 `id`：原 `fund_fee_rules.id` 没有任何外部引用，`fund_code` 是唯一业务键且已有唯一约束，保留双键只会制造「两个都像主键」的歧义。

`fund_risk_profiles` 保持现有 `id` 主键 + `fund_code` 唯一约束，只补外键；改主键会牵动已有数据与代码，收益为零。

`fund_nav` 不另设代理主键：`(fund_code, nav_date)` 已经是稳定、窄、单调的业务键，再加 `bigserial` 只会多一个索引和一次唯一性检查。

### 3.3 规范化与冗余取舍

| 设计 | 范式判断 | 理由 |
|---|---|---|
| `fund_nav` 存明细，最新值不落该表以外的计算 | 3NF | 明细是唯一事实 |
| `fund_nav_state` 冗余 `latest_unit_nav` | 反规范化 | 持仓页要一次 `IN` 查询拿到全部最新价；若从明细取，需要窗口函数或 N 次查询 |
| `fund_nav_revision` 独立成表 | 3NF | 追加型审计，不能覆盖；与主表生命周期不同 |
| `fund` 与 `fund_trade_rule` 拆分 | 3NF | 身份/描述（变化慢、来源单一）与准入/费率（可单独失败、有独立生命周期）不是同一实体；`fund_type` 同名不同义（`of/etf` 是交易分类，`ftype` 是上游描述） |
| `fund_catalog` 视图 | 反规范化（只读） | 兼容原 `fund_fee_rules` 的读取形状，调用方无需在应用层拼两张表；视图不存数据，不产生一致性负担 |
| `fund` 不存「是否可交易」布尔 | 3NF | 可交易由「规则行是否存在 + lifecycle」推导；存布尔会与事实表不一致 |
| `source` 存在每个净值点 | 反规范化 | 跨源混写时能定位「这行是谁写的」；不引入 source 维表 |

被明确拒绝的冗余：

- 不在 `fund_nav_state` 里再存 `latest_accumulated_nav` / `latest_daily_growth`：当前没有任何消费者需要，加了就是无主字段；
- 不在 `fund` / `fund_trade_rule` 里存「是否指数基金」「是否联接基金」等派生布尔：先用 `ftype` 原值 + 规则，等有真实消费者再加；
- 不在 `fund` 里重复存放费率：费率只属于交易规则，主数据不参与下单计算。

### 3.4 完整性约束

| 约束 | 类型 | 说明 |
|---|---|---|
| `fund_nav` 主键 | 实体完整性 | 一基金一天一行 |
| `unit_nav > 0`（可空） | 域完整性 | 0 是异常值；宁可写入失败并记录，也不落 0 |
| `accumulated_nav > 0`（可空） | 域完整性 | 同上 |
| `revision_count >= 0` | 域完整性 | 计数不允许为负 |
| `history_status IN (...)` | 域完整性 | 防止拼写错误的中间状态 |
| `latest_nav_date` 与 `latest_unit_nav` 同时为空或同时非空 | 域完整性 | 避免「有日期没净值」的半状态 |
| `ready` 时 `latest_nav_date` 必须非空 | 域完整性 | `get_nav_on` 的判定依赖它；否则四态会落空 |
| 更正记录必须真的发生变化 | 域完整性 | `old_* IS DISTINCT FROM new_*`，防止无意义审计 |
| `is_qdii` 与 `qdii_reason` 同时为空或同时非空 | 域完整性 | QDII 判为真/假必须有依据；未知时两列都为 NULL |
| `lifecycle_status IN ('active','removed')` | 域完整性 | 防止拼写错误的生命周期 |
| `net_asset_scale >= 0`（可空） | 域完整性 | 规模不允许为负 |
| `fund_trade_rule` 外键 → `fund` | 参照完整性 | 规则不能是孤儿 |
| `fund_risk_profiles` 外键 → `fund` | 参照完整性 | 风险画像不能是孤儿 |
| `max_purchase_amount > 0`（可空） | 域完整性 | 0/负数无业务含义 |
| 引用白名单 | 应用完整性 | `fund_nav*` 不建外键，由同步服务保证只写目录内代码（§2.2） |

### 3.5 查询模式

**Q1 持仓批量最新**

```sql
SELECT fund_code, latest_nav_date, latest_unit_nav
FROM fund_nav_state
WHERE fund_code = ANY(%(codes)s);
```

行数 = 持仓数；主键扫描。

**Q2 历史净值**

```sql
SELECT nav_date, unit_nav, accumulated_nav, daily_growth
FROM fund_nav
WHERE fund_code = %(code)s
ORDER BY nav_date DESC
LIMIT %(limit)s;
```

`(fund_code, nav_date)` 主键支持反向扫描，不需要额外降序索引。应用层反转后按升序返回。

**Q3 指定日期单点**

```sql
SELECT nav_date, unit_nav, accumulated_nav, daily_growth, source
FROM fund_nav
WHERE fund_code = %(code)s AND nav_date = %(date)s;
```

**Q4 基金主数据批量**

```sql
SELECT * FROM fund WHERE fund_code = ANY(%(codes)s);
```

主键 `IN` 扫描，行数 = 请求数。

**Q5 待修复基金**

```sql
SELECT fund_code, history_status, last_error, last_error_at
FROM fund_nav_state
WHERE history_status IN ('failed', 'partial')
ORDER BY last_error_at NULLS FIRST
LIMIT 100;
```

2300 行的表做顺序扫描即可，不建索引。

**Q6 覆盖率自检**

```sql
SELECT history_status, count(*) FROM fund_nav_state GROUP BY 1;
```

**Q7 可交易目录（原 `fund_fee_rules` 读取路径）**

```sql
SELECT * FROM fund_catalog
WHERE fund_type = %(fund_type)s
```

视图内部是 `fund` 主键 JOIN 规则主键，再按 `lifecycle_status` 过滤；2328 行的量级下顺序扫描可接受。

**Q8 单只准入与费率**

```sql
SELECT * FROM fund_catalog WHERE fund_code = %(code)s;
```

### 3.6 写入模式

#### 3.6.1 净值合并（含更正）

不能在应用层用「先查、再改」两步完成，因为中间失败会留下「数据改了、更正没记」或反之。设计为**一个数据库函数、一个事务**（Q-D1 待确认是否接受多这个函数）：

```
merge_fund_nav(rows jsonb)
  1. 取事务级咨询锁，串行化合并
  2. 逐行按 (fund_code, nav_date) 查旧值
  3. 不存在            → INSERT
  4. 存在且数值未变化  → 跳过（不写主表、不写更正）
  5. 存在且数值变化    → INSERT revision + UPDATE 主表
  6. 返回 inserted / updated / revised 计数
```

要点：

- 函数由 `service_role` 通过 PostgREST RPC 调用，PostgREST 的 RPC 天然在一个事务里；
- `pg_advisory_xact_lock(hashtext('fund_nav_merge'))` 让并发的多 worker / 定时任务与手工脚本排队，而不是互相覆盖；
- 重复执行同一批数据，第二次的 `inserted/updated` 都是 0，满足幂等；
- 咨询锁是事务级，函数结束自动释放，不会死锁。

#### 3.6.2 状态更新

> **2026-10-26 补充（实现阶段发现）**：本节的两条语句需要 `ON CONFLICT ... DO UPDATE ... WHERE`，而 PostgREST / `supabase-py` 的 `upsert` 不支持 `DO UPDATE` 的 `WHERE` 子句，应用层也无法把两条裸 SQL 放进同一事务。因此新增第三个 RPC `upsert_fund_nav_state(...)`（§4.4.3），由它在一个事务里执行本节的两条语句。**状态更新仍然不在 `merge_fund_nav` 内**，两条语句的语义不变。

合并成功后单独写 `fund_nav_state`。**必须拆成两条语句**（同一事务），不能用一条 `ON CONFLICT DO UPDATE ... WHERE` 兼顾两件事：

| 语句 | 字段 | 保护条件 |
|---|---|---|
| ① 推进最新 | `latest_nav_date`、`latest_unit_nav`、`history_start_date` | 只在 `EXCLUDED.latest_nav_date > 现有值`（或现有值为 NULL）时执行；`history_start_date` 取 `LEAST` |
| ② 刷新检查痕迹 | `last_checked_at`、`last_success_at`、`updated_at` | 无条件刷新 |

原因是两条语义的触发频率不同：`latest_*` 一天最多推进一次，`last_checked_at` 每轮都刷新。若把它们写进同一条 upsert 并加 `WHERE EXCLUDED.latest_nav_date > ...`，`last_checked_at` 会被一并跳过，"这轮检查过了但没新数据"就看不出来。

```sql
-- ① 只前进：更旧或相同的日期不覆盖
INSERT INTO "public"."fund_nav_state" AS s
    ("fund_code", "latest_nav_date", "latest_unit_nav", "history_start_date")
VALUES (%(code)s, %(nav_date)s, %(unit_nav)s, %(history_start_date)s)
ON CONFLICT ("fund_code") DO UPDATE SET
    "latest_nav_date"    = EXCLUDED."latest_nav_date",
    "latest_unit_nav"    = EXCLUDED."latest_unit_nav",
    "history_start_date" = LEAST(
        COALESCE(s."history_start_date", EXCLUDED."history_start_date"),
        EXCLUDED."history_start_date"),
    "updated_at"         = now()
WHERE EXCLUDED."latest_nav_date" > s."latest_nav_date"
   OR s."latest_nav_date" IS NULL;

-- ② 每轮都刷：不动 latest_*
INSERT INTO "public"."fund_nav_state" AS s
    ("fund_code", "last_checked_at", "last_success_at", "history_status")
VALUES (%(code)s, now(), CASE WHEN %(got_data)s THEN now() END, %(status)s)
ON CONFLICT ("fund_code") DO UPDATE SET
    "last_checked_at" = now(),
    "last_success_at" = COALESCE(EXCLUDED."last_success_at", s."last_success_at"),
    "history_status"  = EXCLUDED."history_status",
    "updated_at"      = now();
```

补充约定：

- 失败时只写 `last_error` / `last_error_at`（第三条语句或在 ② 中追加字段），**不动** `latest_*`；
- `history_status` 只能由同步服务推进（§2.4），语句 ② 是它唯一的写入口；
- `ready` 与 `latest_nav_date IS NULL` 互斥由 CHECK 保证（§3.4），因此把某基金的历史删空后必须同步把状态降级为 `pending`，否则约束会拒绝（见 §4.9 L3）。

状态更新不在合并函数内：它按基金而不是按净值点更新，失败时最多让状态滞后一轮，下一轮会修复；把两件事塞进一个函数会让参数与返回结构变复杂，收益不大。

#### 3.6.3 主数据与交易规则写入

三张表由一次 RPC 写入：`upsert_fund_catalog(funds, trade_rules, risk_profiles)`，一个事务。

规则：

- **主数据**（`fund`）：`ON CONFLICT (fund_code) DO UPDATE`，刷新描述字段、`is_qdii`、`qdii_reason`、`metadata_source`、`synced_at`、`updated_at`；
- **生命周期不随同步改写**：`lifecycle_status` 只由人工/管理接口修改，避免「上游重新收录 → 自动复活已下架基金」；
- **交易规则**（`fund_trade_rule`）：只有 jjfl 解析与费率档位都成功时才写；失败时保留旧规则，不删行；
- **主数据可独立成功**：`fetch_basic_info` 成功、jjfl 失败时，仍写 `fund` 与风险画像，只是不写规则；该基金仍不可交易（无规则行）；
- **风险画像**（`fund_risk_profiles`）：按 `fund_code` upsert，不做更正日志；
- 批次失败时逐行重试，隔离坏行（沿用 `FundCatalogSync._flush` 的现有做法）。

为什么不是一个函数写三张表就够了、还要「规则可缺失」：白名单准入与元数据是两件事。费率高频变动且解析易失败，元数据稳定；把二者绑成「一起成功或一起失败」，会让一次费率解析异常连带丢失公司/经理/QDII 信息（这正是当前 `fund_fee_rules` 把两件事塞一张表的后果）。

### 3.7 与现有表的关系

| 现有对象 | 关系 |
|---|---|
| `fund_fee_rules` | **被 `fund` + `fund_trade_rule` 取代**；迁移完成后读路径改走 `fund_catalog`，旧表在观察期后删除（Q-D15） |
| `fund_catalog` 视图 | 原 `fund_fee_rules` 的只读兼容层；字段名保持 `fund_code/fund_name/fund_type/...`，`FundFeeService` 只改表名 |
| `fund_risk_profiles` | 保留并补外键；`market_score=3` 仍是 `resolve_delays` 的输入。`fund.is_qdii` 是更直接的标识，但本轮不替换延迟计算（接入方案 §4.9） |
| `positions` / `watchlist` | `fund_code` 逻辑引用 `fund`，**不建外键**；它们还冗余 `fund_name` 作为展示快照，改名不回填（R13） |
| `trade_orders` / `trade_flow` | 同上；订单里的 `fund_name`、费率、金额都是成交时快照，不能随主数据变化 |
| `trade_orders.confirm_date` | 订单确认按它与 `fund_nav` 的 `(fund_code, nav_date)` 对齐 |
| `trading_calendar` | 决定哪些日期应有净值；本文不复制日历 |

### 4.2 索引设计

**只建主键索引，不建额外索引。**

| 潜在索引 | 结论 | 理由 |
|---|---|---|
| `(fund_code, nav_date DESC)` | **不建** | 主键 B-tree 支持反向扫描；`ORDER BY nav_date DESC` 直接走主键。额外索引只会增加写入与磁盘 |
| `(history_status, last_error_at)` | **不建** | `fund_nav_state` 只有约 2300 行，顺序扫描成本可忽略 |
| `(fund_code, nav_date)` on revision | **暂不建** | 更正极少，按 `fund_code` 查审计时顺序扫描足够；等真有查询需求再加 |
| `fund(is_qdii)` | **不建** | 2300 行，筛选 QDII 直接顺序扫描 |
| `fund_trade_rule(subscribe_status)` | **不建** | 目录查询先走主键连接，再过滤；2300 行顺序扫描足够 |
| `fund_catalog` | **不建** | 视图不占存储；查询计划落到两张基表的主键 |

这是基于实测量级的选择，不是「先不建以后再说」：当前数据量下，多一个索引的写放大大于读收益。若 `fund_nav` 超过 2000 万行或出现慢查询，再按实际执行计划补（Q-D2）。

### 4.3 类型与精度

| 列 | 类型 | 理由 |
|---|---|---|
| `unit_nav` / `accumulated_nav` | `numeric(18,6)` | 上游通常 4 位小数；6 位留出余量，且避免浮点误差 |
| `daily_growth` | `numeric(10,4)` | 百分数，允许负值 |
| `net_asset_scale` | `numeric(20,2)` | 元为单位，规模可达千亿级 |
| `nav_date` / `establish_date` | `date` | 净值归属日是自然日，不带时区 |
| 所有时间戳 | `timestamptz` | 记录的是「何时写入/检查」，必须带时区 |
| `fund_code` | `varchar(10)` | 场外基金 6 位，预留前缀 |
| `is_qdii` | `boolean`（可空） | 真/假/未知三态；未知时与 `qdii_reason` 一起为 NULL，待首次同步补齐 |
| `lifecycle_status` | `text` | 两态枚举，CHECK 约束；不用布尔，后续可扩 `merged` 等状态 |

时区口径：`nav_date` 按 `Asia/Shanghai` 的自然日解释；数据库会话时区不影响 `date` 值，但运维查询时需注意 `now()` 与北京时间的差异（Q-D5）。

### 4.4 写入函数

#### 4.4.1 主数据、交易规则与风险画像

```sql
CREATE OR REPLACE FUNCTION "public"."upsert_fund_catalog"(
```

调用与降级：

- 应用层一次 RPC 传三个数组，同一事务提交；任何一行违反约束导致整批回滚；
- 批次失败时按单只重试（`_flush` 现有做法），坏行不影响其他基金；
- `trade_rules` 与 `funds` 的顺序固定：先写主数据，再写规则（外键依赖）；
- 规则可以为空数组：只同步元数据的场景（jjfl 失败）合法。

#### 4.4.2 净值合并

```sql
CREATE OR REPLACE FUNCTION "public"."merge_fund_nav"("rows" jsonb)
RETURNS TABLE ("inserted" integer, "updated" integer, "revised" integer)
LANGUAGE plpgsql
SET search_path = public
AS $$
DECLARE
    r           jsonb;
    v_code      varchar(10);
    v_date      date;
    v_unit      numeric(18,6);
    v_acc       numeric(18,6);
    v_growth    numeric(10,4);
    v_source    text;
    old_unit    numeric(18,6);
    old_acc     numeric(18,6);
    n_inserted  integer := 0;
    n_updated   integer := 0;
    n_revised   integer := 0;
BEGIN
    -- 合并是低频写；串行化比并发冲突处理更简单、更可预测。
    PERFORM pg_advisory_xact_lock(hashtext('fund_nav_merge'));

    FOR r IN SELECT * FROM jsonb_array_elements("rows") LOOP
        v_code   := r->>'fund_code';
        v_date   := (r->>'nav_date')::date;
        v_unit   := (r->>'unit_nav')::numeric;
        v_acc    := (r->>'accumulated_nav')::numeric;
        v_growth := (r->>'daily_growth')::numeric;
        v_source := r->>'source';

        SELECT "unit_nav", "accumulated_nav"
          INTO old_unit, old_acc
          FROM "fund_nav"
         WHERE "fund_code" = v_code AND "nav_date" = v_date;

        IF NOT FOUND THEN
            INSERT INTO "fund_nav"
                ("fund_code", "nav_date", "unit_nav", "accumulated_nav",
                 "daily_growth", "source")
            VALUES (v_code, v_date, v_unit, v_acc, v_growth, v_source);
            n_inserted := n_inserted + 1;
        ELSIF old_unit IS DISTINCT FROM v_unit
           OR old_acc  IS DISTINCT FROM v_acc THEN
            INSERT INTO "fund_nav_revision"
                ("fund_code", "nav_date", "old_unit_nav", "new_unit_nav",
                 "old_accumulated_nav", "new_accumulated_nav", "source")
            VALUES (v_code, v_date, old_unit, v_unit, old_acc, v_acc, v_source);

            UPDATE "fund_nav"
               SET "unit_nav"        = v_unit,
                   "accumulated_nav" = v_acc,
                   "daily_growth"    = v_growth,
                   "source"          = v_source,
                   "updated_at"      = now(),
                   "revision_count"  = "revision_count" + 1
             WHERE "fund_code" = v_code AND "nav_date" = v_date;

            n_updated := n_updated + 1;
            n_revised := n_revised + 1;
        END IF;
        -- 数值未变化：不写主表、不写更正、不刷新 updated_at
    END LOOP;

    RETURN QUERY SELECT n_inserted, n_updated, n_revised;
END;
$$;
```

调用方式（应用层）：

```python
client.rpc("merge_fund_nav", {"rows": payload}).execute()
```

`payload` 是 `[{"fund_code","nav_date","unit_nav","accumulated_nav","daily_growth","source"}]`。单次建议不超过 500 行，避免 RPC 请求体过大；超过则分批，函数本身可重复调用。

边界行为：

- `unit_nav` 为 `null` 时，`IS DISTINCT FROM` 能正确比较 NULL；
- 插入违反 `unit_nav > 0` 时整批回滚（PostgREST RPC 单事务），错误上抛，不静默跳过——这符合「宁可失败也不写脏值」；
- 函数不更新 `fund_nav_state`，状态由应用层随后更新（§3.6.2）。

#### 4.4.3 状态更新

```sql
CREATE OR REPLACE FUNCTION "public"."upsert_fund_nav_state"(
    "p_fund_code" text,
    "p_history_status" text DEFAULT NULL,
    "p_latest_nav_date" date DEFAULT NULL,
    "p_latest_unit_nav" numeric DEFAULT NULL,
    "p_history_start_date" date DEFAULT NULL,
    "p_got_data" boolean DEFAULT false,
    "p_error" text DEFAULT NULL
)
RETURNS void
LANGUAGE plpgsql
SET search_path = public
AS $$
BEGIN
    IF "p_fund_code" IS NULL OR "p_fund_code" = '' THEN
        RAISE EXCEPTION 'fund_code 不能为空';
    END IF;
    IF "p_history_status" IS NOT NULL
       AND "p_history_status" NOT IN ('pending', 'ready', 'partial', 'failed') THEN
        RAISE EXCEPTION '非法 history_status: %', "p_history_status";
    END IF;

    -- ① 只前进：更旧或相同的日期不覆盖
    IF "p_latest_nav_date" IS NOT NULL THEN
        INSERT INTO "fund_nav_state" AS s
            ("fund_code", "latest_nav_date", "latest_unit_nav",
             "history_start_date", "history_status", "updated_at")
        VALUES ("p_fund_code", "p_latest_nav_date", "p_latest_unit_nav",
                "p_history_start_date", COALESCE("p_history_status", 'pending'), now())
        ON CONFLICT ("fund_code") DO UPDATE SET
            "latest_nav_date"    = EXCLUDED."latest_nav_date",
            "latest_unit_nav"    = EXCLUDED."latest_unit_nav",
            "history_start_date" = LEAST(
                COALESCE(s."history_start_date", EXCLUDED."history_start_date"),
                EXCLUDED."history_start_date"),
            "updated_at"         = now()
        WHERE EXCLUDED."latest_nav_date" > s."latest_nav_date"
           OR s."latest_nav_date" IS NULL;
    END IF;

    -- ② 每轮都刷：不动 latest_*；history_status 为 NULL 表示本轮不改状态
    INSERT INTO "fund_nav_state" AS s
        ("fund_code", "history_status", "last_checked_at", "last_success_at",
         "last_error", "last_error_at", "updated_at")
    VALUES ("p_fund_code", COALESCE("p_history_status", 'pending'), now(),
            CASE WHEN "p_got_data" THEN now() END,
            "p_error",
            CASE WHEN "p_error" IS NOT NULL THEN now() END,
            now())
    ON CONFLICT ("fund_code") DO UPDATE SET
        "last_checked_at" = now(),
        "last_success_at" = COALESCE(EXCLUDED."last_success_at", s."last_success_at"),
        "history_status"  = COALESCE("p_history_status", s."history_status"),
        "last_error"      = COALESCE(EXCLUDED."last_error", s."last_error"),
        "last_error_at"   = CASE WHEN EXCLUDED."last_error" IS NOT NULL
                                 THEN EXCLUDED."last_error_at"
                                 ELSE s."last_error_at" END,
        "updated_at"      = now();
END;
$$;
```

> **注意**：`history_status` 必须写成 `COALESCE("p_history_status", s."history_status")`，不能写 `EXCLUDED."history_status"`——`EXCLUDED` 里的值已被插入列表的 `COALESCE(..., 'pending')` 兜底过，会让「传 NULL 表示不改状态」退化成「重置为 pending」。

调用约定：

- `update_batch` 只推进最新点：传 `latest_*` + `p_got_data=true`，`p_history_status` 留空（不改状态）；
- `ensure_history` 成功后：传 `latest_*` + `history_start_date` + `p_history_status='ready'`；
- 失败：只传 `p_got_data=false` + `p_error`，`latest_*` 留空；
- `last_error` 在后续成功时保留（便于运维回看最近一次失败原因），`last_error_at` 不会被成功覆盖。

### 4.5 权限与安全

- `fund`、`fund_trade_rule`、`fund_risk_profiles`、`fund_nav*` 只由 `service_role` 读写；RLS 开启但不建用户策略，`anon` / `authenticated` 无权限；
- 新表不继承旧表对 `anon` / `authenticated` 的授权；显式只授予 `service_role`（PostgREST 需要表级 GRANT，RLS 不能替代）：

  ```sql
  REVOKE ALL ON "public"."fund", "public"."fund_trade_rule",
                 "public"."fund_risk_profiles", "public"."fund_nav",
                 "public"."fund_nav_state", "public"."fund_nav_revision"
    FROM "anon", "authenticated";
  GRANT SELECT, INSERT, UPDATE, DELETE ON
        "public"."fund", "public"."fund_trade_rule",
        "public"."fund_risk_profiles", "public"."fund_nav",
        "public"."fund_nav_state"
    TO "service_role";
  -- 更正日志只追加：授权层面就不给 UPDATE / DELETE，与 §4.1 的注释一致
  GRANT SELECT, INSERT ON "public"."fund_nav_revision" TO "service_role";
  REVOKE ALL ON SEQUENCE "public"."fund_nav_revision_id_seq" FROM "anon", "authenticated";
  GRANT USAGE, SELECT ON SEQUENCE "public"."fund_nav_revision_id_seq" TO "service_role";
  REVOKE ALL ON "public"."fund_catalog" FROM "anon", "authenticated";
  GRANT SELECT ON "public"."fund_catalog" TO "service_role";
  ```

  > **注意（2026-10-26 实测）**：基线迁移的 `ALTER DEFAULT PRIVILEGES`（`20260819113859_remote_schema.sql:2690-2691`）会给 `postgres` 在 `public` 新建的表自动 `GRANT ALL` 给 `anon` / `authenticated`。因此上面每条 `REVOKE` 都是必需的，不能省略。

- `fund_catalog` 视图 `security_invoker = true`，权限按调用者检查基表；不单独给 `anon` / `authenticated` 授权，因此前端只能通过后端接口读目录；
- 三个写入函数只授予 `service_role`：

  ```sql
  REVOKE ALL ON FUNCTION "public"."upsert_fund_catalog"(jsonb, jsonb, jsonb) FROM PUBLIC, "anon", "authenticated";
  REVOKE ALL ON FUNCTION "public"."merge_fund_nav"(jsonb) FROM PUBLIC, "anon", "authenticated";
  REVOKE ALL ON FUNCTION "public"."upsert_fund_nav_state"(text, text, date, numeric, date, boolean, text) FROM PUBLIC, "anon", "authenticated";
  GRANT EXECUTE ON FUNCTION "public"."upsert_fund_catalog"(jsonb, jsonb, jsonb) TO "service_role";
  GRANT EXECUTE ON FUNCTION "public"."merge_fund_nav"(jsonb) TO "service_role";
  GRANT EXECUTE ON FUNCTION "public"."upsert_fund_nav_state"(text, text, date, numeric, date, boolean, text) TO "service_role";
  ```

  函数体内写表，`SECURITY INVOKER`（默认）下需要调用者对 `fund` / `fund_trade_rule` / `fund_risk_profiles` / `fund_nav` / `fund_nav_state` 的相应表级权限；`service_role` 已具备（见上）。`FROM PUBLIC` 是 PostgreSQL 函数的内建默认授权，必须显式收回；`anon` / `authenticated` 则来自上面的 `ALTER DEFAULT PRIVILEGES`。



- 不在表中存任何用户标识，不涉及个人信息；
- 迁移与运维脚本通过服务端连接执行，不暴露给前端。

### 4.6 迁移与回滚

分两阶段，中间留观察期：

**M1 建新表 + 回填 + 视图（不改旧表）**

1. 暂停白名单定时任务（避免回填与同步交叉写）；
2. 执行建表、回填、补外键、建视图的 SQL（§4.1，顺序固定）；
3. 更新 `supabase/seed.sql`：在原有 21 条 `fund_fee_rules` 之后追加同一套回填 SQL，把数据派生进 `fund` + `fund_trade_rule`（保持单一数据源，`supabase db reset` 后 `fund_catalog` 仍有 21 行）；
4. 校验：`fund` 行数 = `fund_fee_rules` 行数；`fund_trade_rule` 行数同上；`fund_catalog` 行数 = `fund_trade_rule` 且 lifecycle 全为 `active`；
5. 恢复任务，部署新代码（读写走新表/视图）；
6. 观察至少一个完整同步周期，核对目录数量、费率、申购状态与旧表一致。

**M2 删除旧表（单独迁移、单独提交）**

```sql
DROP TABLE "public"."fund_fee_rules";
```

删除前确认代码中已无任何 `fund_fee_rules` 引用（`grep -r fund_fee_rules server/ src/` 为空），并且回滚方案已不需要旧表。

**回滚**

- M1 之后、代码部署之前：删新表与视图即可，旧表未动 —— **必须按 §4.9 L7 的依赖倒序执行**（视图 → 外键 → 表）；
- 代码部署之后若发现设计问题：先把读路径切回旧表（代码回滚），新表可保留；M2 之后则依赖数据库备份恢复；
- 回填与同步都只做 `DO NOTHING` / upsert，重复执行不会产生重复行。

迁移文件命名：`<timestamp>_create_fund_master_and_trade_rule.sql`、`<timestamp>_drop_fund_fee_rules.sql`，按 `db-migration` 技能流程执行，禁止改基线。

### 4.9 写入回滚与修复

§4.6 只覆盖**迁移**回滚；本节覆盖**数据**回滚 —— 同步脚本 bug、上游脏数据、手工误操作之后怎么恢复。

原则：**能靠"再合并一次"解决的，绝不用手工 `UPDATE`；必须动 SQL 的，先按条件查出来再删，并同步修正派生状态。**

| 层 | 场景 | 手段 | 状态 |
|---|---|---|---|
| L0 事务 | 任一行违反约束 | PostgREST RPC 单事务整批回滚，错误上抛（§4.4.2） | ✅ 已有 |
| L1 幂等 | 同一批重跑 | `inserted=updated=revised=0`，重跑无副作用（R3） | ✅ 已有 |
| L2 值写错 | 单位净值 / 累计净值错了 | **用正确值再调一次 `merge_fund_nav`**，旧值自动进 `fund_nav_revision` | ✅ 机制已有，本节把它定为正式回滚路径 |
| L3 行不该存在 | `nav_date` 解析错、整批污染 | 无批次标识，只能按 `source` + `first_seen_at` 时间窗定位后人工 `DELETE` | ⚠️ 手工，见 Q-D18 |
| L4 审计粒度 | 想逐列还原上一版 | `fund_nav_revision` 不存 `daily_growth` 旧值，无法精确还原 | ⏸ 接受，见 Q-D19 |
| L5 上游重取 | 净值整体可疑 | 重新拉全量覆盖；会产生大量 revision，`first_seen_at` 丢失 | ⚠️ 兜底 |
| L6 备份 | 库级事故 | Supabase 平台备份 / PITR | ⏳ 需写明 RPO |
| L7 迁移 | M1 回退 | 顺序见下 | ✅ 补顺序 |

只有 L2 / L3 / L7 需要成文的操作步骤（见下），L0 / L1 由 RPC 事务与幂等语义直接覆盖，L4 / L5 / L6 是取舍与兜底说明。

#### L2：值写错 —— 反向合并就是回滚

不需要手工 `UPDATE`。把正确值作为一批输入再调 `merge_fund_nav`：

- 主表被改成正确值；
- 自动生成一条 revision，`old_*` = 错值、`new_*` = 正确值；
- `revision_count` 再 +1。

这是有意的：**"改回"本身是一次真实改值，审计应当记下来**，而不是抹掉上一次记录。因此 `fund_nav_revision` 永不删除、永不更新（§4.5 已收回 `UPDATE/DELETE` 授权）。

**净值整体可疑时不要逐条反向合并**（900 万行级别会产生海量 revision 与写放大），走 L5：重新拉全量覆盖，再把该轮 revision 作为差异清单人工抽查。

#### L3：错插入的定位与删除

`merge_fund_nav` 只能改值，不能表达"这一行不该存在"。当前也没有批次标识，唯一的定位依据是 `source` + `first_seen_at`（Q-D18）。

```sql
-- ① 先查：确认时间窗与行数，不要直接 DELETE
SELECT fund_code, nav_date, unit_nav, source, first_seen_at
FROM "public"."fund_nav"
WHERE "source" = 'ttjj_history'
  AND "first_seen_at" >= '2026-10-26 02:00+08'
  AND "first_seen_at" <  '2026-10-26 03:00+08'
ORDER BY fund_code, nav_date;

-- ② 再删：pg_safeupdate 要求 DELETE 必须带 WHERE
DELETE FROM "public"."fund_nav"
WHERE "source" = 'ttjj_history'
  AND "first_seen_at" >= '2026-10-26 02:00+08'
  AND "first_seen_at" <  '2026-10-26 03:00+08';
```

删除后**必须重建该基金的派生状态**，否则 `latest_nav_date` 会指向一个已不存在的净值点，`get_nav_on` 的四态判定（§2.5）会落到 `FETCH_FAILED`：

```sql
WITH agg AS (
    SELECT min(nav_date) AS min_date, max(nav_date) AS max_date
    FROM "public"."fund_nav" WHERE "fund_code" = %(code)s
)
UPDATE "public"."fund_nav_state" s
   SET "latest_nav_date"    = agg.max_date,
       "latest_unit_nav"    = (SELECT n."unit_nav" FROM "public"."fund_nav" n
                                WHERE n."fund_code" = %(code)s
                                  AND n."nav_date" = agg.max_date),
       "history_start_date" = agg.min_date,
       "updated_at"         = now()
  FROM agg
 WHERE s."fund_code" = %(code)s;
```

删空的特殊情况：`agg.max_date IS NULL` 时 `latest_*` 都变 NULL，而 CHECK 约束禁止 `history_status='ready'` 且 `latest_nav_date IS NULL`（§3.4）。此时必须在同一条语句里把状态降级：

```sql
UPDATE "public"."fund_nav_state"
   SET "history_status" = 'pending', "latest_nav_date" = NULL,
       "latest_unit_nav" = NULL, "history_start_date" = NULL, "updated_at" = now()
 WHERE "fund_code" = %(code)s;
```

（`pending` 会让下次读取重新触发历史补齐，语义正确。）

删除的**边界**：只删 `fund_nav` 行，不改 `fund` / `fund_trade_rule` / 订单；如果污染来自主数据或费率，走 L2（再调一次 `upsert_fund_catalog` 覆盖），不要手工改行 —— 该 RPC 是这三张表唯一的写入口（R12）。

#### L7：M1 的回退顺序

§4.6 说的"直接删新表与视图"需要按依赖倒序执行，否则会被依赖挡住：

1. 代码回滚到读 `fund_fee_rules`（观察期内旧表未动，这一步随时可做）；
2. `DROP VIEW "public"."fund_catalog";`
3. `ALTER TABLE "public"."fund_risk_profiles" DROP CONSTRAINT "fund_risk_profiles_fund_code_fkey";`
4. `DROP TABLE "public"."fund_nav_revision", "public"."fund_nav_state", "public"."fund_nav", "public"."fund_trade_rule", "public"."fund";`

回滚干净后 M1 可重跑：`CREATE TABLE IF NOT EXISTS` 幂等，但 `ADD CONSTRAINT` / `CREATE VIEW` 没有重复保护，所以**只能在"已回滚"或"空库"上重跑**，不能在同一库直接重跑 M1。M2 之后旧表已删，回退只能依赖备份。

#### 本节不负责的事

- 不提供"撤销一条 revision"的接口：审计只追加（L2 已覆盖真实需求）；
- 不做自动化的错误数据识别（例如"单位净值偏离前一日 20%"的异常检测）—— 属于后续能力，不在本次范围；
- 回滚期间**必须停掉白名单与净值定时任务**，否则同步会在你删除的过程中把数据写回来。

## 7. 决策记录

| 日期 | 决策 | 说明 |
|---|---|---|
| 2026-10-24 | **DB 一层，不做 L1/L2** | 场外净值无实时需求；读放大不在内存 |
| 2026-10-24 | **历史 = 持仓预热 + 详情按需** | 全量预热约 900 万行 / 1 GB / 2300 次请求，收益低 |
| 2026-10-24 | **基金域拆 `fund` + `fund_trade_rule`（方案 B）** | 身份/描述与准入/费率是两个实体；`fund_fee_rules` 把准入、费率、名称混在一张表，失败会互相牵连 |
| 2026-10-24 | **准入 = 规则行存在 + `lifecycle_status='active'`** | 不再用「行存在」隐式表达白名单；下架可单独控制 |
| 2026-10-24 | **`fund_catalog` 视图兼容旧读路径** | 调用方字段不变，迁移只改表名；视图不存数据 |
| 2026-10-24 | **QDII 规则推导 + `qdii_reason` 留证** | 上游无官方 QDII 布尔字段 |
| 2026-10-24 | **只建主键索引** | 当前数据量下额外索引的写放大大于读收益 |
| 2026-10-24 | **合并与更正走数据库函数** | 应用层两步无法保证原子性（Q-D1 待确认） |
| 2026-10-24 | **主数据/规则/画像走一个 RPC** | 三张表同一事务；规则缺失仍可写主数据，但不可交易 |
| 2026-10-26 | **新增状态 RPC `upsert_fund_nav_state`** | 状态写入改由 RPC 保证「不回退 + 两段式 + 幂等」，应用层不再直接 UPDATE；先改文档再写代码 |
| 2026-10-26 | **M1 迁移只生成、不执行** | 本机无 Supabase 栈，且推送远端需人工确认；设计与代码先行，DB 验收留到迁移执行后 |
| 2026-10-26 | **目录内外分流（`FundNavService.tracks`）** | 目录内读 DB；目录外（场内 ETF）保留上游，避免详情页 503（接入方案 §4.9） |
| 2026-10-26 | **不引入业务触发器，审计表用授权强制只追加** | R2/R3/R12 已由函数覆盖，触发器会与函数自身的 UPDATE 双写；`fund_nav_state` 单向前进靠 §3.6.2 的两条受保护语句；`fund_nav_revision` 收回 `UPDATE/DELETE` 授权（§4.5） |
| 2026-10-26 | **回滚分 L0–L7 七层，值写错的正式路径是「反向合并」** | 见 §4.9；手工 `DELETE` 只用于 L3 错插入，且必须重建派生状态 |
| 2026-10-26 | **新增第三个 RPC `upsert_fund_nav_state`** | 实现阶段发现 PostgREST / `supabase-py` 的 `upsert` 无法表达 `ON CONFLICT ... DO UPDATE ... WHERE`，且应用层无法把 §3.6.2 的两条裸 SQL 放进同一事务。改为由该 RPC 在一个事务内执行两条受保护语句；状态更新仍不在 `merge_fund_nav` 内（§3.6.2、§4.4.3） |
| 2026-10-26 | **Q-D21 采纳：`merge_fund_nav` 校验 `fund_code` 存在于 `fund`** | 不建外键（Q-D4）的代价是代码拼错会静默落库；函数内 `EXISTS` 主键查找成本可忽略，下架基金 `fund` 行仍在，不误伤历史净值 |
| 2026-10-26 | **Q-D22 采纳：函数内 `DISTINCT ON (fund_code, nav_date)` 去重，保留最后一条** | 否则同批重复键会读到刚插入的行并生成「假更正」，污染 `fund_nav_revision` 与 `revision_count` |
| 2026-10-26 | **`is_qdii=false` 时 `qdii_reason` 写 `no_qdii_signal` 而非 NULL** | §4.1 的 CHECK 要求两列同 NULL 或同非 NULL；`false` + 非空原因同时满足约束与「留证」目的 |
