# 订单确认：数据结构

> 这份文件回答「库里长什么样」：新增/修改哪些表与列、约束与索引、全量不变量，以及表之间的关系。
> 业务语义见 [业务规则](订单确认-业务规则.md)。
>
> 本文件包含：§3.3 数据模型（3.3.1–3.3.8） · §3.8.3 持仓汇总
>
> 章节号沿用拆分前的全局编号（§0–§9）；四份文档共用同一套编号，跨文件引用按原编号在对应文件里找。
> 每份文件末尾都是同一张**未解决问题表**的一部分（编号 U1–U19 全局唯一），未列出的项在其余三份文件里。

## 表关系概览

```
trade_orders  1 ── 0..1  trade_flow        唯一索引 uq_trade_flow_order；存量流水 order_id 为 NULL
trade_orders  1 ── 0..1  position_lots     唯一索引 uq_position_lots_order；期初/收益 lot 的 order_id 为 NULL
positions     1 ── N     position_lots     按 (user_id, fund_code) 聚合；lot 是事实来源，positions 是读模型
accounts      1 ── N     trade_orders      逻辑关系（无外键）：frozen_cash 应等于未完成买单 amount 之和
confirm_runs  独立批次审计表，与订单无外键
```

> 关系正确性由 §3.3.8 的全量不变量与《执行机制》§9.3 的对账 SQL 保证，不靠外键全部兜住。

## 3. 最终方案

### 3.3 数据模型

#### 3.3.1 `trade_orders` 新增列

| 列 | 类型 | 语义 |
|---|---|---|
| `accepted_date` | `date` | 受理日 T，**买卖双方的成交净值日** |
| `settle_date` | `date` | 赎回到账日 |
| `net_amount` | `numeric(18,2)` | 买：`amount - fee`；卖：`amount - fee`（应收净额） |
| `estimated_nav` | `numeric(18,4)` | 下单时的预估净值（展示用，不参与确认） |
| `fee_rule_snapshot` | `jsonb` | 下单时的费率/周期快照（§3.7） |
| `available_date` | `date` | 买单份额可赎回日 |
| `processing_at` | `timestamptz` | 认领时间 |
| `processing_by` | `text` | 认领 worker 标识（`hostname:pid:run_id`） |
| `attempt_count` | `integer not null default 0` | 确认尝试次数 |
| `last_attempt_at` | `timestamptz` | 最后一次尝试 |
| `last_error_code` | `text` | 错误码（§3.11） |
| `last_error_message` | `text` | 可读错误信息，不截断到 200 字 |
| `processed_at` | `timestamptz` | 实际确认时间 |
| `settled_at` | `timestamptz` | 实际到账时间 |
| `client_order_id` | `text` | 调用方幂等键 |

约束与索引：

```sql
-- 关键：status 原来是 varchar(10)，manual_review 有 13 个字符，必须先扩宽。
-- 先删 CHECK 再改类型，避免改类型时被旧约束卡住。
ALTER TABLE trade_orders DROP CONSTRAINT trade_orders_status_check;
ALTER TABLE trade_orders ALTER COLUMN status TYPE varchar(20);
ALTER TABLE trade_orders ADD CONSTRAINT trade_orders_status_check
  CHECK (status IN ('pending','processing','completed','cancelled',
                    'rejected','reserved','settling','settled','manual_review'));

-- 幂等键：同一用户下唯一
CREATE UNIQUE INDEX uq_trade_orders_client_order
  ON trade_orders(user_id, client_order_id)
  WHERE client_order_id IS NOT NULL;

-- 扫描 / 到账 / 回收 / 人工
CREATE INDEX idx_trade_orders_confirm_scan
  ON trade_orders(confirm_date, id) WHERE status = 'pending';
CREATE INDEX idx_trade_orders_settle
  ON trade_orders(settle_date, id) WHERE status = 'settling';
CREATE INDEX idx_trade_orders_processing
  ON trade_orders(processing_at) WHERE status = 'processing';
CREATE INDEX idx_trade_orders_manual
  ON trade_orders(updated_at) WHERE status = 'manual_review';
```

> `amount >= 0`、`fee >= 0`、`quantity >= 0` 的 CHECK 先以 `NOT VALID` 添加，盘点存量通过后再 `VALIDATE CONSTRAINT`；不要直接加，否则存量脏数据会让迁移失败。

#### 3.3.2 `position_lots`

lot 是持仓的事实来源。`positions` 由 lot 汇总，不再由应用层读改写。

```sql
CREATE TABLE public.position_lots (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id        uuid REFERENCES trade_orders(id) ON DELETE RESTRICT,
  user_id         uuid NOT NULL,
  fund_code       varchar(10) NOT NULL,
  fund_name       varchar(100) NOT NULL DEFAULT '',
  source          text NOT NULL CHECK (source IN ('order','initial','income')),
  source_ref      text,                    -- initial: 'initial'; income: 入账日 ISO
  nav_date        date NOT NULL,           -- lot 的成交净值日（买单 = accepted_date T）
  available_date  date,
  quantity        numeric(18,2) NOT NULL CHECK (quantity > 0),
  remaining_qty   numeric(18,2) NOT NULL
                  CHECK (remaining_qty >= 0 AND remaining_qty <= quantity),
  cost_price      numeric(18,4) NOT NULL CHECK (cost_price >= 0),
  remaining_cost  numeric(18,2) NOT NULL CHECK (remaining_cost >= 0),
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now()
);

-- 一笔订单最多一个 lot
CREATE UNIQUE INDEX uq_position_lots_order
  ON position_lots(order_id) WHERE order_id IS NOT NULL;
-- 期初/收益 lot 的幂等键
CREATE UNIQUE INDEX uq_position_lots_source
  ON position_lots(user_id, fund_code, source, source_ref)
  WHERE source <> 'order';
-- FIFO 扫描
CREATE INDEX idx_position_lots_fifo
  ON position_lots(user_id, fund_code, nav_date, created_at, id)
  WHERE remaining_qty > 0;
```

字段口径：

| 字段 | 普通基金 | 货基（000198） |
|---|---|---|
| `quantity` / `remaining_qty` | 份额 | 份额 |
| `cost_price` | 买入净额 / 份额 | 恒 1.0000 |
| `remaining_cost` | 剩余份额的成本（净申购额，不含费） | 剩余本金（不含复投收益） |
| `source='order'` | 买单确认生成 | 买单确认生成 |
| `source='initial'` | 迁移时按期初持仓生成 | 同左 |
| `source='income'` | 不使用 | 每日万份收益复投生成，`cost_price=0`、`remaining_cost=0` |

`positions` 汇总规则（所有写 lot 的 RPC 末尾统一执行，保证 `SUM(lot) == positions`）：

```sql
UPDATE positions p SET
  quantity      = q.qty,
  cost_price    = CASE WHEN p.fund_code = '000198' THEN 1.0000
                       WHEN q.qty > 0 THEN ROUND(q.cost / q.qty, 4)
                       ELSE 0 END,
  principal     = CASE WHEN p.fund_code = '000198' THEN q.cost ELSE 0 END,  -- 列是 NOT NULL DEFAULT 0

  confirm_date  = q.max_nav_date,
  available_date= q.max_available_date,
  updated_at    = now()
FROM (
  SELECT COALESCE(SUM(remaining_qty),0)  AS qty,
         COALESCE(SUM(remaining_cost),0) AS cost,
         MAX(nav_date)                   AS max_nav_date,
         MAX(available_date)             AS max_available_date
  FROM position_lots
  WHERE user_id = $1 AND fund_code = $2
) q
WHERE p.user_id = $1 AND p.fund_code = $2;
```

- `positions.confirm_date/available_date` 只用于展示；业务判定（持有期、可赎回）一律读 lot。
- 卖出后份额为 0 时**保留** `positions` 行（`quantity=0`），不删除；`list_positions` 过滤 `quantity > 0`。这样 lot 汇总始终有落点，也保留历史。
- **并发前提（必须）**：任何写 lot 的 RPC，在写 lot 前先锁 `positions` 行：
  `SELECT 1 FROM positions WHERE user_id=$1 AND fund_code=$2 FOR UPDATE`；
  无行则 `INSERT ... ON CONFLICT DO NOTHING` 后再 `SELECT ... FOR UPDATE`。
  然后**另起一条语句**做上面的汇总（READ COMMITTED 下新语句取新快照）。如果不等锁、直接把「锁 lot + 汇总」写在同一条语句里，两个并发事务可能各自基于旧快照汇总并互相覆盖，导致 `positions.quantity` 与 lot 总和对不上。
- 锁顺序统一为：**订单 → lot（按 nav_date, created_at, id）→ positions → accounts**；买入是**订单 → accounts → positions → 插 lot**。买入不锁已有 lot，卖出不锁 accounts，因此不会形成环。

#### 3.3.3 `confirm_runs`

CREATE TABLE public.confirm_runs (

#### 3.3.4 `trade_flow.order_id`

```sql
ALTER TABLE trade_flow ADD COLUMN order_id uuid REFERENCES trade_orders(id);
CREATE UNIQUE INDEX uq_trade_flow_order
  ON trade_flow(order_id) WHERE order_id IS NOT NULL;
```

- 新确认的订单必须写 `order_id`；存量流水保持 `NULL`，不回溯（见 §7 U9）。
- 一笔订单的确认只允许产生一条流水；唯一索引是最后一道防线。

#### 3.3.5 `fund_trade_rule.redeem_available_delay`

```sql
ALTER TABLE fund_trade_rule
  ADD COLUMN redeem_available_delay integer NOT NULL DEFAULT 2
  CHECK (redeem_available_delay >= 0);

-- 兼容视图补字段。注意：CREATE OR REPLACE VIEW 只能“在末尾追加”，
-- 不能改已有列名/顺序/类型；新列必须放在最后，否则迁移直接失败。
CREATE OR REPLACE VIEW public.fund_catalog
WITH (security_invoker = true) AS
SELECT f.fund_code, f.fund_name, f.ftype, f.manager_company,
       f.fund_manager, f.tracking_index, f.tracking_index_code,
       f.establish_date, f.net_asset_scale, f.risk_level_code,
       f.is_qdii, f.qdii_reason, f.lifecycle_status,
       r.fund_type, r.share_class, r.min_purchase_amount,
       r.max_purchase_amount, r.subscribe_status, r.confirm_delay,
       r.redeem_settle_delay, r.management_fee_rate, r.custody_fee_rate,
       r.sales_service_fee_rate, r.commission_rate,
       r.purchase_fee_tiers, r.redemption_fee_tiers,
       r.redeem_available_delay,   -- 追加在末尾
       r.updated_at                -- 费率快照的版本依据
FROM public.fund f
JOIN public.fund_trade_rule r ON r.fund_code = f.fund_code
WHERE f.lifecycle_status = 'active';
```

- 上游没有 `redeem_available_delay`，`upsert_fund_catalog` 不写它；默认 2，按基金在库内配置。
- `updated_at` 用于快照的 `rule_updated_at`；它不参与费率计算。
- 货基是否改为 0/1 天见 §7 U8；默认 2 保持现有行为。

#### 3.3.6 `accounts` 约束

```sql
ALTER TABLE accounts ADD CONSTRAINT accounts_cash_nonnegative
  CHECK (cash >= 0) NOT VALID;
ALTER TABLE accounts ADD CONSTRAINT accounts_frozen_nonnegative
  CHECK (frozen_cash >= 0) NOT VALID;
-- 存量盘点通过后：
-- ALTER TABLE accounts VALIDATE CONSTRAINT accounts_cash_nonnegative;
-- ALTER TABLE accounts VALIDATE CONSTRAINT accounts_frozen_nonnegative;
```

不变量：

- `frozen_cash >= 0`、`cash >= 0`。
- 每个用户 `frozen_cash = SUM(买单 amount WHERE status IN ('pending','processing','manual_review'))`。`manual_review` 买单继续冻结，等人工处理；`rejected/completed` 已解冻。

#### 3.3.7 状态迁移触发器

```sql
CREATE OR REPLACE FUNCTION public.enforce_order_status_transition()
RETURNS trigger LANGUAGE plpgsql SET search_path = public AS $$
BEGIN
  IF NEW.status = OLD.status THEN RETURN NEW; END IF;
  IF OLD.status IN ('completed','rejected','cancelled','settled') THEN
    RAISE EXCEPTION 'terminal order % cannot transition % -> %',
      OLD.id, OLD.status, NEW.status;
  END IF;
  IF NOT (
    (OLD.status = 'pending'    AND NEW.status IN ('processing','cancelled','rejected','manual_review')) OR
    (OLD.status = 'processing' AND NEW.status IN ('pending','completed','settling','rejected','manual_review')) OR
    (OLD.status = 'settling'   AND NEW.status = 'settled') OR
    (OLD.status = 'manual_review' AND NEW.status = 'pending')
  ) THEN
    RAISE EXCEPTION 'illegal order status transition % -> %', OLD.status, NEW.status;
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER trg_trade_orders_status_transition
  BEFORE UPDATE OF status ON trade_orders
  FOR EACH ROW EXECUTE FUNCTION enforce_order_status_transition();
```

> 上线顺序：**先**切新 Runner，确认旧代码不再写 `pending → completed`，**再**单独迁移加触发器。
> 灰度期如果必须回滚旧代码，触发器要允许 `pending → completed`（加一个 `legacy` 条件），并在回滚后移除。

#### 3.3.8 全量不变量

每次确认批次后必须为 0 行异常：

1. `accounts.cash < 0` 或 `frozen_cash < 0`。
2. `frozen_cash != SUM(pending/processing/manual_review 买单.amount)`。
3. `completed` 买单中 `trade_flow` 数量 ≠ 1；或 `trade_flow.order_id` 重复。
4. 同一用户同一基金 `SUM(position_lots.remaining_qty) != positions.quantity`（容差 0.01）。
5. 普通基金 `positions.cost_price != ROUND(SUM(position_lots.remaining_cost) / NULLIF(SUM(position_lots.remaining_qty), 0), 4)`（容差 0.0001）；
   货基 `SUM(remaining_cost) != positions.principal`（容差 0.01）。
   > 不要用 `quantity * cost_price == SUM(remaining_cost)` 判定：`cost_price` 是 4 位小数的加权均价，大额持仓时乘积与成本和的舍入差会超过 0.02，会误报。
6. `positions.quantity < 0`。
7. 非法状态迁移（触发器会阻止，巡检兜底查询审计日志/最近更新）。
8. 买入 `amount != net_amount + fee`。
9. 买入 `net_amount != quantity * price + residual`（residual 不落库，用 `amount - fee - quantity*price` 校验；允许 0.01 容差）。
10. 卖出 `amount = quantity * price`、`net_amount = amount - fee`。
11. 买单生成的 lot，`nav_date` 必须等于订单的 `accepted_date`（方案 A 的成交净值口径）；历史数据中等于 `confirm_date` 的 lot 用完即止，不做批量改写（见 §7 U2 的同类处理）。

对账 SQL 见附录 §9.3。


### 3.8 FIFO、lot 与持仓汇总（数据侧）

> `positions` 为只读模型，直接写 `positions` 视为缺陷；FIFO 计划与期初迁移见《实现方案》§3.8.1/§3.8.2，
> 业务口径见《业务规则》§3.8。

#### 3.8.3 持仓汇总

所有写 lot 的 RPC（买、卖、收益）末尾都调用 §3.3.2 的汇总 SQL，禁止应用层直接改 `positions.quantity/cost_price/principal`。

- 买入：插入 lot → 汇总。
- 卖出：扣 lot → 汇总。
- 收益：插入 income lot → 汇总。
- 卖出后 `quantity=0`：保留 `positions` 行；`list_positions` 过滤 `quantity > 0`。
- `positions.confirm_date` 取 `MAX(lot.nav_date)`，`available_date` 取 `MAX(lot.available_date)`，只用于展示。
