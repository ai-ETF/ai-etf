# 账户日终估值与快照

## 1. 背景与术语

复盘功能需要一条可信的账户资产曲线。现状只有手动快照，快照日期不判断交易日，
估值取的是「最新净值」而不是「T 日净值」，日收益又把缺失日直接当成单日——三个问题叠加，
曲线既可能稀疏，也可能把多日涨跌画成单日尖峰。

本文定义一套**以 A 股交易日为单位**的账户日终估值与快照口径：

| 术语 | 含义 |
|---|---|
| 估值日 T | A 股交易日历中的交易日；不是自然日 |
| T 日终估值 | 用 T 日已公布的基金净值，对 T 日收盘后的账户状态估值 |
| 有效快照 | 满足本文 §4.2 全部条件的 `account_snapshots` 行；只有有效快照参与日收益 |
| 区间收益 | 相邻两个有效快照之间的总资产收益率，可能跨多个交易日 |
| 日收益 | 相邻两个**交易日**各有一条有效快照时的区间收益；缺口日不伪造单日收益 |

需求来源见 [复盘功能](../../10-需求/复盘功能.md)。

## 2. 当前实现与业务口径

以下只写代码里读不出来的口径与约束；函数调用链以代码为准。

- **总资产的构成**：可用现金 + 冻结资金 + 在途赎回款 + 持仓市值。冻结资金是已受理
  但未确认的买单资金；在途赎回款是卖单已确认、现金尚未到账的应收。两者都必须计入，
  否则总资产会在成交/到账前后凭空跳动。
- **货基估值**：净值恒 `1.0000`，每日万份收益在次日 00:05 折算成份额复投；因此货基市值
  就是当前份额，不另加「未入账收益」。
- **无外部入金/出金**：账户初始资金固定 100,000 元；总资产的变化只来自盈亏、交易费用和
  货基收益。所以日收益可以直接用相邻有效快照的总资产计算。
- **交易时点与资产守恒**：买单受理时 `cash` 转 `frozen_cash`；确认时冻结款换成分额并扣费。
  卖单确认时份额换成 `settling_cash`；到账时再转 `cash`。这些内部转移不改变总资产。
- **净值发布节奏**：场外基金净值通常在交易日 18:00 后公布；T+1 00:30/01:30、08:05
  还有补抓轮。交易日历是判断「今天是不是交易日」的唯一来源，日历不可用时不得猜。
- **快照重试窗口**：T 日快照在 T+1 08:45 生成。此时 T+1 的买卖尚未确认，账户总资产
  仍等于 T 日收盘值；T+1 00:05 已入账的货基 T 日收益属于 T，应计入。

## 3. 发现的问题

- 快照只有手动入口，没有每日任务；快照日期默认北京「今天」，周末/节假日/盘中都会写入。
- 快照复用 `account_summary()`：该方法有自动货基申购副作用，异常时返回全 0，快照会把
  系统故障写成「资产为 0」。
- 估值用 `fund_nav_state.latest_*`，T 日净值未公布时会静默使用更早净值，且快照无法复核。
- `account_snapshots` 缺 `frozen_cash`，总资产与分项不闭合；也没有有效性、来源、净值明细。
- 日收益直接对相邻行相除；缺一天就把多日收益当成单日。查询异常返回空列表。
- 货基收益入账按「最近一条非今日」取数，没有补漏；漏一天可能永久少计（已登记 B138）。
- 账户概况异常返回全 0 的兜底仍存在于 `/account`、`/overview`（已登记 B137，不在本文范围）。
- 卖出确认只扣 `position_lots.remaining_qty`，不持久化 FIFO 分配；精确回补任意历史日
  持仓需要重放全部买卖，成本高且依赖初始 lot 的迁移口径。本方案因此不做历史回补。

## 4. 设计方案

### 4.1 估值口径

对交易日 T：

```text
position_value_T = Σ 非货基持仓 quantity_T,f × nav_T,f
                 + Σ 货基持仓 quantity_T              # 货基 nav 恒 1.0000
total_assets_T   = cash_T + frozen_cash_T + settling_cash_T + position_value_T
total_pnl_T      = total_assets_T - INITIAL_CASH
total_return_rate_T = total_pnl_T / INITIAL_CASH
```

- 非货基持仓的 `nav_T,f` 必须来自 `fund_nav(nav_date = T)`，不得回退到更早日期。
- 货基在生成迟到快照时，从当前份额中剔除 `position_lots.source='income' AND nav_date > T`
  的份额，避免把 T 之后入账的收益算进 T。
- 金额保留 2 位小数，收益率保留 6 位小数，沿用现有精度。

### 4.2 有效快照

一条快照记为 `valid` 必须同时满足：

1. `snapshot_date` 是交易日历中的交易日。
2. 账户创建时间早于 `T+1 00:00（北京）`。
3. 该用户所有 `quantity > 0` 的非货基持仓，都有 `fund_nav(nav_date=T, unit_nav>0)`。
4. 本轮批量读取账户、持仓、净值、在途赎回款均成功；系统异常中止本轮，不写半成品。
5. 计算出的金额非负且有限。

货基当日收益是否已入账**不**作为硬门槛；快照记录 `money_fund_income_date`（T 日收益
lot 存在时写 T，否则为空），便于事后核对，不因无关任务失败而让整条快照作废。

【我们先暂时放弃货币基金，只要这部分代码不影响当前etf的订单确认和每日快照的逻辑，就不管】

缺失净值、负的货基调整量等记为 `invalid`，写入 `invalid_reason` 与 `nav_coverage`，
不参与日收益。上线前的旧快照统一记为 `legacy`，同样不参与日收益。

### 4.3 生成时序

调度器每天 08:45（含周末/节假日）执行，目标日期固定为：

```text
target = prev_trading_day(今天)
```

- 周六 08:45 生成周五；周日/周一 08:45 仍以周五为目标，已有效则跳过，失败可重试。
- 周二 08:45 生成周一；以此类推。
- 08:45 位于 08:05 净值补抓、08:30 确认轮之后，09:30 开盘之前。此时 T+1 的买卖尚未
  确认，总资产仍等于 T 日收盘值。
- 每个交易日只有「下一个交易日 08:45 之前」的重试窗口；再晚不做历史回补。
- 迟到生成时对货基做 §4.1 的收益 lot 剔除，避免周末收益被算进周五。

【请你重新确认此时 T+1的买卖是否真的尚未确认？】

【只要货币基金不影响我们计算ETF的快照，就暂时先放弃相关的问题】

【这个方法对于QDII基金是否通用？QDII基金在A股交易日可能会存在不交易，即没有最新净值的情况，它们的交易时段是否基本为某个交易日历交上a股票的交易日历？是的话我们一共支持几类QDII基金（按照交易日历来分类，港股交易日、美股交易日。。。）如果要为每一类拓展维护多一个交易日历是否值得？如果不值得我们应该如何做取舍？注意，我们的用户可能多数会持有美股的QDII基金和港股的QDII基金，可能这两类是不能放弃的】

### 4.4 数据模型

`account_snapshots` 追加：

| 字段 | 类型 | 说明 |
|---|---|---|
| `frozen_cash` | numeric(18,2) NOT NULL DEFAULT 0 | 冻结资金，补全分项 |
| `status` | text NOT NULL | `valid` / `invalid` / `legacy` |
| `invalid_reason` | text | 无效原因，`; ` 分隔 |
| `source` | text NOT NULL | `scheduled` / `manual` / `backfill` / `legacy` |
| `position_count` | integer NOT NULL DEFAULT 0 | 持仓只数 |
| `valuation_at` | timestamptz | 实际计算时刻 |
| `nav_coverage` | jsonb | 每只持仓的 `fund_code/quantity/nav_date/unit_nav/value` |
| `money_fund_income_date` | date | 本次估值包含到的货基收益日 |

写入使用 `(user_id, snapshot_date)` 冲突键 upsert：

- 已存在 `valid` → 跳过，不覆盖。
- 已存在 `invalid` / `legacy` → 允许本轮重算更新。
- 不存在 → 插入。

迁移先把旧行标为 `status='legacy'`、`source='legacy'`，随后去掉这两列的默认值，
强制新写入显式给出状态。补 `(user_id, status, snapshot_date desc)` 索引。

### 4.5 日收益

`GET /portfolio/daily-returns?days=N`：

1. 只取 `status='valid'` 的快照，按日期升序；多取一条作为首条收益的基准。
2. `period_days` = 两个快照之间的交易日数（不含前一日、含当前日）。
3. `period_return = curr.total_assets / prev.total_assets - 1`。
4. `daily_return = period_return` 当 `period_days == 1`；否则为 `null`。
5. 首条快照的 `period_days` / `period_return` / `daily_return` 均为 `null`。
6. 数据库或交易日历异常 → HTTP 503，不再返回空列表冒充「没有收益」。

### 4.6 接口

- `GET /portfolio/daily-returns`：只返回有效快照；新增 `frozen_cash`、`settling_cash`、
  `period_days`、`period_return`；`daily_return` 改为可空。
- `POST /portfolio/snapshot`：保留，改为调用同一估值服务，默认目标是
  `prev_trading_day(今天)`。非交易日或净值不齐返回 HTTP 409 + 原因，不再写「当前市值」。
- `SnapshotData` 增加 `frozen_cash`、`status`、`invalid_reason`。
- `/account`、`/positions` 仍用最新净值，属于实时视图，不在本方案范围内。

### 4.7 失败处理与可观测

- 交易日历不可用、批量读取失败：记录 ERROR，本轮中止，不写半成品。
- 单用户缺净值：写 `invalid` 快照并记录 `invalid_reason`，不影响其他用户。
- 每轮日志输出：目标交易日、账户数、有效/无效/跳过数、无效原因分布、耗时。
- 不在本轮引入独立 `snapshot_runs` 表；调度日志足够定位。若后续需要审计每次运行，
  再按 `confirm_runs` 的模式补。

### 4.8 批量性能

一次任务按表批量读取并分页：`accounts`、`positions(quantity>0)`、`fund_nav(nav_date=T)`、
`trade_orders(status=settling)`、`position_lots(source=income)`。净值按持仓代码集合
批量查，不逐用户查；快照按 500 行分块 upsert。复杂度随「账户行数 + 持仓行数」线性增长，
不随用户数产生 N 倍请求。

## 5. 测试策略

按项目现有偏好只写关键用例，不铺大套件：

1. 全部净值齐全：快照金额/分项正确（含货基 1.0、冻结、在途）。
2. 一只非货基缺 T 日净值：该用户 `invalid`，不参与日收益。
3. 非交易日：拒绝生成。
4. 首条快照：收益字段为空；跨多日有效快照：`period_days > 1`、`daily_return=null`。
5. 同一交易日重复执行：不重复写入，已 `valid` 不覆盖。
6. 账户创建于 T 之后：不生成 T 日快照。
