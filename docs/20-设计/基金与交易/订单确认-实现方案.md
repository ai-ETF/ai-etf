## 3. 最终方案

### 3.4 下单侧原子化（确认重写的前置依赖）

如果下单仍用「读账户 → 改 → 写订单」两次独立请求，两个并发申购会互相覆盖 `cash/frozen_cash`，确认侧再严谨也只能把结果判成「数据不一致」。因此本期必须同时把下单写入 RPC 化。

#### 3.4.1 `place_purchase_order`

```sql
place_purchase_order(
  p_user_id uuid,
  p_fund_code varchar,
  p_fund_name varchar,
  p_amount numeric,
  p_fee numeric,
  p_net_amount numeric,
  p_estimated_nav numeric,
  p_accepted_date date,
  p_confirm_date date,
  p_available_date date,
  p_fee_snapshot jsonb,
  p_max_purchase_amount numeric,   -- NULL = 不限
  p_client_order_id text           -- NULL = 不做幂等
) RETURNS jsonb
```

事务内：

1. `PERFORM pg_advisory_xact_lock(hashtext(p_user_id || ':' || p_fund_code))`，串行化同一用户同一基金的申购额度与冻结。
2. 幂等：若 `p_client_order_id` 非空且该用户已有同键订单：
   - `fund_code/direction` 与本次一致 → 直接返回既有订单（`result='existing'`）。
   - 不一致 → `{result:'idempotency_conflict'}`，不新建、不扣款。
3. 日期守卫：`p_confirm_date >= p_accepted_date` 且 `p_available_date >= p_confirm_date`；否则 `{result:'invalid_dates'}`，不写任何数据。
4. 锁账户：`SELECT ... FROM accounts WHERE user_id = ... FOR UPDATE`；不存在则 `INSERT ... ON CONFLICT (user_id) DO NOTHING` 后再 `SELECT ... FOR UPDATE`（两个不同基金的并发首单可能同时建账户）。
5. 校验 `p_amount > 0 AND cash >= p_amount`；不足返回 `{result:'insufficient_cash'}`，不写任何数据。
6. 单日额度：`SUM(amount) WHERE accepted_date = p_accepted_date AND status IN ('pending','processing','completed','manual_review')`；`p_max_purchase_amount IS NOT NULL` 且超限返回 `{result:'limit_exceeded'}`。`manual_review` 的单仍可能成交，必须计入额度。
7. 原子扣款：`cash = cash - p_amount`、`frozen_cash = frozen_cash + p_amount`。
8. 插入 `trade_orders`：`status='pending'`、`amount/fee/net_amount/estimated_nav`、`accepted_date/confirm_date/available_date`、`fee_rule_snapshot`、`client_order_id`；`price=COALESCE(p_estimated_nav,0)`、`quantity=0`（买单份额在确认时回填）。
9. 返回订单行（JSONB）。

应用层仍负责：白名单、ETF 拦截、申购状态、金额上下限、「限大额但无上限」拒绝、净值预估、风险提示。RPC 只做资金与额度的原子校验，避免两套业务规则漂移。

#### 3.4.2 `place_redeem_order`

```sql
place_redeem_order(
  p_user_id uuid,
  p_fund_code varchar,
  p_fund_name varchar,
  p_quantity numeric,
  p_accepted_date date,
  p_confirm_date date,      -- 卖单净值日 = T
  p_settle_date date,
  p_fee_snapshot jsonb,
  p_client_order_id text
) RETURNS jsonb
```

事务内：

1. 同一把 `user:fund` advisory lock。
2. 幂等：同 `client_order_id` 返回既有订单；若既有订单的 `fund_code/direction` 与本次不一致，返回 `{result:'idempotency_conflict'}`。
3. 日期守卫：`p_quantity > 0`、`p_confirm_date = p_accepted_date`（卖单净值日就是 T）、`p_settle_date >= p_accepted_date`；否则 `{result:'invalid_dates'}`。
4. 校验无 pending/processing 买单（沿用现有规则；若业务决定放开，改这一条）。
5. 计算可赎份额：
   ```sql
   available = (SELECT COALESCE(SUM(remaining_qty),0) FROM position_lots
                 WHERE user_id=$1 AND fund_code=$2
                   AND remaining_qty > 0
                   AND COALESCE(available_date, nav_date) <= p_accepted_date)
             - (SELECT COALESCE(SUM(quantity),0) FROM trade_orders
                 WHERE user_id=$1 AND fund_code=$2 AND direction='sell'
                   AND status IN ('pending','processing','settling','manual_review'));
   ```
   不足返回 `{result:'insufficient_shares', available}`。`manual_review` 的卖单仍可能确认，必须占用可赎份额。
6. 插入 `trade_orders`：`status='pending'`、`quantity`、`settle_date`、`fee_rule_snapshot`；`amount=0`、`price=0`（金额与净值在确认时回填）。
7. 返回订单行。

> 卖单 pending 时 `amount=0` 是现状（P19）。本期保留该行为以便前端兼容；确认时 `amount` 回填为 `quantity × nav`。如果前端需要展示预估金额，用 `quantity × estimated_nav` 在响应里追加，不写库。

### 3.6 RPC 契约

所有函数：

- `LANGUAGE plpgsql`、`SECURITY DEFINER`、`SET search_path = public, pg_temp`。
- `REVOKE ALL ... FROM PUBLIC, anon, authenticated; GRANT EXECUTE ... TO service_role;`
- 返回 `jsonb`，用 `result` 字段表达业务结果；**预期内的业务失败不抛异常**，避免 PostgREST 把可分类错误压成 500。
- 非预期错误（约束冲突、连接失败）直接抛异常，由应用层归为 `retryable` 或中止批次。

#### 3.6.1 `acquire_confirm_run` / `heartbeat_confirm_run` / `finish_confirm_run`

```sql
acquire_confirm_run(p_trigger text, p_worker text, p_lease_seconds int DEFAULT 1800)
  RETURNS uuid
```

- `pg_advisory_xact_lock(hashtext('confirm_run_acquire'))`。
- 查 `status='running'` 的行：
  - `heartbeat_at > now() - lease` → 返回 `NULL`（busy）。
  - 否则标记该行为 `failed, error='lease_expired'`，再插入新 run。
- 插入新 run，`status='running'`，返回 `run_id`。
- 唯一部分索引 `uq_confirm_runs_running` 是第二道防线。

```sql
heartbeat_confirm_run(p_run_id uuid) RETURNS void
finish_confirm_run(p_run_id uuid, p_status text, p_counts jsonb, p_error text DEFAULT NULL)
  RETURNS void
```

- `finish` 只允许 `running → succeeded/failed/skipped`；写 `finished_at/duration_ms` 和计数。

#### 3.6.2 `reap_stale_processing`

```sql
reap_stale_processing(p_lease_seconds int DEFAULT 300, p_max_attempts int DEFAULT 5)
  RETURNS jsonb   -- {released, manual}
```

- `WHERE status='processing' AND processing_at < now() - p_lease_seconds`。
- **回收时 `attempt_count += 1`**：这样即使 worker 在「认领后、更新 attempt_count 前」崩溃，反复过期也能收敛到上限，不会无限循环。
- `attempt_count >= p_max_attempts` → `manual_review`，`last_error_code='LEASE_EXPIRED_MAX_ATTEMPTS'`。
- 否则 → `pending`，`last_error_code='LEASE_EXPIRED'`，清空 `processing_at/by`。
- 幂等：只处理 `processing`，不会碰已终态；同一行不会被重复加计数（状态改为 pending/manual 后不再命中）。
- 并发安全：回收 `UPDATE ... WHERE status='processing'` 与确认 RPC 的订单行锁互斥；如果原 worker 在租约过期后提交了 `completed`，回收语句等到锁后条件不再命中，不会覆盖终态。

#### 3.6.3 `confirm_buy_order`

```sql
confirm_buy_order(
  p_order_id uuid,
  p_worker text,
  p_nav numeric,
  p_fee numeric,
  p_net_amount numeric,
  p_quantity numeric,
  p_residual numeric,
  p_lease_seconds int DEFAULT 300
) RETURNS jsonb
```

事务步骤：

1. `SELECT * FROM trade_orders WHERE id = p_order_id FOR UPDATE`。
   - 不存在 → `{result:'not_found'}`。
   - 已终态（`completed/rejected/cancelled/settled`）→ `{result:'already_terminal', status}`（幂等）。
   - `processing` 且 `processing_by <> p_worker` 且租约未过期 → `{result:'not_claimed'}`。
   - `status NOT IN ('pending','processing')` → `{result:'not_claimed'}`。
   - `direction <> 'buy'` → 函数内直接置 `manual_review`、`code='WRONG_DIRECTION'` 后返回。
   - `accepted_date IS NULL` → 函数内直接置 `manual_review`、`code='ACCEPTED_DATE_MISSING'` 后返回（成交净值日缺失，不能用 `confirm_date` 顶替）。
   - `confirm_date IS NULL` → 函数内直接置 `manual_review`、`code='CONFIRM_DATE_MISSING'` 后返回。
   - `available_date IS NULL` → 函数内直接置 `manual_review`、`code='AVAILABLE_DATE_MISSING'` 后返回（存量由回填脚本补齐，不猜）。
2. 净值校验：读 `fund_nav` 的 `(fund_code, accepted_date)`（**方案 A：成交净值日 = 受理日 T**）；货基用 1.0000。缺失 → `{result:'nav_unavailable'}`（不改状态）。与 `p_nav` 不一致 → `{result:'retryable', code:'NAV_MISMATCH'}`（不改状态；下一轮用新净值）。
3. 金额校验：
   - `p_fee >= 0`、`p_net_amount > 0`、`p_quantity > 0`、`p_residual >= 0`。
   - `abs(p_net_amount - (p_quantity * p_nav + p_residual)) <= 0.01`。
   - `abs(order.amount - (p_net_amount + p_fee)) <= 0.01`。
   - 不满足 → 函数内直接置 `status='manual_review'`、`code='INVALID_AMOUNTS'` 后返回 `{result:'manual_review'}`，不补偿、不认领。
4. 认领：`status='processing'`、`processing_at=now()`、`processing_by=p_worker`、`attempt_count+1`、`last_attempt_at=now()`。
5. 解冻：`UPDATE accounts SET frozen_cash = frozen_cash - order.amount WHERE user_id=... AND frozen_cash >= order.amount RETURNING cash`。
   - 无行 → 函数内直接置 `status='manual_review'`、`code='FROZEN_CASH_INSUFFICIENT'` 后返回，不补偿。
6. 确保 `positions` 行存在并锁住：`INSERT ... ON CONFLICT DO NOTHING` → `SELECT 1 ... FOR UPDATE`（见 §3.3.2 的并发前提）。
7. 插入 lot：
   - `source='order'`、`order_id`、`nav_date=order.accepted_date`、`available_date=order.available_date`、`quantity=remaining_qty=p_quantity`、`cost_price=round(p_net_amount/p_quantity,4)`、`remaining_cost=p_net_amount`。
   - lot 的日期**取自订单已落库的字段**，不信任调用方另传；这样订单与 lot 不会出现两套时间口径。
8. 按 §3.3.2 的汇总 SQL 重算 `positions`。
9. 尾差回现金：`UPDATE accounts SET cash = cash + p_residual`。
10. 写流水：`order_id`、`direction='buy'`、`amount=order.amount`、`price=p_nav`、`quantity=p_quantity`、`fee=p_fee`、`trade_time=now()`。
11. 订单终态：`status='completed'`、`price=p_nav`、`fee=p_fee`、`quantity=p_quantity`、`net_amount=p_net_amount`、`processed_at=now()`、`last_error_code=NULL`、`processing_at/by=NULL`。
12. 返回 `{result:'completed', order_id, nav, fee, quantity, residual}`。

幂等：若订单已终态，第 1 步直接返回；`trade_flow.order_id` 与 `position_lots.order_id` 的唯一索引兜底。

#### 3.6.4 `confirm_sell_order`

```sql
confirm_sell_order(
  p_order_id uuid,
  p_worker text,
  p_nav numeric,
  p_plan jsonb,             -- [{lot_id, quantity, fee, hold_days}]
  p_lease_seconds int DEFAULT 300
) RETURNS jsonb
```

事务步骤：

1. 订单锁定 + 终态幂等校验同 3.6.3（**先不认领**），但：
   - `direction <> 'sell'` → 函数内直接置 `manual_review`、`code='WRONG_DIRECTION'` 后返回。
   - `accepted_date IS NULL` → 函数内直接置 `manual_review`、`code='ACCEPTED_DATE_MISSING'` 后返回。
   - `confirm_date IS NULL` → 函数内直接置 `manual_review`、`code='CONFIRM_DATE_MISSING'` 后返回。
   - **不要求** `available_date`（卖单不需要）。
   - 到账日见第 3 步。
2. 净值校验同 3.6.3，取价日同样是 `accepted_date`（卖单恒有 `confirm_date == accepted_date == T`）。
3. `order.settle_date` 必须非空；否则函数内直接置 `manual_review`、`code='SETTLE_DATE_MISSING'` 后返回。到账日以下单时落库的订单字段为准，调用方不另传。
4. 计划校验：
   - `p_plan` 非空；`SUM(quantity) = order.quantity`；每项 `quantity > 0`、`fee >= 0`。
   - `lot_id` 不得重复；重复 → 直接置 `manual_review`，`code='INVALID_PLAN'`（防止同一 lot 被扣两次）。
   - `SUM(fee)` 作为总费用；`gross = ROUND(order.quantity * p_nav, 2)`；`net = gross - fee`。
5. `SELECT ... FROM position_lots WHERE id IN (...)` `FOR UPDATE`；按 `nav_date, created_at, id` 升序加锁（与 FIFO 顺序一致，避免两个卖单交叉加锁死锁）。逐项校验：
   - lot 属于该用户/基金。
   - `remaining_qty >= plan.quantity`。
   - `COALESCE(available_date, nav_date) <= order.accepted_date`。
   - 不满足 → 返回 `{result:'retryable', code:'LOT_PLAN_STALE'}`（此时还未认领，订单仍是 `pending`，下一轮重建计划）；若 lot 不存在/不属于该用户 → 直接置 `manual_review`，`code='LOT_INCONSISTENT'`。
6. 认领：`status='processing'`、`processing_at=now()`、`processing_by=p_worker`、`attempt_count+1`、`last_attempt_at=now()`。**认领放在所有业务校验之后**，避免校验失败留下 processing 行。
7. **在锁内**计算每段成本（不信任计划里的成本）：
   ```
   cost_i = CASE WHEN plan.quantity = lot.remaining_qty THEN lot.remaining_cost
                 ELSE ROUND(lot.remaining_cost * plan.quantity / lot.remaining_qty, 2) END
   ```
   扣减：`remaining_qty -= plan.quantity`、`remaining_cost -= cost_i`；若 `remaining_qty = 0`，强制 `remaining_cost = 0`（清掉舍入残值）。
8. 锁 `positions` 行（`SELECT ... FOR UPDATE`），再按 §3.3.2 汇总 SQL 重算。每段都已校验 `plan.quantity <= lot.remaining_qty`，所以汇总后的 `quantity >= 0` 是构造保证；如果仍触发约束异常，**抛异常让整个事务回滚**（不要 return 一个已写了一半的 JSONB），应用层按 `data_inconsistency` 记 ERROR。
9. 写流水：`order_id`、`direction='sell'`、`amount=gross`、`price=p_nav`、`quantity=order.quantity`、`fee=总费用`、`trade_pnl = gross - 总费用 - SUM(cost_i)`（用汇总值，避免逐段舍入残差）、`trade_time=now()`。
10. 订单：`status='settling'`、`amount=gross`、`fee=总费用`、`net_amount=net`、`price=p_nav`、`settle_date=order.settle_date`（不改写）、`processed_at=now()`、清空 processing 字段。
11. 返回 `{result:'settling', order_id, amount, fee, net_amount, settle_date}`。

> **分工**：RPC 不重算费率，每段持有天数和费用由应用层用订单快照计算；RPC 只校验金额边界、lot 归属和剩余量，并在锁内重算成本（成本是 lot 的事实，不能由调用方给）。费率档位匹配已在 `FundFeeService`，复制到 SQL 会形成两套规则；lot 的并发安全由 `FOR UPDATE` + 计划校验保证。

#### 3.6.5 `reject_trade_order`

```sql
reject_trade_order(p_order_id uuid, p_worker text, p_code text, p_message text)
  RETURNS jsonb
```

- 锁定订单；已终态 → `{result:'already_terminal', status}`。
- `status NOT IN ('pending','processing','manual_review')` → `{result:'not_claimed'}`。**`settling` 不能拒单**：份额已扣、应收已生成，要撤销必须走反向冲正（本期不做）。
- `processing` 且不是本 worker 且租约未过期 → `not_claimed`。
- 买单且状态在 `pending/processing/manual_review`：
  - `UPDATE accounts SET frozen_cash = frozen_cash - amount, cash = cash + amount WHERE user_id=... AND frozen_cash >= amount`。
  - 无行 → `manual_review`，`code='FROZEN_CASH_INSUFFICIENT'`，**不退款**。
- 卖单：不动现金/份额（份额只在确认事务内扣，失败已回滚）。
- 订单：`status='rejected'`、`reject_reason`、`last_error_code=p_code`、`last_error_message=p_message`、`processed_at=now()`、清空 processing 字段。
- 返回 `{result:'rejected', order_id, code}`。

> 这条 RPC 取代 `_reject_order` + `_refund_rejected_buy` 的假设式补偿：解冻和退款在同一个事务、按订单实际状态判断，不再依赖「此时一定已解冻」。

#### 3.6.6 `mark_order_manual_review`

```sql
mark_order_manual_review(p_order_id uuid, p_worker text, p_code text, p_message text)
  RETURNS jsonb
```

- 锁定订单；已终态 → 幂等返回。
- `status='settling'` → `{result:'not_claimed'}`：`settling` 已扣份额、生成应收，不能走「转人工再重排」的路径；它的异常由 `settle_redeem_order` 返回 `manual_review` 结果但**保持 settling** 处理。
- 设置 `status='manual_review'`、错误码/信息、清空 processing 字段。
- **不补偿**：买单的冻结资金继续挂着，卖单份额未动（能在 `pending/processing` 走到这里的卖单，lot 尚未扣）。人工处理出口见 §3.11。
- 返回 `{result:'manual_review', order_id, code}`。

#### 3.6.7 `settle_redeem_order`

```sql
settle_redeem_order(p_order_id uuid, p_worker text, p_today date)
  RETURNS jsonb
```

- 锁定订单；`status='settled'` → `{result:'already_terminal'}`；`status <> 'settling'` → `not_claimed`。
- `settle_date > p_today` → `{result:'not_due'}`。
- `net_amount` 必须非空；否则**保持 `settling` 不变**，返回 `{result:'manual_review', code:'NET_AMOUNT_MISSING'}`。不能把 `settling` 转 `manual_review`：份额已扣、应收已生成，转人工再重排会重复扣份额。管理员补齐 `net_amount` 后重新调用本 RPC 即可。
- `UPDATE accounts SET cash = cash + net_amount WHERE user_id=...`；账户不存在 → `RAISE EXCEPTION` 回滚（不静默丢钱）。
- 订单：`status='settled'`、`settled_at=now()`、`processed_at=now()`、清空 processing 字段。
- 返回 `{result:'settled', order_id, net_amount}`。
- 幂等：状态 CAS；重复调用返回 `already_terminal`，不会重复入账。

#### 3.6.8 `credit_money_fund_income_atomic`

```sql
credit_money_fund_income_atomic(
  p_user_id uuid,
  p_fund_code varchar,
  p_income numeric,
  p_income_date date
) RETURNS jsonb
```

- `p_income <= 0` → 直接返回 `{result:'no_income'}`（不插 0 份额 lot，`quantity > 0` 约束会拒绝）。
- 先锁 `positions` 行（`SELECT ... FOR UPDATE`；不存在说明持仓已清空，直接返回 `{result:'no_position'}`）。
- 插入 `position_lots`：`source='income'`、`source_ref=p_income_date`、`nav_date=p_income_date`、`available_date=p_income_date`、`quantity=remaining_qty=p_income`、`cost_price=0`、`remaining_cost=0`。
- 命中唯一键 → 返回 `{result:'already_credited'}`，不再加份额。
- 按 §3.3.2 汇总 `positions`（货基 `principal` 不变，因为 income lot 的 `remaining_cost=0`）。
- 返回 `{result:'credited', qty_added}`。

### 3.8 FIFO、lot 与持仓汇总

#### 3.8.1 FIFO 计划

应用层读该用户该基金的 lot：

```sql
SELECT id, nav_date, available_date, remaining_qty, remaining_cost
FROM position_lots
WHERE user_id = $1 AND fund_code = $2 AND remaining_qty > 0
ORDER BY nav_date ASC, created_at ASC, id ASC;
```

按顺序取够 `order.quantity`，生成 `p_plan`。每项包含 `lot_id/quantity/fee/hold_days`；`cost` 由 RPC 在锁内按 lot 的 `remaining_cost × quantity / remaining_qty` 重算，应用层算出的成本只用于展示/预估，不作为记账依据。

- 只取 `COALESCE(available_date, nav_date) <= order.accepted_date` 的 lot；不足 → `manual_review`（下单时已校验，出现即数据不一致）。
- 计划是**乐观**的：RPC 会 `FOR UPDATE` 重新校验；lot 被并发卖出时返回 `LOT_PLAN_STALE`，下一轮重建。

#### 3.8.2 期初 lot 迁移

对每个 `positions.quantity > 0` 且没有 `initial` lot 的持仓：

```sql
INSERT INTO position_lots(
  user_id, fund_code, fund_name, source, source_ref,
  nav_date, available_date, quantity, remaining_qty,
  cost_price, remaining_cost, created_at, updated_at)
SELECT p.user_id, p.fund_code, p.fund_name, 'initial', 'initial',
       COALESCE(p.confirm_date, p.created_at::date),
       COALESCE(p.available_date, p.confirm_date, p.created_at::date),
       p.quantity, p.quantity,
       p.cost_price,
       CASE WHEN p.fund_code = '000198'
            THEN CASE WHEN p.principal > 0 THEN p.principal ELSE p.quantity END
            ELSE ROUND(p.quantity * p.cost_price, 2) END,
       now(), now()
FROM positions p
WHERE p.quantity > 0
  AND NOT EXISTS (
    SELECT 1 FROM position_lots l
    WHERE l.user_id = p.user_id AND l.fund_code = p.fund_code
      AND l.source = 'initial');
```

- `nav_date` 用 `positions.confirm_date` 是近似值（该列历史上被最后一次买入覆盖），首笔赎回的持有期可能偏差；在运维手册和 §7 U2 标注。
- **方案 A 之后的口径差异**：新 lot 的 `nav_date = accepted_date`（T），而期初 lot 仍是 `positions.confirm_date`（历史语义为最后一次确认日）。两者相差 1 个交易日，`nav_date` 的排序（FIFO）和持有期都会受影响。接受理由与处理：期初 lot 的 `nav_date` 只会偏晚（持有期偏短 → 赎回费偏高），按 U2 记录；如果后续出现集中投诉，再按订单表回溯重建期初 lot（成本高，非本期）。
- 脚本必须可重复执行（`NOT EXISTS` 幂等）。
- 迁移前先做只读盘点：持仓数、金额、有无 `confirm_date` 为空、货基 `principal` 是否齐全。
- **必须报告的数据质量问题**（不自动猜）：
  - 货基 `quantity > 0 AND principal = 0`：本金缺失；回填脚本用 `quantity` 兜底并打 WARNING，人工确认。
  - 普通基金 `quantity > 0 AND cost_price = 0`：成本缺失；lot 成本会记为 0，卖出盈亏会虚高，必须人工补成本后再启用赎回。
  - `confirm_date IS NULL`：lot 的 `nav_date` 退化为 `created_at::date`，持有期不准确；在报告里列出订单/持仓。

#### 3.15.3 上线顺序（推荐：短维护窗口）

1. **冻结交易写入**（或至少暂停确认任务），记录当前 pending/持仓盘点。

### 5.3 故障注入

在 RPC 内无法直接注入网络故障；用以下方式：

- 集成测试在事务中手工 `RAISE EXCEPTION` 包装，验证回滚。
- 用非法 `p_plan`/超出剩余量/lot 归属错误触发业务分支。
- 用 `processing_at` 手动改旧触发租约回收。
- PostgREST 断开连接模拟 DB 错误，验证批次中止且订单不变。

### 5.4 重放/幂等

- 同一订单连续调用 `confirm_buy_order` 3 次：第 2、3 次返回 `already_terminal`，无新增写。
- 同一批 pending 连续跑 3 轮：第 2、3 轮 `scanned=0`/`confirmed=0`。
- 同一 `client_order_id` 连续下单 3 次：只建一单。

### 5.5 性能

- 合成 1000 笔 pending / 100 只基金，单轮 < 5 分钟；内存不随订单总数线性增长。
- 单笔 RPC 的 SQL 往返固定；扫描页大小 200。
