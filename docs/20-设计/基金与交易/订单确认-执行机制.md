## 3. 最终方案

### 3.5 确认 Runner

新建 `server/services/order_confirm_service.py`（编排）与 `server/services/order_confirm_rules.py`（错误分类/费用/时间纯函数）。`PortfolioService.confirm_pending_orders` 保留为兼容薄壳，委托给 Runner；调度器与 API 直接调用 Runner。

#### 3.5.1 批次流程

```
run_id = acquire_confirm_run(trigger, worker, lease=1800s)
if run_id is null:
    log busy; return {status:'busy'}
try:
    reap_stale_processing(lease=300s, max_attempts=5)
    cursor = None
    while 未超时 and 未达本轮上限:
        orders = keyset_scan_pending(confirm_date <= today, cursor, limit=200)
        if not orders: break
        for order in orders:
            outcome = process_one(order, run_id, worker)
            counters[outcome] += 1
            heartbeat_confirm_run(run_id)  # 每 50 单或 30 秒
        cursor = (last.confirm_date, last.id)
    settled = settle_due_redemptions(today, worker)
    finish_confirm_run(run_id, counters, settled, error=null)
except Exception as e:
    finish_confirm_run(run_id, counters, error=str(e))
    raise
```

扫描条件：`status='pending' AND confirm_date <= p_today`，按 `(confirm_date, id)` 升序 keyset 分页。PostgREST 写法：

```
.or_(f"confirm_date.gt.{last_date},and(confirm_date.eq.{last_date},id.gt.{last_id})")
```

`p_today` 用 `trading_calendar.beijing_now().date()`，不查日历。

#### 3.5.2 单笔分类

```
process_one(order):
  if order.accepted_date is null:          # 成交净值日缺失，不能用 confirm_date 顶替
      return mark_manual_review(order, 'ACCEPTED_DATE_MISSING')
  if order.confirm_date is null:
      return mark_manual_review(order, 'CONFIRM_DATE_MISSING')
  if not order.fee_rule_snapshot:
      return mark_manual_review(order, 'FEE_SNAPSHOT_MISSING')
  nav = read_nav(order.accepted_date)   # 取 T 日净值；货基 1.0000；内存缓存 (code, accepted_date)
  if nav.status == NOT_YET_PUBLISHED:
      return skipped_nav('NAV_NOT_YET_PUBLISHED')
  if nav.status == FETCH_FAILED:
      return skipped_nav('NAV_FETCH_FAILED')   # 同时 WARNING，提示 repair
  if nav.status == NO_NAV:
      return mark_manual_review(order, 'NO_NAV')
  if order.direction == 'buy':
      fee, net = calc_purchase_from_snapshot(order)
      qty = floor(net / nav, 2)
      residual = round(net - qty * nav, 2)
      return rpc('confirm_buy_order', order, nav, fee, net, qty, residual)
  else:
      plan = build_fifo_plan(order, nav)       # 读 lot；每段 lot_id/qty/fee/hold_days，cost/pnl 由 RPC 锁内重算
      return rpc('confirm_sell_order', order, nav, plan)
```

RPC 返回值映射：

| RPC 返回 | 订单最终状态 | 计数器 | 日志级别 |
|---|---|---|---|
| `completed` | `completed` | `confirmed` | INFO |
| `settling` | `settling` | `confirmed` | INFO |
| `settled`（确认后立即到账） | `settled` | `confirmed` + `settled` | INFO |
| `rejected`（含补偿） | `rejected` | `rejected` | WARNING |
| `nav_unavailable` | 不变 | `skipped_nav` | INFO |
| `retryable` | `pending`（attempt+1） | `retryable` | WARNING |
| `data_inconsistency` | `manual_review` | `manual_review` | ERROR |
| `not_claimed` | 不变 | 不计入（DEBUG） | DEBUG |
| `not_found` | — | 不计入 | ERROR |

单笔异常：`BusinessReject` 类在 RPC 内完成补偿并返回 `rejected`；应用层只负责计数。数据库连接级异常（连不上、超时）**中止本轮**，`finish_confirm_run(error=...)`，订单保持原状态，下一轮重试。单笔非连接级异常记 ERROR 并计 `retryable`，继续下一单。

**例外：唯一约束冲突不重试。** 如果 `trade_flow.order_id` 或 `position_lots.order_id` 已存在，说明该订单之前已经写过业务数据，再重试只会无限撞同一约束（且事务回滚连 `attempt_count` 都不增加）。这类错误直接 `mark_order_manual_review`，`code='DUPLICATE_SIDE_EFFECT'`，由人工核对后处理。

#### 3.5.3 批次边界

- 页大小 200；本轮最多处理 `CONFIRM_MAX_ORDERS`（默认 2000）或 `CONFIRM_TIME_BUDGET_SECONDS`（默认 240）。
- 超时/超量：正常结束本轮，`finish_confirm_run` 记 `error='time_budget_exceeded'`（`status='succeeded'`），下一轮继续。
- 与下一轮重叠：`acquire_confirm_run` 返回 null，下一轮直接跳过，不叠加。
- 内存：只持有一页订单 + 净值缓存字典；不累计全部订单。

### 3.11 错误分类与重试

| 类别 | 例子 | 动作 | 计数器 | 是否重试 |
|---|---|---|---|---|
| `NavUnavailable` | `NOT_YET_PUBLISHED` | 保持 `pending`，零业务写入 | `skipped_nav` | 下一轮 |
| `NavUnavailable` | `FETCH_FAILED` | 保持 `pending`，WARNING 提示 repair | `skipped_nav` | 下一轮 |
| `NavUnavailable` | `NO_NAV` | `manual_review`，`code='NO_NAV'`，零业务写入 | `manual_review` | 否，人工 |
| `RetryableSystemError` | DB 超时、PostgREST 5xx、锁冲突、`NAV_MISMATCH`、`LOT_PLAN_STALE` | 订单回 `pending`（或保持 `processing` 等回收），`attempt_count+1`，`last_error_code` | `retryable` | 是，带上限 |
| `BusinessReject` | 管理员/明确业务规则判定不可成交（如基金公司拒单） | RPC 内 `rejected` + 同事务补偿 | `rejected` | 否 |
| `DataInconsistency` | 负余额、冻结不足、lot 汇总不等于持仓、金额恒等式不成立 | `manual_review`，不自动退款 | `manual_review` | 否，人工 |
| `CalendarUnavailable` | 下单路径日历未就绪/越界 | 下单返回 503；确认路径不应出现 | — | 人工修复后重跑 |

错误码（`last_error_code`）：

| 错误码 | 含义 | 类别 |
|---|---|---|
| `NAV_NOT_YET_PUBLISHED` | 净值未公布 | skip |
| `NAV_FETCH_FAILED` | 净值抓取失败/缺口 | skip |
| `NO_NAV` | 该日确实无净值 | manual |
| `CONFIRM_DATE_MISSING` | 订单缺确认日 | manual |
| `AVAILABLE_DATE_MISSING` | 买单缺可赎回日（存量未回填） | manual |
| `FEE_SNAPSHOT_MISSING` | 订单缺费率快照 | manual |
| `INVALID_AMOUNTS` | 金额恒等式不成立 | manual |
| `INVALID_PLAN` | FIFO 计划结构非法（如 lot_id 重复） | manual |
| `FROZEN_CASH_INSUFFICIENT` | 冻结不足 | manual |
| `NET_AMOUNT_MISSING` | 卖单缺应收净额 | manual |
| `SETTLE_DATE_MISSING` | 卖单缺到账日 | manual |
| `LOT_INSUFFICIENT` | lot 不足 | manual |
| `LOT_INCONSISTENT` | lot 不存在/不属于该用户 | manual |
| `WRONG_DIRECTION` | 订单方向与 RPC 不符 | manual |
| `NAV_MISMATCH` | 读到的净值与 RPC 校验不一致 | retry |
| `LOT_PLAN_STALE` | FIFO 计划过期 | retry |
| `LEASE_EXPIRED` | 租约超时回收 | retry |
| `LEASE_EXPIRED_MAX_ATTEMPTS` | 超过最大尝试次数（租约回收路径） | manual |
| `MAX_ATTEMPTS_EXCEEDED` | 超过最大尝试次数（Runner 调用前检查） | manual |
| `PENDING_TOO_LONG` | 确认日过久仍未确认 | manual |
| `DUPLICATE_SIDE_EFFECT` | 流水/lot 已存在但订单未终态 | manual |
| `DB_ERROR` | 数据库/网络错误 | retry |

重试上限：

- `attempt_count >= CONFIRM_MAX_ATTEMPTS`（默认 5）→ `manual_review`，`code='MAX_ATTEMPTS_EXCEEDED'`。检查点在 Runner 调用 RPC 之前：`pending` 且 `attempt_count` 已达上限的订单不再重试。
- 净值类不增加 `attempt_count`（不认领）；用「**成交净值日**距今天数」告警：`today - accepted_date > NAV_PENDING_ALERT_DAYS`（默认 5 个自然日）→ WARNING；超过 `PENDING_MAX_DAYS`（默认 14 个自然日）→ 转 `manual_review`，`code='PENDING_TOO_LONG'`。用自然日而不是交易日，避免确认路径依赖交易日历。
- `manual_review` 的人工出口：
  - 查询：`GET /admin/orders/health`（管理员）或 `server/scripts/order_ops.py list-manual`。
  - 修复数据后重排：`POST /admin/orders/{id}/requeue` 或脚本调用 `requeue_manual_review_order`。
  - 拒单退款：管理员调用 `reject_trade_order`（带补偿）。
  - 本期先交付脚本；管理接口可随后补。

### 3.12 调度

#### 3.12.1 删除与新增

| 项 | 决策 |
|---|---|
| 15:37 确认任务 | **删除** |
| `before_today` 参数 | **删除** |
| 确认与抓取 | **解耦**：确认只读 DB；抓取成功后触发一次确认 |
| 触发 1 | `update_batch` 成功后触发（异步、单飞、不阻塞同步） |
| 触发 2 | 兜底扫描：每天 18:00–09:00，每 30 分钟一次 |
| 非交易日 | 兜底扫描照常运行 |
| 触发 3 | 启动补偿：进程启动时一次 |
| 触发 4 | 手动：`POST /portfolio/confirm-pending`（管理员） |
| 时区 | `AsyncIOScheduler(timezone=ZoneInfo("Asia/Shanghai"))`，所有 `CronTrigger` 显式同时区 |
| 扫描条件 | `status='pending' AND confirm_date <= today`（份额到账日未到不确认）；能否确认由 `get_nav_on(accepted_date)` 决定 |
| 单飞 | `confirm_runs` 唯一运行 + advisory lock |

兜底窗口精确时刻：

- `18:00, 18:30, 19:00, 19:30, 20:00, 20:30, 21:00, 21:30, 22:00, 22:30, 23:00, 23:30`
- `00:00, 00:30, 01:00, 01:30, 02:00, 02:30, 03:00, 03:30, 04:00, 04:30, 05:00, 05:30, 06:00, 06:30, 07:00, 07:30, 08:00, 08:30`
- `09:00`

实现：`CronTrigger(hour="18-23,0-8", minute="0,30", timezone=TZ)` + `CronTrigger(hour=9, minute=0, timezone=TZ)`，或一个 `hour="18-23,0-8"` 加 09:00 单独任务。**不要**用 `hour="18-23,0-9"`，否则会多出 09:30。

#### 3.12.2 净值同步后的触发

- `_fund_nav_update_job` 保留现有的净值更新窗口，但删除 `with_confirm` 参数；`update_batch` 成功后调用 `trigger_confirm(trigger='sync')`。
- 触发方式：`asyncio.create_task`，模块级 `set` 持有任务引用防 GC；不再 `await` 确认，避免确认耗时拖住下一轮同步。
- 确认任务内部用 `acquire_confirm_run` 单飞；拿不到锁视为本轮跳过，**不算失败**。
- 同步成功 → 触发确认；同步失败 → 只记 ERROR，不额外触发（已入库的净值仍可被下一轮兜底确认）。两者只在「同步成功后触发」这一点有单向依赖，确认失败不会回滚/阻断同步。
- 启动补偿 `_startup_nav_and_confirm` 保持串行：先补净值，再确认；避免确认先扫到净值还没入库的订单。

#### 3.12.3 多 worker / 多实例

- `app.py:93` 在 lifespan 启动调度器；多 worker 部署时每个进程都会注册任务。
- 确认：`acquire_confirm_run` 的数据库锁保证只有一个批次执行，其余 `busy` 跳过。
- 净值同步：现有 `flock` 只能覆盖同机多进程，多实例仍可能并发抓取。这是**确认范围外**的已知问题，登记在 §7 U7；确认侧不受影响。
- 建议部署：API 多 worker + 调度器单独进程（或只在一个实例启用调度）；在完成 U7 之前，至少保证同一台机器只有一个调度器进程。

### 3.13 性能与分页

- keyset 分页 200 条/页，内存有界。
- 净值按 `(fund_code, accepted_date)` 在单轮内缓存（成交净值日 = 受理日 T），避免同基金多订单重复查询。
- 费率从订单快照读取，不查 `fund_catalog`。
- lot 读取按订单的用户/基金；同一用户同基金的多笔卖单可共用一次 lot 查询（实现阶段按需优化，先保证正确）。
- 单笔 RPC 的数据库往返固定，不随订单数线性增长；批量扫描是 O(订单数/页)。
- 目标：1000 笔 pending / 100 只基金，单轮 < 5 分钟；超出时 `time_budget_exceeded`，下一轮继续。
- 一轮未结束时下一轮 `busy` 跳过，不叠加。

### 3.14 可观测、对账与告警

#### 3.14.1 批次记录

`confirm_runs` 记录 `run_id/trigger_source/worker/started_at/finished_at/scanned/confirmed/rejected/skipped_nav/retryable/manual_review/settled/error/duration_ms`。

#### 3.14.2 结构化日志

每轮：

```
[确认] run_id=... trigger=sync worker=... scanned=... confirmed=...
       rejected=... skipped_nav=... retryable=... manual_review=... settled=... duration_ms=...
```

每单（INFO/WARNING/ERROR 按结果）：

```
[确认] run_id=... order_id=... user_id=... fund_code=... accepted_date=... confirm_date=... result=... code=...
```

#### 3.14.3 对账脚本

`server/scripts/order_ops.py` 提供：

- `reconcile`：跑附录 §9.3 的不变量 SQL，输出差异和订单 ID；干净数据集零差异。SQL 建议封装成只读 RPC `reconcile_orders()` 返回 JSONB，脚本经 PostgREST 调用；若直接连库执行，必须用只读事务，禁止在脚本里拼写业务写操作。
- `list-manual`：列 `manual_review` 订单。
- `list-stuck`：列超过阈值的 `pending` / 超租约的 `processing` / 超到账日的 `settling`。
- `requeue <order_id>`：调用 `requeue_manual_review_order`。
- `reject <order_id> <code>`：调用 `reject_trade_order`（人工确认后）。

脚本必须 `load_dotenv`（一次性脚本不会自动加载 `.env`），并与服务共用 `get_supabase()`。

#### 3.14.4 告警

本期不接外部告警平台，用以下方式：

- `manual_review` 出现 → ERROR 日志。
- 不变量失败 → ERROR 日志 + 对账脚本非零退出。
- `pending` 超 `NAV_PENDING_ALERT_DAYS` → WARNING。
- `FETCH_FAILED` → WARNING，提示 `fund_nav_admin repair`。
- 单轮失败/超时 → ERROR 日志。
- 后续接入告警平台见 §7 U3。

## 4. 关键流程时序

### 4.1 买入确认成功

```
Runner: get_nav_on(accepted_date) == OK      # 成交净值日 = 受理日 T；扫描门槛仍是 confirm_date <= today
  → fee/net 从快照计算；qty=floor(net/nav,2)；residual=net-qty*nav
  → confirm_buy_order
      lock order → 校验 nav/金额 → claim(processing)
      → frozen_cash -= amount
      → insert lot(order, nav_date=order.accepted_date, available_date=order.available_date)
      → 汇总 positions
      → cash += residual
      → insert trade_flow(order_id)
      → order completed
  → 计数 confirmed
```

### 4.2 卖出确认成功

```
Runner: get_nav_on(accepted_date) == OK      # 卖单 accepted_date == confirm_date
  → 读 lot，构建 FIFO plan（每段 lot_id/qty/fee/hold_days）
  → confirm_sell_order
      lock order → 校验 nav/plan → claim(processing)
      → lock lots FOR UPDATE → 校验剩余量 → 锁内重算每段 cost
      → 扣 lot remaining_qty/remaining_cost
      → 汇总 positions
      → insert trade_flow(order_id, pnl)
      → order settling, settle_date=order.settle_date
  → 计数 confirmed
  → 若 settle_date <= today：settle_redeem_order → cash += net_amount, order settled
```

### 4.3 业务拒单（买入）

```
Runner/RPC 检测确定性业务错误
  → reject_trade_order
      lock order → 状态允许
      → frozen_cash -= amount AND cash += amount（同一事务）
      → order rejected, code/message
  → 计数 rejected
  → 若 frozen_cash < amount：manual_review，不退款
```

### 4.4 到账

```
settle_due_redemptions(today):
  scan status='settling' AND settle_date <= today (keyset, 200/页)
  → settle_redeem_order(order_id, worker, today)
      lock order → status='settling' → cash += net_amount → settled
  → 计数 settled
```

### 4.5 租约回收

```
Runner 开始:
  reap_stale_processing(lease=300s, max_attempts=5)
    processing_at 超时:
      attempt_count >= 5 → manual_review (LEASE_EXPIRED_MAX_ATTEMPTS)
      else → pending (LEASE_EXPIRED)
```

### 4.6 批次

```
trigger (sync/fallback/startup/manual)
  → acquire_confirm_run
      busy → skip
      acquired → reap → keyset scan → process_one → settle → finish
```

## 9. 附录

### 9.3 对账 SQL（每轮后执行，期望 0 行）

```sql
-- 1. 负余额
SELECT user_id, cash, frozen_cash FROM accounts
WHERE cash < 0 OR frozen_cash < 0;

-- 2. 冻结 vs 未完成买单
SELECT a.user_id, a.frozen_cash,
       COALESCE(SUM(o.amount) FILTER (
         WHERE o.direction='buy'
           AND o.status IN ('pending','processing','manual_review')),0) AS expected
FROM accounts a
LEFT JOIN trade_orders o ON o.user_id = a.user_id
GROUP BY a.user_id, a.frozen_cash
HAVING a.frozen_cash <> COALESCE(SUM(o.amount) FILTER (
         WHERE o.direction='buy'
           AND o.status IN ('pending','processing','manual_review')),0);

-- 3. completed 买单流水数 != 1
SELECT o.id, COUNT(f.id) AS flows
FROM trade_orders o
LEFT JOIN trade_flow f ON f.order_id = o.id
WHERE o.direction='buy' AND o.status='completed'
GROUP BY o.id
HAVING COUNT(f.id) <> 1;

-- 4. lot 汇总 != positions.quantity
SELECT p.user_id, p.fund_code, p.quantity,
       COALESCE(SUM(l.remaining_qty),0) AS lot_qty
FROM positions p
LEFT JOIN position_lots l
  ON l.user_id=p.user_id AND l.fund_code=p.fund_code
GROUP BY p.user_id, p.fund_code, p.quantity
HAVING ABS(p.quantity - COALESCE(SUM(l.remaining_qty),0)) > 0.01;

-- 5a. 普通基金成本均价 = lot 剩余成本 / 剩余份额（4 位）
SELECT p.user_id, p.fund_code, p.cost_price,
       ROUND(COALESCE(SUM(l.remaining_cost),0)
             / NULLIF(COALESCE(SUM(l.remaining_qty),0),0), 4) AS lot_cost_price
FROM positions p
LEFT JOIN position_lots l
  ON l.user_id=p.user_id AND l.fund_code=p.fund_code
WHERE p.fund_code <> '000198'
GROUP BY p.user_id, p.fund_code, p.cost_price
HAVING ABS(p.cost_price - ROUND(COALESCE(SUM(l.remaining_cost),0)
             / NULLIF(COALESCE(SUM(l.remaining_qty),0),0), 4)) > 0.0001;

-- 5b. 货基本金 = lot 剩余成本
SELECT p.user_id, p.fund_code, p.principal,
       COALESCE(SUM(l.remaining_cost),0) AS lot_cost
FROM positions p
LEFT JOIN position_lots l
  ON l.user_id=p.user_id AND l.fund_code=p.fund_code
WHERE p.fund_code = '000198'
GROUP BY p.user_id, p.fund_code, p.principal
HAVING ABS(COALESCE(p.principal,0) - COALESCE(SUM(l.remaining_cost),0)) > 0.01;

-- 6. 负份额
SELECT user_id, fund_code, quantity FROM positions WHERE quantity < 0;

-- 7. 买入金额恒等式
SELECT id, amount, net_amount, fee FROM trade_orders
WHERE direction='buy' AND status IN ('completed','settling','settled')
  AND ABS(amount - (net_amount + fee)) > 0.01;

-- 8. 卖出金额恒等式
SELECT id, amount, net_amount, fee, quantity, price FROM trade_orders
WHERE direction='sell' AND status IN ('settling','settled')
  AND (ABS(amount - quantity*price) > 0.01
       OR ABS(net_amount - (amount - fee)) > 0.01);

-- 9. 流水 order_id 重复（唯一索引已阻止，巡检兜底）
SELECT order_id, COUNT(*) FROM trade_flow
WHERE order_id IS NOT NULL GROUP BY order_id HAVING COUNT(*) > 1;
```
