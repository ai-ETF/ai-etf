## 1. 背景与术语

### 1.1 要解决的问题

主要用于确定今天是不是交易日。

**决策（2026-10-18）**：日历采用「**人工全量拉取 + DB 持久化 + 内存常驻**」。

**刷新方式（2026-10-18 修订）**：不做每日定时刷新，也不做启动自动拉取。日历只在**人工调用管理接口**时更新——每年 11–12 月调用一次拉取接口，每月调用一次状态接口核验。操作步骤见 [`trading-calendar-ops`](../../../.claude/skills/trading-calendar-ops/SKILL.md)，人工核验标准见 [`交易日历运维手册.md`](../../40-运维/交易日历/交易日历运维手册.md)。

**无兜底（2026-10-21 决策）**：取不到、覆盖不到、拉取失败一律显式报错。`is_trading_day` 只在「快照已就绪且日期在覆盖区间内」时返回 bool，其余情况抛 `CalendarUnavailable` / `CalendarOutOfCoverage`；不再有「工作日兜底」，也不再有 `degraded` 模式。

### 1.2 术语

| 术语 | 含义 |
|---|---|
| **交易日历** | A 股交易日集合，覆盖历史与上游已公布未来日期 |
| **覆盖区间** | 内存/状态里的 `[coverage_start, coverage_end]`；两者都直接取自源返回的交易日集合（当前 `1990-12-19 → 2026-12-31`） |
| **全量拉取** | 一次性取回源返回的全部日期，不是按需查某一天；整份落库 |
| **人工拉取** | 运维调用管理接口触发的全量拉取：同步执行，写库并原子替换内存。每年一次，异常时追加 |
| **人工核验** | 运维按月执行的**只读**检查：覆盖区间、最后成功时间、抽样对照交易所日历；不写库 |
| **内存层** | 进程内 `frozenset[date]`，请求路径只读它，不触网 |
| **持久层** | `trading_calendar`（逐日）+ `trading_calendar_state`（单行状态） |
| **不可用** | 快照未载入，或查询日期超出 `[coverage_start, coverage_end]`；调用方收到 `CalendarUnavailable` / `CalendarOutOfCoverage`，不返回猜测值 |
| **快照替换** | 人工拉取成功后，在一个事务内用源返回的完整日历替换表内容，再原子替换内存；失败则整体回滚 |
| **T 日 / confirm_date** | 订单受理交易日 / 实际确认日，计算依赖 `is_trading_day` |

### 1.3 不可违反的约束

- **不可使用默认值**
- **不把「取不到」当成「全年休市」**：覆盖区间外或数据为空必须显式报错，不能返回 `False` 了事。
- **无兜底**：快照未就绪或日期超出覆盖区间时，`is_trading_day` / `is_trading_time` 必须抛错，不得按星期几猜测。
- **单一日历源**：`CAP_CALENDAR` 只允许注册一个源；第二个源会自动启用换源，可能写入覆盖区间更短的日历。
- **启动不阻塞在日历上**：DB 为空或覆盖不足时进程仍要能启动，因为管理刷新接口在同一个进程里；日历相关的业务操作直接报错。
- **不掩盖错误**：失败必须留下可查痕迹（`last_error` + 日志），不允许静默兜底。
- **人工核验是正确性的最终保障**：自动拉取只能发现变更，不能判断对错。
- **管理接口必须鉴权且默认关闭**：未配置管理凭证时返回 503，不做「无凭证也能刷新」。
- 数据库结构唯一权威来源是 `supabase/migrations/`。

## 2. 实现现状

### 2.1 现有行为

| 场景 | 现状 |
|---|---|
| 当天首次调用 | 请求一次上游，把整份日历放进 `_cache["dates"]` |
| 当天后续调用 | 纯内存，不再触网 |
| 进程重启 | `_cache` 清空，下次调用重新请求 |
| 当天请求失败、但历史上成功过 | 用内存里的旧副本，**且不更新 `day`**，下次调用继续重试 |
| 进程重启后首次请求失败 | 内存里没有旧副本 → `dates is None` → 退化为「周一至周五」 |
| 覆盖区间 | 实测源返回 `1990-12-19 → 2026-12-31`；代码**不检查**这个区间 |

## 4. 设计方案

### 4.1 架构

```
启动
  │
  ├─ 读 DB：trading_calendar_state + 交易日行（is_trading_day=true）
  │    ├─ 有数据 → 构建交易日 frozenset，ready=true
  │    └─ 无数据 / 读取失败 → ready=false + ERROR，进程继续启动
  │         （管理刷新接口在同一个进程里，不能因日历缺失而崩）
  │         （此后任何日历相关调用抛 CalendarUnavailable）
  │
运行期
  │
  ├─ is_trading_day / is_trading_time → 只读内存，不触网
  │    └─ 未就绪 / 日期越界 → 抛错，不猜
  │
  └─ 无定时刷新；日历变更只由人工触发

人工（运维）
  │
  ├─ POST /api/admin/trading-calendar/refresh?dry_run=true
  │     └─ 拉取 + 计算 diff，不写库、不替换内存
  ├─ POST /api/admin/trading-calendar/refresh
  │     └─ 拉取 → upsert → 原子替换内存（在服务进程内执行）
  └─ GET  /api/admin/trading-calendar/status
        └─ 只读核验：覆盖区间、最后成功、最近错误
```

**设计原则**：请求路径**永远不等待上游**，进程启动**也不等待上游**。上游只在人工调用管理接口时出现。请求路径只读快照；快照不可用或日期越界时抛错，不返回猜测值。

### 4.2 数据库设计

1. **需求简述**：持久化一份 A 股交易日历快照，供 `is_trading_day` 只读；记录覆盖区间与最后一次成功/失败时间；每个自然日一行，区分交易日与非交易日。
2. **概念设计（E-R）**：两个独立实体，无外键。
   - `CALENDAR_DAY(trade_date, is_trading_day, source)`
   - `CALENDAR_STATE(id=1, coverage_start, coverage_end, last_success_at, last_error, last_error_at)`
   - 关系：`CALENDAR_STATE` 描述 `CALENDAR_DAY` 当前快照的元信息（1:1 语义，不是数据库外键）。
3. **逻辑设计**：`trade_date` 主键；`is_trading_day`、`source` 非空；`state.id` 用 `boolean PRIMARY KEY CHECK (id)` 保证单行；`coverage_start <= coverage_end` 由应用层校验。
4. **物理设计**：见 §4.2.1 / §4.2.2 的 DDL。表启用 RLS；迁移文件建议 `supabase/migrations/20261018XXXXXX_create_trading_calendar.sql`，沿用现有 `时间戳_描述.sql` 风格；数据量约 1.3 万行，主键即查询路径，无需额外索引。

#### 4.2.1 `trading_calendar` —— 逐日表

```sql
CREATE TABLE IF NOT EXISTS "public"."trading_calendar" (
    "trade_date"     date PRIMARY KEY,
    "is_trading_day" boolean NOT NULL,
    "source"         text NOT NULL,
    "updated_at"     timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE "public"."trading_calendar" ENABLE ROW LEVEL SECURITY;

COMMENT ON TABLE "public"."trading_calendar" IS
  'A 股交易日历逐日表：源覆盖区间内每个自然日一行，is_trading_day=false 表示周末/节假日';
COMMENT ON COLUMN "public"."trading_calendar"."source" IS
  '这一行由哪个日历源产出（当前为 sina_trade_date），便于审计';
```

**为什么存「每个自然日」而不是只存交易日**：

- `is_trading_day(d)` 变成一次主键查询，不需要额外判断「这个日期是假期还是超出覆盖区间」；
- 周末/节假日显式落库，排查「为什么某天没更新」时能直接看到；
- 源返回约 8800 个交易日，展开成自然日约 1.3 万行，存储量级可忽略。

**存全量历史（2026-10-21 修订）**：不再裁剪「入库窗口」，每次拉取把源返回的全部日期
（当前 `1990-12-19 → 2026-12-31`）整份写入。

- 表内容与源快照一一对应，`coverage_start/end` 就是源的真实覆盖，没有「窗口外旧行」这种半快照状态；
- 历史日期也能直接回答，不需要为将来的对账再回填；
- 约 1.3 万行、一次年度写入，成本可以忽略；换来的是查询语义完整和写入逻辑简单。

**为什么不再保留窗口外的旧行**：整表替换意味着「表 = 最后一次成功快照」。
保留旧行会让表变成多次拉取的并集，无法回答「现在这份日历到底是哪来的」，
也会在源截断时掩盖问题。

**为什么保留 `source`**：单源之后正常只有 `sina_trade_date`；`source` 列仍保留，
用于将来人工指定源或数据迁移时审计。

#### 4.2.2 `trading_calendar_state` —— 单行状态

```sql
CREATE TABLE IF NOT EXISTS "public"."trading_calendar_state" (
    "id"              boolean PRIMARY KEY DEFAULT true CHECK (id),
    "coverage_start"  date,
    "coverage_end"    date,
    "last_success_at" timestamptz,
    "last_error"      text,
    "last_error_at"   timestamptz,
    "updated_at"      timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE "public"."trading_calendar_state" ENABLE ROW LEVEL SECURITY;

COMMENT ON TABLE "public"."trading_calendar_state" IS
  '交易日历缓存状态：单行，记录覆盖区间与最后一次成功/失败';
```

**为什么单行**：状态是全局的（一份日历），用 `id boolean PRIMARY KEY CHECK (id)` 保证只有一行。`coverage_start/end` 让启动时不必对主表做 `min/max` 聚合，也让运维能一眼看出「日历到哪一天」。

**注意 `coverage_start` 的语义**：它等于源返回的最早日期（当前 `1990-12-19`），不是「当年 1 月 1 日」；`coverage_end` 等于源返回的最晚日期。两者都在一次成功刷新中整体更新，不做 `max` 合并。

**`last_success_at` vs `last_error_at` 分开**：前者回答「数据有多新」，后者回答「最近一次失败是什么」。混用会看不出「是没刷新，还是刷新了但上游挂了」。

#### 4.2.3 写入策略

| 动作 | 规则 |
|---|---|
| 人工拉取 | 拉取 → 校验 → `dry_run` 只计算 diff；正式调用执行数据库函数 `replace_trading_calendar(...)`，函数内 `DELETE` + 展开自然日 `INSERT` + 更新 `state` 在**同一事务**完成 |
| 覆盖区间 | `coverage_start/end` 直接取本次源返回值，**不取 max、不沿用旧值** |
| 异常数据 | 任一校验失败 → **拒绝整次刷新**，不写库、不替换内存（校验项见 §4.4） |
| 数值更正 | 同一日期 `is_trading_day` 变化时随快照一起写入；`dry_run` 的 diff 会显示，正式调用时打 WARNING（正常不应发生） |
| 状态更新 | 与主表写入在同一个数据库函数/事务里完成，主表失败则 `state` 不动 |
| 重复调用 | 整表替换天然幂等：同一份源结果重复写入，表内容不变；`Idempotency-Key` 仅用于日志追踪 |

**为什么必须用数据库函数（2026-10-21 补充）**：本项目只使用 Supabase PostgREST 客户端，
没有直连数据库（无 `psycopg` / `DATABASE_URL`）。PostgREST 的每次 `DELETE` / `INSERT`
都是独立 HTTP 请求，**客户端无法跨调用开启事务**；按「先 DELETE 再分批 INSERT」实现，
中途失败会留下空表或半份快照，直接违反「失败整体回滚」。

因此迁移里提供 `public.replace_trading_calendar(p_trading_days date[], p_source text)`：
入参是本次源返回的交易日集合（ISO 日期数组），函数内展开为自然日、整表替换并更新
`trading_calendar_state`，任一语句失败整个函数回滚。应用侧只调一次 `rpc()`，
所有请求都在一个 PG 事务里。返回值携带 `coverage_start/end`、`rows`、`trading_days`，
供接口响应与日志使用。

**为什么整表替换而不是「只 upsert 差异」**：

- 表语义是「最后一次成功快照」，整表替换能保证这一点；增量 upsert 会保留源已不再返回的行，形成并集；
- 约 1.3 万行的批量写入在一次年度操作里可以忽略；
- 失败时整体回滚，不会留下半份快照。

**不再有「只增不减」和「`coverage_end` 取 max」**：这两条都是为了在源截断时保留旧数据，
本质上是用旧值兜底。现在源返回异常就拒绝整次刷新，旧快照原样不动，由人工判断。

### 4.3 内存层

| 项 | 设计 |
|---|---|
| 数据结构 | `frozenset[date]`（交易日集合）+ `coverage_start/end` + `source` + `ready` 标记 |
| 载入时机 | 进程启动时一次性执行 `SELECT trade_date FROM trading_calendar WHERE is_trading_day`（约 8.8k 行）构建快照。**非交易日不入内存**：覆盖区间内不在集合中的日期即可推出 `NON_TRADING`，无需保留 1.3 万行自然日。**DB 为空或读取失败时不触网**，`ready=false`，进程继续启动；没有 DB 依赖的测试可注入假快照 |
| 内存占用 | 常驻就是一个 8.8k 元素的 `date` 集合，实测约 **0.75 MB**，不随请求增长。曾评估用 bitset（按 `date.toordinal()` 定位，约 1.6 KB）把占用再降 500 倍，但收益远小于可读性损失，**不采用** |
| 读路径 | 无锁读不可变快照；`is_trading_day` 只做集合成员判断 |
| 刷新 | 管理接口在**服务进程内**执行：构建新的 `frozenset` 后原子替换引用（`threading.Lock` 只保护替换动作），**不需要重启**。多 worker 时只有处理该请求的进程更新内存，见 Q5 |
| `reset_cache()` | 保留，测试专用；现在同时清空内存与 `ready` 标记 |

**签名不变，错误语义改变**：`is_trading_day(d: date) -> bool` 仍返回 bool，但只对「已就绪且在覆盖区间内」的日期返回；其余情况抛异常。内部先走 `calendar_status(d)`：

| `calendar_status(d)` | 含义 | `is_trading_day` 的行为 |
|---|---|---|
| `TRADING` | 覆盖区间内且是交易日 | 返回 `True` |
| `NON_TRADING` | 覆盖区间内但不是交易日（周末/节假日） | 返回 `False` |
| `UNAVAILABLE` | 快照未载入 | 抛 `CalendarUnavailable` |
| `OUT_OF_COVERAGE` | 日期早于 `coverage_start` 或晚于 `coverage_end` | 抛 `CalendarOutOfCoverage` |

`is_trading_time` 同样：日历不可用或日期越界时抛错，不返回 `False`。

这样既不改调用方签名，也不会把「未知」静默当成「非交易日」或「交易日」。异常信息携带 `date`、`coverage_start/end`、`last_error`，运维/健康检查可以直接读 `calendar_status` 和 `trading_calendar_state`。

### 4.4 人工全量拉取

**触发方式（只有管理接口）**：

| 场景 | 调用 |
|---|---|
| 每年 11–12 月 | `POST /api/admin/trading-calendar/refresh`（先 `?dry_run=true` 看 diff） |
| 每月核验发现问题 | 同上 |
| 交易所临时调整 | 人工确认公告后同上 |
| 新环境首次部署 | 作为部署步骤调用一次，否则启动后 `ready=false`，日历相关业务接口直接报错 |

**没有**启动自动拉取，也没有每日定时任务。进程启动只读 DB：DB 为空时记 ERROR、`ready=false`，进程继续运行，等待人工处理；日历相关业务调用直接抛 `CalendarUnavailable`。

**接口契约**：

| 项 | 约定 |
|---|---|
| 鉴权 | `X-Admin-Token` 与环境变量 `ADMIN_API_TOKEN` 做常量时间比较；未配置时返回 503（默认关闭） |
| 幂等 | 调用方必须提供 `Idempotency-Key`（缺失返回 400）；接口按「整表替换」实现，重复调用不产生额外副作用，同一 key 重放安全；key 仅用于日志追踪 |
| dry_run | `?dry_run=true` 时只拉取、计算 diff 并返回，不写库、不替换内存 |
| 并发 | 进程内非阻塞锁；已有拉取在跑时返回 409 |
| 超时 | 适配器强制 timeout；接口整体超过 30s 返回 504，不写库 |
| 响应 | `request_id`、`coverage_start/end`、`source`、`dry_run`、`stats{inserted,updated,unchanged,deleted}`、`diff`、`diff_truncated`、`elapsed_ms` |
| 状态查询 | `GET /api/admin/trading-calendar/status`，同一鉴权；只读，返回 `ready` + 顶层核验字段（`coverage_start/end`、`last_success_at`、`last_error`、`days`、`trading_days`）+ 原始 `state`/`snapshot`，不触上游 |

**流程**：

```
POST /api/admin/trading-calendar/refresh
  → 校验管理凭证、Idempotency-Key
  → 获取进程内锁（失败 → 409）
  → get_router().fetch_calendar()（单一源 sina_trade_date；适配器超时）
  → 校验：返回非空、行数量级正常、coverage_start <= coverage_end（见下）
  → 把全部交易日展开成自然日，得到新快照
  → 读取现有行并比对，得到 diff
  → dry_run？→ 返回 diff，释放锁，结束
  → 调用 replace_trading_calendar(交易日数组, source)
       （函数内 DELETE + INSERT 自然日 + 更新 state，同一事务）
  → 成功：构建新 frozenset，原子替换内存引用
  → 失败：事务已回滚，旧快照与内存原样保留
  → 返回 stats + diff
```

人工核验顺序：先 `dry_run=true` 拿 diff，对照交易所公告确认，再正式调用。正式调用返回的 diff 应与预览一致；不一致说明期间源或 DB 变了，需重新核验。

**实现注意**：适配器调用是阻塞的，接口用同步 `def`（FastAPI 自动放线程池）或 `run_in_threadpool`，不要阻塞事件循环。

**人工拉取必须有超时**：适配器层强制 timeout；失败则保留旧数据、记 `state.last_error`，**不重试、不猜、不写入任何替代数据**。请求路径本身不触发拉取。

**异常数据的拒绝条件**（避免把坏数据写进唯一真相源）：

- `trading_days` 为空；
- 交易日数量明显偏少（< 1000 条；正常是 8000+）；
- `coverage_start > coverage_end`；
- `coverage_end < today`（源连当天都没覆盖，说明数据不可用）；
- 任一日期无法解析（解析层应已抛 `PARSE_ERROR`，不会走到这里）。

命中任一条 → **拒绝整次刷新**，不写库、不替换内存，返回 422。
不再有「只告警、继续写」或「保留旧行合并」的分支。

**失败映射**：

| 失败点 | HTTP | 行为 |
|---|---|---|
| 未配置管理凭证 | 503 | 接口默认关闭 |
| 凭证错误 | 401 | 不执行 |
| 已有拉取在跑 | 409 | 不排队、不重复请求上游 |
| 源失败（`SourceError` / `AllSourcesFailed`） | 502 | `tried` 原样返回；不写库 |
| 源超时 | 504 | 不写库 |
| 数据校验失败 | 422 | 不写库 |
| DB 事务失败 | 500 | 回滚，旧快照与内存不动 |

**熔断器行为**：`SourceRouter` 的域名熔断对日历同样生效。连续 3 次域名级失败
（`TIMEOUT` / `HTTP_403` / `HTTP_429` / `HTTP_5XX` / `CONNECTION_ERROR`）后，
源进入冷却（60s 起，半开失败翻倍，上限 30 分钟）。冷却期内 `refresh` **不会请求上游**，
直接返回 `AllSourcesFailed(tried=[])`。解析类失败（空数据/解析失败/结构漂移/代码异常）
不触发域名熔断，单源场景下仍会尝试源。进程重启会清空熔断状态；运维看到 `tried=[]`
时应等待冷却后重试，详见运维手册 §6。

**年度滚动**：源当前覆盖到 `2026-12-31`，下一年的日期要等源在国务院公布安排后更新。每月核验时检查 `coverage_end`：

- `coverage_end >= 次年 1 月 1 日`：正常，可以安排年度拉取；
- `coverage_end < today + 45 天`：WARNING，准备年度拉取；
- 进入 12 月后仍拿不到次年数据：ERROR，人工确认源与交易所公告。

年度拉取的前置条件不是「到了 12 月」，而是「源已经包含次年日期」。源未更新时拉取只会得到和旧数据一样的区间，跨年仍会断档。**不把覆盖区间外的日期猜成交易日或非交易日**。

### 4.5 调度与节奏（全人工）

| 时机 | 动作 | 判断依据 |
|---|---|---|
| 进程启动 | **只载入 DB**，不触网 | `trading_calendar_state` / `trading_calendar` |
| 每年 11–12 月 | 调用 `POST .../refresh` 一次 | 国务院下一年节假日安排已公布、源已包含次年日期 |
| 每月一次 | 调用 `GET .../status` 只读核验 | `coverage_end`、`last_success_at`、`last_error` |
| 交易所临时调整 | 人工确认后调用 `POST .../refresh` | 上交所/深交所公告 |
| 新环境首次部署 | 调用 `POST .../refresh` 一次 | 部署清单 |

**为什么取消定时刷新**：A 股交易日 = 周一至周五 − 法定节假日，周末从不开市；一年真正会变的情况只有「国务院公布下一年安排」和极罕见的临时调整。每日拉取只能把发现延迟从「月检」压缩到 1 天，而新年日历的生效日是 1 月 1 日、公告在 11 月前后，这几十天宽限期没有被压缩的必要。反过来，源自身出错时每日拉取只会把同一份错数据重复写一遍，反而制造「一直在刷新所以可靠」的错觉。正确性的最终保障是对着交易所公告**人工核验**。

**人工核验的权威依据**：国务院办公厅每年发布的《关于××年部分节假日安排的通知》，以及上交所/深交所的休市安排公告。

**并发控制**：接口用进程内 `threading.Lock` **非阻塞**获取；已有拉取在跑时直接返回 409，不排队、不重复请求上游。当前部署是单进程，进程内锁足够；若将来多 worker，需要换成 DB 级锁（如 `pg_try_advisory_lock`），否则每个 worker 都可能并发拉取。

### 4.6 错误与就绪状态

| 情况 | 行为 |
|---|---|
| 快照未载入（DB 为空/读取失败） | `ready=false` + ERROR；进程继续运行；`is_trading_day` / `is_trading_time` 抛 `CalendarUnavailable`；管理刷新接口仍可用 |
| 日期超出覆盖区间 | 抛 `CalendarOutOfCoverage`，错误信息带日期与覆盖区间；不返回 `False` / `True` |
| 人工拉取失败（源/校验/DB） | 旧快照与内存原样保留；`state.last_error` 记录；接口返回对应错误；不自动重试、不换源 |
| 旧快照覆盖不到今天 | 等价于「日期超出覆盖区间」→ 抛错；不因为「有旧数据」就猜测 |
| 多进程 | 刷新只在处理请求的进程内替换内存；其他进程仍用旧快照。当前单进程部署；多 worker 时需重启或引入共享版本号（Q5） |

**没有「降级模式」**：不存在「用工作日规则继续跑」的状态。要么快照就绪且覆盖该日期，
要么抛错。健康检查暴露的是 `ready` + `coverage` + `last_error`，不是模糊的 `degraded`。

**启动不因日历缺失而失败**：管理刷新接口与本服务同进程，崩进程会让「新环境首次拉取」
无法执行。正确做法是进程起来、`ready=false`、业务操作报错、运维调刷新接口。

**运维含义**：每月核验和 12 月年度检查仍是必须动作。若 12 月底仍未拿到次年数据，
12 月之后的日期查询会直接报错；是否暂停下单由人工决定（见 Q1），不再有兜底值掩盖。

### 4.7 与订单确认、净值调度的关系

| 消费者 | 用法 | 日历不可用/越界时 |
|---|---|---|
| `portfolio_service._next_trading_day` | 计算 `confirm_date` | 抛错；删除循环末尾 `return d + timedelta(days=1)` 的兜底 |
| `portfolio_service._is_trading_day` | 判断今天是否交易日 | 抛错；下单/确认接口返回 503，不猜分支 |
| `confirm_pending_orders(skip_trading_day_check=True)` | 启动补偿 | **必须先跳过日历调用**（`portfolio_service.py:1046` 目前无条件调用；原文写 1048，已核正），否则补偿也被日历卡住 |
| 净值批量更新（场外净值缓存 §4.5） | 判断 18:00–23:00 / 次日 00:00、01:00 是否运行 | 任务失败并记录，不空跑、不按星期几判断 |
| `is_trading_time` | 行情时段判断（场内轮询将删除） | 抛错；刷新任务失败并记录 |

**原则**：日历失真的影响面比行情大，因此宁可让请求失败，也不能猜一个值。
「失败」必须可观测：异常类型、覆盖区间、`state.last_error` 都能查到。

## 5. 与多源适配器的接缝

`TradingCalendarCache` **不直接调 akshare / HTTP**，只调用 `SourceRouter` 的 `calendar` 能力：

```python
from server.sources import CalendarData, get_router

data: CalendarData = get_router().fetch_calendar()
```

**单一源约束（2026-10-21 决策）**：注册表里 `CAP_CALENDAR` 只允许一个源
（`sina_trade_date`）。取数仍走 Router，但**不启用自动换源**：

- `sina_index_daily` 不注册。它由上证指数日 K 反推，只能覆盖已发生的交易日，
  给不出未来日期；作为「备源」会把 `coverage_end` 从年末静默缩到今天，直接破坏
  `_next_trading_day` 和跨年覆盖。
- 新增第二个 `CAP_CALENDAR` 源 = 启用自动换源 = 改变本文的「无兜底」语义，
  必须同时修改本文的覆盖校验与运维手册。
- 注册处（`server/sources/registry.py` 的 `default_sources()`）保留一句注释说明这一点。

| 责任 | 归属 |
|---|---|
| 用哪个源、akshare 混淆串解析、超时、失败分类 | 源层（`SinaTradeDateSource`） |
| 按能力选源、健康状态、熔断、错误包装 | `SourceRouter` |
| 快照落库、整表替换、内存快照、人工刷新入口、覆盖校验 | 本文 |
| 消费 `is_trading_day` / `is_trading_time` | `trading_calendar.py` 对外接口保持不变 |

**熔断器行为**：Router 的域名熔断对日历同样生效，详见 §4.4。它不是「换源」——
冷却期内会直接失败；解析类错误不触发域名熔断，仍会尝试源。

**为什么保留 Router**：统一入口，复用超时/解析/错误分类/日志；将来若出现同样能给出
未来日期的等价源，只需在注册表加一行。多源本身不是目的，当前也不存在等价备源。

| **Q8** | 入库窗口取「当年 1 月 1 日」还是保留完整上一年（§4.2.1） | 直接相关 | 否 | ✅ 已定（2026-10-21）：取消入库窗口，`coverage_start` = 源最早日期 |
| **Q9** | 历史日期查询返回 `UNKNOWN` 是否影响对账（§4.3） | 附带发现 | 否 | ✅ 已定：存全量历史后，历史日期可直接判断；仅早于源最早日期或晚于 `coverage_end` 时抛错 |
| **Q10** | 人工拉取写库后，运行中的服务如何感知（§4.3/§4.4） | 直接相关 | 否 | ✅ 已定：接口在服务进程内执行，写库后原子替换内存，**不需要重启** |

| **Q11** | 手工修正与整表替换冲突（§4.2.3、运维手册 §7） | 直接相关 | 否 | ✅ 已定：不引入 override 表；手工修正只在下次成功刷新前有效，`dry_run` 会显示冲突，由人决定是否 apply |
| **Q12** | 熔断器挡住人工刷新（§4.4、§5） | 直接相关 | 否 | ✅ 已定（2026-10-21）：接受该行为，不做 bypass；`tried=[]` 的含义、触发条件与冷却参数写入运维手册 §6 |
