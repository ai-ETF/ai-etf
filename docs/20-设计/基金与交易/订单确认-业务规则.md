## 0. 结论

> 一笔订单的确认 = 一次**资金守恒的原子记账**：解冻、建仓、建批、写流水、改订单、退尾差，全成或全不成。

围绕这句，下面四件事必须钉死：**哪天成交、状态能怎么走、钱怎么算、钱什么时候能看见。**

## 1. 口径

### 1.1 日期：六个「什么时候」，六个不同答案

混用一次就是一次错账。这张表是本文最值钱的部分。

| 术语 | 业务含义 | 由谁决定 |
|---|---|---|
| 受理日 `accepted_date` | 客户真正下单的那个交易日 T：15:00 前算当日，否则顺延到下一交易日。**它同时就是成交净值日** | 下单时按 `Asia/Shanghai` 算定并落库 |
| 份额确认日 `confirm_date` | 份额出现在持仓里的日期 = T + `confirm_delay` 个交易日。**只决定何时可见，不决定价格** | 下单时算定 |
| 到账日 `settle_date` | 赎回款变成可用现金的日期 = T + `redeem_settle_delay` 个交易日，遇非交易日**顺延** | 下单时算定 |
| 可赎回日 `available_date` | 该批份额最早能卖出的日期 = 份额确认日 + `redeem_available_delay` 个交易日 | 下单时算定 |
| 批次净值日 `nav_date` | 这批份额的成本按**哪天**的净值算 = 该买单的受理日 | 确认时写入批次 |
| 实际确认 / 到账时刻 | 跑批真正执行的钟点，只用于审计与排查，不参与任何计算 | 执行时 `now()` |

三条口径，顺序不能乱：

1. **成交价只认受理日，不认确认日。**
   15:00 之后下的单，价格是次一交易日的净值；确认延迟多久都不改变价格。
   > 依据真实代销口径：「申购按申请日 T 的净值成交，T+N 只是份额确认」。
   > 早期草稿把成交净值日取成 `confirm_date`，等于让客户以晚 1~2 天的价格成交。2026-10-30 修正。
   > 同时拆了列：原来 `trade_date` 一个名字同时表示「受理日」和「净值日」，这种同名不同义是错账的温床，现在是 `accepted_date` 和 `nav_date` 两个名字。

2. **持有期 = 卖出受理日 − 买入受理日**，即两个成交净值日之差。
   不能用跑批日，否则一次延迟确认就把持有期整体推后，费率按错档位算，钱直接算错。

3. **当天的净值没公布就等，不许拿邻近交易日的净值顶替。**
   净值不可用（未公布 / 拉取失败 / 无此净值）**不是拒单理由**，订单留在 `pending` 等下一轮。
   拒单是业务判定（暂停申购、超限、份额不足），不是技术故障。两者的区别一旦混掉，客户会莫名其妙被拒单。

### 1.2 状态机：为什么买入和卖出的终点不一样

```
pending ──认领──► processing ──成交(买)──► completed
   ▲                  │
   │                  ├──成交(卖)──► settling ──到账──► settled
   │                  ├──业务拒单──► rejected
   │                  └──需人工──► manual_review ──重排──► pending
   └──────租约超时回收──────┘
```

| 当前 | 允许的下一状态 | 含义 |
|---|---|---|
| `pending` | `processing` | 被某个 worker 认领 |
| `pending` | `rejected` | 业务拒单（同事务退款解冻） |
| `pending` | `manual_review` | 数据对不上，人不看不敢动 |
| `processing` | `completed` / `settling` | 买入 / 卖出成交 |
| `processing` | `pending` | 租约超时，放回重试 |
| `processing` | `rejected` / `manual_review` | 业务拒单 / 数据不一致 |
| `settling` | `settled` | 赎回款到账 |
| `manual_review` | `pending` | 管理员重排 |
| `completed` / `rejected` / `settled` | 不可再迁移 | 终态 |

规则背后的理由（这部分代码里读不出来）：

- **卖出比买入多一个 `settling`**：份额扣减（确认）和钱到账（结算）之间隔着 1~2 个交易日，这段"在途"是真实存在的。硬塞进一个状态，就只能靠 `settle_date` 字段猜"钱到底到没到"，猜错就是重复入账。
- **`manual_review` 不是终态**：它是"人没看完，先别动"，必须能放回去。设计成终态等于把一批订单永久冻结。
- **状态只能通过 RPC 迁**，应用层不许直接 `UPDATE status`：一旦留了这个口子，等于同时存在两套状态机。
- 状态迁移的数据库触发器是兜底，**要等灰度稳定后单独上线**，否则旧代码的 `pending → completed` 会被误伤。

### 1.3 费用与舍入

**费率是受理时的契约，不是确认时的市价。**

下单时把费率、申赎状态、确认/到账天数固化到订单上，确认时只读这份快照，不再查基金目录。
> 理由：基金公司随时调费率。若确认时才查最新规则，等于事后改价——已受理的订单会被重定价，客户和我们对账时都无法解释。

三个必须成立的等式（钱不能凭空多出或少掉一分）：

```
买入：amount == net + fee
      net    == qty * nav + residual      # residual >= 0，退回可用现金
卖出：gross - fee - cost == pnl
```

- **份额向下取整**，残差 `residual ≥ 0` 回现金。若改成四舍五入，残差可能为负，就必须从现金扣且不许扣成负数——那就得处理"客户余额不够扣残差"这种荒唐场景。
- **卖出费用按批次分段计算后求和**，不对总额二次舍入。逐段算、逐段舍，总额才不会吃掉几分钱。
- **卖出成本按批次剩余成本的比例消耗**，不按均价。否则部分赎回之后成本会漂移，盈亏永久失真。
- **记账以事务内重算的结果为准**；应用层算出来的金额只能用于给用户提示，不能落账。

### 1.4 批次（lot）与先进先出

- **持仓的事实来源是批次，不是持仓汇总行。** 汇总行是读模型，坏了可以从批次重建；反过来不行。
- 卖出按 `nav_date, created_at, id` 排序，只消耗 `available_date <= 卖出受理日` 的批次。先进先出不是偏好，是持有期费率的计算基础。
- **期初存量持仓是已知近似**：迁移时用原持仓的确认日当净值日，这部分批次的持有期会偏差 0~N 天，可能落到相邻费率档。存量一次性、规模有限，**接受不修**；新订单不受影响。

### 1.5 赎回到账与在途资金

- 卖出确认只扣份额、写流水，**现金一分不动**。钱在到账日才进可用现金。
- 这段在途必须**可见**：可用现金 + 冻结 + 在途赎回款 + 持仓市值 = 总资产。
  少算在途那一项，客户会看到"确认之后总资产凭空少了一截"，然后来问是不是吃了他钱。
- 确认晚于到账日时（跑批积压），确认成功后在同一轮直接完成到账，**只入账一次**。
- 到账日遇非交易日顺延（已定）。宁可晚一天到账，也不在非交易日假装能取钱。

### 1.6 货币基金

货基是唯一"净值不变、收益体现在份额上"的特例，规则集中在一处，不要散在确认 / 收益 / 自动申购三个地方各写一遍。

| 规则 | 为什么 |
|---|---|
| 净值恒为 1.0000，确认时不查净值表 | 摊余成本法，1 元面值不动，收益靠份额增长体现 |
| 买入金额全额计本金，成本价 = 1 | 没有申购费扣减导致的本金损耗（费率通常为 0） |
| 每日收益生成**零成本批次**，只增份额、不改本金 | 收益不是客户投入的钱。算进本金就永远算不对收益率；本金不变，收益率才等于累计收益 / 本金 |
| 赎回时成本即消耗的本金，盈亏含累计收益 | 否则客户看到的"赚了多少"只算了卖出当天的差价 |
| 自动申购仍生成 `pending` 订单，走统一确认 | 绕开统一流程就会长出第二套状态，两天后两边打架 |
| 收益入账的幂等键含入账日期 | 同日重跑不能重复发钱，这属于不可逆错误 |
| 可赎回日默认 2 天 | 待业务确认（U8） |

## 2. 不可违反的约束

这些不是建议，是违反就会算错钱或算不清账的红线：

1. **确认路径不触网、不修补数据、不依赖交易日历。** 全部日期在下单时算定，确认时只读。
2. **一笔订单的确认是一个事务。** 资金、份额、批次、流水、订单状态在同一事务内变更，失败整体回滚。禁止"写一半再补偿"。
3. **资金与份额在库内原子增减**，应用层不做"读出来加一下再写回去"。
4. **资金守恒**：账户总资产的任何变化，都必须能由「成交」「费用」「盈亏」三项解释。解释不了的差额就是 bug，不是"尾差"。
5. **成交价只认受理日**；该日净值缺失就等待，绝不改用邻近交易日净值。
6. **费率按受理时快照**，确认时不查最新规则。
7. **状态只经 RPC 迁移**，应用层不直接改状态列。
8. **幂等**：同一订单确认执行两次，结果必须与执行一次完全相同（金额、份额、流水条数都不变）。
9. **反推不可靠就进人工**：存量数据补不齐的，宁可留在 `manual_review`，不用猜测值填。

## 3. 怎么验证

验收清单在[需求 §3](../../10-需求/订单确认.md)，**此处不复制**——复制出来的清单会和需求文档互相打脸，且没人会同时更新两处。

但下面五条要优先变成**不变量测试**，因为它们错了不报错、只算错钱：

1. 任意订单：`amount == net + fee`，且 `qty * nav + residual == net`，`residual >= 0`
2. 任意时点：总资产的变化只能由成交盈亏和费用解释（含在途赎回款）
3. 同一笔订单确认跑两遍 ≡ 跑一遍
4. 15:00 前下单按当日净值成交；15:00 后按次一交易日
5. 净值未公布时订单仍为 `pending`，且资金、份额、流水**零变动**
