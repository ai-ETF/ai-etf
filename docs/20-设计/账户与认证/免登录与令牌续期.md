# 免登录（长效登录态）功能设计文档

> 版本：v1.1
> 日期：2026-10-11
> 状态：**后端已实现，单元测试通过**（前端由用户另行实现，见第七章）
> 前置依赖：`docs/20-设计/账户与认证/用户注册.md`、`docs/20-设计/账户与认证/登出与注销账号.md`
> 分支：`feature/persistent-login`（基于 `origin/dev` @ `60ed1b3`）

## 一、概述

### 1.1 背景

用户诉求：**登录一次后，长期不用重新登录**。

业界做法：**双 token + 滑动续期**。

- 短命 **access_token** 只用于日常请求，过期不心疼；
- 长命 **refresh_token** 持久化在本地，只在 access 过期时用一次，去换新的一对 token；
- 每次刷新都换发新的 refresh_token 并重置有效期（**轮转 / rotation**），因此"只要 7 天内打开过一次，就再续 7 天"。

关键前提：Supabase 的 `sign_in_with_password` 返回的 `session` 里本来就有 `refresh_token`（见 2.1 实测证据），后端 `LoginResponse` 没有透传它。

### 1.2 目标

1. 用户登录一次后，**活跃即可持续免登录**（滑动续期）。窗口沿用 Supabase 默认 refresh token TTL = **30 天**：即"连续 30 天不打开"才需重新登录。
2. access_token 有效期**维持 3600 秒不变**——不扩大被盗 token 的有效窗口，也不破坏现有登出即时失效能力。
3. 登出现有语义**一行不改**：`admin.sign_out(token, "global")` 撤销整条会话（含 refresh_token），登出后必须重新登录。
4. 前端在 token 失效时**自动静默续期**，用户无感；仅当 refresh_token 也失效才回登录页。
5. 不新增任何运维依赖（不引入 Redis、不加表）。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| access_token | Supabase 签发的 **无状态 HS256 JWT**，1 小时有效，随请求头 `Authorization: Bearer <t>` 下发 |
| refresh_token | Supabase 签发的**有状态**长期凭证，仅在 `auth.sessions` 表中有记录，用于换取新会话 |
| 轮转（rotation） | 每次 `refresh_session` 都签发**新的** refresh_token，旧的立即作废。`supabase/config.toml:171` 已开启 |
| 滑动续期 | 因轮转而产生的效果：每次刷新重置 refresh_token 的有效期，活跃用户永不掉线 |
| 双 token | access（短/内存）+ refresh（长/持久化）的组合模式 |

### 1.4 现状约束

| 约束 | 说明 | 来源 |
|---|---|---|
| access_token 无状态 | HS256 自验证，Supabase 无法提前撤销 → 依赖应用侧黑名单 | `server/auth/jwt_handler.py:17` |
| 黑名单不持久化 | `token_store` 纯内存，**进程重启即清空** | `server/auth/token_store.py:8` 自述 |
| refresh_token 有状态 | 存于 Supabase `auth.sessions`，可被服务端撤销 | Supabase Auth |
| 轮转已开启 | `enable_refresh_token_rotation = true` | `supabase/config.toml:171` |
| 轮转宽限窗口 | `refresh_token_reuse_interval = 10`（秒） | `supabase/config.toml:174` |
| 登出作用域 | `admin.sign_out(token, "global")` 撤销该用户**所有**会话 | `server/services/auth_service.py:135` |
| 后端不存 token | 登录/登出均为无状态透传，后端无 session 表 | 现有实现 |

## 四、核心设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| **方案层级** | **L2 双 token 最小实现** | 唯一能同时满足"免登录"与"登出即时失效"的方案，见 4.1 备选方案对比 |
| 登录态载体 | access（1h，内存）+ refresh（长，前端持久化） | 业界通行；Supabase 原生支持 |
| refresh 端点路径 | `POST /api/secure-chat/refresh`，**公开接口（不需 JWT）** | 调用它时 access 恰恰已过期，带 JWT 无意义；与 login/register 同模块，对称 |
| 鉴权依赖复用 | **不复用** `get_current_user` | access 已过期无法验签；refresh_token 本身就是凭证 |
| 后端是否保存 refresh_token | **不保存**。无状态透传 | refresh_token 的状态由 Supabase `auth.sessions` 维护；后端加存储等于重复实现会话管理 |
| access 有效期 | **保持 3600 秒不变** | 撤销窗口不扩大；`token_store` 内存局限的影响面维持现状 |
| 轮转（rotation） | **保持开启** | 滑动续期的实现基础；每次刷新作废旧 token，降低泄露风险 |
| 免登录窗口 | **滑动续期，窗口 = 30 天**（Supabase 默认 refresh TTL，不改配置） | 原定 1 周需在生产实例设 `GOTRUE_REFRESH_TOKEN_EXPIRY`；用户确认默认 30 天可接受，故**本方案零配置变更**。语义：30 天内活跃即无限续期，"连续 30 天不打开"才需重新登录 |
| 刷新失败处理 | 返回 401，前端**清空本地凭证并跳登录页** | refresh_token 已被轮转作废 / 已过期 / 已登出，唯一出路是重新登录 |
| 登出 | **不改动** | `sign_out(global)` 恰好撤销整条会话，语义完全正确 |
| 日志 | **禁止记录 refresh_token** | 长期凭证等同密码，落日志即泄漏 |

## 五、流程设计

### 5.1 首次登录 / 注册（一次性）

```
前端                          后端 (FastAPI)                    Supabase Auth
 │                              │                                  │
 ├─ POST /secure-chat/login ───→│                                  │
 │   {email, password}          ├─ sign_in_with_password ─────────→│
 │                              │←── AuthResponse{session,user} ───┤
 │                              │    session 含 access + refresh    │
 │←── 200 {access_token,        │                                  │
 │        refresh_token, ◄──────┤  ★ 本次新增透传                  │
 │        expires_in, user_id}  │                                  │
 │                              │                                  │
 ├─ 持久化 refresh_token         │                                  │
 ├─ 内存保存 access_token        │                                  │
 └─ 进入应用                     │                                  │
```

### 5.2 日常请求与静默续期（核心）

```
前端                                后端 (FastAPI)                Supabase Auth
 │                                    │                              │
 ├─ 请求受保护接口                      │                              │
 │   Authorization: Bearer <access>   │                              │
 │                                    ├─ verify_supabase_token       │
 │←── 200 正常返回 ────────────────────┤  （access 有效）              │
 │                                    │                              │
 │  …… 1 小时后 ……                    │                              │
 ├─ 请求受保护接口                      │                              │
 │←── 401 令牌无效或已过期 ─────────────┤  （access 过期）              │
 │                                    │                              │
 ├─ 触发续期（★ 全局单例锁，见 7.3）    │                              │
 ├─ POST /secure-chat/refresh ────────→│                              │
 │   {refresh_token}                  ├─ refresh_session(refresh) ──→│
 │                                    │←── 新 session ───────────────┤
 │                                    │    （rotation：refresh 也换新） │
 │←── 200 {access_token,              │                              │
 │        refresh_token, ◄────────────┤  ★ 两个都返回                 │
 │        expires_in, user_id}        │                              │
 │                                    │                              │
 ├─ 覆盖保存两个 token                  │                              │
 ├─ 重放原请求 ───────────────────────→│                              │
 │←── 200 正常返回 ────────────────────┤                              │
 │                                    │                              │
 │  （若 refresh 返回 401）             │                              │
 └─ 清空本地凭证 → 跳登录页             │                              │
```

**滑动续期的效果**：第 5.2 步中，refresh_token 的有效期在每次刷新后重置。用户只要在 7 天内打开过小程序（哪怕是第 6 天），就再获得完整的 7 天。

### 5.3 登出（不改动，仅说明其正确性）

```
前端                          后端                             Supabase Auth
 │                              │                                  │
 ├─ POST /secure-chat/logout ──→│                                  │
 │   Authorization: Bearer <t>  ├─ revoke(t, exp)  加入本地黑名单    │
 │                              ├─ admin.sign_out(t,"global") ─────→│ 撤销整条会话
 │←── 200 ──────────────────────┤                                  │ （含 refresh_token）
 │                              │                                  │
 └─ 前端清空本地 access + refresh_token                             │
```

登出后：原 access_token 1 小时内被本地黑名单拦截；refresh_token 已在 Supabase 侧作废，**即使前端未清干净也无法续期**。这是双 token 方案相对 L1 的核心优势。

## 六、API 接口设计

### 6.1 登录（响应新增字段）

```
POST /api/secure-chat/login（公开）
```

**响应 `200`：**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "v1.MRqX...",          // ★ 新增，必填
  "token_type": "bearer",
  "user_id": "uuid-string",
  "expires_in": 3600
}
```

### 6.2 注册（响应新增字段）

```
POST /api/secure-chat/register（公开）
```

**响应 `201`（auto-confirm 模式，即当前线上模式）：**

```json
{
  "success": true,
  "needs_email_confirmation": false,
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "v1.MRqX...",          // ★ 新增，可选（邮箱确认模式下为 null）
  "user_id": "uuid-string",
  "expires_in": 3600,
  "message": "注册成功，已自动登录"
}
```

### 6.3 刷新登录态（★ 新增）

```
POST /api/secure-chat/refresh（公开，无需 JWT）
Content-Type: application/json
```

**请求体：**

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| refresh_token | string | ✅ | 登录/注册/上次刷新返回的 refresh_token |

```json
{ "refresh_token": "v1.MRqX..." }
```

**响应 `200`：**

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "v1.NEWTOKEN...",       // ★ rotation 开启，与请求体不同，必须覆盖保存
  "token_type": "bearer",
  "user_id": "uuid-string",
  "expires_in": 3600
}
```

**响应 `401`（以下情况统一处理）：**

```json
{ "detail": "登录态已失效，请重新登录" }
```

触发条件：refresh_token 无效 / 已过期 / 已被轮转作废（重复使用）/ 已被登出撤销。

> ⚠️ **前端注意**：rotation 开启后，一个 refresh_token **只能成功使用一次**。若前端并发调用两次刷新，第二次会拿到 401，进而把用户踢下线。必须实现全局单例锁，见 7.3。

## 七、前端对接要求（前端不在本仓库）

> 前端（小程序）代码不在 `ai-etf` 仓库内（仓库中仅有 `src/types/supabase.ts`，`package.json` 为空壳）。本章是交给前端的**接口契约**，其落地情况计入 Q4。

### 7.1 持久化 refresh_token

- **必须**写入本地持久化存储（小程序：`uni.setStorageSync('refresh_token', ...)` / `wx.setStorageSync`），不能只放内存或 Pinia/Vuex。
- access_token 可放内存，进程结束即丢，无妨。
- 小程序 storage 在用户不主动删除小程序、不清缓存的前提下**永久保留**，这正是"长期免登录"能成立的基础。

### 7.2 全局 401 拦截 + 自动重放

在请求封装层统一处理：

1. 响应 401 → 判断是否为"access 过期"（而非登录接口本身的 401）；
2. 有 refresh_token 则调 `/refresh`，成功后**覆盖保存两个新 token**，并**重放**原请求；
3. refresh 也失败（401）→ 清空本地两个 token，跳登录页。

### 7.3 并发刷新加锁（最容易踩的坑）

**问题**：小程序冷启动时常并发数个请求，若同时 401，会同时触发多次 `/refresh`。rotation 下只有一个能成功，其余全部 401 —— 用户被无故踢下线。

**要求**：用**全局单例 Promise** 保证同一时刻只有一个刷新在途，其余调用方 await 同一个 Promise：

```js
// 伪代码
let refreshing = null;
async function ensureRefreshed() {
  if (refreshing) return refreshing;      // 已在刷新 → 共享同一个 Promise
  refreshing = doRefresh().finally(() => { refreshing = null; });
  return refreshing;
}
```

### 7.4 登出时清理

调用 `/logout` 成功后，**必须同时清空**本地的 access_token 与 refresh_token。

## 九、错误处理

`auth_service.refresh_session_token` 的异常映射（沿用 `auth_service.py:32` 的 `_AUTH_ERROR_MAP` 风格）：

| Supabase 异常 / 场景 | HTTP | 文案 | 说明 |
|---|---|---|---|
| 刷新成功 | 200 | —— | 返回新 token 对 |
| `AuthSessionMissingError`（请求体为空/缺字段） | 400 | 缺少 refresh_token | 参数错误，前端 bug |
| refresh_token 无效 / 过期 / 已轮转作废 | 401 | 登录态已失效，请重新登录 | **主路径**，前端应清理本地并跳登录 |
| 请求过于频繁（`over_request_rate_limit`） | 429 | 请求过于频繁，请稍后重试 | Supabase 侧限流 |
| Supabase 未就绪 | 500 | 数据库连接未就绪 | 与现有 login 一致 |
| 其他未知异常 | 502 | 刷新服务暂时不可用，请稍后重试 | 兜底，原始异常记日志 |

## 十、安全与边界

1. **refresh_token 等同密码**：拿到它即可长期冒充用户。禁止写入日志（含 debug 级）、禁止返回给非本人。
2. **access 有效期不变**：仍为 3600 秒，被盗 token 的可用窗口与现状一致，登出即时失效能力完好。
3. **refresh 端点无 JWT 鉴权是刻意设计**：调用时 access 必已过期；凭证即是 refresh_token 本身。靠 Supabase 侧的签发/校验与限流防护。
4. **轮转降低重放风险**：refresh_token 每次使用即作废，被窃取的旧 token 在真实用户下一次刷新后立即失效。
5. **登出为全局撤销**：`sign_out(global)` 会终止该账号所有设备会话（见 Q5）。
6. **前端存储是明文**：小程序 storage 不加密，root/调试工具可读。这是所有小程序方案的共同边界，非本设计引入；如需更高安全等级需配合设备绑定，超出本次范围。
7. **不扩大攻击面**：不新增表、不新增运维依赖、不改动鉴权链路。

|---|---|---|---|
| 登录透传 refresh_token | Fake session 含 refresh_token | 响应体含该字段且值一致 | ✅ |
| 登录 session 为空 | session 为 None 分支 | 返回 401（现有行为不回归） | ✅ |
| 注册透传 refresh_token | auto-confirm 模式的 Fake session | 响应体含该字段 | ✅ |
| 刷新成功 | 合法 refresh_token | 200，返回新的 access + refresh 对 | ✅ |
| 刷新返回值原样透传 | Fake 返回 new-refresh | 响应 refresh_token == `new-refresh`（**不得回显请求中的 token**） | ✅ |
| refresh_token 无效 / 已轮转 / 过期 | Fake 抛 400/401/403 的 `AuthApiError` | 401 | ✅ |
| 失效判定不跨越 5xx | Fake 抛 5xx + 失效类 code | 502（不得判为登录失效） | ✅ |
| 刷新触发限流 | Fake 抛 `over_request_rate_limit` | 429 | ✅ |
| 网络类故障 | Fake 抛 `AuthRetryableError` | 502，且日志走「网络异常」分支 | ✅ |
| Supabase 未就绪 | `get_supabase()` 返回 None | 500 | ✅ |
| 空 refresh_token | 传 `"   "` | 400，且**不调用** Supabase | ✅ |
| **不泄漏日志** | 异常 message 内含 token | 日志中不含 refresh_token 明文 | ✅ |

关键实现取舍（与设计一致处不再赘述）：

- **`AuthRetryableError` 单独映射为 502，而非 401。** 这是本次实现里最要紧的一处：网络/网关类故障若被归成 401，前端会按契约清空本地凭证，用户在服务恢复后仍被登出。已在 §4 接口文档中以 ⚠️ 显式告知前端。
- **`AuthApiError` 的 `e.code` / `e.status` 记日志，`e.message` 不记。** GoTrue 的 message 可能回显 token 片段；有专门用例（`test_刷新_日志不得泄漏refresh_token`）守住这条线。
- **空 refresh_token 在应用层提前拦截（400），不落到 Supabase。** 用例断言 `refresh_calls == []`，确保无谓的网络往返。

### 14.2 计划外改动：`gen_index.py`（Q7）

按项目「新增接口规范」第 4 步运行校验时发现两个真实缺陷，**若不管，本次新增接口的生成行必错**（故按规则 5 的「不解决就无法完成」纳入本轮）：

|---|---|---|
| 模块归组错误 | `module_for("/api/secure-chat/refresh")` → `02-对话与会话.md` | 本次新增接口触发 |

实现过程中由测试反查出并修掉的一处设计漏洞，记录在案：

> 初版 `_REFRESH_DEAD_CODES` 判定没有状态码边界，写法是
> `if e.status in (400,401,403) or e.code in _REFRESH_DEAD_CODES`。
> 这意味着一个 **5xx 响应只要带上 `session_expired` 之类的错误码就会被判为「凭证失效」**，
> 与本章「5xx 一律不登出」的原则直接冲突。已改为 `if e.status < 500 and (...)`，
> 并加了 `test_刷新_失效判定不跨越5xx边界` 三条用例（含 500/503 反例）锁死该边界。
>
> 该缺陷是我在补强测试时发现的：最初的网络异常用例只断言 `502`，而通用 `Exception`
> 兜底同样返回 `502` —— **用例无论分支对不对都会通过**。已改为同时断言日志文案
> （`网络异常` 必须在、`未知异常` 必须不在），确保走的是 `AuthRetryableError` 分支。
