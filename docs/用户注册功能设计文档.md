# 用户注册功能设计文档

> 版本：v1.1
> 日期：2026-09-16
> 状态：已实现（含 §11 线上故障修订）
> 前置依赖：现有 Supabase Auth 登录体系（`POST /api/secure-chat/login`）

---

## 一、概述

### 1.1 背景

系统目前已实现**登录**：`POST /api/secure-chat/login` 调用 Supabase Auth 的 `sign_in_with_password`，校验邮箱密码后返回 JWT。用户身份 = Supabase `auth.users` 的 UUID，后续所有受保护接口（自选股、风险测评、会话、持仓等）都通过 JWT 的 `sub` 字段识别用户。

但当前**没有注册接口**：新用户只能通过 Supabase 控制台或 Admin API 手动创建账号，无法自助完成注册并直接使用应用。

### 1.2 目标

1. 提供**自助注册**接口，新用户可注册账号。
2. 注册成功后**直接返回 JWT 登录态**，前端无缝进入应用。
3. 复用 Supabase Auth 托管密码哈希、邮箱唯一性、会话签发，**不自行实现**任何账号安全逻辑。

### 1.3 配置约束（设计要求，非"现状假设"）

| 配置 | 设计要求 | 对设计的影响 |
|---|---|---|
| `enable_signup` | **`true`** | Supabase 允许邮箱密码注册；若为 `false`，注册接口返回 403 |
| `enable_confirmations`（Dashboard 中为 **Confirm email**） | **`false`（必须关闭）** | **注册即激活**，`sign_up` 直接返回 session，无需邮箱确认 |
| 邮件通道（SMTP） | 不依赖 | 关闭 `Confirm email` 后注册不发任何邮件，SMTP 开关无关紧要 |
| 密码最小长度 | 8 位 | 与 Supabase 端 `minimum_password_length` 保持一致 |

> ⚠️ **本表原先把 `enable_confirmations` 写成"当前值 `false`"是错的** —— Supabase 该项**默认就是开启**，线上实际为 `true`，整个注册功能据此直接失效。踩坑经过与修复见 [§11 线上故障：注册一律 502](#十一线上故障注册一律-5022026-09-16)。

## 二、核心设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 接口路径 | `POST /api/secure-chat/register`，与登录同模块 | 登录已挂在 `secure_chat` 模块（prefix `/secure-chat`），注册与其对称；改动最小，不破坏现有路由 |
| 实现方式 | 调用 `supabase.auth.sign_up({"email", "password"})` | 与现有 `sign_in_with_password` 同一体系，密码哈希、邮箱唯一、会话签发全部由 Supabase 托管 |
| 邮箱确认 | v1 **不开启**确认（`Confirm email` 必须关闭），代码仍**兼容**确认模式 | 设计要求是"注册即激活"，注册即返回 JWT，前端体验最顺；代码按 `session` 是否存在兼容配置漂移，但拿到空 `session` 时会打 WARNING 告警（§11） |
| 用户资料表 | v1 **不新增** `profiles` 表 | 所有业务表（watchlist / chats / user_risk_answers / positions 等）已按 `auth.users` UUID 关联，注册即可用 |
| 重复邮箱 | 返回 `409` | 清晰告知用户，优于模糊处理 |
| 认证模块归属 | 逻辑抽到 `server/services/auth_service.py` | 与 risk 模块「api 放路由、service 放逻辑」的惯例一致 |

## 三、注册流程设计

```
前端                        后端 (FastAPI)                      Supabase Auth
  │                            │                                   │
  ├─ POST /secure-chat/register→ │                                   │
  │   {email, password}         ├─ 校验：邮箱格式、密码≥8位          │
  │                              ├─ sign_up({email, password}) ─────→│
  │                              │  （幂等：已注册邮箱会抛异常）      │
  │                              │←─ session + user ─────────────────┤
  │                              ├─ session 存在（auto-confirm）？    │
  │                              │   ├─ 是 → 返回 access_token+user_id │
  │                              │   └─ 否 → 返回「请查收确认邮件」     │
  │←── 201 注册结果 ─────────────┤                                   │
```

两种模式说明：

- **当前模式（auto-confirm）**：`sign_up` 返回 `session`（含 `access_token` 与 `user`），注册成功即完成登录，前端直接用返回的 token 进入应用。
- **确认模式（未来若开启）**：`sign_up` 只返回 `user`，不返回 `session`，需提示用户查收邮箱确认链接，确认后再走登录接口。

## 四、API 接口设计

### 4.1 注册

```
POST /api/secure-chat/register（公开，无需 token）
Content-Type: application/json

{
  "email": "user@example.com",
  "password": "your-password"
}
```

**请求体：**

| 字段 | 类型 | 必需 | 说明 |
|---|---|---|---|
| email | string | ✅ | 邮箱，格式校验 |
| password | string | ✅ | 密码，至少 8 位 |

**响应（auto-confirm 模式）`201`：**

```json
{
  "success": true,
  "needs_email_confirmation": false,
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "bearer",
  "user_id": "uuid-string",
  "expires_in": 3600,
  "message": "注册成功，已自动登录"
}
```

**响应（邮箱确认模式）`201`：**

```json
{
  "success": true,
  "needs_email_confirmation": true,
  "access_token": null,
  "user_id": null,
  "message": "注册成功，请前往邮箱完成验证后登录"
}
```

**Pydantic 模型（与现有 `LoginResponse` 同风格）：**

```python
class RegisterRequest(BaseModel):
    """注册请求"""
    email: str = Field(..., description="邮箱")
    password: str = Field(..., description="密码（至少 8 位）")

class RegisterResponse(BaseModel):
    """注册响应"""
    success: bool
    needs_email_confirmation: bool
    access_token: Optional[str] = None
    token_type: str = "bearer"
    user_id: Optional[str] = None
    expires_in: Optional[int] = None
    message: str
```

### 4.2 与登录的关系

- 登录接口 `POST /api/secure-chat/login` **保持不变**。
- 前端引导：注册成功（auto-confirm 模式）直接用返回的 `access_token` 作为登录态；确认模式下提示用户查收邮件，确认后走登录接口。

## 五、数据存储设计

| 数据 | 存储位置 | 说明 |
|---|---|---|
| 用户主数据（邮箱、加密密码、UUID） | Supabase `auth.users` | 由 Supabase Auth 管理，应用不落库、不改动结构 |
| 业务数据 | watchlist / chats / user_risk_answers / positions 等既有表 | 均以 `user_id = auth.users UUID` 关联，注册即可用，无需迁移 |
| 用户资料（昵称/头像/手机号） | 无 | v1 不涉及；若后续需要，通过 Supabase CLI 迁移新增 `profiles` 表并关联 `auth.users` |

> 无额外建表需求，本次注册功能**不涉及数据库迁移**。

### 6.2 auth_service 错误映射要点

```python
def register_user(email: str, password: str) -> dict:
    supabase = get_supabase()
    try:
        result = supabase.auth.sign_up({"email": email, "password": password})
    except Exception as e:
        # Supabase 对已注册邮箱会抛 "User already registered"
        # 需匹配错误信息区分：重复邮箱 → 409；其他 → 502
        ...
    return {"session": result.session, "user": result.user}
```

## 七、错误处理

| 场景 | HTTP 状态码 | message |
|---|---|---|
| 邮箱格式非法 | 400 | 邮箱格式不正确 |
| 密码长度不足 8 位 | 400 | 密码长度至少 8 位 |
| 邮箱已注册 | 409 | 该邮箱已注册，请直接登录 |
| Supabase 服务异常 / 网络异常 | 502 | 注册服务暂时不可用，请稍后重试 |

> 与现有登录的错误语义保持一致：登录失败 `401`，注册重复 `409`。

---

## 八、安全与边界

1. **密码安全**：密码由 Supabase 哈希存储，应用层不落盘、不打日志。
2. **传输安全**：线上经 Caddy（HTTPS）访问，注册请求全程加密。
3. **不泄露敏感信息**：响应不返回密码相关字段；错误信息不回显用户输入。
4. **防批量注册（可选）**：v1 依赖 Caddy / Supabase 层策略；若需更严，可在注册接口加限流。
5. **邮箱真实性**：当前未开邮箱确认，无法校验邮箱是否真实存在；若未来需要实名或防滥用，开启 `enable_confirmations` 即可，代码已兼容。

## 十一、线上故障：注册一律 502（2026-09-16）

### 11.1 现象

前端反馈"后端注册返回 502"；**单元测试全绿**（334 passed），但线上注册**从未成功过一次**。

### 11.2 排查（服务器日志实证）

```bash
journalctl -u fastapi --no-pager | grep -iE '注册|register'
```

```
注册失败: code=over_email_send_rate_limit, status=429, message=email rate limit exceeded
POST /api/secure-chat/register HTTP/1.1" 502 Bad Gateway
```

| 指标 | 值 |
|---|---|
| 日志中 `用户注册成功` 出现次数 | **0** |
| 失败 code 统计 | `over_email_send_rate_limit` × 5、`email_address_invalid` × 2 |
| 后端进程 `fastapi.service` | active，未崩溃（**不是** Caddy 网关 502） |

### 11.3 根因

线上 Supabase 项目的 **`Confirm email` 是开启状态**（Supabase 该项默认即为开启），与 §1.3 的设计要求相反：

```
sign_up 需要邮箱确认 → Supabase 尝试发确认邮件
  → custom SMTP 未启用，走内置邮件服务（每小时仅个位数封，且只能投递给项目成员邮箱）
  → GoTrue 返回 429 over_email_send_rate_limit
  → auth_service 的错误映射未覆盖该 code，落到兜底分支
  → 502「注册服务暂时不可用，请稍后重试」   ← 语义错误：这是配置问题，重试无用
```

### 11.4 为什么单元测试没拦住

测试用的是 `FakeSupabase` 替身（`sign_up` 被伪造），只验证"Supabase 返回 X → 映射成哪个状态码"这套**映射逻辑**，与真实 Supabase 会不会成功无关。

更关键的是，当时 `test_其他AuthApi错误_抛502` 一条用例把 `over_request_rate_limit` **断言为 502** —— 测试恰好把错误行为锁死了，全绿与"线上 100% 失败"完全兼容。

> **教训**：替身测试只能证明映射逻辑自洽，**不能证明外部依赖的配置正确**。外部服务（Supabase Auth / SMTP / 第三方 API）的配置类假设，必须做一次真实端到端验证，或至少在文档里标注"未验证"。

### 11.5 修复

| # | 位置 | 改动 |
|---|---|---|
| 1 | **Supabase 控制台**（人工） | Authentication → Sign In / Providers → Email → **关闭 `Confirm email`**。这是真正让注册跑通的一步 |
| 2 | `server/services/auth_service.py` | 新增 `_AUTH_ERROR_MAP`：`over_*_rate_limit` → **429**、`signup_disabled`/`email_provider_disabled` → **403**、`email_address_not_authorized` → **503**；502 只留给未覆盖的未知错误 |
| 3 | `server/services/auth_service.py` | 注册成功但 `session` 为空时打 **WARNING**（配置漂移时立刻可见，避免又变成"点了注册没反应"的哑巴故障） |
| 4 | 单元测试 | 上述映射各补一例；原"限流 → 502"用例改为"限流 → 429"，并新增"注册无 session → 告警"回归用例 |

### 11.6 验证方式

```bash
curl -X POST "https://ai-etf.xyz/api/secure-chat/register" \
  -H "Content-Type: application/json" \
  -d '{"email": "<测试邮箱>", "password": "<8位以上>"}'
# 期望: 201，且 needs_email_confirmation=false、access_token 非空
# 若仍返回 needs_email_confirmation=true → Confirm email 没关干净
```

> 排查该故障时的关键区分：**我们自己返回的 502**（JSON body `{"detail":"注册服务暂时不可用，请稍后重试"}`）与 **Caddy 网关的 502**（HTML 页面、无 JSON body，且所有接口一起挂）是两回事，前者是业务错误，后者是进程问题。
