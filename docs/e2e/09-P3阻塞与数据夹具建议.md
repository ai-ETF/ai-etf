## 3. 阻塞二：行情数据拉不到

### 3.1 现象（2026-10-01 从 Windows 侧实测）

```
GET /api/market/search?keyword=510300  -> 200   33ms  {"total":0,"items":[]}
GET /api/market/search?keyword=沪深300  -> 200    3ms  {"total":0,"items":[]}
GET /api/market/search?keyword=110020  -> 200    3ms  {"total":0,"items":[]}
GET /api/market/spot/510300            -> 200   27ms  {"data":null,"error":"未找到基金代码: 510300"}
GET /api/market/detail/510300          -> 200   31s   realtime=null  nav_history=[]
GET /api/market/kline/510300           -> 200         items=60      ← 只有这条有数据
```

参数名不是问题：用 `?q=` 会返回 422 且明确说 `Field required: keyword`，说明 `keyword` 是对的。

### 3.2 缓存为什么是空的

**search / spot / detail.realtime 这三样全部来自同一个内存缓存 `_spot_dict`：**

| 出口 | 依据 |
|---|---|
| `search_etf` → `d = self._ensure_spot_dict(); if not d: return []` | `server/services/finance_api_service.py:620-622` |
| `query_spot`（`/spot` 用）→ `d = self._ensure_spot_dict(); return d.get(fund_code)` | `server/services/finance_api_service.py:267-278` |
| `query_detail` 的 realtime → `spot = self.query_spot(fund_code)` | `server/services/finance_api_service.py:510-514` |

而 `_ensure_spot_dict()` **只读不拉**（`finance_api_service.py:250-254`：`if cls._spot_dict is not None: return ...; return {}`）。
唯一填它的地方是 `refresh_spot_cache()`（`finance_api_service.py:1089`），它调
`ak.fund_etf_spot_em()`（`finance_api_service.py:1104`）。

**这个函数没有文件缓存兜底**——失败只 `return False`（`finance_api_service.py:1111-1115`），
旧缓存（这里是 None）原样保留。所以**拉取失败 = 行情一直是空的**。

填充时机只有两条（`server/services/spot_cache_scheduler.py`）：
- 启动预热 `_warmup_cache()` —— `spot_cache_scheduler.py:23-31`，由 `start_scheduler()` 在 `:154`
  用 `asyncio.ensure_future` 触发（不阻塞启动）
- 每 30 秒的定时任务 —— `IntervalTrigger(seconds=30)`（`:105-111`），直接调
  `FinanceApiService.refresh_spot_cache`

**今天 10-01 不在 9:30–15:00 交易时段内**，所以主要就看启动预热那一下——那一下失败了。

> ⚠️ **2026-10-03 合并 dev（PR #18）后这段实现变了，上面那句要重读。**
> 调度器自己的 `_is_trading_time()`（原 `spot_cache_scheduler.py:21`）**已被删除**，
> 交易时段判断搬进了 `refresh_spot_cache` 内部 ——
> `finance_api_service.py:1097`：`if not is_trading_time(beijing_now()) and cls._spot_dict is not None:`。
> 日历来自**全项目唯一来源** `server/services/trading_calendar.py`
> （`is_trading_time` `:98`、`beijing_now` `:37`、日历源 `ak.tool_trade_date_hist_sina()` `:56`）。
>
> **差别在条件的后半截**：现在只有「非交易时段 **且缓存已有**」才跳过。
> 缓存空着时（首次启动，或一直拉失败），**每 30 秒都会真去拉一次，不看时段**。
> 所以合入之后夜间不再是"只试一次"，而是**整夜每 30 秒重试、整夜全败** ——
> 这反而更硬地证明了 §3.1（是**拉不到**，不是**没去拉**）。
> 对夹具是好事：夹具装晚了，那个 30 秒任务也会用夹住的函数把缓存填上。

### 3.3 为什么 K 线看起来是好的（这是最大的障眼法）

`kline/510300` 返回了 60 条数据，第一眼会以为「行情是通的，只有搜索坏了」。**不是。**

`query_kline`（`finance_api_service.py:394`）**有文件缓存**：
- 目录 `KLINE_CACHE_DIR = "/tmp/etf_kline_cache"` —— `finance_api_service.py:16`
- TTL `KLINE_CACHE_TTL = 86400`（一天）—— `finance_api_service.py:17`
- 命中就直接 `pd.read_json`，**根本不打网络** —— `finance_api_service.py:869-885`

实测 `/tmp/etf_kline_cache/510300_daily.json` 的 mtime 是 **2026-10-01 23:35**——
那一下**恰好拉成功了**，写下了这个文件。之后连它也拉不动了。

> **结论：「kline 通、spot 不通」不代表 spot 的代码有问题，只代表 kline 有缓存文件挡着。**
> 排查时千万别把这个当成「网络没问题」的证据。

### 3.4 网络层：不是断网，是东财的 API 路径被挡

从 **Windows 侧** curl（换一套网络栈，排除 WSL 的嫌疑）：

| 请求 | 结果 |
|---|---|
| `https://push2delay.eastmoney.com/`（根路径） | **404** ← DNS/TCP/TLS 全正常，主机是通的 |
| `https://push2delay.eastmoney.com/api/qt/clist/get?...` | `000` 连接被重置 |
| `https://push2.eastmoney.com/api/qt/stock/get?secid=1.510300...` | `000` |
| `https://push2his.eastmoney.com/.../kline/get?...` | `000` |
| `https://www.baidu.com`（对照） | `200` |

WSL 侧结果**完全一致** → **不是 WSL 网络的问题，是这台机器到东财行情 API 被挡。**

在项目 `.venv` 里直接调 `ak.fund_etf_spot_em()`：
- 重试 **6 次**（间隔 15s）**全部失败**，报 `ConnectionError: Remote end closed connection without response` 与 `ReadTimeout`
- 冷却 120 秒后再试，**仍然失败** → 不是瞬时限流

根路径给 404、API 路径被重置，是典型**针对 API 的反爬/IP 拦截**。
具体是东财封了这个出口 IP、还是这个网络到东财链路有问题，**需要你们判断**——我只负责把现象钉死。

`akshare` 版本 `1.18.64`；该函数打的地址是
`https://push2delay.eastmoney.com/api/qt/clist/get`
（`.venv/lib/python3.12/site-packages/akshare/fund/fund_etf_em.py:51`），
且带正常浏览器 UA（`akshare/utils/cons.py:8`），所以**不是 UA 问题**。

## 5. 行情数据夹具 —— ✅ 2026-10-03 已实现

**出发点是**：E2E 本来就不该把结论押在第三方行情源上。真实链路验证要验的是
「页面 → store → request → API → 渲染」这一串**我们自己的**逻辑，
不是东财今天通不通。这个依赖还让用例变成了**不可重复**的（网络一抖全红）。

### 5.1 怎么用（三步）

```bash
# ① 生成快照（默认是合成数据，不需要网络；文件已进版本库，一般不用重新生成）
poetry run python docs/e2e/scripts/make_market_snapshot.py

# ② 带着开关启动后端
E2E_MARKET_FIXTURE="$PWD/docs/e2e/fixtures/market_snapshot.json" \
  poetry run uvicorn server.app:app --port 8000

# ③ 验证一下数据真的进来了（应该看到 3 只，而不是 0 只）
curl -s "http://127.0.0.1:8000/api/market/search?keyword=300"
# → {"total":1,"items":[{"code":"510300","name":"沪深300ETF","price":3.876,...}]}
```

启动日志里会出现这一行，是夹具生效的标志：

```
[market_fixture] ⚠️ 行情夹具已启用：akshare 的 8 个行情函数已被固定快照替换（快照：...）
[预热] 全量行情加载完成
哈希表构建完成，共 3 只ETF          ← 夹具没开的话这里是 0
```

**不设 `E2E_MARKET_FIXTURE` = 完全现有行为，对生产零影响**（连 `import akshare` 都不会执行）。
设了但文件缺失/非法 → **启动时直接抛错**。这是故意的：静默失败的症状（「行情又空了」）
和夹具要解决的问题长得一模一样，很难查。

### 5.2 落地成什么样了

原计划改 `refresh_spot_cache()` / `query_kline()` 两个函数，**实际没这么做**，原因见 §5.3。

| 新增/改动 | 文件 | 说明 |
|---|---|---|
| 新增 | `server/services/market_fixture.py` | 夹具本体：读快照 + 把 akshare 的 8 个行情函数换成读快照的实现 |
| 新增 | `docs/e2e/fixtures/market_snapshot.json` | 快照数据（合成，值写死） |
| 新增 | `docs/e2e/scripts/make_market_snapshot.py` | 生成/重建快照，带 `--capture` 可抓真实数据 |
| 改动 | `server/app.py:75-83` | lifespan 里加一行 `install_market_fixture()` |

**怎么做到不改业务代码的**：项目里每一处 akshare 调用都是**函数内** `import akshare as ak`
然后 `ak.xxx(...)`，而 Python 的 `import` 拿到的是 `sys.modules` 里**同一个模块对象**。
所以把 `akshare.fund_etf_spot_em` 这个属性换掉，全项目所有调用点一起生效。
被替换的 8 个函数：

| akshare 函数 | 调用点 | 用途 |
|---|---|---|
| `fund_etf_spot_em()` | `finance_api_service.py:1104` | 全量实时行情 → `_spot_dict`（search/spot/realtime 全靠它） |
| `fund_etf_hist_em(symbol, period, adjust)` | `:423` | 日/周/月 K 线 |
| `fund_etf_hist_min_em(symbol, period, adjust)` | `:915` | 分时 K 线 |
| `fund_overview_em(symbol)` | `:187`、`:221`、`:528` | 基金详情概览 |
| `fund_etf_fund_info_em()` | `:578` | 历史净值（`nav_history`） |
| `fund_open_fund_info_em(symbol, indicator)` | `:205`、`portfolio_service.py:257` | 申购用的单位净值 |
| `fund_name_em()` | `:63` | 基金名称 → 代码映射 |
| `tool_trade_date_hist_sina()` | `server/services/trading_calendar.py:56` | 交易日历 —— **PR #18 后全项目唯一来源**；`portfolio_service.py:466` 的 `_is_trading_day` 只是委托给它 |

### 5.3 为什么不是在业务函数里加 `if 夹具开启`

原方案是在 `refresh_spot_cache()` / `query_kline()` 里各加一个分支。放弃它的原因：

- 喂数据的 akshare 调用实际有 **9 处**（不是当初估的 2 处、也不是复查时的 4 处），
  `portfolio_service.py` 里还有 2 处 —— 逐个加 if 既容易漏，也没法一次性回滚。
- 在 akshare 这一层替换，**业务代码一行不改**，夹具文件删掉、环境变量不设，就完全回到现状。
- 快照用英文键（`code`/`price`/`kline`），中文列名映射集中在 `market_fixture.py` 一个文件里。
  这样 akshare 改了列名，只需要改那一个文件，快照本体不用动。

### 5.4 快照里有什么

| 段 | 内容 |
|---|---|
| `spot` | `510300` / `510500` / `159915` 三只，字段给全（含主力净流入、量比、市值等） |
| `kline.510300.daily` | 6 根日 K，最后一根收盘刻意等于 spot 里的现价 `3.876` |
| `overview` | `510300`、`110020` 的基金概览 |
| `fund_info` | 5 条历史净值（`nav_history`） |
| `open_fund_nav.110020` | 3 条单位净值（申购用） |
| `trade_dates` | 2026 全年工作日（已排除国庆 10-01~10-08） |

数据是**手挑的、写死的**，就是为了让断言能精确到小数位，例如：

- 搜 `"300"` → **恰好 1 条**，`code=510300`、`price=3.876`（`"300"` 只出现在「沪深300ETF」里）
- 搜 `"etf"` → 3 条（大小写不敏感）
- `/api/market/kline/510300` → 6 条，最后一条 `close=3.876`

### 5.5 三个已知的坑

1. **K 线有文件缓存**（`/tmp/etf_kline_cache/`，TTL 一天，`finance_api_service.py:16-17`）。
   **改了快照里的 `kline` 当天不生效**，要 `rm -rf /tmp/etf_kline_cache`。
   没绕过它是因为「缓存命中」本身也是被测逻辑。
2. ⚠️ **同一个 K 线请求，缓存命中与否会返回** **不同的小数值** —— 这会让「精确相等」的断言随机变红。
   > **实测（2026-10-03）**：清掉缓存后第一次 `GET /api/market/kline/510300` 返回
   > `high=3.82`；**原样再请求一次**（这次命中缓存文件）返回 `high=3.8200000000000003`。
   > 缓存文件里写的就是 `3.82`，噪声是**读的时候**引入的。
   > 已定位到 `pd.read_json(path, orient="split")`（`finance_api_service.py:880`）：
   > 同一个 JSON，`pd.read_json` 解析出来是 `3.8200000000000003`，
   > 而 `pd.DataFrame(data, columns)` 解析出来是 `3.82` —— **pandas 的 `read_json` 会引进 1 ULP 误差**。
   > 而且是**零星的**：同一列里 `3.795` 就没问题。**这是真实链路的行为，与夹具无关**
   > （真实 akshare 数据走同一条缓存路径也是这个结果）。
   >
   > **⇒ 写用例时：K 线数值断言一律用 `toBeCloseTo(x, 3)` 或先 `round(x, 3)`，
   > 不要用 `toBe(3.82)`。** spot / search 走内存缓存，没有这个问题，可以精确断言。
3. **`nav_history` 与请求的基金代码无关** —— `_query_nav_history()` 调的是
   `ak.fund_etf_fund_info_em()`，这个 akshare 函数**不接 symbol**，一次返回全市场，
   然后 `.tail(limit)`（`finance_api_service.py:578-595`）。
   所以查任何代码的 `nav_history` 拿到的都是同一批记录。
   这是**既有缺陷**，夹具如实复现、不掩盖。**已登记，未修。**

### 5.6 原本被否掉的两个方案（留个记录）

- **方案 B**：只预先写好 K 线缓存文件放进 `/tmp/etf_kline_cache/`。零后端改动，
  但解决不了 `spot`（`search`/`spot`/`realtime` 还是空的），而且 TTL 一天、每天得重灌。
- **方案 C**：本地起假行情源 + 改 hosts + 伪造证书。零后端改动，但要 MITM，
  akshare 解析逻辑一变就碎，维护成本远高于现在这个做法。
