**① 原生弹窗/提示要桩掉 —— ⚠️ `showModal` 不能用 `mockUniMethod`（2026-10-10 实测推翻）**

`uni.showModal` / `uni.showToast` 是**原生 UI**，automator 无法像 DOM 一样读取或驱动它们，必须桩掉。

**`showToast` 这类「不被 `await` 的通用 API」**：按老办法用 `mockUniMethod` 结果式即可。

```js
// ⚠️ 本项目用 uni-automator，API 名是 mockUniMethod（U，不是 W）。
//    mockWxMethod 是另一个 SDK（miniprogram-automator）的名字，在本项目里不存在。
// ⚠️ 只能用「结果式」：第二个参数只能是可 JSON 序列化的值。
//    传函数（用来捕获实参）会抛 `(intermediate value) is not a function`。
await program.mockUniMethod('showToast', { errMsg: 'showToast:ok', title: '' });
await program.restoreUniMethod('showToast'); // 用完必须还原，否则残留到后面的用例
```

**`showModal` 要看应用那边怎么写 —— 只有「回调写法」能用 `mockUniMethod`：**

```js
// ✅ 回调写法 —— mock 管用（应用自己传了 success，mock 会去调它）
//     uni.showModal({ ..., success: (res) => { if (res.confirm) ... } })
//     例：src/pages/watchlist/index.vue#L548-L560（移除自选）。P3-03 就是这么跑的。
await program.mockUniMethod('showModal', { confirm: true, cancel: false, errMsg: 'showModal:ok' });
await program.restoreUniMethod('showModal');

// ❌ await 写法 —— mock **不管用**（2026-10-10 实测）
//     const result = await uni.showModal({ ... }); if (!result.confirm) return;
//     例：src/pages/settings/index.vue#L202-L208（退出登录）。
//     这条 await 依赖 uni-app 的 promisify 包装，而 mock 的实现是 `uni[method] = mockFn`
//     （改的是 uni-app 自己的 `uni`），包装被换成裸函数后没人 resolve → await 拿到 undefined
//     → `!result.confirm` 抛 TypeError。**看起来就是「点了没反应」。**
//     实测表现：装完 mock 从 evaluate 看 `wx.showModal` 一个字节没变；
//     点「退出登录」4 个 auth key 一直没清。

// ✅ await 写法请换 helper（做法：从 evaluate 里直接改写 `wx.showModal`）。
//    evaluate 里的 `uni` 实测**就是 `wx`**（`uni === wx` 为 true），而应用调
//    `uni.showModal` 最终落到 `wx.showModal`。实测：点完约 500ms 键就清空、页面跳到登录页。
//    ⚠️ 只对**通用 API** 有效；路由类（`wx.reLaunch` 等）在 uni-app 启动时就被缓存了，改不动。
await helpers.withNativeModal(program, { confirm: true }, async () => {
  const el = await (await program.currentPage()).$('#settings-logout');
  await el.tap();
  modalCalls = await helpers.readNativeModalCalls(program); // 顺带把弹窗文案录下来了
});
```

**② 等待策略：一律轮询，不用固定 `sleep`**

```js
async function waitFor(fn, { timeout, interval = 200, desc }) { /* 轮询 fn 直到真值或超时 */ }
```
| 场景 | timeout |
|---|---|
| 页面跳转（含 `expireAuthAndRedirect` 的两段 setTimeout） | **3s**（必须 > 250+300ms） |
| 普通接口渲染 | 10s |
| SSE 首个 token | **130s**（前端超时是首 token 65s / 总请求 120s，见 [index.vue:63-66](application/src/pages/index/index.vue#L63-L66)） |

**③ ⭐ 切 Tab 前必须先滚到底部**

⚠️ 依据 [01 §六之二](01-页面与API调用关系.md)：真机确认本项目的 TabBar（[TabBar.vue](application/src/components/common/TabBar.vue)）
**没有固定在底部** —— `.tab-bar` 只有 `flex-shrink: 0`，没有 `position: fixed`，是普通文档流里的块，
跟着页面内容一起滚。

后果：**不滚动的话根本点不到 Tab**，或者滚动位置不同导致点到了别的元素。统一做法是封装一个函数，
**内部先滚动再点击**，不要让每条用例各写一遍：

```js
// helpers/selectors.js
async function gotoTab(page, name) {
  await page.scrollTo(0, 99999);          // 滚到底，让 TabBar 进入视口
  await waitFor(() => page.$(name), { timeout: 3000, desc: `Tab ${name} 出现` });
  await (await page.$(name)).tap();
  await page.waitFor(600);                // Tab 切换会销毁当前页栈，给跳转留窗口
}
```

> 📌 如果将来前端同学把 `position: fixed` 补上（见 01 §六之二 的待办），这个滚动步骤**应当删掉** ——
> 所以要封装成 `gotoTab` 而不是散落各处：修好之后只改一个地方。

### 1.3 断言风格（三条纪律）

1. **UI 文本 vs API 返回值双断言**：涉及数值的用例，用同一 token 直接请求后端拿到真值，再比对 UI 文本。避免"写死数字"与"只比对 UI 自己"两种假绿。
2. **禁止断言 LLM 的具体回复文本**（非确定性）。只断言结构。
3. **负例必须断言到具体文案**，因为后端文案是产品语义的一部分（下表为已核对的确切文案，来自 [portfolio_service.py](ai-etf/server/services/portfolio_service.py)）：

### 二.1 ⚠️ 重要修正：确认后建仓**不做 E2E**（原 P1-C1/C2 已删）

> **修正日期 2026-09-20。** 本文件初版把确认扩展写成"仅在交易日 00:00–14:59 可跑的时间门控用例"。**这个门控是错的，已删除。**

**错在哪**：`confirm_date` 被推进了**两次**（[portfolio_service.py:581-591](ai-etf/server/services/portfolio_service.py#L581-L591)）：

```python
confirm_delay = int(_require_rule_field(rule, fund_code, "confirm_delay"))   # 110020 = 1
if self._is_trading_day(...) and self._is_before_cutoff(...):
    confirm_date = now_beijing.date()          # 当日「受理」
else:
    confirm_date = self._next_trading_day(...)  # 下一交易日「受理」

actual_confirm = confirm_date
for _ in range(confirm_delay):
    actual_confirm = self._next_trading_day(actual_confirm)   # ← 再往后推 T+1
```

而**落库的是 `actual_confirm`**（[:673](ai-etf/server/services/portfolio_service.py#L673) `confirm_date=actual_confirm.isoformat()`），不是 `confirm_date`；`confirm-pending` 只确认 `confirm_date <= today`（[:1058-1064](ai-etf/server/services/portfolio_service.py#L1058-L1064)）。

**推论：申购单当天永远确认不了。** 即使交易日 14:00 下单（`day_label = "当日"`），持久化的确认日仍是**下一个交易日**（`110020` 的 `confirm_delay = 1`，见 [seed.sql:5](ai-etf/supabase/seed.sql#L5)）。所以"下单后立刻调 `confirm-pending`"**必然返回 `processed=0`** —— 不存在任何"当天可确认"的时间窗口。

> ⚠️ **这段只对买单成立。** 上面的 `confirm_delay` 循环在 `apply_purchase` 里；`apply_redeem` **是另一条路径**，落库的是**未推进**的 `confirm_date` → 赎单在交易日 15:00 前下单**当天就能确认**。详见 [§二.2](#二2-赎回链路的确认日与申购不对称已修正)。

**仓库自己的集成测试就是证据**：`tests/integration/server/jobs/test_scheduler_jobs.py` 里 `SUBMIT_DAY = 2026-09-14 14:00`（周一、交易日、盘中），`CONFIRM_DAY = 2026-09-15 14:00`（**次日**）—— 它必须跨日才能确认。

**处置**：

| 覆盖目标 | 交给谁 | 理由 |
|---|---|---|
| **确认日计算是否正确**（含 T+1、跨周末/节假日） | **后端集成测试（已有）** | `test_scheduler_jobs.py` 用 `time_machine` 冻结时钟跨日跑，这正是**只有后端能做的事** |
| **确认动作执行后的用户可见结果**（持仓出现、冻结归零、流水新增） | **暂不做** | 状态**能造**（改库回填，或走货基自动申购立即确认，见 [01 §5.4](01-页面与API调用关系.md)），但为它引入夹具构造状态，收益仍低于已有集成测试——**这是取舍，不是不可能** |

→ **净收益**：P1 路径**彻底摆脱时钟依赖**，6 条用例任何时候可跑、可进 CI；报告里也**不再需要"SKIP(时间窗口)"这个状态**。这是分层原则（[02 §三](02-核心路径与分层策略.md)）的一次正确应用：**能下沉的断言就下沉，E2E 不重复做集成测试的事。**

> **如果将来确实想验证"确认后 UI 正确"**：唯一实用的做法是**夹具回填状态**——下单后把该订单的 `confirm_date` 直接改到今天/昨天，再调 `confirm-pending`（它读库里的值），然后断言 UI。这属于"为测 UI 而构造状态"，可接受，但必须显式标注：**它验证的是"确认动作之后的展示"，不验证"确认日算得对不对"**（后者已由集成测试覆盖）。此时才需要夹具新增 `backdate-order` 子命令。
>
> ✅ **需确认 #3 已结（2026-09-20 读完 sell 分支）**：`_confirm_one_order` 的 sell 分支**没有**独立的到账延迟——它先扣份额（[portfolio_service.py:1385-1401](ai-etf/server/services/portfolio_service.py#L1385-L1401)），**紧接着**就把 `new_cash = current_cash + net_amount` 写回 `accounts.cash`（[:1403-1417](ai-etf/server/services/portfolio_service.py#L1403-L1417)），`net_amount = 赎回金额 - 实际费用`。**现金在"确认"那一刻入账。**

## 二.2 赎回链路的确认日与申购不对称（**已修正**）

**这是本文档曾经写错的一处，值得完整记下来。**

[§二.1](#二1-为什么「申购--确认-持仓出现」不做-e2e已修正) 的结论「落库确认日 = 受理日 + `confirm_delay` 个交易日 → 会话内永远确认不了」**只对买单成立**。根因是 `confirm_delay` 只出现在 `apply_purchase`：

| | 受理日计算 | `confirm_delay` 循环 | **落库字段** | 结果 |
|---|---|---|---|---|
| **申购** `apply_purchase` | [:582-587](ai-etf/server/services/portfolio_service.py#L582-L587) | ✅ [:589-591](ai-etf/server/services/portfolio_service.py#L589-L591) | `actual_confirm`（**推进过**）[:673](ai-etf/server/services/portfolio_service.py#L673) | 确认日 ≥ 次日 → **当天不可确认** |
| **赎回** `apply_redeem` | [:778-781](ai-etf/server/services/portfolio_service.py#L778-L781) | ❌ 无 | `confirm_date`（**未推进**）[:846](ai-etf/server/services/portfolio_service.py#L846) | 交易日 15:00 前 → 确认日 = 当天 → **当天可确认** |

`apply_redeem` 里那个 `for _ in range(redeem_delay)` 循环（[:836-838](ai-etf/server/services/portfolio_service.py#L836-L838)）推的是**另一个变量 `settle_date`**，它只被拼进提示文案「将于 {settle_date} 到账（T+N）」（[:849](ai-etf/server/services/portfolio_service.py#L849)），**从不落库**。所以「T+3 到账」是话术，**实际入账时刻是确认日**。

**旁证（仓库自己就在同一个瞬间完成赎回确认）**：`tests/integration/server/services/test_portfolio_trade_flow.py:106-129` 的 `test_赎回_持仓清空现金入账` 在**同一个冻结时刻** `CONFIRM_DAY` 里完成赎回与确认——若赎单也要 T+N，这条测试根本写不出来。

### 那「赎回 → 现金变多」为什么不写成 E2E 用例

不是「不可达」，而是三件事叠起来让 E2E 不划算：

| # | 障碍 | 性质 |
|---|---|---|
| 1 | **前置「已确认持仓」要夹具造**：常规申购要跨日；会话内唯一可达的是货基自动申购（立即确认，[:134-165](ai-etf/server/services/portfolio_service.py#L134-L165)），但它**前端零调用 + UI 无入口** | 需要构造状态 |
| 2 | **确认触发者前端零调用**：`POST /portfolio/confirm-pending` 前端零命中，15:37 调度器只是后台任务——**UI 上没有任何"让确认发生"的按钮** | 窗口期不可达 |
| 3 | **窗口门控**：只有「交易日且当前 < 15:00」下的单，确认日才是当天 | 窗口期不可达 |

→ 结论：**`N/A(不可达)`，但理由是「前置须构造 + 无 UI 触发路径」，不是「确认日必然跨日」。** 覆盖下沉到已有的 `test_portfolio_trade_flow.py:106`（现金入账）与 `test_scheduler_jobs.py`（跨日推进），两者都用 `time_machine`。

### 教训（比这一条用例更重要）

**可达性要按「分支/方向」逐条判，不能按「功能」一刀切。** 申购与赎回在前端是同一套 UI、同一个 `pending` 概念、同一个 `confirm-pending` 端点，但**落库字段不同**（`actual_confirm` vs `confirm_date`），可达性就完全相反。看到「同一个业务概念」就套用同一个结论，正是这次出错的根因。

**具体动作**：判可达性时一路跟到**落库那一行**（这里是 [:673](ai-etf/server/services/portfolio_service.py#L673) 与 [:846](ai-etf/server/services/portfolio_service.py#L846)），**不要停在第一次赋值**。

**E2E 的具体做法（按可靠性排序，建议 ①+②组合）**：

| 手段 | 做法 | 评价 |
|---|---|---|
| ① **UI 文本采样（推荐，无需钩子）** | 发送后对 bot 气泡文本以 300ms 间隔采样 5 次，要求**至少出现 2 个互不相同的非空文本** | 「流式」的可观测证据；非流式实现会一次到位 → 该断言会红。**不需要前端配合** |

| ❌ 监听网络请求 | — | **automator 没有 `page.on('response')` 这类能力**，做不到 |
| ⭐④ **换掉 `wx.request` 自己造流**（2026-10-10 实测可行，**已封装**） | 用 `application/e2e/helpers/streamMock.js`：`withStreamMock(program, {urlIncludes}, fn)` → 点发送 → `waitChunkHandler` → `pushChunkSplitMidChar(program, sse文本, {onHead})` → `finishStream(program)`。**别再手抄假实现** | **最强**，且**不需要后端配合**。唯一代价：替换掉了传输层，验的是「前端拿到这些字节后会怎样」，不是「微信运行时真的会这么切」。**和 ①②③ 组合用**——①②③ 证明真实链路通，④ 证明解码逻辑对。<br>两个坑：喂字节前不 `waitChunkHandler` 会**静默丢**（表现为气泡一直空）；`onHead` 是观察「半块」状态的唯一窗口 |
