### 1.2 两个基础技术手段（后面每条用例都会用到）

**① `mockWxMethod` 桩掉原生弹窗/提示**

`uni.showModal` / `uni.showToast` 是**原生 UI**，automator 无法像 DOM 一样读取或驱动它们。统一做法：

```js
// 桩掉 toast，只记录参数（不阻断后续逻辑：expireAuthAndRedirect 的 reLaunch 仍会执行）
const toasts = [];
await miniProgram.mockWxMethod('showToast', function (opts) { toasts.push(opts); });
// 断言：toasts 里存在 { title: '登录状态已过期，请重新登录' }

// 桩掉 modal，模拟用户点「确认」并回填输入
await miniProgram.mockWxMethod('showModal', { confirm: true, cancel: false, content: '新标题' });
```
> ⚠️ **可桩性需实机确认**（`mockWxMethod` 对 `showModal`/`showToast` 的支持与基础库版本相关，`project.private.config.json` 里 `libVersion = 3.16.1`）。**需确认 #1**。若不可桩 → P2 的重命名/删除、P1 的退出确认需降级为"只断言最终结果（列表标题变了/会话消失了）"，看不到中间文案。

**② 等待策略：一律轮询，不用固定 `sleep`**

```js
async function waitFor(fn, { timeout, interval = 200, desc }) { /* 轮询 fn 直到真值或超时 */ }
```
| 场景 | timeout |
|---|---|
| 页面跳转（含 `expireAuthAndRedirect` 的两段 setTimeout） | **3s**（必须 > 250+300ms） |
| 普通接口渲染 | 10s |
| SSE 首个 token | **130s**（前端超时是首 token 65s / 总请求 120s，见 [index.vue:63-66](application/src/pages/index/index.vue#L63-L66)） |

### 二.1 ⚠️ 重要修正：确认后建仓**不做 E2E**（原 P1-C1/C2 已删）

> **修正日期 2026-09-20。** 本文件初版把确认扩展写成"仅在交易日 00:00–14:59 可跑的时间门控用例"。**这个门控是错的，已删除。**

**错在哪**：`confirm_date` 被推进了**两次**（[portfolio_service.py:542-552](ai-etf/server/services/portfolio_service.py#L542-L552)）：

```python
confirm_delay = int(_require_rule_field(rule, fund_code, "confirm_delay"))   # 110020 = 1
if self._is_trading_day(...) and self._is_before_cutoff(...):
    confirm_date = now_beijing.date()          # 当日「受理」
else:
    confirm_date = self._next_trading_day(...)  # 下一交易日「受理」

actual_confirm = confirm_date
for _ in range(confirm_delay):
    actual_confirm = self._next_trading_day(actual_confirm)   # ← 再往后推 T+1
```

而**落库的是 `actual_confirm`**（[:610](ai-etf/server/services/portfolio_service.py#L610) `confirm_date=actual_confirm.isoformat()`），不是 `confirm_date`；`confirm-pending` 只确认 `confirm_date <= today`（[:990-996](ai-etf/server/services/portfolio_service.py#L990-L996)）。

**推论：申购单当天永远确认不了。** 即使交易日 14:00 下单（`day_label = "当日"`），持久化的确认日仍是**下一个交易日**（`110020` 的 `confirm_delay = 1`，见 [seed.sql:5](ai-etf/supabase/seed.sql#L5)）。所以"下单后立刻调 `confirm-pending`"**必然返回 `processed=0`** —— 不存在任何"当天可确认"的时间窗口。

> ⚠️ **这段只对买单成立。** 上面的 `confirm_delay` 循环在 `apply_purchase` 里；`apply_redeem` **是另一条路径**，落库的是**未推进**的 `confirm_date` → 赎单在交易日 15:00 前下单**当天就能确认**。详见 [§二.2](#二2-赎回链路的确认日与申购不对称已修正)。

**仓库自己的集成测试就是证据**：`tests/integration/server/jobs/test_scheduler_jobs.py` 里 `SUBMIT_DAY = 2026-09-14 14:00`（周一、交易日、盘中），`CONFIRM_DAY = 2026-09-15 14:00`（**次日**）—— 它必须跨日才能确认。

**处置**：

| 覆盖目标 | 交给谁 | 理由 |
|---|---|---|
| **确认日计算是否正确**（含 T+1、跨周末/节假日） | **后端集成测试（已有）** | `test_scheduler_jobs.py` 用 `time_machine` 冻结时钟跨日跑，这正是**只有后端能做的事** |
| **确认动作执行后的用户可见结果**（持仓出现、冻结归零、流水新增） | **暂不做** | 状态**能造**（改库回填，或走货基自动申购立即确认，见 [01 §5.4](01-页面与API调用关系.md)），但为它引入夹具构造状态，收益仍低于已有集成测试——**这是取舍，不是不可能** |

→ **净收益**：P1 路径**彻底摆脱时钟依赖**，6 条用例任何时候可跑、可进 CI；报告里也**不再需要"SKIP(时间窗口)"这个状态**。这是分层原则（[02 §三](02-核心路径与分层策略.md)）的一次正确应用：**能下沉的断言就下沉，E2E 不重复做集成测试的事。**

> **如果将来确实想验证"确认后 UI 正确"**：唯一实用的做法是**夹具回填状态**——下单后把该订单的 `confirm_date` 直接改到今天/昨天，再调 `confirm-pending`（它读库里的值），然后断言 UI。这属于"为测 UI 而构造状态"，可接受，但必须显式标注：**它验证的是"确认动作之后的展示"，不验证"确认日算得对不对"**（后者已由集成测试覆盖）。此时才需要夹具新增 `backdate-order` 子命令。
>
> ✅ **需确认 #3 已结（2026-09-20 读完 sell 分支）**：`_confirm_one_order` 的 sell 分支**没有**独立的到账延迟——它先扣份额（[portfolio_service.py:1245-1261](ai-etf/server/services/portfolio_service.py#L1245-L1261)），**紧接着**就把 `new_cash = current_cash + net_amount` 写回 `accounts.cash`（[:1263-1277](ai-etf/server/services/portfolio_service.py#L1263-L1277)），`net_amount = 赎回金额 - 实际费用`。**现金在"确认"那一刻入账。**
> ⚠️ 但**不要断言"到账日"与"入账日"一致**：`apply_redeem` 返回给前端的 `settle_date` 是按 `redeem_settle_delay` 推出的（`110020` = T+3），**只用于拼提示文案**（[:786](ai-etf/server/services/portfolio_service.py#L786)），**代码里没有任何按 `settle_date` 入账的逻辑**。这是**产品口径与实现不一致**——已登记为已知问题，不在 E2E 里断言两者相等。

## 二.2 赎回链路的确认日与申购不对称（**已修正**）

**这是本文档曾经写错的一处，值得完整记下来。**

[§二.1](#二1-为什么「申购--确认-持仓出现」不做-e2e已修正) 的结论「落库确认日 = 受理日 + `confirm_delay` 个交易日 → 会话内永远确认不了」**只对买单成立**。根因是 `confirm_delay` 只出现在 `apply_purchase`：

| | 受理日计算 | `confirm_delay` 循环 | **落库字段** | 结果 |
|---|---|---|---|---|
| **申购** `apply_purchase` | [:543-548](ai-etf/server/services/portfolio_service.py#L543-L548) | ✅ [:550-552](ai-etf/server/services/portfolio_service.py#L550-L552) | `actual_confirm`（**推进过**）[:610](ai-etf/server/services/portfolio_service.py#L610) | 确认日 ≥ 次日 → **当天不可确认** |
| **赎回** `apply_redeem` | [:715-718](ai-etf/server/services/portfolio_service.py#L715-L718) | ❌ 无 | `confirm_date`（**未推进**）[:783](ai-etf/server/services/portfolio_service.py#L783) | 交易日 15:00 前 → 确认日 = 当天 → **当天可确认** |

`apply_redeem` 里那个 `for _ in range(redeem_delay)` 循环（[:773-775](ai-etf/server/services/portfolio_service.py#L773-L775)）推的是**另一个变量 `settle_date`**，它只被拼进提示文案「将于 {settle_date} 到账（T+N）」（[:786](ai-etf/server/services/portfolio_service.py#L786)），**从不落库**。所以「T+3 到账」是话术，**实际入账时刻是确认日**。

**旁证（仓库自己就在同一个瞬间完成赎回确认）**：`tests/integration/server/services/test_portfolio_trade_flow.py:106-129` 的 `test_赎回_持仓清空现金入账` 在**同一个冻结时刻** `CONFIRM_DAY` 里完成赎回与确认——若赎单也要 T+N，这条测试根本写不出来。

### 那「赎回 → 现金变多」为什么不写成 E2E 用例

不是「不可达」，而是三件事叠起来让 E2E 不划算：

| # | 障碍 | 性质 |
|---|---|---|
| 1 | **前置「已确认持仓」要夹具造**：常规申购要跨日；会话内唯一可达的是货基自动申购（立即确认，[:129-160](ai-etf/server/services/portfolio_service.py#L129-L160)），但它**前端零调用 + UI 无入口** | 需要构造状态 |
| 2 | **确认触发者前端零调用**：`POST /portfolio/confirm-pending` 前端零命中，15:37 调度器只是后台任务——**UI 上没有任何"让确认发生"的按钮** | 窗口期不可达 |
| 3 | **窗口门控**：只有「交易日且当前 < 15:00」下的单，确认日才是当天 | 窗口期不可达 |

→ 结论：**`N/A(不可达)`，但理由是「前置须构造 + 无 UI 触发路径」，不是「确认日必然跨日」。** 覆盖下沉到已有的 `test_portfolio_trade_flow.py:106`（现金入账）与 `test_scheduler_jobs.py`（跨日推进），两者都用 `time_machine`。

### 教训（比这一条用例更重要）

**可达性要按「分支/方向」逐条判，不能按「功能」一刀切。** 申购与赎回在前端是同一套 UI、同一个 `pending` 概念、同一个 `confirm-pending` 端点，但**落库字段不同**（`actual_confirm` vs `confirm_date`），可达性就完全相反。看到「同一个业务概念」就套用同一个结论，正是这次出错的根因。

**具体动作**：判可达性时一路跟到**落库那一行**（这里是 [:610](ai-etf/server/services/portfolio_service.py#L610) 与 [:783](ai-etf/server/services/portfolio_service.py#L783)），**不要停在第一次赋值**。

### SSE 断言专项（**对应交付项 (a)**）

**核心判断：SSE 协议的正确性不要靠 E2E 来证明。**

| 层 | 断言什么 | 为什么 |
|---|---|---|
| **L3 契约（主战场）** | 用 httpx 直连后端，逐帧解析响应体：<br>① `Content-Type: text/event-stream`<br>② 响应头有 **`X-Session-ID: <uuid>`**（[sse.py:33-41](ai-etf/server/utils/sse.py#L33-L41)）<br>③ 帧格式严格为单行 `data: {"type":...}\n\n`，**无 `event:`/`id:`/`retry:`**<br>④ 至少 1 个 `{"type":"token","content":str}`<br>⑤ **恰好 1 个收尾** `{"type":"done","chat_id":str}`<br>⑥ 中文以**原始 UTF-8** 出现（校验 `ensure_ascii=False`） | 这一层能拿到**原始字节**，是唯一能可靠验证分块/帧格式的地方。放在 E2E 里既慢又不准 |
| **L4 E2E（只验用户可见结果）** | 见 P2-01 各断言 | E2E 无法观测网络层 |

**E2E 的具体做法（按可靠性排序，建议 ①+②组合）**：

| 手段 | 做法 | 评价 |
|---|---|---|
| ① **UI 文本采样（推荐，无需钩子）** | 发送后对 bot 气泡文本以 300ms 间隔采样 5 次，要求**至少出现 2 个互不相同的非空文本** | 「流式」的可观测证据；非流式实现会一次到位 → 该断言会红。**不需要前端配合** |
| ② **`X-Session-ID` / 后端交叉验证** | 发送后夹具轮询 `GET /api/secure-chat/chats`，确认出现新会话且标题 == 输入前 20 字（后端 [secure_chat.py:271-274](ai-etf/server/api/secure_chat.py#L271-L274) 的 `question[:20] + "..."`） | 验证 `done` 帧的 `chat_id` 确实被前端落地了（`setCurrentChatId`） |
| ③ `miniProgram.evaluate()` 读 Pinia store | 读 `chatStore.messages` 直接断言 | 最精确，但 **Vue3 + Pinia 的 store 不在页面实例 `data` 上** → 需前端加测试钩子（`getApp().globalData.__chatStore`）。**需确认 #4**，非首选 |
| ❌ 监听网络请求 | — | **automator 没有 `page.on('response')` 这类能力**，做不到 |

**必须规避的假阳性**：前端在出错时会把异常写进气泡 —— `抱歉，${message}。`（[index.vue:557](application/src/pages/index/index.vue#L557)）。→ **任何"AI 有回复"的断言都必须排除以「抱歉，」开头的文本**，否则 LLM 超时/报错会被判成成功。
