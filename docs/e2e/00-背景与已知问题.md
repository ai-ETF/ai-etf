#### D-01 赎回拦截挡掉合法操作（2026-10-10 登记）

**代码位置**：[portfolio_service.py:788-803](ai-etf/server/services/portfolio_service.py#L788-L803)

```python

if pending_buys.data:
    return {"success": False,
            "message": f"基金 {fund_code} 存在待确认的申购订单，份额确认前无法赎回", ...}
```

**问题**：这儿的判断粒度是**基金**，不是**份额**。只要该基金存在任意一笔 pending 申购，`redeem` 就整个返回失败 ——

**为什么算缺陷**：真实产品（蚂蚁财富 / 天天基金等）的做法是**份额分账** —— 申购在途的那部分

（昨天买的已确认，今天又买一笔）。

**触发条件**：同时满足 ① 该基金有**已确认**持仓 ② 该基金有 **pending** 申购。

**为什么 E2E 曾经测不到**（这跟「是不是缺陷」无关，别混）：用例跑的是新账号、当天买当天赎，
`position` 恒为 `None` → 先撞上 `:785-786` 的「未持有基金」分支，走不到 `:788-803`。

#### D-06 K 线命中缓存时带浮点噪声（原登记：2026-10-03）

**代码位置**：[finance_api_service.py:880](ai-etf/server/services/finance_api_service.py#L880)

```python
df = pd.read_json(path, orient="split")   # :880
```

**问题**：**同一个 K 线请求，缓存命中与否会返回不同的小数值。**

**实测佐证**（2026-10-03）：清掉缓存后第一次 `GET /api/market/kline/510300` 返回 `high=3.82`；
**原样再请求一次**（这次命中缓存文件）返回 `high=3.8200000000000003`。
缓存文件里写的就是 `3.82`，**噪声是读的时候引入的** —— 已定位到 `pd.read_json`：
同一个 JSON，`pd.read_json` 解析出来是 `3.8200000000000003`，而 `pd.DataFrame(data, columns)` 解析出来是 `3.82`
⇒ **pandas 的 `read_json` 会引进 1 ULP 误差**。而且是**零星的**（同一列里 `3.795` 就没问题）。
**这是真实链路的行为，与夹具无关**（真实 akshare 数据走同一条缓存路径也是这个结果）。

**复核（2026-10-10）**：`:880` 仍是 `pd.read_json(path, orient="split")` ⇒ **还在**。

**对 E2E 的处置**：写用例时 K 线数值断言一律用 `toBeCloseTo(x, 3)` 或先 `round(x, 3)`，
**不要用 `toBe(3.82)`**。spot / search 走内存缓存，没有这个问题，可以精确断言。

**建议的修法**（交给后端定）：读缓存时改用不引入误差的路径（如 `pd.DataFrame(json.load(f)['data'], columns=...)`）。
⚠️ 影响面小、优先级低，登记为主。

  只有 P2-01（专验流式那条）拿它判红，且失败信息里会直接把这条已知行为写出来；
  P2-02 / P2-03 只警告不判红 —— 否则一次服务方抖动会被误读成「续聊坏了 / 新建会话坏了」。
- 这条**不影响 P2-07 造流的断言**：那条不经过真实模型，分块由测试自己喂。
- ✅ **2026-10-19 追加**：D-07 在**应用侧**的表现已被 **P2-11**（`p2-chat.e2e.js`）用造流钉住 ——
  HTTP 200、一个 token 都没有、正常收尾时，气泡必须显示 `抱歉，AI 服务未返回有效回复。`，
  且 `sendingMessage` 复位、之后还能再发。**注意这只能证明应用兜底正确，不能证明服务方什么时候会空流**；
  「长回答」仍不覆盖（见 `application/e2e/README.md` §8）。

**建议的修法**（交给后端定，这里只写方向）：`stream_with_save` 在 `full_response` 为空时，
不要静默存空消息 + 回 `done`，而应回 `error` 帧（或至少 `done` 里带一个「答案为空」的标记），
让前端能区分「模型没答」和「正常空回答」；前端也可在 `done` 且零 token 时给更准确的提示。
⚠️ 具体做法（重试？换模型？直接报错？）要与服务方的限制口径一起定。

### 技术难点（E2E 要专门处理）

- **SSE 流式对话**：首页发消息是 `text/event-stream`，小程序端用 `uni.request` + `enableChunked` 分块接收（`pages/index/index.vue`）。自动化工具对 SSE 的捕获是已知痛点，断言方式要专门设计。
  - 2026-10-10 已落地：**真实链路**靠对 Pinia store 高频采样（每 200ms 读一次 bot 气泡长度，
    要求出现 ≥2 个不同的非空长度）证流式；**分块细节**（汉字切两半分块、半块不提前渲染、
    `done` 的 `chat_id` 落地）靠 `application/e2e/helpers/streamMock.js` 换掉 `wx.request` 自己造流，
    不依赖真实模型。两条都在 `application/e2e/p2-chat.e2e.js`。
  - ⚠️ 真实 LLM 有 **D-07**（答得慢就整条返回空流）这个坑，挑问句的规矩见该条。
- **行情接口放行未登录**：`request.ts` 里 `/api/market/` 被特判为公开请求，未登录也放行。测试登录态时要留意这个例外。
- **登录态是 1 小时本地会话**：token 过期由前端 `expireAuthAndRedirect` 处理，E2E 要覆盖过期/401 场景（即 P4）。

#### D-09 后端每个请求都新建 Supabase 客户端 → 并发下请求近似串行、秒级延迟（2026-10-19 登记，**本机实测**）

**代码位置**：[supabase_client.py:13-33](ai-etf/server/storage/supabase_client.py#L13-L33) —— `get_supabase()` 每次调用都 `create_client(url, key)`，**没有任何缓存**。
而各服务是「每个请求 new 一个」，构造函数里立刻取客户端：例如
[watchlist_service.py:18-21](ai-etf/server/services/watchlist_service.py#L18-L21)（`WatchlistService()` 在 [watchlist.py:36](ai-etf/server/api/watchlist.py#L36) / [:62](ai-etf/server/api/watchlist.py#L62) / [:84](ai-etf/server/api/watchlist.py#L84) / [:101](ai-etf/server/api/watchlist.py#L101) 每个请求各建一次）、
[portfolio_service.py:88-89](ai-etf/server/services/portfolio_service.py#L88-L89)。

**慢在哪（拆开量过）**：

- `create_client()` 单次实测：**p50 311 ms、最慢 3.0 s**（30 次）。
- 用 cProfile 看，耗时几乎全在 httpx 建 SSL 上下文 → `SSLContext.load_verify_locations(certifi)`。
  一个客户端要建 **3 个**：请求本身 1 个 + 两个代理传输层各 1 个（因为本机环境里设了 `HTTP_PROXY` / `HTTPS_PROXY`）。
- 证书包在本仓库的 `.venv/.../certifi/cacert.pem`，而仓库在 `/mnt/d`（WSL 跨盘）：
  跨盘加载 **81 ms/次**，同一文件拷到 `/tmp` 只要 **14 ms/次**。
- 去掉代理环境变量后 `create_client`：244 ms → **83 ms**；再把 `SSL_CERT_FILE` 指到本地副本 → **16 ms**。

**并发下会串起来（2026-10-19 本机实测，128 条请求）**：

| 负载 | 端点 | p50 | 最慢 | 超过 1 秒 |
|---|---|---|---|---|
| 16 并发 × 8 | `/api/market/health`（**不**建客户端） | 11 ms | 261 ms | 0 条 |
| 16 并发 × 8 | `/api/portfolio/test/account`（**每请求建**） | **11 801 ms** | 17 014 ms | 128/128 |
| 8 并发 × 10 | 同上 | 6 977 ms | 10 316 ms | 79/80 |

压测期间后端 APScheduler 的「job was missed」从 1 条涨到 6 条 —— 与 2026-10-18 全量跑/P3 单跑里看到的
「后端卡了 2–4.5 秒」是同一个现象。

**修复对照（只在临时进程里打内存补丁，仓库代码一行没改）**：把 `get_supabase` 包一层缓存后，
同一负载 16 并发 × 8 → **p50 638 ms、最慢 923 ms、0 条超过 1 秒**（约 18 倍改善）；
进程全程只初始化 **1 次**客户端；压测期间定时任务**零延迟**。

**对 E2E 的影响**：小程序一屏经常同时发好几个请求（列表 + 行情 + 持仓…），后端把它们近似串行处理，
就会出现「偶发某一次 2 秒内没回包」。`P3-04` 的两处 `waitFor`（10 秒总预算、**每次尝试 2 秒上限**）
超时就是这一条：同一秒后端日志里其实回了 200。

**处置（按约定只登记、不修）**：

- **E2E 侧**：不要调大 `waitFor` 的单次 2 秒上限去迎合 —— 这不是用例写得不对，也不是产品功能坏了。
- **后端侧建议**（须负责人拍板）：① 缓存 `supabase` 客户端；② 本地开发时不要给后端进程设
  `HTTP(S)_PROXY`（本项目连的是本地 Supabase），可把单次创建从 244 ms 降到 83 ms。
- ⚠️ 缓存前要确认的：`supabase-py` 的 `Client` 内含 `httpx.Client`（本身线程安全）与 auth 会话状态；
  若服务端用到 auth 的刷新逻辑，需要确认多线程共享的语义。**登记不等于批准修改。**
