#### D-01 赎回拦截挡掉合法操作（2026-10-10 登记）

**代码位置**：[portfolio_service.py:788-803](ai-etf/server/services/portfolio_service.py#L788-L803)

```python
# 2a. 检查是否存在 pending 申购（份额未确认前不可赎回）
pending_buys = (... direction == "buy" ... status == "pending" ...)
if pending_buys.data:
    return {"success": False,
            "message": f"基金 {fund_code} 存在待确认的申购订单，份额确认前无法赎回", ...}
```

**问题**：这儿的判断粒度是**基金**，不是**份额**。只要该基金存在任意一笔 pending 申购，`redeem` 就整个返回失败 ——
**不管用户手里那部分份额是不是早就确认过了**。下面的 `:805-807` 计算可用份额时只扣除了 pending **赎回**，
并没有把 pending **申购**的那部分从可赎份额里剔掉、再放行剩余部分。

**为什么算缺陷**：真实产品（蚂蚁财富 / 天天基金等）的做法是**份额分账** —— 申购在途的那部分
根本不计入「可用份额」，用户**照样可以赎回已确认的份额**。按这个口径，本实现挡住的是
「已确认持有 + 另有一笔在途申购」这个组合，而**这个组合在真实使用中很常见**
（昨天买的已确认，今天又买一笔）。

**触发条件**：同时满足 ① 该基金有**已确认**持仓 ② 该基金有 **pending** 申购。

**为什么 E2E 测不到**（这跟「是不是缺陷」无关，别混）：用例跑的是新账号、当天买当天赎，
`position` 恒为 `None` → 先撞上 `:785-786` 的「未持有基金」分支，走不到 `:788-803`。
**这块不是死代码** —— 是本会话内造不出「已确认持仓」（当天买的确认不了，见 [03 §二.1](03-E2E用例清单.md)）。

**实测佐证**（2026-10-08，本机 curl，临时账号验完即删）：P1-03 下单 1000 后立刻赎回 110020
→ `HTTP 400 {"detail":"未持有基金 110020，无法赎回"}`。

**建议的修法**（交给后端定，这里只写方向）：把 `:805` 的可用份额改成
`position.quantity − pending_buy_quantity`（或按确认日拆分份额），只在**可赎份额为 0** 时才拦。
⚠️ 具体口径要和确认规则（`confirm_delay` / 确认日）对齐，别拍脑袋。

**对 E2E 的处置**：已在 [03 §二 P1-04](03-E2E用例清单.md) 与 `application/e2e/p1-trading.e2e.js`
里 `it.skip` 登记，并附一条**可执行的替代断言** —— 断言实际命中的是「未持有」文案。
将来若这条变成 pending 文案，说明**校验顺序被改了**，那条会红并提示回来更新本行。

#### D-02 设置页「我的持仓」卡片点了没反应（原登记：2026-09-24，真机实测）

- **现象**：真机点「个人中心 → 我的持仓」卡片，**没有任何反应**，卡片上只显示一个金额。
- **代码**：[settings/index.vue:310](application/src/pages/settings/index.vue#L310) 的 `handleHoldingsClick()` 调
  `uni.switchTab({ url: '/pages/watchlist/index' })`，但 [pages.json](application/src/pages.json) **没有 `tabBar` 段**。
- **为什么静默失败**：`uni.switchTab` 只对 `pages.json` 里登记为 tabBar 的页面有效。本项目的四个 Tab 是
  [TabBar.vue](application/src/components/common/TabBar.vue) 自定义组件 + `uni.redirectTo` 模拟的，不是真 tabBar

#### D-04 登录过期：凭证已清、跳转被吞、且无兜底（原登记：2026-10-09）

**代码位置**：[auth.ts:185-186](application/src/utils/auth.ts#L185-L186)

```ts

  clearAuthSession();            // :185 ← 清存储写在旗标判断【之前】
  if (redirecting) return;       // :186 ← 撞上就直接 return
  ...
```

**问题**：`redirecting` 旗标只在 `reLaunch` 的 `complete` 回调后再等 300ms 才复位。

**触发条件**：两次鉴权失败间隔小于约 1 秒（`redirecting` 复位所需时间）。

**实测佐证**：见 `application/e2e/README.md` §6.6 —— 探针先自证有效（P4-01 稳绿时记录到应用的
`showToast` + 6 次 `removeStorageSync`），装探针后跑 P4-04 **3/3 红**、每次都是「删了 key 却没有 toast」；
`-t 'P4-04'` 单独跑是绿的、紧跟 P4-02 后跑就红 ⇒ 状态来自上一条用例。

**对 E2E 的处置**：测试侧已绕开（发导航前 `waitForStablePage(program, {stableMs: 2500})`）。
⚠️ **别再往上调等待时长** —— 残余红是「导航被环境丢弃」，加多少毫秒都堵不住。

**建议的修法**（交给前端定）：把 `clearAuthSession()` 挪到旗标判断**之后**；或给被吞的那次加一次重试/兜底提示。

#### D-06 K 线命中缓存时带浮点噪声（原登记：2026-10-03）

**代码位置**：[finance_api_service.py:880](ai-etf/server/services/finance_api_service.py#L880)

```python
df = pd.read_json(path, orient="split")   # :880
```

**问题**：**同一个 K 线请求，缓存命中与否会返回不同的小数值。**

**实测佐证**（2026-10-03）：清掉缓存后第一次 `GET /api/market/kline/510300` 返回 `high=3.82`；
**原样再请求一次**（这次命中缓存文件）返回 `high=3.8200000000000003`。
缓存文件里写的就是 `3.82`，**噪声是读的时候引入的** —— 已定位到 `pd.read_json`：
同一个 JSON，`pd.read_json` 解析出来是 `3.8200000000000003`，而 `pd.DataFrame(data, columns)` 解析出来是 `3.82`
⇒ **pandas 的 `read_json` 会引进 1 ULP 误差**。而且是**零星的**（同一列里 `3.795` 就没问题）。
**这是真实链路的行为，与夹具无关**（真实 akshare 数据走同一条缓存路径也是这个结果）。

**复核（2026-10-10）**：`:880` 仍是 `pd.read_json(path, orient="split")` ⇒ **还在**。

**对 E2E 的处置**：写用例时 K 线数值断言一律用 `toBeCloseTo(x, 3)` 或先 `round(x, 3)`，
**不要用 `toBe(3.82)`**。spot / search 走内存缓存，没有这个问题，可以精确断言。

**建议的修法**（交给后端定）：读缓存时改用不引入误差的路径（如 `pd.DataFrame(json.load(f)['data'], columns=...)`）。
⚠️ 影响面小、优先级低，登记为主。

#### D-07 模型服务方返回空流 → 空答案被当成功存库、UI 显示兜底文案（2026-10-10 登记，**本日新发现**）

**代码位置（本仓这几处是「没有防线」的地方，不是写错了的地方）**：

- [llm.py:69](ai-etf/server/llm.py#L69) `async for chunk in llm.astream(messages):`
  —— 上游一个内容事件都不给时，这个循环**正常结束、不抛错**，`astream_text` 一个字符串都不产出。
- [secure_chat.py:217-236](ai-etf/server/api/secure_chat.py#L217-L236)
  —— `full_response` 停在 `""`，照样 `save_message(content="")`（:225-228）并回 `done` 帧（:236）。
  **没有任何「答案为空」的判断**，所以调用方（含测试）从响应上看不出这次跟成功有什么区别。
- 前端 [index.vue:233-236](application/src/pages/index/index.vue#L233-L236) 与
  [:246-249](application/src/pages/index/index.vue#L246-L249)：分块一个都没来 → `receivedToken` 为 false
  → `reject('AI 服务未返回有效回复')` → [:557](application/src/pages/index/index.vue#L557)
  把气泡写成 `抱歉，${message}。`。

**现象**：HTTP `200 OK`、`content-type: text/event-stream`、`transfer-encoding: chunked` 全都正常，
但**一个 token 帧都没有**，只有一个 `done` 帧；生成耗时稳定落在 **21-23 秒**。
应用侧气泡最终显示 `抱歉，AI 服务未返回有效回复。`（16 字）。

**触发条件（实测归纳）**：**后端这次回答要生成超过约 21 秒**。问句长不长**不是**决定因素 ——
28 个字的问句若答得快（6.5 秒 / 395 字）照样逐帧流式；而 22 个字的问句若答得慢，就整条落空。

**实测佐证（2026-10-10，本机直连后端 `curl -N`，同一个账号逐条换问句）**：

| 问句 | token 帧 | 正文字数 | 耗时 |
|---|---|---|---|
| `ETF 和场外基金到底有什么区别？请详细讲讲` | **0** | **0** | 21.5 / 21.5 / 23.0 秒（**连跑 3 次全空**） |
| `帮我讲讲ETF和场外基金的申购赎回机制有什么不同` | **0** | **0** | 23.2 秒 |
| `介绍一下ETF和股票的区别` | 605 | 1024 | 20.9 秒（贴边，能过但余量小） |
| `为什么要分散投资？` | 416 | 742 | 9.9 秒 |
| `ETF、场外基金、LOF 这三种基金分别在哪个市场交易？` | 216 | 395 | 6.5 秒 |
| `再解释一下` | 85 | 138 | 2.3 秒 |

同时段用 `GET /chats/{id}/messages` 回查后端落库的 assistant 消息：**`content` 长度为 0** ——
证明不是「帧在路上丢了」，而是**上游压根没产出内容**。

**已排除的原因（别再往这些方向查）**：

1. ❌ 开发者工具长跑退化 —— 重启开发者工具后仍复现。
2. ❌ WSL 网络 / 端口转发 —— 从 **Windows 侧** `curl` 一样复现（`body bytes: 75`，只有 done 帧）。
3. ❌ 后端进程冷启动或后端 bug —— 同一后端、同一时刻用短问句就是完整 19,684 字节的逐帧流式。
4. ❌ 应用或 `wx.request` 分块通路坏了 —— 真流式的回答帧一个不少；P2-07 造流用例也走的是同一条通路。
5. ❌ 「小程序进程的第一条分块请求必丢」—— **这个曾经是我的错误结论**（据此在 `p2-chat.e2e.js` 里加过
   一段「预热」逻辑，已删除并在代码注释里写明为什么不能加回来）。当时「第一条红、第二条绿」其实是
   **第一条问句答得慢、第二条问句答得快**。

**模型服务方**：日志里是 `POST https://api.deepseek.com/anthropic/v1/messages`（Anthropic 兼容端点），
`model=claude-sonnet-4-20250514`、`stream: true`（见 [llm.py:36-40](ai-etf/server/llm.py#L36-L40)）。
21-23 秒这个**几乎不变的**耗时指向服务方的首字节/总时长限制。**根因要服务方或后端负责人确认**（需确认）。

**对 E2E 的处置**：

- 真实 LLM 的用例**必须挑「答案短、回答稳定在 10 秒内」的问句**，并把理由写在代码注释里
  （`application/e2e/p2-chat.e2e.js` 文件头「真实 LLM 的已知行为」）。
- **`抱歉，` 开头的文案只能说明「这次模型没给内容」，不能当成应用缺陷的证据**。
  只有 P2-01（专验流式那条）拿它判红，且失败信息里会直接把这条已知行为写出来；
  P2-02 / P2-03 只警告不判红 —— 否则一次服务方抖动会被误读成「续聊坏了 / 新建会话坏了」。
- 这条**不影响 P2-07 造流的断言**：那条不经过真实模型，分块由测试自己喂。

**建议的修法**（交给后端定，这里只写方向）：`stream_with_save` 在 `full_response` 为空时，
不要静默存空消息 + 回 `done`，而应回 `error` 帧（或至少 `done` 里带一个「答案为空」的标记），
让前端能区分「模型没答」和「正常空回答」；前端也可在 `done` 且零 token 时给更准确的提示。
⚠️ 具体做法（重试？换模型？直接报错？）要与服务方的限制口径一起定。
