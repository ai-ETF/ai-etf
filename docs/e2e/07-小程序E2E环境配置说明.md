## 0. 一句话结论

跑 E2E 之前，`application` 要**多一个文件**：

```
application/src/project.private.config.json
```

**源码一行都没动** —— `src/manifest.json` 与 git HEAD 完全一致。
（我们最早的想法是去改 `src/manifest.json`，**那是错的**，已经撤销，见 §4。）

---

## 1. `project.private.config.json` 是什么

微信开发者工具打开一个小程序项目时，会读**两份**配置文件：

| 文件 | 谁生成的 | 作用 |
|---|---|---|
| `project.config.json` | **公共层**。我们这边由 uni-app 编译时**自动从 `src/manifest.json` 生成** | 项目名、appid、`urlCheck` 等 |
| `project.private.config.json` | **个人层**。微信专门加的一层，给「每个开发者自己的本地偏好」用 | 覆盖公共层里的同名项 |

两者重名时，**private 覆盖 public**。

微信加这一层的本意就是：让「我个人想关掉域名校验」这种**只跟本机有关**的事，
不用去改那个全组共享的公共文件。

**我们正是用了这个机制** —— 把两个「只对本地测试有意义、又绝不能污染仓库」的开关放进 private 层。

---

## 2. 为什么非加不可（两个原因，都很硬）

### 2.1 不关校验，请求根本发不出去

开发者工具默认会做「合法域名校验」：`uni.request` 打的目标域名必须在白名单里。
我们的本地后端是 `http://localhost:8000`，当然不在白名单 → **请求被拦，压根发不出去**。

而 E2E 又**必须**打本地后端 —— 打线上 `https://ai-etf.xyz` 就是拿测试数据去写生产库，
这是绝对不能碰的红线。所以这个校验必须关掉，对应配置项就是 `setting.urlCheck: false`。

### 2.2 appid 不对，项目**根本打不开**（而且报错是假的）

项目真正的 appid 是 `wx4345af65c586dd70`。它要求登录的微信账号是这个小程序的**开发者**，
否则开发者工具去微信要权限会被拒：

```
错误: 登录用户不是该小程序的开发者 (code 10)
```

然后 CLI 直接退出。**最坑的是最后暴露给我们的报错是另一句话：**

```
Failed to launch Wechat web DevTools , please make sure http port is open
```

⚠️ **这句话跟端口一点关系都没有**，是 appid 权限问题。
看到它先查 appid 和登录状态，**别去查端口**（我们当时就往端口方向查了很久）。
想一眼看到真话，用 CLI 手跑一次：
`cli.bat auto --project <产物目录> --auto-port 9420`。

两条出路：

| 方案 | 状态 |
|---|---|
| 真 appid + 管理员把你的微信账号加进「开发者」列表 | ✅ **2026-10-03 已加好**，实测能跑 |
| private config 里写 `"appid": "touristappid"`（游客模式） | ✅ 也能跑，**且不依赖任何权限** |

## 3. 具体做了什么 / 现在是什么状态

### 3.1 文件内容

`application/src/project.private.config.json`（**新增，未跟踪**）：

```json
{
  "appid": "touristappid",
  "libVersion": "3.16.1",
  "projectname": "application",
  "setting": {
    "urlCheck": false,
    "coverView": true,
    "lazyloadPlaceholderEnable": false,
    "skylineRenderEnable": false,
    "preloadBackgroundData": false,
    "autoAudits": false,
    "showShadowRootInWxmlPanel": true,
    "compileHotReLoad": true
  }
}
```

真正起作用的只有两项：`appid` 和 `setting.urlCheck`。
其余是开发者工具自己写进去的默认值，跟着原样留着，不用管。

### 3.2 为什么「开发者权限都加好了」还留着 `touristappid`

因为权限是**跟着账号走**的，而这个文件是要**提交进仓库、给所有人用**的：

- 用 `touristappid` → 谁 clone 下来都能直接跑，不需要求管理员加权限；
- 用真 appid → **只有有开发者权限的账号**能跑，别人一跑就撞上 §2.2 那句误导性报错。

**选用 `touristappid` 是拿「更接近真实环境」换「谁来都能跑」。** 对 E2E 来说后者更值。

代价只有一个：游客模式下开发者工具会报 `gettestpublib Error 41002, appid missing`。
**已证实这个错不影响跑通**（成功的运行里也有它），它只是说明拿不到测试库/发布相关能力 ——
那两样我们不用。

> **想切回真 appid**：把 `"appid"` 那一行改成 `"wx4345af65c586dd70"` 即可，一行的事。
> 什么时候才需要切：要测**跟 appid 绑定**的能力（`wx.login` 的真实 code、云能力、真机发布）。
> 切之前请确认跑测试的账号有开发者权限，否则就是 §2.2。

### 3.3 文件**必须**放 `src/`，不能放仓库根目录

这是整件事里最容易踩错、也最花时间的一点。

uni-app 编译小程序时会把一批文件拷进产物目录 `dist/dev/mp-weixin/`。
它的拷贝清单在 `@dcloudio/uni-mp-weixin/dist/uni.compiler.js:211-232` 的 `copyOptions.targets` 里，
里面**确实有** `project.private.config.json` —— 但清单里的路径是相对**编译入口目录**（也就是 `src/`）
解析的，**不是仓库根目录**。

而开发者工具打开的是**产物目录**。所以：

| 文件放哪 | 结果 |
|---|---|
| `application/project.private.config.json`（仓库根） | ❌ **不会进产物**，开发者工具读不到 → 改了等于没改 |
| `application/src/project.private.config.json` | ✅ 出现在 `dist/dev/mp-weixin/`，生效 |

**这不是推断，是实测**：放根目录 → dist 里没有这个文件；放 `src/` → 出现且生效。

## 5. 怎么验证它真的生效了

三步，都可直接跑：

```bash
# ① 编译（Windows 侧；WSL 里跑 uni build 会因为 node_modules 是 Windows 装的面报 rollup 错）
cd application && npm run dev:mp-weixin

# ② 产物里必须有这个文件
ls dist/dev/mp-weixin/project.private.config.json

# ③ 生效值要是「合并后」的 —— private 覆盖 public，别只看 uni 生成的那份
node -e "const b=require('./dist/dev/mp-weixin/project.config.json');const p=require('./dist/dev/mp-weixin/project.private.config.json');console.log({...b.setting,...p.setting}.urlCheck, p.appid||b.appid)"
# 期望输出：false touristappid
```

另外，E2E 用例自己会拦一道：`application/e2e/helpers/env.js` 里的
`assertUrlCheckDisabled()` 和 `assertTouristAppId()` 读的就是**合并后**的值，
对不上会直接让用例失败，而不是让你跑出一个莫名其妙的红。

## 6. 注意点

1. **别用开发者工具里「不校验合法域名」那个勾选框代替这个文件。**
   那个勾选框改的是**产物目录**下的 private config，重新编译可能被清掉；
   而且后面 E2E 是 jest 无人值守跑的，**没有 UI 可以点**。只能当临时排查手段。

2. **报错 `please make sure http port is open` 不等于端口问题。**
   上面 §2.2 说过。这条 + 「残留的开发者工具进程占着 9420」是同一句话的两个来源，
   排查顺序：先看 appid 和登录，再看残留进程，最后才怀疑端口配置。

3. **`urlCheck: false` 到底是不是必需的，我们没能证明。**
   实测：在 `urlCheck` 设回 `true` 的情况下，整套 P4 用例**依然全绿**
   （其中 P4-02 需要一次真实的 HTTP 往返才能拿到 401，所以请求确实发出去了）。
   也就是说，开发者工具在当前配置下**可能本来就放行 localhost**。
   我们保留 `urlCheck: false` 是**零成本保险**（将来换真 appid 时更可能需要它），
   **但别把「必须关 urlCheck」当成已验证的事实。** 详见 [08 §3.4](08-实测记录-2026-09-30.md)。

4. **`urlCheck` 只管本地开发。** 发布后的域名校验由微信服务端强制，跟这个开关无关 →
   关掉它**不构成线上风险**。

5. **这个文件是「个人层」，开发者工具可能自己改写它。**
   如果哪天发现内容变了、多了字段，先看是不是工具自己加的，别急着当 bug 处理。

## 7. 还没做完的（接手前要知道）

- ⚠️ **【2026-10-03 订正】之前写在这里的「`jest` / `cross-env` 没写进 `package.json`，换机器就装不上」
  是错的。** 实测：只拿 `package.json` + `package-lock.json` 在一个空目录跑 `npm ci`，
  装出来的正是 `jest 27.0.4` + `cross-env 7.0.3` + `jest-environment-node 27.5.1`，
  二进制也在 `node_modules/.bin/` 下。
  原因是 `@dcloudio/uni-automator` 自己声明了 `jest: "27.0.4"` / `jest-environment-node: "27.5.1"`
  为 **peerDependencies**（还是**精确版本**，不会漂），`cross-env: ^7.0.3` 则是它的**直接依赖**。
  npm 7+ 会自动装 peer，cross-env 被提升到根 → 两者都会到位。
  **所以依赖这块本来就是可复现的，不用补 `devDependencies`。**
- ✅ **`test:e2e` 脚本已加**（2026-10-03）。还有 `e2e:patch` / `e2e:patch:check` 两个辅助脚本。
- ✅ **`node_modules` 的补丁已固化**（2026-10-03）。原先的「4 处手工补丁」已精确核实为
  **2 个文件里的 4 处改动**，写成了可审阅、幂等的脚本
  `application/e2e/patches/apply-node-modules-patches.js`，
  由 `npm run test:e2e` 在开跑前自动应用。详见 [08 §5.2](08-实测记录-2026-09-30.md)。
  **故意不做 `postinstall` 钩子** —— 这两个文件只有跑 E2E 才用到，不该让日常开发的人也承担副作用。
- `E2E_MOCK_LLM`（要不要 mock 大模型）、CI 怎么跑 —— **均未定**。
- 以上所有改动**都还没提交**（两个仓库都没提交）。
