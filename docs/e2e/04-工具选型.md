## 二、候选方案逐个评估

### A. `@dcloudio/uni-automator` + jest ⭐ 推荐

**它是什么**：uni-app 官方 E2E 框架。`Automator → Launcher → Puppet → Program` 分层，微信小程序平台的 Puppet 实现（`packages/uni-mp-weixin/lib/uni.automator.js`）**底层同样是驱动微信开发者工具 CLI**，与 `miniprogram-automator` 属同一套底层机制，但对上暴露跨平台的 `program` 对象。

**为什么适合本项目**：

| 契合点 | 说明 |
|---|---|
| ⭐ **已在依赖里** | 见上。只需再加 `jest` + `jest-environment-node` + `cross-env` |
| ⭐ **Mock API 是 `uni.` 前缀** | `program.mockUniMethod('showModal', ...)` / `program.callUniMethod('setStorageSync', ...)`。本项目代码里用的**正是** `uni.showModal` / `uni.showToast` / `uni.setStorageSync`（[SessionDrawer.vue:184](application/src/components/chat/SessionDrawer.vue#L184)、[auth.ts:110-120](application/src/utils/auth.ts#L110-L120)）→ **不用做 `wx.` ↔ `uni.` 的适配**，桩的粒度与代码调用点一一对应 |
| **自带编译** | `testEnvironmentOptions.compile: true` → 测试前自动跑 uni 编译，不需要单独的 build 步骤（本项目没有 build 产物目录，正好） |
| **`program.evaluate` 可用** | 用于读页面内全局可达对象（[03 §三](03-E2E用例清单.md) 的断言手段 ③） |
| **不挑平台** | 若以后 `API_BASE` 改成可配置、想在 H5 上跑更快的冒烟，同一套 `program` API 可复用（但**SSE 仍必须在小程序端跑**，见 §五） |

**配置模板**（新增 `application/jest.e2e.config.js`）：

```js
module.exports = {
  globalTeardown: '@dcloudio/uni-automator/dist/teardown.js',
  testEnvironment: '@dcloudio/uni-automator/dist/environment.js',
  testEnvironmentOptions: {
    compile: true,
    'mp-weixin': {
      port: 9420,
      launch: true,
      teardown: 'disconnect',   // 保留开发者工具，避免每轮冷启动 6~12s
      remote: false
      // executablePath: 开发者工具 cli 路径，自动查找失败时填
    }
  },
  testTimeout: 30000,                 // 全局；SSE 用例内部单独设 130000
  testMatch: ['<rootDir>/e2e/**/*.e2e.js'],
  watchPathIgnorePatterns: ['/node_modules/', '/dist/', '/.git/']
}
```

```jsonc
// package.json 追加（不新增生产依赖）
"scripts": {
  "test:e2e": "cross-env UNI_PLATFORM=mp-weixin jest -i --config jest.e2e.config.js",
  "test:e2e:auth": "cross-env UNI_PLATFORM=mp-weixin jest -i --config jest.e2e.config.js -t 'P4'"
}
```

**已知约束（必须在用例里绕开）**：

| 约束 | 影响 |
|---|---|
| **微信 element 不能跨组件选择**，且**不支持父子选择器** | `page.$('.a .b')` 无效。→ 强化了 [03 §1.4](03-E2E用例清单.md) 的"请前端补 `id`"要求：**顶层用 `page.$('#id')` 最稳**，祖先→后代要分两次 `$` |
| 分包页面 `reLaunch` 后需 `await page.waitFor(7000)` 再取 `currentPage()` | 本项目**未配置分包**（`pages.json` 无 `subPackages`）→ 不受影响，但改动 `pages.json` 时要留意 |
| `evaluate` 仅开发者工具模拟器可用、**无法闭包引用外部变量** | 读 store 只能读全局可达对象；[03](03-E2E用例清单.md) 的"需确认 #4"依然成立 |
| jest **≤ 27.0.4**、`jest-environment-node` **≤ 27.5.1** | 见 §六 版本风险 |

### B. `miniprogram-automator`（裸用，微信官方 SDK）

- npm 最新 **v0.12.1**，**自 2023-11 起停止更新**，无公开仓库、无法 fork/提 PR。
- 2025 年在新版开发者工具（实测 `2.01.2510290`）下出现**两处硬伤**：① `launch()` 在 Windows + 新 Node 下稳定 `spawn EINVAL`（BatBadBut 相关，却误报为"cliPath 不正确"）；② **`Page.*` 协议族整族超时** → `page.$` / `page.$$` / `page.data()` / `setData` / `tap` 全部超时，而 `App.*`（`evaluate`/`reLaunch`/截图）正常。社区判定为 SDK 与开发者工具的版本错配。
- 另有"**亚秒级 launch 假成功**"陷阱：devtools 被 kill 后不会立即释放 9420 端口，残留会话会让 `launch()` 在 0.4s 内假连成功。冷启动正常需 6.5–12.3s。
- **结论**：不是不能用（社区有 `miniprogram-automator-next` 等 fork 重建了 Page 能力），但**引入一个停更的官方 SDK 或它的第三方 fork，对"组长 review"这个场景是减分项**。且 uni-automator 已覆盖它的能力 → **不选**。

### C. `Minium`（微信官方，Python 版）

| 项 | 情况 |
|---|---|
| 性质 | 微信官方小程序自动化框架，**JS 版已停止维护，Python 版在维护**（最新 `1.0.0b2`，beta 编号） |
| 运行位置 | **开发者工具模拟器 / 真机 / 云测三端都能跑**（不是只能真机） |
| 语言 | Python 3.8+（部分资料建议避开 3.10+） |
| ⭐ **与后端栈的配合度** | **这是它唯一无可替代的优势**：同为 Python，基于 `unittest` 封装，**pytest 可以直接收集并运行 `unittest.TestCase`** → E2E 与 `docs/api/` 的接口测试、L3 契约测试可以用**同一条 `pytest` 命令、同一套 fixture、同一份报告** |
| 短板 | ① 版本号仍是 `b`（beta）；② 需要单独的 minium 运行时（`pip3 install https://minitest.weixin.qq.com/minium/Python/dist/minium-latest.zip` —— **是 URL 直装，不走 PyPI**，与"poetry 管理依赖"的规范冲突，只能装在**独立虚拟环境**里）；③ 装上后与后端 poetry 环境**不能共存**（Python 版本/依赖冲突风险）；④ 元素定位 API 与 `program` 完全不同 → [03](03-E2E用例清单.md) 的用例要重写一遍 |

**判定**：**作为 Plan B 保留**，不作为首选。理由：它的核心优势（同语言）被"必须独立虚拟环境 + URL 直装 + beta"抵消了；而 uni-automator 的核心优势（已在依赖里 + `uni.` 前缀桩直接对应）无法被替代。**如果实测 jest 27 在当前 Node 22 上跑不起来，再切它**。

### D. 微信云测 MiniTest

| 项 | 情况 |
|---|---|
| 成本 | 普通小程序开发者 **每周 150 分钟免费**；专有云 **1600 元/台/月（<10 台）、1400 元/台/月（≥10 台）** |
| 扣费规则 | 总时长 = Σ(设备数 × 测试时长)，**每台至少扣 10 分钟**；Minium 自定义任务默认 20 分钟（范围 10–240） |
| 容量测算 | 本方案 25 条用例、单轮约 15–25 分钟 → **每周 150 分钟只够跑 7 次左右**，且**无法按需只跑一条**（最小 10 分钟/台） |
| 致命问题 | ① **它跑的是真机上的小程序包，测试脚本跑在云上，本机 CI 无法编排**；② 自动化脚本只能上传、不能调试；③ **它会打到你在 `API_BASE` 里配置的那个后端**（当前硬编码生产 `https://ai-etf.xyz`）—— 在云真机上跑交易用例就是**对生产库做真实申购** |
| 判定 | **不用**。与"逐步落地、随时本地回归"的目标不符；且当前 `API_BASE` 硬编码生产，用它等于直接对生产做写操作 |

### E. 明确排除的两条"捷径"

| 方案 | 为什么排除 |
|---|---|
| **用 H5 端 + Playwright/Cypress 代跑** | ⭐ H5 与小程序是**两条不同的代码路径**：H5 走 `fetch` + `ReadableStream`（[index.vue](application/src/pages/index/index.vue) 的 H5 分支），小程序走 `uni.request` + `enableChunked` + `onChunkReceived`。**全项目技术风险最高的正是小程序那一支**，用 H5 跑等于把风险最大的部分排除在覆盖外。可作为**补充**（H5 冒烟更快），不能作为**替代** |
| **只做接口级测试，不碰 UI** | 无法覆盖 `request.ts` 的本地过期分支、`expireAuthAndRedirect` 的跳转时序、页面级状态与后端的对齐 —— 而这些恰好是 P4 的全部价值。接口级测试（已有）与 E2E 是**互补**不是替代 |

## 四、⚠️ SSE + `enableChunked` 在自动化上的难点（用户点名项）

**先给结论：小程序端的 SSE 无法在自动化里被"直接观测"。** 分块协议的正确性只能靠单测证明，E2E 只能证明"用户最终看到了回复"。以下是逐条原因与对策。

### 4.1 根本原因：automator 没有网络层

`program` / `miniProgram` 的 API 全集是：**页面导航、元素查询与交互、页面数据读写、截图、`callMethod` / `mockMethod` / `evaluate`**。它**没有** go 标准的：

- ❌ 网络拦截 / 请求响应监听（无 `page.on('response')`、无 `networkidle`）
- ❌ CDP / DevTools Protocol 挂载点
- ❌ 请求计数

> 微信开发者工具本身有 Network 面板，但**automator 协议不暴露它**。因此"抓 SSE 的原始帧"在小程序自动化里**做不到**——这不是工具选得好不好的问题，是协议能力的边界。

### 4.2 因此产生三个必须接受的现实

**① 无法断言"数据是分块到达的"。**
`RequestTask.onChunkReceived` 的**回调时机、chunk 大小、是否合并小 chunk 全部由微信运行时决定，不受你控制**。写 `expect(chunkCount).toBeGreaterThan(1)` 这种断言**必然不稳定**（运行时完全可能一次把整个响应交给你）。这是最反直觉的一点：*在小程序自动化里，"验证流式"这件事本身是不可靠的*。

**② 能做的只有弱证据。** E2E 里对 SSE 唯一稳健的断言是：**对 bot 气泡文本按固定间隔采样，要求出现 ≥2 个互不相同的非空文本**（[03 P2-01](03-E2E用例清单.md) 断言③）。它能区分"流式"与"一次到位"，但**不能**证明分块边界处理正确。

**③ 正确的做法是把协议断言下沉到两层**：

| 层 | 能拿到什么 | 断言什么 |
|---|---|---|
| **L1 单测（关键）** | 人造的分块字节流 | ⭐ `createUtf8StreamDecoder`：**把 3 字节中文手动切成 2+1 两个 chunk**，断言输出无 `�`；emoji（4 字节）同理；非法字节 → `�`；有/无 `TextDecoder` 两条实现<br>⭐ `parseSSELine`：`data: {...}` / `done` 带 `chat_id` / `error` / 坏 JSON → `null` / 空行 |
| **L3 契约（关键）** | **原始响应字节**（httpx 直连后端） | 帧格式严格 `data: {...}\n\n`、无 `event:`/`id:`/`retry:`、至少 1 个 `token` 帧、**恰好 1 个** `done` 帧、`X-Session-ID` 响应头、中文为原始 UTF-8（`ensure_ascii=False`） |
| L4 E2E | 只有 UI | 结构断言（非空、非「抱歉，」、角色正确、"文本变化过"、`chat_id` 被落地 → 用后端 `GET /chats` 交叉验证） |

> **一句话**：`enableChunked` 的难点不在于"难写用例"，而在于**"自动化工具的能力边界恰好缺了观测流的那一环"**。承认它、把断言放到能拿到字节的两层去，是唯一正确的处置。硬在 E2E 里做流式断言，只会得到一条随机红绿的用例。

### 4.3 三个可操作的缓解手段

1. **SSE 用例必须单独设超时**：前端首 token 65s / 总请求 120s（[index.vue:63-66](application/src/pages/index/index.vue#L63-L66)）→ 该用例 `testTimeout` 至少 **130000**，远超 jest 默认 5s 与全局 30s。这也意味着**它会独自拖长整个 suite 2 分钟以上**。
2. **⭐ 建议给后端加一个 LLM mock 开关**（**需确认 #6**，本轮唯一建议的后端改动）：环境变量如 `E2E_MOCK_LLM=1`，命中时把 SSE 换成**固定内容的确定性流**（仍走真实的 `StreamingResponse` 与 `sse.py` 封装，只是内容可预测）。收益：
   - P2 从"有成本 + 非确定性 + 130s"变成**可进 CI 的确定性用例**；
   - 可以断言**内容**而不只是结构（"回复里必须含 `ETF`"）；
   - 若 mock 实现成**故意分成多个小帧**，还能让"文本递增"这条弱证据变成强证据。
   - ⚠️ 必须确保 mock 分支**仅在非生产环境**可用，与 `_get_test_user` 的 `ENV != production` 保护同款（[portfolio.py:50-56](ai-etf/server/api/portfolio.py#L50-L56)）。
3. **不要试图在 E2E 里断言"没发请求"**：像 P4-01（本地过期不发请求）在 automator 上无请求计数可用。改为**读后端访问日志做反向证据**（"这段时间内该 token 无新请求"）——这是唯一可靠的做法，比 UI 断言强。

## 五、⚠️ 执行环境与版本风险（**这块比选型更容易翻车**）

### 5.1 拓扑：E2E 必须在 **Windows 侧**跑，不能从 WSL 拉起（**已实测确认**）

本机实测：`uname -a` = `Linux ... microsoft-standard-WSL2`，`/etc/resolv.conf` nameserver = `10.255.255.254`。

**问题链条**：
1. 微信开发者工具是 **Windows/macOS 应用**，WSL 里没有（默认路径 `"/mnt/c/Program Files (x86)/Tencent/微信web开发者工具"` 实测不存在）。
2. uni-automator 对 mp-weixin 的处理是**spawn 开发者工具的 `cli.bat`** 并通过 **WebSocket 连 `ws://127.0.0.1:9420`** 驱动它。
3. WSL2 的 localhost 转发是**Windows → WSL 单向**可用。devtools 的 9420 **只监听 Windows 侧 127.0.0.1** → **WSL 里的 jest 连不上**。

**→ 推荐拓扑（Windows 侧只放测试运行器，一切业务代码仍在 WSL）**：

```
┌─ WSL2 ─────────────────────────┐      ┌─ Windows ───────────────────────┐
│ 后端 uvicorn  :8000             │◄─────┤ 微信开发者工具 + cli.bat :9420   │
│  pytest / 契约测试 / fixture     │      │ jest + uni-automator            │
│  poetry / Node 22（开发用）      │      │ Node 16/18（E2E 专用，见 5.2）    │
└────────────────────────────────┘      └─────────────────────────────────┘
        ▲  Windows→WSL localhost 转发可用  ▲  同机 127.0.0.1 直连
```

- ✅ **Windows → WSL 的 `http://localhost:8000` 可用**（WSL2 localhostForwarding）→ 小程序能打到 WSL 里的后端。
- ❌ 反向不可用 → E2E 的 jest **必须在 Windows 上运行**，`application` 仓库需要**在 Windows 侧也放一份**（或在 Windows 上 clone）。
- 若坚持从 WSL 跑：需要在 Windows 上 `netsh interface portproxy` 把 `0.0.0.0:9420` 转发到 `127.0.0.1:9420`，并处理防火墙 —— **不建议**（多一层会坏的环节）。

> **需确认 #8**：开发者工具的实际安装路径与版本。当前默认路径未找到 → 需你确认装在哪、什么版本，并**登记版本号后锁死**（见 5.3）。

### 5.2 Node 版本冲突（**高概率翻车点**）

| 事实 | 后果 |
|---|---|
| uni-automator 要求 `jest ≤ 27.0.4`、`jest-environment-node ≤ 27.5.1` | 必须装 jest 27 |
| 本机 `node -v` = **v22.21.0** | **jest 27 官方支持的 Node 范围是 10/12/14/15/16**，Node 22 **不在支持列表内** |
| jest 27 的传递依赖（`graceful-fs` 等）在 Node 18+ 有已知告警/报错 | 可能直接 `Cannot find module` 或启动即崩 |

**处置（按优先级）**：
1. **E2E 专用 Node 16 或 18**（Windows 侧用 `nvm-windows`），与开发用的 Node 22 **隔离**。这是最稳的。
2. 先实测一次 `Node 22 + jest 27` 能否跑通（可能没事，只是不在支持列表）。**若可跑通就不要折腾 nvm**。
3. 若二者都不行 → 切 **Plan B（Minium）**。

> **需确认 #9**：Node 22 + jest 27 的实测结果。这是**阶段 1 的第一个动作**，它决定整条技术路线是否成立。

### 5.3 必须**锁死**开发者工具版本

§2.B 记录的两处硬伤（`launch()` spawn EINVAL、`Page.*` 整族超时）**都是版本错配引起的**，而非基础库问题。因此：

- ✅ **记录当前可用的开发者工具版本号，写入测试文档，禁止自动更新**（工具设置里关掉自动升级）。
- ✅ 出现 `Page.*` 超时时的第一反应是**换回已知可用版本**，不要去改用例。
- ⚠️ 另需区分两个端口：**9420 是自动化端口**（automator 用），**服务端口**（如 55975）用于 CLI 登录/预览/上传 —— 在开发者工具「设置 → 安全设置 → 服务端口」里开启自动化测试。

## 六、与后端 pytest 栈的配合方式

选 uni-automator 就意味着**两套运行器**，需要明确分工（这也是它不是"完美方案"的唯一代价）：

| 受众 | 命令 | 报告 |
|---|---|---|
| 后端（你） | `poetry run pytest` — 含 L3 契约测试（新增 marker `contract`） | 现有 pytest 报告（`docs/单元测试/`） |
| 前端（同学） | `npm run test:e2e` — L4 用例 | jest 报告（需加 `--json --outputFile` 便于汇总） |

**桥接两套的方式（低成本）**：

1. **夹具复用后端能力**：`ai-etf/scripts/e2e_fixture.py` 提供 3 个子命令（`register` / `token` / `cleanup`），E2E 用例通过 `child_process.execSync` 调用它 → **账号注册、token 获取、清理全部由后端仓库脚本负责**，前端仓库不写任何后端调用逻辑。（**没有 `confirm-pending`**：确认后建仓已从 E2E 删除，见 [03 §二.1](03-E2E用例清单.md)。）
2. **交叉断言**（[03](03-E2E用例清单.md) 每条用例都用了）：E2E 用例用夹具拿到的 token 直连后端读真值，再比对 UI 文本。这一步天然把两个仓库串起来。
3. **统一的"用例 ID"**：jest 的 `test.each` 名字里带 `P1-03` 这类编号，与 [03](03-E2E用例清单.md) 一一对应 → 两套报告可以人工拼成一张总表。
4. **CI 编排**：L3 与 L4 分开 job，L4 只在 Windows runner 上跑（若将来上 CI，需 Windows runner —— 这是本方案唯一的 CI 成本）。
