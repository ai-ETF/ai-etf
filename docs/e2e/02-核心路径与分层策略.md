## 一、对 00 文档 4 条候选路径的取舍

| 候选（00 文档 §4.4） | 判定 | 理由 |
|---|---|---|
| **P1** 注册→登录→风险测评→申购→持仓/账户→赎回→流水 | ⚠️ **必须拆开** | ① **申购一律 pending**（[portfolio_service.py:596](ai-etf/server/services/portfolio_service.py#L596)），申购后**没有持仓、没有流水**；② 赎回会被「存在待确认的申购订单」拦截（[:725](ai-etf/server/services/portfolio_service.py#L725)）；③ 确认只发生在交易日 15:37 的调度任务或 `confirm-pending`（且只确认 `confirm_date <= today`），而**买单**落库的确认日 = `confirm_date` **再加 `confirm_delay` 个交易日** → **买单在任何时间、走任何途径都无法在会话内确认**（**赎单不同**：它落库的是未推进的 `confirm_date`，交易日 15:00 前下单当天即可确认——见 [03 §二.2](03-E2E用例清单.md)）。→ **"申购 → 持仓页看到该基金"这条链路永远走不通**，不是"前端走不通"而是"业务上就不通"。原样落地会得到一个永远失败、没人信的用例。（正确做法见 [03 §二.1](03-E2E用例清单.md)） |
| **P2** 登录→发消息(SSE)→会话列表→历史消息→重命名→删除 | ✅ **保留**，拆出 SSE 断言策略 | 5 个接口全部有真实入口（[01 §4.1](01-页面与API调用关系.md#41--有前端活跃调用点23-个-e2e-只能从这 23-个里挑) #4–#8）。重命名/删除走 `uni.showModal` → 自动化需桩（见 §四风险） |
| **P3** 登录→搜索→详情/K线→加自选→自选列表→移除/清空 | ✅ **保留**，删掉"榜单"暗示 | 4 个 watchlist 接口 + `search` + `detail` + `kline` 全部有入口。⚠️ 但 `ranking`（涨幅榜）**无前端入口**（[01 §5 修正清单](01-页面与API调用关系.md#二对-00-背景与已知问题md-的修正清单) 第 4 条），**不能**进用例 |
| **P4** 登录→访问受保护接口→登出→再访问(401)→跳转登录 | ✅ **保留并扩充** | 扩成**两条独立分支**：本地过期（不发请求就跳）与服务端 401（发请求后跳）。原写法把两者混为一谈，而它们的代码路径完全不同（[request.ts:39](application/src/utils/request.ts#L39) vs [:61](application/src/utils/request.ts#L61)），只覆盖一条会漏掉一半 |

### 另有两处 00 文档未意识到的问题

1. **`注销账号` 不能做成 E2E 路径**：它在 ✅要测范围内，但 `POST /api/secure-chat/delete-account` **前端零调用**（[01 §4.2](01-页面与API调用关系.md#42--无前端入口的业务端点19-个-不要设计进-e2e)）。→ 降级为**接口级用例**（含"密码错误返回 401"负例）。
2. **「个人中心 → 我的持仓」卡片疑似坏入口**：[settings/index.vue:309](application/src/pages/settings/index.vue#L309) 用 `uni.switchTab`，但 `pages.json` **无 `tabBar`** 段。→ E2E **绕开**此入口走 TabBar，并把该入口单列为「待确认缺陷」。

## 二、最终推荐：5 条核心路径（含优先级）

> 若只能做 3 条，取 **P1 / P2 / P4**。P3 与 P1 共用自选页与持仓 Tab，可合并；P5 最先砍。

| 序 | 路径 | 覆盖接口 | 优先级 | 为什么值得测 |
|---|---|---|---|---|
| **P1** | **交易核心：登录 → 自选页(持仓Tab) → 申购 → pending 语义 → 赎回拦截 → 交易记录** | account、positions、trade-flow、apply-purchase、apply-redeem、market/detail（6） | **P0** | 唯一涉及"钱"的路径；规则最复杂（白名单/最低额/冻结/pending/拦截）；`INITIAL_CASH=100000` 恒定 → **可精确断言数值**，不需要模糊匹配 |
| **P2** | **AI 对话核心：登录 → 首页发消息(SSE) → 会话列表 → 历史消息 → 重命名 → 删除** | secure-chat(SSE)、chats、messages、title、delete（5） | **P0** | 首页门面；SSE + `enableChunked` 是全项目**技术风险最高**的一处；历史上的重命名 404 bug 就出在这条链上 |
| **P4** | **鉴权失效：本地过期分支 + 服务端 401 分支** | 任意受保护接口 + `/api/market/` 放行例外 | **P0** | 横切所有页面；`expireAuthAndRedirect` 有互斥锁与两段延时，**最容易被改坏且最不容易被发现**；组长明确要求覆盖 |
| **P3** | **行情 + 自选：登录 → 搜索 → 详情/K线 → 加自选 → 自选列表 → 移除 → 清空** | search、detail、kline、watchlist×4（7） | **P1** | 高频日常操作；接口简单、风险低 → 顺位在 P4 之后（但改坏了最容易被用户立刻发现） |
| **P5** | **注册 + 风险测评：注册 → 自动登录 → 风险测评 → 提交 → 画像展示 → 重新进入显示已测评** | register、questionnaire、submit、profile（4） | **P2** | 一次性路径，回归价值低；且**每跑一次就在 Supabase 真实建一个用户**（需清理脚本），成本最高 |

### 为什么这样排序

- **P1 > P2？** P1 涉及资产数值与多条业务规则，缺陷后果最重；且它的"pending 语义"是**产品规则**，必须被固化下来，否则以后有人改成"立即建仓"没人知道。
- **P4 进 P0 而不是 P2？** 它代码量最小、断言最确定、覆盖所有页面，**投入产出比最高**。而且 `expireAuthAndRedirect` 的 `redirecting` 锁 + `setTimeout(250)` + `complete` 里再 `setTimeout(300)` 这种写法，任何重构都可能悄悄破坏它。
- **P5 最后？** 注册是真写库操作，且风险测评与交易无耦合（[portfolio_service.py:579](ai-etf/server/services/portfolio_service.py#L579) 风险提示是"建议性，不影响交易"）→ 拆开没有任何损失。

## 三、分层策略

> 现状：后端已有单元 + 集成测试（`docs/单元测试/`、`docs/integration/`）；**前端零测试**。
> 原则：**把每一层断言下沉到能拿到原始字节的最低层**，E2E 只验证"用户看见的东西"。

| 层 | 做什么 | 工具 | 优先级 | 现状 |
|---|---|---|---|---|
| **L1 前端单元** | 纯函数：JWT 解析、会话有效期计算、SSE 行解析、UTF-8 流式解码、store 纯状态变更 | Vitest | **P0** | ❌ 从零 |
| **L2 前端集成** | `store / composable ↔ utils/request.ts` 的交互：401 跳转、token 注入、行情放行、竞态丢弃旧响应 | Vitest + mock `uni.*` | **P1** | ❌ 从零 |
| **L3 契约** | ①「前端 23 个调用点 ↔ 后端路由」存在性与参数名对齐；② openapi schema 校验；③ 鉴权分级（JWT/公开/`X-User-Id`）不被误改 | pytest（复用现有 marker 体系） | **P0** | ❌ 新增（**成本最低、直接防住已发生过的两类 bug**） |
| **L4 E2E** | 上述 5 条路径，真跑微信小程序 | uni-automator / miniprogram-automator（见 [04](04-工具选型.md)） | **P0**（P1/P2/P4） | ❌ 从零 |

### 3.1 L1 前端单元测试 — 具体清单

### 3.2 L2 前端集成测试 — 具体清单

手段：Vitest + 自写 `uni` 全局桩（`uni.request` / `uni.getStorageSync` / `uni.showToast` / `uni.reLaunch` 记录调用）。**不测 `.vue` 渲染**（uni-app 的组件测试环境不成熟，收益低）。

| 目标 | 断言 |
|---|---|
| `utils/request.ts` 的 401 拦截 | mock 返回 401 → `reLaunch` 被调用且 url=`/pages/login/index`；`removeStorageSync` 清掉 4 个 auth key；**且 promise rejected** |
| **行情放行例外** | `GET /api/market/search` 在**无 token** 时**照常发请求**、**不**跳登录；而 `GET /api/watchlist/list` 无 token 时**不发请求**、直接跳登录 |
| token 注入 | 有会话时 header 带 `Authorization: Bearer <token>`；请求 URL 非 `http` 开头时自动补 `API_BASE` |
| 竞态丢弃 | `watchlistStore.searchEtf` 连续两次调用，先返回的旧响应**不得**覆盖新结果（`searchRequestId` 机制，[stores/watchlist.ts:151-157](application/src/stores/watchlist.ts#L151-L157)）；`settings` 的 `accountRequestId`（[:211](application/src/pages/settings/index.vue#L211)）、`watchlist` 的 `portfolioRequestId` 同理 |

| # | 断言 | 防住的历史问题 |

| 视觉回归（截图比对） | 收益低、维护成本高 |

## 四、本阶段已知风险（在设计用例时已规避或标注）

| 风险 | 处置 |
|---|---|
| 交易路径**受真实时钟/交易日影响**（见 [01 §5.3](01-页面与API调用关系.md#53-交易链路的硬约束这条会决定-p1-能不能跑通)） | **已消除**：P1 全部 6 条用例只覆盖 pending 语义（下单/冻结/拦截/边界），**零时钟依赖**。曾设计的「确认后建仓」扩展**已删除**——因 `confirm_delay=1` 使**买单**确认日必然 ≥ 次日，E2E 内无法触发确认；该覆盖由后端集成测试 `tests/integration/server/jobs/test_scheduler_jobs.py` 承担。**赎单存在"交易日 15:00 前可当天确认"的窗口，已记入 [03 §二.2](03-E2E用例清单.md)——同样不做 E2E**（理由：确认触发者前端零调用 + 前置须夹具构造，收益低于已有集成测试）。详见 [03 §二.1](03-E2E用例清单.md)（含代码级论证） |
| SSE 走**真实 LLM**，非确定性 + 有成本 + 可能慢到 65s/120s 超时 | E2E 只断言结构（非空、非「抱歉，」开头、角色为 bot），**协议细节下沉到 C4**；CI 默认跳过完整流式用例。后端是否有 mock LLM 开关**需确认**（[01 §六](01-页面与API调用关系.md#六需确认不要当成事实用) #6） |
| 重命名 / 删除走 **`uni.showModal` 原生弹窗**，automator 难以驱动 | 用 `mockWxMethod('showModal', ...)` 桩掉弹窗并断言调用参数（**需前端同学配合确认可桩**） |
| **行情接口放行未登录**，容易让"401 该跳转"的用例假绿 | P4 显式断言这个例外：未登录时 `/api/market/` **不跳转**，其他**必须**跳转 |
| `API_BASE` **硬编码生产** | 见 [05-执行计划.md](05-执行计划.md) 阶段 0（必须让前端改成可配置，否则 E2E 只能打生产） |
| 注册用例**真写 Supabase 用户表** | P5 需配套清理（`delete-account` 或后台删除）；P5 优先级最低 |
