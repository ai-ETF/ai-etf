# 11-场外净值

**被测模块**：`server/services/fund_nav_service.py`（读）、`server/services/fund_nav_sync_service.py`（写）
**测试文件**：`tests/unit/server/services/test_fund_nav_service.py`、`test_fund_nav_sync_service.py`
**测试方法**：内存 `FakeClient` 记录查询链与 RPC 参数（`eq` 做等值过滤、`range` 做分页切片），
`FakeRouter` 造上游批量/单只/历史结果；不联网、不连 Supabase。

> 2026-10-27 新增。此前这两个服务零单测覆盖（`tests/unit/server/services/` 下没有对应文件），
> 而它们是订单确认取价的唯一通道，因此优先补契约用例，不追求行数。

## 功能

- **读服务**：净值唯一读入口，无缓存；`get_nav_on` 用五步判定区分「还没公布」「真实缺口」「本来就没有」。
- **写服务**：净值唯一写入口；批量源为主 + 单只兜底，写库只走 `merge_fund_nav` / `upsert_fund_nav_state` 两个 RPC。

## 业务场景 / 预期结果 / 测试结果（36 例，全部通过）

## 测试说明

- **未覆盖**：`startup_update_if_stale`、`_whitelist_codes` / `_position_codes` 的分页细节、
  `_fill_history` 中途写库失败的 `partial` 分支。这三处是调度胶水与异常路径，
  需要 APScheduler 运行或注入分段失败，收益低于成本；真实环境由集成测试与运维脚本覆盖。
- **契约优先于行数**：目录边界（`in_catalog`）、五步判定、不写 0 净值、失败只写
  `last_error`、写库只走 RPC —— 这五条是订单确认算错价的直接来源，各有用例守住。
- Fake 只实现 `eq` 等值过滤与 `range` 切片；`gt` / `in_` 由用例直接配置目标行，
  避免把 Fake 写成半个 PostgREST。
