# 10-交易日历缓存

**被测模块**：`server/services/trading_calendar_cache.py`、`server/services/trading_calendar.py`、
`server/api/admin.py`（日历部分）、`server/app.py`（lifespan 日历接线）、
`server/sources/registry.py`（`CAP_CALENDAR` 单源约束）
**测试文件**：`tests/unit/server/services/test_trading_calendar_cache.py`（25 例）、
`tests/unit/server/services/test_trading_calendar.py`（19 例）、
`tests/unit/server/api/test_admin_trading_calendar.py`（12 例）、
`tests/unit/server/api/test_app.py`（3 例）、`tests/unit/server/sources/test_registry.py`（新增 1 例）
**测试方法**：假 Supabase 客户端（按表返回预设行、模拟 `replace_trading_calendar` 展开）+
假 `SourceRouter` + `TestClient` 注入假缓存；门面通过 `install_snapshot()` 注入快照。
**全程禁网、禁外部 IO**，不连 Supabase、不调真实源。

> 原设计文档 §6「测试策略」与 §7.1 的测试结果已整体移入本文；设计契约见
> [`../../20-设计/基金与交易/交易日历缓存.md`](../../20-设计/基金与交易/交易日历缓存.md)。

## 功能

A 股交易日历的持久化快照：进程启动从 DB 载入交易日集合，请求路径只读内存；
运维通过管理接口人工全量刷新（拉取 → 校验 → diff → 事务性整表替换 → 原子替换内存）。
**无兜底**：快照未载入抛 `CalendarUnavailable`，日期越界抛 `CalendarOutOfCoverage`，
不按星期几猜测、不返回默认值。

## 测试数据集

| 数据组 | 内容 | 覆盖场景 |
|---|---|---|
| A 真实源形态 | `1990-12-19 → 2026-12-31`，工作日集合并剔除 2026 国庆假期（10/1、2、5、6、7），约 9.4k 个交易日 | 正式刷新、连续两次刷新幂等、dry_run diff、假期判定 |
| B 数量下限边界 | 以 `2026-12-31` 为终点倒数 999 / 1000 个工作日 | `MIN_TRADING_DAYS` 拒绝与恰好通过 |
| C 覆盖终点边界 | 以「今天」「昨天」为 `coverage_end` 各取 1200 个工作日 | `coverage_end < today` 拒绝、`== today` 通过 |
| D 空与非法 | 空交易日集合；`coverage_start > coverage_end` | 拒绝整次刷新，不写库 |
| E DB 快照行 | `trading_calendar_state` 单行 + 逐日行（含 `is_trading_day=false`），1002 行跨 1000 分页 | 启动载入、分页读取、`describe()` |

数据组 A 的 `REAL_END` 与源当前覆盖一致；**源年度滚动后需同步更新该常量**（见「数据集建议」）。

## 业务场景 / 预期结果 / 测试结果

### 一、门面 `trading_calendar.py`（19 例）✅

| 场景 | 预期 | 结果 |
|---|---|---|
| 集合判断：交易日 / 区间内周末 / 法定节假日（2026-10-01 周四） | 分别返回 `True` / `False` / `False` | ✅ |
| 快照未载入（`is_trading_day` / `is_trading_time`） | 抛 `CalendarUnavailable`，不返回 `False` | ✅ |
| 早于 / 晚于覆盖区间 | 抛 `CalendarOutOfCoverage`，错误信息带目标日期与区间 | ✅ |
| `calendar_status` 四态 | `TRADING` / `NON_TRADING` / `OUT_OF_COVERAGE` / `UNAVAILABLE` | ✅ |
| `reset_cache` 后 | 重新变为不可用 | ✅ |
| 交易时段边界 | 9:29 `False`、9:30 `True`、14:59 `True`、15:00 `False`、午夜 `False` | ✅ |
| 时区处理 | 带时区先换算北京时间（UTC 01:30 = 北京 09:30）；naive 视为北京时间 | ✅ |
| 非交易日盘中 / 日期越界 / 未载入 | 分别返回 `False` / 抛越界错 / 抛不可用错 | ✅ |

### 二、快照缓存 `trading_calendar_cache.py`（25 例）✅

| 场景 | 预期 | 结果 |
|---|---|---|
| 启动载入：DB 有数据 | `ready=true`，构建交易日集合，**不访问上游**（假 Router 被调用即失败） | ✅ |
| 启动载入：DB 为空 | `ready=false`，`CalendarUnavailable` 信息含「state 为空」 | ✅ |
| 启动载入：DB 读取异常 | 不抛异常、进程继续；`CalendarUnavailable` 信息含底层原因 | ✅ |
| 启动载入：state 缺覆盖区间 / 无交易日行 | 均视为不可用 | ✅ |
| 启动载入：交易日 1002 行 | 按 `PAGE_SIZE=1000` 分两页读完，集合完整 | ✅ |
| dry_run | 只计算 diff；已安装的旧快照引用不变；不调用 RPC | ✅ |
| 正式刷新 | 调用一次 `replace_trading_calendar`，参数为全部交易日 ISO 数组；内存立即替换；国庆假期判为 `False` | ✅ |
| 连续两次刷新（幂等） | 第二次 `inserted=0 / updated=0 / deleted=0`，`unchanged=自然日总数` | ✅ |
| 并发刷新 | 锁已被占用时抛 `RefreshInProgress` | ✅ |
| 整体超时（`REFRESH_TIMEOUT_SECONDS`） | 抛 `CalendarRefreshTimeout`，不调用 RPC，内存不变 | ✅ |
| 源失败 | 原始 `AllSourcesFailed` 上抛；旧快照引用不变；`last_error` 写入内存与 DB | ✅ |
| 写库失败 | 原始异常上抛；内存不替换；`last_error` 记录 | ✅ |
| 校验：空集合 / 999 个交易日 / 区间倒置 / `coverage_end < today` | 抛 `CalendarDataInvalid`，不写库 | ✅ |
| 校验边界：恰好 1000 个交易日 / `coverage_end == today` | 通过 | ✅ |
| 自然日展开 | 覆盖区间内周末展开为 `False`，行数 = 区间天数 | ✅ |
| diff 统计与明细 | 新增 / 更新 / 删除 / 未变计数正确，明细按日期排序 | ✅ |
| diff 超上限 | `truncated=true`，明细截断到 `DIFF_LIMIT`，统计仍完整 | ✅ |
| `install_snapshot` 无日期且无覆盖区间 | 抛 `ValueError` | ✅ |
| `describe` | 合并内存快照与 DB state；`days` / `trading_days` 取 DB 精确计数 | ✅ |
| `describe` DB 异常 | 不抛异常，响应带 `db_error` | ✅ |

## 数据集建议

1. **年度滚动时更新数据组 A 的终点**：`REAL_END = 2026-12-31` 与源当前覆盖一致；
   进入 2027 年后 `_validate` 会因 `coverage_end < today` 拒绝刷新，相关用例会失败。
   建议把终点改为源新公布的年末日期，并同步补一组「跨年新增交易日」的 diff 样本
   （预期 `inserted ≈ 365`、`deleted = 0`）。
2. **固化一份真实日历快照 fixture**：当前数据组 A 由「工作日 − 国庆假期」生成，
   不含调休补班（周末开市）等真实形态。建议录制一次 `sina_trade_date` 解码后的
   日期列表（约 8.8k 个交易日），断言「某春节周 / 某调休周六」的判定，防止用
   简化规则掩盖解析或数据问题。
3. **补一组「源截断」样本**：上游只返回近三年数据（约 730 个交易日）时，当前
   `MIN_TRADING_DAYS=1000` 会拒绝；若上游覆盖率下降到 1000–2000 之间，
   现有用例不会报警。建议补一组「覆盖终点正常但起点后移」的样本，确认整表替换会
   `deleted > 0` 且 `dry_run` 明细可被人核验。
4. **多进程场景不写单测**：Q5 已接受「多 worker 内存不一致」，进程内锁的单测
   只锁定当前单进程语义；引入共享版本号后再补。
