# 货币基金复投方案（万份收益 → 份额逐日增长）

## Context（背景）

当前货币基金（000198 天弘余额宝）的模拟方式为「份额不变 + 收益单独累计到 `positions.accrued_income`」：

- 每日 `当日收益 = 份额 × 万份收益 / 10000`，收益累加到 `accrued_income` 列，`quantity` 份额始终保持不变。
- 估值时 `市值 = 份额 × 1.0 + accrued_income`，盈亏 = `accrued_income`。

这是**单利**：`accrued_income` 本身不参与次日计息。

真实货基是**复投**：净值恒 1.0000，每日收益按净值 1.0 折算成份额加进去（`份额 += 收益`），次日收益在更大的份额上计算，份额逐日增长。

本次改动目标：把当前逻辑改为**真实复投**——份额逐日增长、复利计息。

## 关键事实

- 货基代码 `MONEY_FUND_CODE = "000198"`（天弘余额宝），净值恒 1.0000（`_get_nav` 直接返回 1.0，不走 akshare）。
- 万份收益数据源：天天基金 `api.fund.eastmoney.com/f10/lsjz`（DWJZ = 万份收益，如 0.2229 元/万份），由 `_money_fund_per10k_income()` 取最近一个完整计息日，失败时**直接抛错、不兜底**（既定决策）。
- 每日入账由 `spot_cache_scheduler` 的 `credit_money_fund_income` 任务在 **00:05** 执行（届时昨日万份收益已披露）。
- `positions` 表当前列：`quantity numeric(18,2)`（份额）、`cost_price numeric(18,4)`（加权平均成本）、`accrued_income numeric`（本次已上线的收益累计列，本地+远端均已应用 20260829094326）。
- 现有货基持仓仅 1 条：`b978e5f5-2908-4dc5-991e-5c4371cb60b0`，`quantity=56321.36`、`cost_price=1.056`（旧合成净值口径）、`accrued_income=1.26`。
- `accrued_income` 的引用范围（需全部改）：`portfolio_service.py`（`credit_money_fund_income`/`list_positions`/`_confirm_one_order` 买卖）、`schemas.py` `PositionItem`、`server/types/supabase.ts` + `src/types/supabase.ts`。前端组件与测试均不引用。

## 目标数据模型（改造后）

货基净值恒 1.0000，因此 `份额(quantity) = 市值(元)`。区分两个概念：

| 字段 | 含义 | 何时变化 |
|---|---|---|
| `quantity` | 份额（= 市值，NAV=1.0） | 申购 +、赎回 −、**每日收益 +** |
| `principal`（新列） | 累计投入本金（元） | 申购 +、赎回按比例 − |
| `cost_price` | 恒 1.0000（仅展示，不再作本金基准） | 不变 |

核心公式：

- **每日入账**：`income = quantity × per10k / 10000`（复利：quantity 已含历史收益）→ `quantity += income`，`principal` 不变。
- **估值**：`market_value = quantity × 1.0 = quantity`，`cost_value = principal`，`pnl = quantity − principal`，`pnl_pct = pnl / principal × 100`。
- **申购**：`quantity += amount`，`principal += amount`（申购费 0，net_amount = amount）。
- **赎回**：`redeem = quantity_sold × 1.0`，`principal_portion = principal × quantity_sold / current_qty`，`trade_pnl = redeem − principal_portion`，`principal −= principal_portion`。

不再需要 `accrued_income` 列，迁移时并入 quantity 后删除。

## 实施步骤（按顺序）

### 1. 数据库迁移（新建，不修改已 push 的 accrued_income 迁移）

`supabase migration new add_positions_principal_reinvest` 生成文件后写入：

```sql
-- 1. 新增本金列
ALTER TABLE public.positions ADD COLUMN principal numeric(18,2) NOT NULL DEFAULT 0;
COMMENT ON COLUMN public.positions.principal IS '货基累计投入本金（元）；非货基持仓恒为0';

-- 2. 回填货基：本金=份额×成本价；份额折算到 NAV 1.0 并并入已累计收益；成本价归 1.0
UPDATE public.positions
   SET principal  = ROUND(quantity * cost_price, 2),
       quantity   = ROUND(quantity * cost_price + COALESCE(accrued_income, 0), 2),
       cost_price = 1.0000
 WHERE fund_code = '000198';

-- 3. 删除 accrued_income（已被 quantity 取代）
ALTER TABLE public.positions DROP COLUMN accrued_income;
```

回填对现有持仓验证：principal=59475.36，quantity=59476.62，cost_price=1.0 → pnl=1.26 不变 ✓。成本价≈1.0 的新持仓同样成立。

执行：`supabase db push --linked --yes`，`supabase migration list --linked` 对齐；`supabase gen types typescript --project-id "wiynpkkfsiiqnofhifhs" > server/types/supabase.ts`，并同步 `src/types/supabase.ts`（positions 的 `accrued_income` → `principal`）。

### 2. 代码改动

**`server/services/portfolio_service.py`（主改动）**

- `credit_money_fund_income()`：不再写 `accrued_income`，改为
  - `income = (qty × per10k / 10000).quantize(0.01, ROUND_HALF_UP)`（qty 已含历史收益 → 复利）
  - `income <= 0` 跳过（子分位舍入到 0，非亏损；货基无日亏）
  - `UPDATE positions SET quantity = qty + income, updated_at = now`
  - 数据源失败仍直接抛错不兜底（保留既有行为）；单仓 DB 失败只记错不中断。
- `list_positions()` 货基分支：`principal = item.get("principal")`；`market_value = quantity`；`cost_value = principal`；`pnl = quantity − principal`；`pnl_pct = pnl / principal × 100`；`market_price = 1.0`；删除 `accrued_income` 相关代码。
- `_confirm_one_order()` 买入分支：货基专用分支替换加权平均成本——新仓 `quantity=actual_qty, principal=net_amount, cost_price=1.0`；加仓 `quantity+=actual_qty, principal+=net_amount, cost_price=1.0`；删除 `insert_data["accrued_income"]=0.0`。
- `_confirm_one_order()` 卖出分支：替换 `income_portion/accrued_income` 逻辑为 `principal_portion = principal × quantity / current_qty`；`net_amount = redeem_amount − actual_fee`；部分赎回 `quantity −= quantity_sold`、`principal −= principal_portion`；`trade_pnl = redeem_amount − principal_portion`；删除 `accrued_income` 核减。
- 注释更新：模块 docstring、`_get_nav` 注释等涉及 `accrued_income` 的说明，统一改为「收益转份额、份额逐日增长」。

**`server/services/spot_cache_scheduler.py`**：`_credit_money_fund_income_job()` docstring「入账到 accrued_income」→「收益转份额（quantity 增长）」。

**`server/models/schemas.py`**：`PositionItem` 删 `accrued_income`，加 `principal: Optional[float] = None`。

**类型文件**：`server/types/supabase.ts` 与 `src/types/supabase.ts` 的 positions Row/Insert/Update：`accrued_income` → `principal`。

## 已知取舍（非阻塞，可后续调整）

- **份额精度**：`quantity` 为 `numeric(18,2)`（2 位小数），与余额宝「按分」一致。单日收益不足 0.01 元（份额约 < 450 份）时舍入为 0、当日不增长——与真实货基按分计息一致。若需更细粒度可后续把 quantity 扩为 `numeric(18,4)`。
- **不回填历史**：沿用既定决策，从本改动上线后的下一个 00:05 起逐日入账。

## 验证

1. 迁移应用后查库：`positions` 有 `principal` 列、无 `accrued_income`；货基行 `principal=59475.36`、`quantity=59476.62`、`cost_price=1.0`。
2. 临时单测脚本（用完即删）：
   - 测试用户申购 100000 → 确认后 quantity≈100000、principal≈100000、cost_price=1.0。
   - 手动调 `credit_money_fund_income()` → 断言 quantity 增长、principal 不变、`list_positions` 的 pnl == quantity − principal。
   - 连续调用两次，断言第二次收益 ≥ 第一次（复利递增）。
   - 赎回全部 → 断言现金入账含全部收益、持仓删除、`trade_flow` 记录 `trade_pnl`。
   - 模拟数据源失败（改 fundCode 或断网）→ 断言 `credit_money_fund_income()` 抛 `RuntimeError` 且 quantity 不变。
3. `poetry run python -c "import server.app"` 确认应用可加载（18 条 portfolio 路由）。
