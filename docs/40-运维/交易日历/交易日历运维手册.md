# 交易日历 · 人工核验手册

> 配套技能：[`trading-calendar-ops`](../../../.claude/skills/trading-calendar-ops/SKILL.md)。
> **分工**：具体命令、接口调用、查库脚本都在技能里，由 AI 执行；本文只负责
> 「什么时候做、做完看什么、什么算正常、异常怎么决策、如何留痕」。
>
> **人工核验是日历正确性的最终保障**。接口返回 200 只能证明数据拉到了，
> 不能证明数据与国务院节假日安排、交易所公告一致；这一层判定必须由人完成。

---

## 1. 什么时候做什么

**每月 1–5 日 · 月度核验（只读）**

让 AI 按 `trading-calendar-ops` 的「流程 A」执行，或自己在 Supabase SQL Editor 跑
[附录 A](#附录-a独立核验-sql)。核对四件事：`ready`、覆盖区间、最近成功时间、下月非交易日。
把关键值填进 [交易日历核验记录](交易日历核验记录.md)。发现异常先不要改库，按 §5 判断。

**每年 11–12 月 · 年度拉取（写库）**

先确认国务院办公厅已发布**下一年**节假日安排。让 AI 先做 dry_run，把 diff 整理给你；
你对照公告确认后，再让它正式写库。写库后复核 status 和数据库行数，抽查元旦、春节。

> 判断依据不是「到了 12 月」，而是 **dry_run 返回的 `coverage_end` 已跨到次年 1 月 1 日**。
> 源没更新时 dry_run 仍会成功，但 `inserted=0`、覆盖区间不变，这时不写库，改为每周复检。

**交易所临时调整时 · 专项核验**

上交所/深交所临时延迟或暂停开市时（先例：2020 年春节后开市推迟），先看源是否已同步；
源未同步则以公告为准，按 §5 处理，并通知下单/确认相关方。

**服务部署或迁移后 · 首次初始化**

确认迁移已推送、`ADMIN_API_TOKEN` 已配置、首次刷新已完成。初始化后必须做一次月度核验：
`ready=true`、`days/trading_days` 正常、`last_error` 为空，才算上线完成。

## 2. 前置知识

| 项 | 值 |
|---|---|
| 交易日规则 | 周一至周五 − 法定节假日。**周末从不开市**，调休上班的周六日也不开市 |
| 唯一源 | `sina_trade_date`，返回 1990-12-19 → 当前源已公布的年末 |
| 覆盖区间 | 源返回的最早 → 最晚日期；整份落库，展开成自然日约 1.3 万行 |
| 权威依据 | 国务院办公厅《关于××年部分节假日安排的通知》；上交所/深交所休市安排公告 |
| 持久层 | `trading_calendar`（逐日）+ `trading_calendar_state`（单行状态） |
| 管理接口 | `POST /api/admin/trading-calendar/refresh`、`GET /api/admin/trading-calendar/status` |
| 鉴权 | 请求头 `X-Admin-Token`，与服务端 `ADMIN_API_TOKEN` 比对；未配置时接口返回 503 |
| 服务 | `fastapi.service`，部署目录 `/root/ai-etf` |

**2026-10-24 实测基线**（用于判断「数量级是否正常」，不是永久常量）：

- 覆盖 `1990-12-19 → 2026-12-31`，共 13162 个自然日，其中 8797 个交易日；
- `source=sina_trade_date`，`last_error` 为空；
- 截至该日，`coverage_end` 尚未跨到 2027-01-01，年度拉取要等源更新。

如果行数突然大幅偏离（例如掉到几千行），先怀疑源截断或写库异常，不要当成正常波动。

## 3. 月度核验判定标准

逐项对照，任一项不符就按「异常处理」列处理。

| 检查项 | 正常 | 异常处理 |
|---|---|---|
| `ready` | `true` | `false` → 快照未载入或读取失败，业务接口会报错；按 §5 转刷新 |
| `coverage_end` | ≥ 今天 + 45 天；11–12 月要求 ≥ 次年 1 月 1 日 | 不足 → 年度拉取前置条件未满足，每周复检；12 月仍不足则升级 |
| `coverage_start` | = 源最早日期（当前 1990-12-19） | 明显晚于源历史起点 → 快照被截断或写错，dry_run 核对 |
| `last_success_at` | 距上次成功拉取 ≤ 13 个月 | 超过 → 年度拉取漏做 |
| `last_error` | 为空，或已知且已处理 | 近期非空 → 看服务日志；仍失败按 §5 处理 |
| 行数完整性 | 覆盖区间内每个自然日恰好一行，无断档 | 断档 → 不要按日历下单/确认，重新 dry_run 并查写库 |
| 周末 | 所有周六/周日都是 `is_trading_day=false` | 出现周末开市 → 数据错误，暂停依赖日历的业务 |
| 下月非交易日 | 只有周末 + 国务院公告的法定节假日 | 含公告之外的工作日，或漏掉公告节假日 → **暂停按日历下单/确认**，按 §5 处理 |
| 抽样 | 下月 1 日、月末、春节/国庆等已知节点抽 1–2 个 | 不符 → 同上 |

### 3.1 怎么看「下月非交易日」

AI 的核验脚本会把下月非交易日按连续段列出，并标出其中的工作日：

- **全为周末** → 该月没有法定节假日，符合预期；
- **含工作日** → 这些工作日就是法定节假日，必须与国务院公告逐段对照。

例如 2026-10-24 实测：

- 2026-10-01 .. 10-07（7 天，含工作日）→ 国庆假期；
- 2026-10-08（周四）为交易日；
- 2026 年 11 月非交易日全部是周末（11/1、11/7–8、11/14–15、11/21–22、11/28–29），无额外休市。

### 3.2 判定结论怎么写

只有人工完成对照后才能写「本次核验通过」。AI 的输出最多写到「机械性检查通过，待人工确认」。
记录格式见 [交易日历核验记录](交易日历核验记录.md)。

## 4. 年度拉取的人工决策

### 4.1 允许写库的三个条件（全部满足）

1. 国务院办公厅已发布下一年节假日安排；
2. dry_run 返回的 `coverage_end` ≥ 次年 1 月 1 日；
3. dry_run 的 diff 已由人工看过，没有无法解释的改判或删除。

### 4.2 diff 重点核对区间

| 区间 | 关注点 |
|---|---|
| 次年 1–2 月 | 元旦、春节（含调休） |
| 4 月 | 清明 |
| 5 月 | 劳动节 |
| 6 月 | 端午 |
| 9–10 月 | 中秋、国庆（可能相连） |

规则：

- 调休上班的周六/周日**必须仍是 `is_trading_day=false`**；
- 历史日期一般不应变化；出现变化说明源修正了历史数据，必须对照公告确认；
- 出现「改判」或「删除」必须逐条对照公告；无法确认就中止，旧快照原样保留。

### 4.3 写库后人工确认

1. 正式调用的 `stats` 与 dry_run 一致；不一致说明期间源或 DB 变了，重新核验；
2. status 的 `coverage_end` 已前移、`last_success_at` 是刚才、`last_error` 为空；
3. 次年 1–3 月的非交易日与公告一致；
4. 下一交易日的确认日计算符合预期；
5. 记录到 [交易日历核验记录](交易日历核验记录.md)。

**不需要重启服务**：刷新在服务进程内完成，写库后直接替换内存快照。

## 5. 异常与临时调整

### 5.1 源未更新（coverage_end 不跨年）

不要反复拉取。每周复检 dry_run，等源包含次年日期后再走 §4。
进入 12 月仍拿不到次年数据：人工确认交易所公告，必要时按 §5.3 手工补，并升级处理。

### 5.2 交易所临时调整

1. 确认公告来源（上交所/深交所官网）；
2. 先 dry_run 看源是否已同步；
3. 源已同步 → 按 §4 正式刷新；
4. 源未同步 → **以公告为准**手工修正受影响日期（§5.3），记录依据和操作人；
5. 通知下单/确认相关方。

### 5.3 手工修正单行（最后手段）

- 只改 `trading_calendar` 中受影响的日期，并在 `trading_calendar_state` 记录依据；
- 改完必须**重启服务**，否则进程内存仍是旧快照；
- 下次成功刷新会整表覆盖，手工修正只在下一次刷新前有效；
- 下次 dry_run 会把这些修正显示为「改判」，由人决定是否 apply；
- 操作人、依据公告、日期范围必须写进[核验记录](交易日历核验记录.md)。

### 5.4 什么时候升级

- 12 月底仍无次年数据；
- 下月非交易日与公告不一致且无法确认原因；
- 连续多次刷新失败（源解析变化、熔断长期不恢复）；
- 需要手工改库且影响范围超过 1–2 天。

升级动作：暂停依赖日历的下单/确认，保留现场（status、日志、diff），通知相关方。

## 7. 常见问题

- **为什么周末调休上班也不是交易日？**
  A 股交易所在周六日从不开市，调休安排不影响证券市场。

- **为什么现在存全量历史，而不是只存当年？**
  表语义是「最后一次成功快照」，整表替换最直接；约 1.3 万行、一次年度写入，成本可忽略。
  只存当年会引入「窗口外旧行」这类半快照状态。见设计 §4.2.1。

- **为什么不每天自动拉？**
  日历一年只在公布下一年安排时变化；日更只能提前发现，不能提高正确性，
  正确性靠人工核验。日更还会在源本身出错时每天复制同一份错数据。见设计 §4.5。

- **为什么不能用上证指数日 K 作为备源？**
  它只能覆盖已经发生过的交易日，给不出未来日期；换源会把 `coverage_end` 缩到今天，
  导致「下一交易日/跨年确认日」直接越界。见设计 §5。

- **为什么快照没载入时接口直接报错，而不是按工作日判断？**
  按星期几猜会把法定节假日当成交易日，确认日会算错；宁可让请求失败并暴露问题。
  见设计 §1.3、§4.6。

- **为什么拉取后不需要重启？**
  刷新接口在服务进程内执行，写完 DB 后直接原子替换内存快照。见设计 §4.3。

- **为什么手工改库后必须重启？**
  内存快照只在启动时从 DB 载入；直接改库不会触发重新载入。刷新接口才会同时更新内存。

- **为什么接口要 `Idempotency-Key`？**
  写接口的幂等契约：整表替换本身幂等，key 用于日志追踪；缺失时接口返回 400。

## 附录 A：独立核验 SQL

在 Supabase SQL Editor 或 `psql` 执行，全部只读。AI 的核验脚本与本附录检查同一批数据。

```sql
-- 1) 状态：覆盖区间、最后成功、最近错误
SELECT coverage_start, coverage_end, last_success_at, last_error
FROM trading_calendar_state;

-- 2) 规模、交易日数、最早/最晚日期
SELECT count(*) AS days,
       count(*) FILTER (WHERE is_trading_day) AS trading_days,
       min(trade_date) AS first_day,
       max(trade_date) AS last_day
FROM trading_calendar;

-- 3) 断档检查：预期行数应等于 max - min + 1
SELECT (max(trade_date) - min(trade_date) + 1) AS expected_days,
       count(*) AS actual_days
FROM trading_calendar;

-- 4) 周末开市检查：应返回 0 行
SELECT trade_date
FROM trading_calendar
WHERE is_trading_day
  AND extract(isodow FROM trade_date) IN (6, 7)
ORDER BY trade_date;

-- 5) 下月非交易日：应只有周末 + 法定节假日
SELECT trade_date,
       to_char(trade_date, 'Dy') AS weekday
FROM trading_calendar
WHERE trade_date >= date_trunc('month', current_date + interval '1 month')::date
  AND trade_date <  (date_trunc('month', current_date + interval '2 month'))::date
  AND NOT is_trading_day
ORDER BY trade_date;

-- 6) 抽查已知节点（按当年公告替换日期）
SELECT trade_date, is_trading_day
FROM trading_calendar
WHERE trade_date BETWEEN '2026-10-01' AND '2026-10-09'
ORDER BY trade_date;
```
