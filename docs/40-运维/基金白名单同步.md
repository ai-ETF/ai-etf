# 白名单运维入口设计文档

> 主题：为「场外基金白名单同步」补一个可手动触发的运维入口，并修复使其无法跑完的写入缺陷。
> 相关联文档：[场外基金申购上限](../20-设计/基金与交易/场外基金申购上限.md)（同步链路的业务语义、白名单口径在该文）。

## 1. 背景与术语

| 术语 | 含义 |
|---|---|
| 白名单 | `fund_catalog` 视图：规则行存在 **且** `fund.lifecycle_status='active'`。能查到 = 系统支持该基金交易（旧表 `fund_fee_rules` 已由该视图兼容，见「2026-10-26 变更」） |
| 同步 | `FundCatalogSync.run()`：全量发现候选基金 → 逐只抓天天基金页面 → 幂等 upsert `fund` + `fund_trade_rule` + `fund_risk_profiles`（一次 RPC，一个事务） |
| flush | `run()` 内每攒够 `UPSERT_BATCH_SIZE=50` 只就调一次 `upsert_fund_catalog`；整批失败时降级为逐只重试（RPC 原子回滚，重试不会重复写） |
| fail-closed | 规则缺失/不可信时**拒绝写入**，不用默认值兜底。本模块既定原则（见同步模块 docstring 与旧设计文档第 4 节） |

**需求**：以后运维能随时手动刷新白名单，不必依赖次日 02:17 的定时任务。

## 2. 当前实现

### 运维入口

新增 `server/scripts/sync_fund_catalog.py`（目录需补 `__init__.py` 以支持 `-m` 调用）：

```bash
cd /root/ai-etf && .venv/bin/python -m server.scripts.sync_fund_catalog [选项]
```

| 选项                    | 说明                                                      |
| ----------------------- | --------------------------------------------------------- |
| `--limit N`             | 只处理前 N 只（试跑用，如 `--limit 5`）                   |
| `--codes 110020,000071` | 只处理指定基金代码                                        |
| `--interval S`          | 逐只抓取间隔秒数，默认沿用 `DEFAULT_REQUEST_INTERVAL=0.3` |
| `--dry-run`             | 抓取并组装，但**不写库**                                  |

- 脚本自行 `load_dotenv(项目根/.env)`（`load_dotenv` 默认不覆盖已有环境变量，本地开发亦安全）；
- 结束打印 `run()` 的统计 dict，并据此决定退出码：`0` 全部成功；`1` 有坏行或异常；`2` 未取到同步锁（已有同步在跑）；
- 服务端用法：`setsid nohup … > /tmp/fund_sync.log 2>&1 < /dev/null &` 可脱离 SSH 会话。



### 具体内容

| 环节 | 位置（行号以 2026-10-26 代码为准） |
|---|---|
| 定时任务（唯一入口） | `server/services/spot_cache_scheduler.py:65` `_fund_catalog_sync_job`，注册于 `:267-270`（`CronTrigger(hour=2, minute=17)`，`misfire_grace_time=7200`） |
| 全量同步主循环 | `server/services/fund_catalog_sync.py:362` `run()` |
| 抓取间隔 / 批大小 | `server/services/fund_catalog_sync.py:76` `DEFAULT_REQUEST_INTERVAL=0.3`、`:77` `UPSERT_BATCH_SIZE=50` |
| 落库行组装 | `build_fund()`（`:129`）／`build_trade_rule()`（`:154`）／`build_risk_profile()`（`:211`） |
| 批量写入 | `_flush()`（`:468`）→ `_upsert_catalog()`（`:510`，一次 RPC 写三表） |
| 费率解析 | `server/services/fund_fee_source.py:293`（销售服务费率）、`:64` `_pct()` |
| 表结构 | `supabase/migrations/20261026120000_create_fund_master_and_trade_rule.sql`（**只生成未执行**）；旧表定义见基线 `:398-446` |

`fund_trade_rule` 非空列的关键约束：

```sql
management_fee_rate    DECIMAL(6,4) NOT NULL
custody_fee_rate       DECIMAL(6,4) NOT NULL
min_purchase_amount    DECIMAL(18,2) NOT NULL
sales_service_fee_rate DECIMAL(6,4) NOT NULL   -- 注释：A类=0，C类通常0.2%~0.4%
fund_name 不再在规则表 —— 名称属于 `fund` 主数据
```

> **2026-10-26 变更（写入模型换了，读侧不变）**：同步从「upsert `fund_fee_rules` + `fund_risk_profiles` 两张表」改为
> 「一次 RPC `upsert_fund_catalog(funds, trade_rules, risk_profiles)` 写三张表，一个事务」。
> 影响本运维文档的几点：
>
> 1. **基础信息与交易规则独立失败**：`fetch_basic_info` 成功、`jjfl` 失败时仍写 `fund`（公司与经理不丢），只是不写规则 → 该基金不可交易；
> 2. **基础信息抓不到才整只跳过**（保留旧行），不再是「名称缺失时用代码兜底」；
> 3. **失败面变成整只基金**：RPC 是一个事务，规则行坏数据会让同一笔的 `fund` / 画像一起回滚，`stats["synced"]` 会相应回退并计入 `failed`；
> 4. `stats` 新增 `rules_synced` 与 `new_codes`（首次进入 `fund` 的代码，供持仓历史补齐使用）。

## 3. 发现的问题

- **统计口径**：`run()` 在 `_flush` **之前**就累加 `stats["synced"]`（`:320`），若 flush 失败，已写与未写的行在统计上无法区分。本次因引入逐行降级而顺带修正（见 4.2）。
- **部分批次已落库**：PostgREST 的单次批 upsert 是原子的，但**先前批次已成功写入且不回滚**。崩在第 50 只时，前 49 只并未写库（首次 flush 就失败），但更大规模故障时会留下半新半旧的数据。

## 4. 设计方案

### 4.1 并发锁

`fund_catalog_sync.py` 暴露 `sync_lock()` 上下文管理器（`fcntl.flock` 非阻塞独占，锁文件 `/tmp/fund_catalog_sync.lock`），**CLI 与定时任务共用**：

- CLI：拿不到锁 → 打印提示并以退出码 `2` 结束（不排队）；
- 定时任务（`_fund_catalog_sync_job`）：拿不到锁 → 记 `WARNING` 并跳过本轮（说明有手工同步在跑），不抛异常。

### 4.2 本次明确不做

| 不做的事 | 理由 |
|---|---|
| HTTP 管理端点（L2） | 代码库当前**完全没有「管理员」概念**，需先定义谁算管理员；且新增一个能触发重负载抓取 + 写库的公开接口是新攻击面。运维实际经 SSH 操作，CLI 已够用。需要时再议（Q2） |
| 任务化 + 状态落库（L3） | 需建表 + 迁移 + 重构调度，超出「便于运维」的即时需求（Q3） |
| 定时任务改写为独立进程 / systemd timer | 现状进程内调度可用，无证据表明需要改动 |

## 5. 测试策略

沿用 `tests/unit/server/services/test_fund_catalog_sync.py` 既有约定（纯函数直测 + 假客户端替身，不联网、不连 Supabase）：

| 用例 | 断言 |
|---|---|
| 销售服务费率缺失 → 落 0.0 | `build_trade_rule` 返回行中该字段为 `0.0`，且行**不为 None** |
| 申购起点缺失 → 不写交易规则 | `build_trade_rule` 返回 `None`；`fund` 照写（`sync_one` 仍返回三件套，`trade_rule` 为 None） |
| 管理费/托管费缺失 → 不写交易规则 | 同上 |
| 批次写入失败 → 降级逐只，坏行计入 failed | 假客户端按事务语义对整批抛错时，`stats["failed"]` 正确、好行仍写入、`codes` 不含坏行 |
| 坏行不留半截数据 | 失败基金的 `fund` / `trade_rule` / `risk_profile` 都不出现在任何成功的 RPC 参数里 |
| CLI 参数解析与锁语义 | `--limit` / `--codes` / `--dry-run` 生效；锁被占用时退出码 2 |
| 锁可重入/释放 | 退出上下文后锁可再次获取 |

集成测试（`tests/integration/…`）按需补充，需本地 Supabase 环境。

###  与设计稿的偏差

- 4.2 原写「`synced` 只在写入成功后累加」，实现改为「收集时累加、flush 失败时回退」—— 对外可观测结果一致，但不改原设计（避免把统计搬到 flush 后导致进度日志口径变化）。已就地更正 4.2 措辞。
