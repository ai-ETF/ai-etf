# 订单确认重写：需求与验收

> 本文回答「要做什么、验收标准是什么」，是需求输入。
> 实现契约（状态机、表结构、RPC、调度、迁移）见
> [订单确认：业务规则](../20-设计/基金与交易/订单确认-业务规则.md)（设计入口，另含
> [数据结构](../20-设计/基金与交易/订单确认-数据结构.md)、
> [执行机制](../20-设计/基金与交易/订单确认-执行机制.md)、
> [实现方案](../20-设计/基金与交易/订单确认-实现方案.md)）。
>
> 2026-10-30 已拍板（详见文末 §7）：费用采用**下单快照**、持仓引入 **lot + FIFO**、
> 赎回**按 settle_date 到账**、`NO_NAV` 转 `manual_review`、可赎回日由规则驱动、
> 手动确认入口仅管理员/内部可调用、本期不做部分确认。本轮先交付方案，不改代码。

## 0. 目标

把「订单确认」从**多表多次写、靠异常补偿、依附抓取任务**的流程，重写为：

> **纯读库、可重入、单笔原子、资金守恒、调度独立**的确认流程。

确认的触发条件从「15：37分触发确认订单任务」改为「该订单今日的确认净值已更新」。

## 1. 为什么要重写

### 1.1 现状链路

#### 下单侧

| 步骤 | 买入 | 卖出 |
|---|---|---|
| 入口 | `server/api/portfolio.py:62` `POST /portfolio/apply-purchase` | `server/api/portfolio.py:93` `POST /portfolio/apply-redeem` |
| 服务 | `portfolio_service.py:569` `apply_purchase` | `portfolio_service.py:784` `apply_redeem` |
| 校验 | 白名单、ETF 拦截、申购状态、交易日/15:00 截止、金额上下限、单日累计限额、现金 | 白名单、ETF 拦截、持仓存在、无 pending 申购、可赎份额（扣 pending 卖单） |
| 资金 | `cash -= amount`、`frozen_cash += amount`（`portfolio_service.py:696-700`） | 不动现金，只写 pending 订单 |
| 落单 | `_write_trade_order(... status="pending", confirm_date=...)` | 同左；`settle_date` **只写进提示语，未落库**（`portfolio_service.py:874-886`） |

#### 确认侧

| 步骤 | 位置 |
|---|---|
| 批量扫描 | `portfolio_service.py:1077` `confirm_pending_orders`：`status='pending' AND confirm_date <= cutoff`，一次 `select("*")` 全量取出 |
| 预加载费率 | 同函数，按 `fund_code` 去重后 `get_fee_rules_batch` |
| 单笔确认 | `portfolio_service.py:1265` `_confirm_one_order` |
| 取确认日净值 | `portfolio_service.py:1236` `_confirm_nav` → `FundNavService.get_nav_on()`，**只读 DB、不触网**（`fund_nav_service.py:189`） |
| 净值不可用 | 抛 `NavUnavailableForConfirm`（`portfolio_service.py:50`），订单保持 pending，计入 `skipped`，不拒单、不退款 |
| 其他异常 | `_reject_order`（`:1177`）落 `rejected`，买单再走 `_refund_rejected_buy`（`:1196`）退回本金 |
| 日历异常 | `CalendarUnavailable` / `CalendarOutOfCoverage` 整批上抛，不拒单 |

#### 调度侧

`server/services/spot_cache_scheduler.py:191` `start_scheduler()`：

| 时间 | 任务 | 行为 |
|---|---|---|
| 周一至周五 15:37 | `confirm_pending_orders` | `before_today=True`，只确认 `confirm_date < today` 的历史遗漏 |
| 交易日 18:00、19:00 | `_fund_nav_update_job(with_confirm=True)` | 先 `FundNavSyncService.update_batch()` 抓上游，再确认 |
| 交易日 20:05、21:05、22:05、23:05 | 同上 | 同上 |
| 每天 00:30、01:30 | `_fund_nav_update_job(with_confirm=False, prev_day=True)` | 只更新净值，不确认 |
| 每天 08:05 | `_fund_nav_update_job(with_confirm=True)` | 更新 + 补漏确认 |
| 启动时 | `_startup_pending_compensation()` | 确认到今天 |

`AsyncIOScheduler()` 与 `CronTrigger` 均未显式指定时区（`spot_cache_scheduler.py:196`、`:203`），默认取**服务器本地时区**。

#### 数据模型

- `trade_orders.status` 取值：`pending`、`completed`、`cancelled`、`rejected`、`reserved`（`portfolio_service.py:1075`）。
- `positions` 是聚合持仓：`quantity`、`cost_price`、`confirm_date`、`available_date`、`principal`（货基）。
- `trade_flow` 是流水，**没有 `order_id`**（`portfolio_service.py:1575` `_write_trade_flow`）。
- 没有「订单尝试记录」「确认批次记录」「逐笔持仓批次（lot）」表。

### 1.2 现状的问题清单

严重度：P0 = 会造成资金/份额错误或数据永久不一致；P1 = 会造成错误但可人工修复；P2 = 可维护性/可观测性。

#### A. 事务与一致性

| 编号 | 问题 | 证据 | 后果 | 级别 |
|---|---|---|---|---|
| P1 | 单笔确认由多次独立 PostgREST 写组成，没有事务 | 买入：解冻 → 建仓 → 写流水 → 改订单（`portfolio_service.py:1307-1428`）；卖出：扣份额 → 入账 → 写流水 → 改订单（`:1440-1545`）。`_confirm_one_order` docstring 自认「已知局限（非事务）」 | 任一步失败，前后步骤不回滚，留下半成品 | P0 |

### 1.3 根因归纳

1. **三件事塞进一个方法**：调度时机、净值可用性判断、资金/持仓/流水的多表写。
2. **没有订单级事务和订单级状态机**：只靠「异常 + 补偿」，补偿本身又依赖前序步骤的假设。
3. **时间口径混用**：「订单交易日」「实际跑批日」「到账日」没有分开命名和存储。
4. **确认的生命周期依附于抓取任务**：确认的触发条件是「抓取跑完了」，不是「净值在库里」。
5. **订单、成交、持仓没有分层**：没有 lot，FIFO、持有期、到账、未来的部分确认都无处落地。
6. **账户级汇总资金 + 读改写**：无法做到订单级幂等和资金守恒。

## 2. 重写必须考虑的问题

### 2.1 领域模型与状态机

**必须显式定义状态，不能再用 `pending/completed/rejected` 三个状态承载全部语义。**

建议状态机（名称可调整，语义必须保留）：

```
pending ──claim──► processing ──成功──► completed
   ▲                   │
   │                   ├──业务拒单──► rejected（同事务完成补偿）
   │                   └──需人工──► manual_review
   │
   └──lease 超时回收────┘

（赎回）completed ──► settling ──到账日──► settled
```

要求：

- `processing` 是**带租约的认领态**，必须有 `processing_at`、`processing_by`（实例/进程标识）、`attempt_count`。
- 租约超时（建议 5 分钟，可配置）由回收任务把 `processing` 放回 `pending`，或超过最大尝试次数转 `manual_review`。
- `settling` / `settled` 只用于赎回；`settle_date` 必须落库。
- 所有状态迁移只允许通过数据库函数完成，应用层不得直接 `UPDATE status`。
- 订单一旦 `completed` / `rejected` / `settled`，不可再被确认流程修改（终态不可逆）。

**持仓批次（lot）**：

- 新增 `position_lots`（或等价结构）：`order_id`、`user_id`、`fund_code`、`trade_date`（= 订单 `confirm_date`）、`quantity`、`remaining_qty`、`cost_price`、`created_at`。
- `positions` 保留为聚合读模型（展示/查询用），由 lot 汇总维护，或由数据库触发器/同一 RPC 维护。
- 卖出按 FIFO 消耗 lot，持有天数按每个 lot 的 `trade_date` 计算，赎回费按 lot 分别计算后汇总。
- 存量持仓没有 lot 历史：迁移时按现持仓生成一条「期初 lot」，`trade_date` 取现有 `positions.confirm_date`，并在文档中标注这是近似值。

**订单、成交、流水的关系**：

- `trade_flow` 增加 `order_id`（唯一约束），一笔订单的确认只允许产生一条确认流水。
- 如果未来要支持部分确认，再引入 `order_executions`；本期可以先不做表，但模型上不要假设「一单只能全成或全拒」。

### 2.2 事务边界

**原则：一笔订单的确认 = 一个数据库事务。**

建议把以下动作放进同一个 PL/pgSQL 函数（Supabase RPC），由应用层传入已算好的 `nav`、`fee`、`net_amount`、`quantity` 等：

- 认领订单（`pending → processing`，原子 CAS）。
- 二次校验：订单仍是 `processing`、`confirm_date` 对应净值仍存在、持仓/份额仍满足条件。
- 买入：解冻、建仓/lot、写流水、订单 `completed`。
- 卖出：扣 lot/持仓、生成应收（`settling`）、写流水、订单 `settling`。
- 拒单：订单 `rejected` + 资金/份额补偿，必须同一事务。
- 赎回到期入账：`settling → settled` + 现金入账，必须同一事务且幂等。

应用层负责：

- 批量扫描、分页、排序。
- 读净值（`get_nav_on`）、算费用、算份额（纯计算，可重试）。
- 调 RPC，记录每单结果。

**不允许**：

- 在一个数据库事务里做网络请求。
- 先解冻、后判断净值；净值判断必须在任何写操作之前，或在 RPC 内作为事务的第一条校验。
- 用 `max(0)` 之类的截断掩盖资金不一致。

### 2.3 幂等与并发

必须同时满足：

1. **订单级认领**：`UPDATE trade_orders SET status='processing', ... WHERE id=:id AND status='pending' RETURNING *`；返回空表示已被别人认领，直接跳过。
2. **RPC 幂等**：同一 `order_id` 重复调用时，若订单已是终态，返回既有结果，不重复写流水/持仓/资金。
3. **唯一约束**：`trade_flow(order_id)`、`position_lots(order_id)`（或等价唯一键），作为最后一道防线。
4. **批次级单飞**：同一时刻只允许一个确认批次在跑。优先用数据库 advisory lock（`pg_try_advisory_lock`）或锁表；`flock` 只能覆盖同机多进程，不能覆盖多实例。
5. **原子增减**：`cash = cash ± x`、`frozen_cash = frozen_cash ± x`、`quantity = quantity ± x` 必须在 SQL 内完成，不得应用层读改写。
6. **多 worker 部署**：确认调度器只能在一个进程/实例上运行，或所有实例竞争同一把数据库锁；不能假设「只有一个 worker」。
7. **回收**：`processing` 超过租约的订单必须能被安全回收；回收本身也要幂等，不能把已经完成的订单改回 pending。

### 2.4 资金守恒

必须定义并实现可校验的账务恒等式。

**买入（下单时）**

```
cash -= amount
frozen_cash += amount
```

**买入（确认时）**

```
frozen_cash -= amount
fee = 确认时费用
net_amount = amount - fee
quantity = round(net_amount / nav, 0.01)
residual = net_amount - quantity * nav      # 尾差，必须回到 cash
position/lot += quantity（成本按 net_amount 或规则）
cash += residual
trade_flow 记录 amount / nav / quantity / fee
订单 completed
```

**卖出（确认时）**

```
lot/position -= quantity（FIFO）
redeem_amount = quantity * nav
fee = 按逐 lot 持有天数计算
net_receivable = redeem_amount - fee
生成应收（settling），此时不动 cash
trade_flow 记录 redeem_amount / nav / quantity / fee / pnl
订单 settling
```

**卖出（到账日）**

```
cash += net_receivable
订单 settled
```

**拒单补偿**

- 买入：若冻结已释放，`cash += amount`；若冻结未释放，`frozen_cash -= amount` + `cash += amount`。两种路径必须由 RPC 根据订单实际状态判断，**不能靠调用方假设**。
- 卖出：份额在确认时才扣，拒单不需要补偿；若已扣份额后失败，必须回滚（事务保证），不能留半成品。

**不变量（每次确认批次后校验）**

1. `accounts.cash >= 0`、`accounts.frozen_cash >= 0`。
2. `frozen_cash == SUM(pending 买单.amount)`（若保留账户级汇总；否则改为订单级冻结后，校验 `SUM(未释放冻结) == frozen_cash`）。
3. 每笔 `completed` 买单有且仅有一条 `trade_flow`，且 `flow.order_id = order.id`。
4. `SUM(position_lots.remaining_qty) == positions.quantity`（同一用户同一基金）。
5. `positions.quantity >= 0`；不允许负份额。
6. 任一订单的状态迁移符合 2.1 的状态机；终态不可再变。
7. 单笔买入：`amount == net_amount + fee`；`net_amount == quantity * nav + residual`。
8. 单笔卖出：`redeem_amount == quantity * nav`；`net_receivable == redeem_amount - fee`。

### 2.5 时间口径

必须区分并落库以下四个时间：

| 名称 | 含义 | 来源 |
|---|---|---|
| `trade_date` | 订单被受理的交易日 T，**也是成交净值日** | 下单时计算并落库为 `accepted_date`；确认时以订单的 `accepted_date` 为准 |
| `confirm_date` | 份额确认（到账）日，**不是净值日** | 下单时按 `confirm_delay` 计算，落库；只决定份额何时可见 |
| `processed_at` | 实际执行确认的时间 | 确认时写入，仅用于审计/排查 |
| `settle_date` | 赎回到账日 | 下单时按 `redeem_settle_delay` 计算，**必须落库** |

规则：

- 持仓/lot 的 `trade_date` 必须用订单的 `accepted_date`（T），不能用 `confirm_date`、更不能用 `processed_at`。
- 持有天数 = `卖出订单的 accepted_date - lot.trade_date`，不能用「跑批日」。
- 可赎回日 = `trade_date + 规则天数`（从规则读取，不再硬编码 2 个交易日）。
- 所有时间统一按 `Asia/Shanghai` 解释和存储；跨时区部署时不能依赖服务器本地时区。
- 确认有两个门槛：扫描按「`confirm_date <= today`」（份额到账日到了才确认），取价按「该订单 `accepted_date` 的净值是否在库」。

### 2.6 净值四态与确认动作

`get_nav_on()` 的四态必须分别定义动作，不能都当成「保持 pending」：

| 状态 | 含义 | 确认动作 | 是否告警 |
|---|---|---|---|
| `OK` | 该日净值在库 | 正常确认 | 否 |
| `NOT_YET_PUBLISHED` | 确认日晚于该基金最新净值日 | 保持 pending，下一轮重试；不写任何业务数据 | 超过阈值（如 3 个交易日）告警 |
| `FETCH_FAILED` | 抓取失败、历史缺口、状态行缺失 | 保持 pending；触发/提示 repair；不拒单、不退款 | 是 |
| `NO_NAV` | 该日确实没有净值（非净值日/基金下架等） | **不能无限 pending**；转 `manual_review` 或按业务规则拒单 | 是 |

补充：

- 货基（000198）净值恒 1.0000，可继续走特判，但特判必须收敛在一处，并写明依据。
- 确认路径**永远不触网、不 repair**；修复由 `fund_nav_admin repair` / `ensure_history` 或人工处理。
- 确认前必须能回答「这一天到底有没有净值」，不能用「最新一条」顶替。

### 2.7 费用、份额与舍入

- 费用口径必须二选一并写进文档：
  - **A（推荐）**：下单时把费率规则快照/版本锁到订单上，确认时用快照计算；规则后续变更不影响已受理订单。
  - **B**：确认时按最新规则计算，但必须在下单响应和订单详情中明确「费用以确认时为准」。
- 金额、份额、费用全程用 `Decimal`；数据库用 `numeric`，避免 `float` 往返。
- 份额精度 0.01；尾差必须回到 `cash`（买入）或明确记账（卖出），不能丢弃。
- `amount == net_amount + fee` 必须严格成立；费用舍入规则要与业务确认。
- 货基 `principal` 的加减、按比例核减，必须与份额更新在同一事务内。

### 2.8 持有期与 FIFO

- 以 lot 为最小单位记录买入批次。
- 卖出按 FIFO 消耗 lot；每段持有天数 = 卖出确认日 - 该 lot 的 `trade_date`。
- 赎回费按每段分别计算后汇总；费用规则按 lot 的持有天数匹配档位。
- 若业务决定不做 FIFO（例如仍按加权平均），必须在文档中明确，并说明持有期费用的近似口径；不能像现在这样「用最后一次买入日代表整个持仓」。
- 存量持仓迁移：生成期初 lot，并在运维手册里注明「历史持有期不可追溯，首笔赎回可能按近似口径计费」。

### 2.9 赎回到账

- 下单时计算并落库 `settle_date`。
- 确认时只生成应收，不增加 `cash`；订单进入 `settling`。
- 到账任务在 `settle_date <= today` 时把应收转入 `cash`，订单 `settled`；必须幂等。
- 如果确认本身已经晚于 `settle_date`，确认后应立即入账，但仍只能入账一次。
- 用户侧展示：待确认金额、在途金额（settling）、可用现金三者分开。

### 2.10 货基特殊规则

- 净值恒 1.0000；买入按金额折算份额，`principal` 累加净申购额；卖出按比例核减 `principal`。
- 每日万份收益入账（`credit_money_fund_income`）只增加 `quantity`，不改 `principal`。
- 货基收益任务与确认任务可能并发更新同一 `positions` 行，必须用原子 `quantity = quantity + x`，不能用读改写。
- 余额理财自动申购（`_auto_invest_money_fund`）与确认的交互要明确：自动申购产生的订单同样走 pending → 确认，不能绕开统一流程。
- 货基的所有特判集中到一个策略/领域服务，不要散落在 `_confirm_one_order`、收益任务、自动申购三处。

### 2.11 错误分类与重试

必须引入明确的错误分类，替代「除净值不可用外一律拒单」：

| 类别 | 例子 | 动作 | 是否重试 |
|---|---|---|---|
| `NavUnavailable` | 未公布、抓取失败、缺口 | 保持 pending，不写业务数据 | 下一轮 |
| `RetryableSystemError` | DB 超时、PostgREST 5xx、锁冲突、网络抖动 | 回滚/保持 pending 或回收 processing | 是，带次数上限 |
| `BusinessReject` | 持仓不存在、可赎份额不足、费率规则缺失、基金下架/暂停 | 拒单 + 同事务补偿，记录原因码 | 否 |
| `DataInconsistency` | 负余额、冻结不匹配、lot 汇总不等于持仓 | 转 `manual_review`，**不自动退款** | 否，人工 |
| `CalendarUnavailable` | 日历快照未就绪/越界 | 整批失败，不拒单、不写业务数据 | 人工修复日历后重跑 |

要求：

- 拒单原因用枚举/错误码 + 可读信息，`reject_reason` 不再截断成 200 字丢上下文。
- 可重试错误不能落 `rejected`；业务拒单不能反复重试。
- 每单记录 `attempt_count`、`last_attempt_at`、`last_error_code`；超过上限告警/转人工。
- 批次的统计口径要区分 `confirmed / rejected / skipped_nav / retryable / manual_review`，不能把「写拒单失败」也算成 rejected。

### 2.12 确认调度（本次已拍板）

**决策：方案 A。**

| 项 | 决策 |
|---|---|
| 15:37 任务 | **删除**，不再保留 |
| 确认与抓取 | **彻底解耦**；确认任务只读 DB，不调用任何上游 |
| 触发 1 | 每次 `FundNavSyncService.update_batch()` 成功落库后，立即触发一次确认（异步、单飞、不阻塞同步） |
| 触发 2 | 兜底扫描：每晚 18:00 至次日 09:00，每 30 分钟一次 |
| 非交易日 | **同样执行兜底扫描**（QDII 补录、停机补偿、人工补数都可能发生在非交易日） |
| 启动补偿 | 保留：进程启动时触发一次确认 |
| 时区 | 调度器与 Cron 显式设置 `timezone=Asia/Shanghai` |
| 扫描条件 | 统一为 `status='pending' AND confirm_date <= today`；能否确认由 `get_nav_on(accepted_date)` 决定 |
| `before_today` 参数 | **删除**；不再需要「今天/昨天」的调用方约定 |
| 单飞 | 数据库 advisory lock 或等价机制；多实例/多 worker 下只允许一个确认批次 |
| 手动入口 | `POST /confirm-pending` 改为管理员/内部调用（见 2.16），并返回批次结果 |
| 日志 | 每轮记录 run_id、触发源、扫描数、确认/拒单/跳过/重试/人工数、耗时 |

说明：

- 确认是幂等的「能确认的就确认，不能的留着」，所以多轮扫描是安全的；这正是去掉固定时点的前提。
- 抓取失败不应阻断确认；确认失败也不应阻断抓取。两者只在「同步成功后立即触发」这一点上有单向依赖。
- 18:00–09:00 之外的白天不扫：白天没有新净值，扫了也是空转；启动补偿和手动入口覆盖异常情况。

### 2.13 批量、性能与分页

- 扫描必须分页（建议 keyset：`ORDER BY confirm_date, id` + `limit`），不能无上限 `select("*")`。
- 批量预加载：净值、费率规则、账户、持仓尽量按批读取，避免每单 N+1；但单笔写入仍走 RPC。
- 每单设置超时和重试预算；单笔失败不影响整批。
- 一轮任务的总时长要有上限；超过下一轮开始时间时，下一轮应跳过并告警，不能叠加。
- 目标：1000 笔 pending / 100 只基金，单轮在可接受时间内完成（建议 < 5 分钟），内存占用有界。

### 2.14 可观测与审计

必须新增：

- **确认批次表** `confirm_runs`：`run_id`、`trigger`（sync/fallback/startup/manual）、`started_at`、`finished_at`、`scanned`、`confirmed`、`rejected`、`skipped_nav`、`retryable`、`manual_review`、`error`。
- **订单尝试信息**：`attempt_count`、`last_attempt_at`、`last_error_code`、`processing_at`、`processing_by`。
- **流水关联**：`trade_flow.order_id` + 唯一约束。
- **结构化日志**：所有确认日志带 `run_id`、`order_id`、`user_id`、`fund_code`、`accepted_date`、`confirm_date`。
- **告警**：
  - 单轮失败 / 耗时超阈值；
  - pending 超过 N 个交易日未确认；
  - `manual_review` 出现；
  - 资金不变量校验失败；
  - 冻结资金与 pending 买单汇总不一致。
- **对账脚本**：给定日期范围，输出 `cash / frozen / positions / lots / flows / orders` 的差异；干净数据集必须零差异。

### 2.15 兼容、迁移与回滚

- **对外 API 保持兼容**：`/apply-purchase`、`/apply-redeem` 的路径和响应字段不变；新增字段只能追加。
- `/confirm-pending` 的响应从裸 `dict` 改为有 schema 的结构（至少包含 `run_id` 和分类计数）；如果前端依赖旧字段，保留旧字段。
- **存量 pending 订单**：新流程上线后必须能直接处理；不得重复退款、重复建仓。上线前先跑一次只读盘点。
- **存量持仓**：生成期初 lot；`positions.confirm_date` / `available_date` 的旧值保留，但新确认按新口径写入。迁移脚本必须幂等。
- **状态枚举扩展**：`processing`、`settling`、`settled`、`manual_review` 需要同步数据库约束和所有查询；旧状态数据要能映射。
- **迁移与 RPC**：通过 `supabase/migrations/` 管理；先加列/表/函数，再切代码，最后清理旧逻辑；每一步有回滚脚本。
- **灰度**：建议先只读 shadow run（新流程只计算不写入，和旧流程结果对比），再切写路径。
- **测试更新**：现有 `tests/unit/server/services/test_portfolio_service.py`、`tests/integration/server/services/test_portfolio_trade_flow.py` 需要按新语义调整；不能为了过测试而保留旧行为。

### 2.16 安全与权限

- `POST /portfolio/confirm-pending` 不能对任意登录用户开放全量确认：
  - 方案 A：仅管理员角色；
  - 方案 B：仅内部调用（共享密钥/内网），对外不暴露；
  - 方案 C：只允许确认当前用户自己的订单（如果要保留用户自助补偿）。
- 开发测试端点（`/test/*`）继续受 `ENV=production` 保护，并复核是否仍需要。
- 确认接口增加限流/幂等键，避免被反复触发。

### 2.17 测试策略

- **单元测试**：状态机迁移、错误分类、费用/份额/尾差、FIFO、货基规则、时间口径。
- **集成测试**：真实数据库 + 假净值读服务；验证 RPC 原子性、唯一约束、迁移。
- **故障注入**：在解冻后、建仓后、写流水后、改订单前分别注入失败；验证要么全回滚，要么可安全重试。
- **并发测试**：两个确认批次同时跑；两个 worker 同时认领；租约超时回收。
- **重放测试**：同一订单/同一批次重复执行 N 次，结果与执行 1 次一致。
- **不变量测试**：每轮后跑 2.4 的校验 SQL。
- **性能测试**：1000 笔订单的扫描/确认耗时与内存。
- **迁移测试**：存量 pending/持仓迁移前后对账。

### 2.18 本期不做（但模型要留口）

- 基金公司的真实「部分确认」；
- 与外部销售机构/托管行的资金对账；
- 税费、分红、份额折算等更复杂的公司行为；
- 实时净值/盘中估值。

以上不要求本期实现，但订单/成交/lot 的模型不要假设「一单一笔全额成交」，否则未来还要再拆一次。

## 3. 验收标准

> 以下每条都必须可执行、可重复验证。验收时以「数据库最终状态 + 批次结果 + 日志/告警」为准，不以代码审查通过为准。

### 3.1 功能验收

| 编号 | 场景 | 预期结果 |
|---|---|---|
| F1 | 买入 pending，确认日净值在库 | 订单 `completed`；生成/累加 lot；`positions` 汇总正确；`trade_flow` 一条且带 `order_id`；`frozen_cash` 减少 `amount`；尾差回到 `cash`；费用与份额符合规则 |
| F2 | 买入 pending，确认日净值未公布 | 订单仍 `pending`；`accounts`、`positions`、`trade_flow` **零变化**；批次计入 `skipped_nav`；下一轮可再次尝试 |
| F3 | 买入 pending，净值缺口/抓取失败 | 订单仍 `pending`；零业务写入；产生告警/repair 提示；不拒单、不退款 |
| F4 | 买入 pending，费率规则缺失 | 按约定口径处理：下单时应已拦截；确认时缺失则 `manual_review` 或 `BusinessReject` + 同事务补偿，不允许半成品 |
| F5 | 买入确认延迟 3 个交易日 | lot 的 `trade_date` = 订单 `accepted_date`（成交净值日，不随确认延迟变化）；持有天数、可赎回日按它计算，不按跑批日 |
| F6 | 卖出 pending，持仓充足 | 按 FIFO 扣减 lot；生成 `settling` 应收；`cash` 在确认当天**不增加**；`trade_flow` 一条带 `order_id`；订单 `settling` |
| F7 | 卖出 pending，确认时持仓不足 | 订单 `rejected` 或 `manual_review`（按错误分类）；不得扣出负份额；不得产生现金 |
| F8 | 赎回到账日到达 | 到账任务把应收转入 `cash`；订单 `settled`；重复执行不重复入账 |
| F9 | 货基买入/卖出 | 净值按 1.0000；`principal` 按规则累加/按比例核减；份额与 principal 一致；不影响普通基金逻辑 |
| F10 | 货基每日收益与确认并发 | 份额更新为原子增减；最终 `SUM(lots) == positions.quantity`；无丢失更新 |
| F11 | 业务拒单（买入） | 订单 `rejected`；补偿与拒单同一事务；`cash`/`frozen_cash` 回到下单前状态，且只回一次 |
| F12 | 业务拒单（卖出） | 订单 `rejected`；份额未被扣减；无现金变化 |
| F13 | 无 pending 订单 | 批次正常结束；`scanned=0`；不产生告警 |
| F14 | 15:00 后下单 | `confirm_date` 为下一交易日；确认日净值未公布时保持 pending，公布后确认 |
| F15 | 周末/节假日下单或扫描 | 下单顺延到下一交易日；兜底扫描照常运行；不因非交易日报错 |
| F16 | `NO_NAV` | 不无限 pending；按 2.6 转 `manual_review`/拒单，并告警 |
| F17 | 净值不可用与拒单的边界 | 只有 `NavUnavailable` 保持 pending；确定性业务错误才拒单；可重试系统错误不得落 `rejected` |

### 3.2 数据不变量验收

每次确认批次后执行 2.4 的校验 SQL，必须全部为 0 行异常：

- [ ] `cash < 0` 或 `frozen_cash < 0` 的账户数为 0。
- [ ] `frozen_cash != SUM(pending 买单.amount)`（或订单级冻结汇总）的账户数为 0。
- [ ] `completed` 买单中，`trade_flow` 数量 ≠ 1 的订单数为 0。
- [ ] `trade_flow.order_id` 重复的订单数为 0。
- [ ] 同一用户同一基金 `SUM(lots.remaining_qty) != positions.quantity` 的记录数为 0。
- [ ] `positions.quantity < 0` 的记录数为 0。
- [ ] 非法状态迁移（终态被再次修改）的订单数为 0。
- [ ] 买入 `amount != net_amount + fee` 的订单数为 0。
- [ ] 买入 `net_amount != quantity*nav + residual` 的订单数为 0。

### 3.3 幂等与并发验收

| 编号 | 验证方法 | 预期 |
|---|---|---|
| I1 | 对同一批 pending 连续跑 3 次确认 | 第 1 次完成；第 2、3 次 `confirmed=0`；无重复流水/持仓/退款 |
| I2 | 两个进程同时跑确认（同一批订单） | 每笔订单只被一个进程处理；另一方认领失败并跳过；最终状态正确 |
| I3 | 在 RPC 执行中途 kill 进程 | 事务回滚，订单仍 `processing` 或 `pending`；租约超时后回收，重试后恰好完成一次 |
| I4 | 同一 RPC 用同一 `order_id` 调用两次 | 第二次返回幂等结果，无新增写入 |
| I5 | 多 worker/多实例启动 | 只有持有数据库锁的实例执行确认；其余跳过并记录 |
| I6 | 确认与货基收益任务并发 | 无丢失更新；不变量全部通过 |

### 3.4 故障注入验收

在以下每个点注入异常，验证最终状态：

| 注入点 | 预期 |
|---|---|
| 认领后、解冻前 | 事务回滚；订单可重试；资金不变 |
| 解冻后、建仓前 | 事务回滚；`frozen_cash` 不变；订单可重试 |
| 建仓后、写流水前 | 事务回滚；无持仓、无流水 |
| 写流水后、改订单前 | 事务回滚；无流水、无持仓 |
| 卖出扣 lot 后、生成应收前 | 事务回滚；份额不变 |
| 到账入账后、改订单前 | 事务回滚；现金不变 |
| 数据库超时/5xx | 订单保持 pending/processing；不拒单、不退款；告警 |
| 日历不可用 | 整批失败；零业务写入；不拒单；修复日历后重跑成功 |
| 净值服务异常 | 保持 pending；零业务写入；告警 |
