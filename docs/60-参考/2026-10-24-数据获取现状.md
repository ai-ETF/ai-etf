# 数据获取现状（2026-10-24）

> ⚠️ **本文是 2026-10-24 的快照，部分内容已失效。** 场内 30 秒行情快照（`_spot_dict`、`refresh_spot_cache`、榜单/筛选/分类/资金流接口）已于 2026-10-26 整体删除；净值线与元数据也已按 DB 架构落地。当前事实以 `docs/20-设计/行情/行情数据源.md` §11 与 `docs/30-接口/03-行情.md` 为准，本文保留作历史对照。

> **口径**：本文只依据 2026-10-24 的仓库代码（HEAD `9920ae1`）和当日实测结果，不引用 `docs/` 下任何既有设计/运维文档。
>
> **实测环境**：Linux / WSL2，`poetry` 虚拟环境，Python 3.10.19，akshare 1.18.64；北京时间 2026-10-24 16:57–17:02（周六，非交易日）。
>
> **实测方法**：直接调用与生产相同的 `SourceRouter` / `FinanceApiService` / `PortfolioService` / `FundCatalogSync` 代码，并读取生产 Supabase 的只读状态。未启动完整 FastAPI 进程，避免触发 pending 订单确认、货基入账等写库定时任务。

## 1. 一页结论

系统里存在**两套互不连通**的取数体系：

1. **多源适配器**（`server/sources/`）：有注册表、能力路由、失败分类、域名/接口级熔断、换源日志。**生产代码中唯一调用方是交易日历**；净值类能力（history / latest / batch）只有测试在用。
2. **业务直连**（`FinanceApiService`、`PortfolioService`、`FundCatalogSync`）：直接调 akshare / requests。**所有行情、K 线、分时、净值、基金目录、货基收益都走这条线**，没有备源、没有熔断。

因此，当前的实际可靠性取决于单个上游接口，而不是 `server/sources/` 里的那套容错设计。

## 4. 多源适配器层（`server/sources/`）

### 4.1 已注册的源

`server/sources/registry.py:66-85` 注册 5 个源：

| 源名 | 能力 | 域名（熔断单位） | priority | timeout | 实测表现 |
|---|---|---:|---:|---:|---|
| `em_pingzhongdata` | `history` | `fund.eastmoney.com` | 100 | 15s | 110020 全量 4168 点 / 0.16s；一次响应同时含单位+累计净值 |
| `em_lsjz` | `latest`、`history_recent` | `api.fund.eastmoney.com` | 90 | 15s | 最新净值 / 0.07–0.16s；`pageSize` 上限 20，最多 200 点 |
| `em_mobile` | `latest` | `fundmobapi.eastmoney.com` | 95 | 15s | 单只最新净值 |
| `em_fund_jjjz` | `batch` | `fund.eastmoney.com` | 100 | **60s** | 全市场约 2.4 万行 / 实测 2.55s；响应可达 4.5MB |
| `sina_trade_date` | `calendar` | `finance.sina.com.cn` | 100 | 15s | 8797 个交易日，覆盖 1990-12-19 → 2026-12-31 |

日历只有 `sina_trade_date` 一个源；旧的 `sina_index_daily` 已于 2026-10-24 随严格清理删除（它只能给出已发生的交易日，作为备源会让「下一交易日/跨年确认日」越界）。

### 4.2 路由语义

- `history` 只接受声明 `history` 的源；`history_recent` 接受 `history|history_recent`；`latest` 接受三者；`batch`、`calendar` 各自独立（`registry.py:22-28`）。
- 同一能力下按 `priority` 升序尝试；`NAV_SOURCE_PRIORITY` / `CALENDAR_SOURCE_PRIORITY` 可覆盖排序（`config.py:15-18`）。`CATALOG_SOURCE_PRIORITY` 已于 2026-10-24 移除（目录线尚未接入）。
- 进程内记住「每个能力上次成功的源」，下次优先用它；不做「失败后自动回切」。重启即清空（`router.py:49-52`）。
- 失败分两类（`models.py:83-91`）：
  - **域级**（TIMEOUT / 403 / 5xx / 429 / CONNECTION_ERROR）：整个域名一起熔断；
  - **接口级**（EMPTY_PAYLOAD / PARSE_ERROR / SCHEMA_DRIFT / INVALID_REQUEST / UNEXPECTED）：只降级该源，继续换源。
- 全部失败抛 `AllSourcesFailed`，**不允许静默返回空列表**。
- 熔断参数默认：连续 3 次失败、冷却 60s 起、指数退避至 1800s、半开探测 1 次、恢复确认 2 次（`config.py:62-90`）。

### 4.3 生产接入情况（关键）

全仓库检索 `get_router` / `SourceRouter` 的调用方，只有：

- `server/services/trading_calendar_cache.py:154-156`（日历刷新）。

**净值类能力没有任何业务调用方**。`FinanceApiService._query_nav_history`、`PortfolioService._get_nav` 仍然是直接 `import akshare as ak`。多源适配器的净值部分目前是「已建好但未接线」。

## 5. 业务取数层

### 5.1 ETF 实时行情（新浪全市场快照）

- 代码：`FinanceApiService.refresh_spot_cache`（`finance_api_service.py:1284-1321`）。
- 调用：`ak.fund_etf_category_sina(symbol="ETF基金")`。
- 缓存：类级 `_spot_dict`（代码 → 行情 dict），交易时段每 30 秒刷新一次；非交易时段跳过，但缓存为空时仍拉一次（首次启动/重启）。
- 门控：`is_trading_time(beijing_now())`，依赖交易日历快照。**日历不可用时直接抛 `CalendarUnavailable`，不会拉行情**。
- 退避：连续失败 n 次后 `min(30 × 2^(n-1), 1800)` 秒内不发请求。
- 字段映射（`_format_spot_data`，`finance_api_service.py:354-435`）：新浪只提供代码、名称、最新价、涨跌额、涨跌幅、买卖价、昨收、今开、最高、最低、成交量、成交额；以下字段**恒填 0.0**：
  - `turnover_rate`、`volume_ratio`
  - `outer_vol`、`inner_vol`、`order_ratio`
  - `main_inflow`、`main_inflow_pct`
  - `latest_shares`、`float_mv`、`total_mv`
- `amplitude` 由 `(最高-最低)/昨收` 还原。
- `data_date` 取**请求当日**，`update_time` 恒为空。

### 5.2 榜单 / 搜索 / 筛选 / 分类

全部基于内存 `_spot_dict`，不额外请求外部：

- 榜单：按字段排序取前 N（`finance_api_service.py:329-352`）。
- 搜索：代码/名称子串匹配（`:704-746`）。
- 筛选：关键词 + 涨跌幅区间 + 排序（`:748-796`）。
- 分类：**按名称关键词硬编码归类**（`:798-886`），共 21 类；匹配不到的进 `其他ETF`。
- 指定分类列表：按硬编码关键词反查（`:888-949`）。

### 5.3 K 线

- 代码：`query_kline`（`finance_api_service.py:439-523`）。
- 源：`ak.fund_etf_hist_sina(symbol=sh/sz+code)`；只有日线，周线/月线由日线重采样（`W-FRI` / `ME`，日期取区间内最后一个交易日）。
- 缓存：`/tmp/etf_kline_cache/{code}_{period}_sina.json`，TTL 86400s；缓存的是归一化后的内部列名。
- 归一化后补 `change`、`change_pct`、`amplitude`；`turnover_rate` 恒 0（新浪不提供）。

### 5.4 分时

- 代码：`query_intraday`（`finance_api_service.py:1071-1120`）。
- 源：`ak.stock_zh_a_minute(symbol=..., period='1')`，返回约 1970 根**滚动窗口**（跨十余个交易日），按当天日期过滤。
- 昨收：优先实时快照；否则取日 K 中「日期 < 今天」的最后一根。
- 降级：取不到当日分钟数据时，用「快照 + 日K」生成 240 点模拟曲线（`_generate_intraday_fallback`，`:1138-1204`），随机种子由基金代码 md5 固定，结果可复现。
- API 通过「首条是否含 `amount`」判断 `data_source=real|simulated`。
- 非交易日/停牌日会稳定返回模拟曲线，而不是空。

### 5.5 详情与历史净值

- 概览：`ak.fund_overview_em(symbol=code)`，取 20 列（基金全称、规模、管理人、费率、跟踪标的等），无缓存（`finance_api_service.py:587-636`）。
- 历史净值：`ak.fund_open_fund_info_em(symbol=code, indicator="单位净值走势")`，再单独请求一次 `累计净值走势` 按日期合并（`:638-700`）。
- 默认返回最近 500 条（约 2 年），上限 5000（`:54-56`）。
- 注释明确记录：曾用的 `fund_etf_fund_info_em` 在 akshare 1.18.64 下会因上游表结构变化抛 `Length mismatch`，故改走 `fund_open_fund_info_em`。

### 5.6 场外持仓与交易

- 持仓估值：`PortfolioService._get_nav`（`portfolio_service.py:248-269`）直接调 `ak.fund_open_fund_info_em`，取最后一行单位净值。
- 赎回/申购确认：同样走 `_get_nav`；取不到就拒绝（`portfolio_service.py:1246`、`:1377`）。
- 货币基金特例：`MONEY_FUND_CODE` 的净值直接返回 `1.0000`，不请求 akshare。
- 货基万份收益：`_money_fund_per10k_income`（`portfolio_service.py:276-345`）用 `urllib` 请求 `api.fund.eastmoney.com/f10/lsjz`，取最近一条「非今天」且 `DWJZ` 有效的记录；按北京日期缓存当天结果；任何失败直接抛 `RuntimeError`，不做兜底。
- `credit_money_fund_income`（`:349`）每日 00:05 把收益折算成份额加进 `positions.quantity`。

### 5.7 场外基金白名单同步

- 入口：每日 02:17 定时任务（`spot_cache_scheduler.py:151-159`）或手动 `python -m server.scripts.sync_fund_catalog`。
- 发现候选：`ak.fund_name_em()` 全量 28162 只 → 名称含「联接」且含 ETF/指数型 → 排除货币/债券/定开/封闭/持有期/外币/后端（`fund_catalog_sync.py:53-57`、`:229-241`）。
- 并上现有白名单，避免改名后掉出目录（`fund_catalog_sync.py:214-227`）。
- 逐只抓取：
  - `https://fundf10.eastmoney.com/jjfl_{code}.html`：申购/赎回费率分档、管理费/托管费/销售服务费、申购起点、申购状态（`fund_fee_source.py:252-304`）；
  - `https://fundmobapi.eastmoney.com/FundMNewApi/FundMNBasicInformation`：`SHORTNAME` / `FTYPE` / `INDEXNAME` / `INDEXCODE` / `MAXSG`（`:307-328`）。
- 组装规则：费率分档缺失、管理费/托管费/申购起点缺失、申购状态缺失 → **整只跳过**；销售服务费率缺失按 0.0（A 类）落库（`fund_catalog_sync.py:127-183`）。
- T+N 不逐只抓：按类别推导，境内 (1,3)、QDII (2,7)（`fund_catalog_sync.py:67-70`、`:120-124`）。
- 风险画像：纯关键词规则推导四维分与等级（`fund_risk_classifier.py`），命中不到时保守兜底并标 `needs_review`。
- 写库：`fund_fee_rules` upsert、`fund_risk_profiles` upsert；CLI 与定时任务共用 `/tmp/fund_catalog_sync.lock`（flock 非阻塞）。
- 逐只间隔 0.3s，数千只串行，正常约 20–30 分钟。

### 5.8 交易日历

- 取数：`SourceRouter.fetch_calendar()` → 仅 `sina_trade_date`（akshare `tool_trade_date_hist_sina`，混淆文本由 akshare 解码）。
- 持久化：`trading_calendar`（逐日，含非交易日）+ `trading_calendar_state`（单行）。
- 内存：进程启动时 `load_from_db()` 一次性载入 `frozenset[date]`；请求路径只读内存。
- 刷新：`POST /api/admin/trading-calendar/refresh`（需 `X-Admin-Token` + `Idempotency-Key`），流程为「拉取 → 校验 → diff → 一次 RPC 整表替换 → 原子替换内存」。
- 校验（`trading_calendar_cache.py:395-412`）：非空、≥1000 个交易日、`coverage_start <= coverage_end`、`coverage_end >= 今天`；不满足整次拒绝写库。
- 整体时限 30s；已有刷新在跑返回 409。
- 查询语义：快照未载入抛 `CalendarUnavailable`；日期越界抛 `CalendarOutOfCoverage`；不按星期几猜。

### 5.9 文档

- `DocumentService.ingest_document(url)`（`document_service.py:175`）与 `process_file_from_edge(...)`（`:233`）用 `requests.get` 下载（超时 30s / 60s），按 PDF/文本/HTML 提取，切块、向量化后写 `documents` / `document_chunks`。
- 与本文件其余「市场数据」链路独立。

## 6. 缓存与刷新

| 缓存 | 位置 | TTL / 刷新 | 失效行为 |
|---|---|---|---|
| 全量 ETF 行情 | 进程内 `_spot_dict` | 交易时段 30s，非交易时段跳过 | 日历不可用则刷新失败，接口返回空 |
| 基金列表 | 进程内 `_fund_list_cache` | 1h | 刷新失败沿用旧缓存；从未成功则为空 |
| K 线 | `/tmp/etf_kline_cache/*.json` | 24h（按文件 mtime） | 过期即删，下次重拉 |
| 交易日历 | 进程内快照 + Supabase 两张表 | 仅人工刷新，无定时任务 | 快照未载入时业务抛错 |
| 货基万份收益 | 进程内 `_money_fund_cache` | 按北京日期，当天有效 | 失败不缓存、抛错 |
| 基金白名单 / 风险画像 | Supabase 表 | 每日 02:17 全量 upsert | 单只失败不影响其余 |

调度任务（`spot_cache_scheduler.py:107-168`）：

| 任务 | 频率 |
|---|---|
| ETF 全量行情刷新 | 每 30 秒检测（交易时段真正拉取） |
| Pending 订单确认 | 每个工作日 15:37 |
| 货基万份收益入账 | 每天 00:05 |
| 场外基金白名单同步 | 每天 02:17 |

启动时还会异步预热行情缓存，并补偿确认遗漏的 pending 订单。

## 8. 现状问题与风险

### P0：可用性直接受影响

1. **业务净值/K线/行情全部单源，且 akshare 内部请求没有超时。**
   实测确认 `fund_open_fund_info_em`、`fund_etf_category_sina`、`fund_etf_hist_sina`、`stock_zh_a_minute`、`fund_overview_em`、`fund_name_em` 内部都是裸 `requests.get(...)`，没有 `timeout`。
   一旦上游卡住，FastAPI 工作线程会被无限期占用；`server/sources/` 里已有的超时、熔断、备源对这些路径完全无效。

2. **行情缓存被交易日历强绑定，失败表现为「空数据」而不是「错误」。**
   `refresh_spot_cache()` 在日历快照未载入时抛 `CalendarUnavailable`；但 `query_spot` 只读 `_spot_dict`，此时返回 `None`，榜单/搜索/分类返回空数组。接口层不区分「没有这只基金」和「整条行情线不可用」。

### P1：架构与契约问题

3. **多源适配器与业务脱节。**
   `em_pingzhongdata` / `em_lsjz` / `em_mobile` / `em_fund_jjjz` 已实现并有测试，但业务仍走 akshare。维护两套净值逻辑，口径和坑位可能漂移（例如货基检测、累计净值合并方式）。

4. **实时行情的 `data_date` / `update_time` 不可信。**
   `data_date` 取请求当日：周六查询 10-23 收盘数据时仍标成 `2026-10-24`；`update_time` 恒为空。前端无法判断数据实际交易日。

5. **资金流向接口返回的是「合法的 0」而不是「不可用」。**
   新浪列表不提供主力净流入、内外盘、委比，`_format_spot_data` 统一填 0.0；`MoneyFlowData` 字段非 Optional，调用方无法区分「净流入为 0」和「没有这个数据」。

6. **交易日历只有单一源。**
   刷新只走 `sina_trade_date`（唯一源）。若新浪该接口格式变化，日历无法刷新；已有 DB 快照可继续用，但覆盖终点一旦过期，越界查询会抛错。

7. **白名单同步的成败不可观测。**
   `fund_fee_rules.updated_at` 只在 INSERT 时有默认值，库里没有 `set_updated_at` 触发器，upsert 也不显式写 `updated_at`。因此「最新 updated_at = 2026-10-11」只能说明当时插入过新行，**不能用来判断每日 02:17 是否成功**。同步没有独立的状态表/成功时间/失败计数。

### P2：数据质量与工程细节

8. **分类是关键词硬编码，不是真实分类。**
   1714 只里 `其他ETF` 有 663 只（38.7%），说明关键词表覆盖不足；同一只基金可能命中多个关键词，实际只取第一个。

9. **K 线缓存是单机 `/tmp` 文件。**
   多实例/多 worker 各存一份；无文件锁，并发写可能互相覆盖；容器重启即丢失。

10. **批量净值源只覆盖场外代码。**
    `em_fund_jjjz` 传入场内 ETF 代码时不会报错，只是不出现在结果里。调用方若把「批量结果缺少某代码」当成「该基金没有净值」，会误判。

11. **详情接口为了 500 条净值拉取全量历史两次。**
    每次 `query_detail` 都请求完整的单位净值 + 累计净值（老基金单次 4000+ 行），再 `tail(500)`；没有缓存。

12. **基金白名单是全量串行重抓。**
    每只固定间隔 0.3s，数千只约 20–30 分钟；没有增量/变更检测，失败只留逐只 warning。

13. **货基与普通基金在净值模型上分叉。**
    `server/sources` 的 `NavPoint` 模型不覆盖货基（三个源都主动拒绝）；货基收益走独立 lsjz 解析，调用方必须特判 `MONEY_FUND_CODE`。

14. **分时降级生成的是模拟数据。**
    非交易日、停牌、上游失败都会返回 240 点模拟曲线；虽然 API 标了 `data_source=simulated`，但字段结构与真实数据一致，下游容易误用。
