> 状态：设计已定稿，待实现

## 1. 背景与术语

| 术语 | 含义 |
|---|---|
| 全市场快照 | 一次请求拿到全部场内 ETF 的实时行情（东财 `fund_etf_spot_em`，约 1555 只；新浪 `fund_etf_category_sina`，实测 1696 只） |
| `_spot_dict` | `FinanceApiService` 的**类级内存缓存**，结构 `{"512890": {行情dict}, ...}`，键是**不带市场前缀的 6 位代码**，是全项目行情数据的唯一底座 |
| 行情缓存刷新 | 定时任务每 30 秒调用 `refresh_spot_cache()`，交易时段真正拉数据，非交易时段跳过 |
| push2 系 | 东财行情集群域名族：`push2.eastmoney.com` / `push2delay.eastmoney.com` / `push2his.eastmoney.com` / `82.push2.*` 等 |
| 交易时段 | 交易日 09:30–15:00（北京时间），唯一来源 `server/services/trading_calendar.py` |

**范围**：本次只替换「行情取数源」，不改任何接口契约（URL、请求参数、响应字段名与结构全部保持不变）。

## 3. 根因分析（生产实测）

> 环境：生产服务器 `47.113.220.182`，部署目录 `/root/ai-etf`，服务 `fastapi.service`。
> 诊断时间：2026-10-12 21:50 ~ 2026-10-13 11:30（CST）。全部为只读操作，未重启、未改代码。

### 3.1 现象：13 个行情端点逐个实测

```
health                          → {"status":"ok"}
spot/512890                     → {"data":null,"error":"未找到基金代码: 512890"}
spot/name/{name}                → {"data":null}          （错误文案误导，见 Q2）
ranking?top_n=3                 → {"total":0,"items":[]}
kline/512890?limit=3            → {"total":0,"items":[]}
kline/name/{name}?limit=3       → {"total":0,"items":[]}  （名称解析成功→512890，数据为空）
intraday/512890                 → 404
money-flow/512890               → 404
money-flow/ranking              → 404 {"detail":"未找到基金代码: ranking"}   （路由缺陷，见 Q1）
search?keyword=…                → 空
categories                      → {"total_categories":0,"total_funds":0}
category/股票型?top_n=2         → {"total":0}
detail/512890                   → ✅ 完整返回（全称/费率/规模/历史净值）
```

**11/13 端点失效，唯一存活的是 `/detail`——它走的是 `fund.eastmoney.com`。**

### 3.2 上游可达性对照（同一台服务器上实测）

| 上游 | 结果 |
|---|---|
| `push2delay.eastmoney.com` | `http_code=000`（Empty reply from server） |
| `push2his.eastmoney.com` | `000` |
| `push2.eastmoney.com` / `82.push2.*` / `1.push2.*` / `82.push2delay.*` | 全部 `000`（6 个子域、6 个不同 IP 段：43.144.251.121 / 101.226.30.206 / 117.184.33.102 / 61.152.229.217 / 114.80.72.189 / 117.184.40.129） |
| `openssl s_client -connect push2delay.eastmoney.com:443` | `CONNECTED`，证书 `O=East Money Information Co., Ltd., CN=*.eastmoney.com`，`Verify return code: 0 (ok)` |
| 明文 HTTP（80 端口）打 `push2delay` | 同样 `000` |
| `fund.eastmoney.com` | ✅ 200 |
| `datacenter-web.eastmoney.com` | ✅ 200 |
| `quote.eastmoney.com` | ✅ 404（页面，说明可达） |
| **同一时刻从其它网络访问 `push2delay`（WebFetch 实测）** | ✅ 正常返回 `"total":1356` 的真实 JSON |

**结论**：TCP 通、TLS 握手成功（证书链校验通过，说明确实连到了东财），但 **HTTP 请求一发出即被立即断开**（耗时 0.08–0.13s）；而完全相同的接口从别的网络访问正常。
→ 这是**针对本服务器出口的、东财侧（或链路中间设备）的应用层拒绝**，不是接口下线，不是 akshare 版本问题，**代码侧无法绕过**。

**⚠️ 2026-10-13 复核（换源实现完成后）：东财出口已自行恢复，上表结论不再成立。**

同一天在生产服务器上重测（`akshare 1.18.64`，同一台机器、同一出口）：

| 新浪 `fund_etf_category_sina`（本次采用） | ✅ 1696 行，**5.1s** |

**这意味着什么（必须让决策人知道）**：
1. 「东财封禁」不是永久状态，而是**在 2026-07-28 ~ 2026-10-13 期间持续、之后自行解除**。成因无法从服务器侧确证（§3.3 的 3.1 万次/两周高频请求是最大嫌疑，但属推断）；
2. 因此换到新浪**不是「唯一活路」，而是一个权衡选择**——它换来的是：更快（5.1s vs 18.8s，30 秒轮询下更安全）、不再依赖一个已经拒绝过本机出口的源；
3. 代价见 §5.3 / Q5 / Q6：**资金流向全为 0、换手率与市值等字段为 0**，这是相对东财源的真实功能损失；
4. 若日后要回到东财字段完整性，建议**先只加退避**（本次已实现，见 §5.4-5）观察一个周期，再在「双源（主东财 + 备新浪）」与「保持新浪」之间选一，不要在没有退避的情况下回切——否则 3.3 的封禁形态有重演风险。

`2880 = 24h × 120 次/h`，即**失败后每 30 秒无退避地重试，24 小时不间断**，连国庆休市（10-01~10-08，市场全休）也在打。近两周累计约 3.1 万次无效请求。

**机制**：`refresh_spot_cache()` 的跳过条件是 `if not is_trading_time(...) and cls._spot_dict is not None`（`:1139`）——只有缓存非空才会在非交易时段跳过。一旦拉取持续失败，`_spot_dict` 永远是 `None`，跳过条件失效，于是变成全天候 30 秒一次的失败循环。

> 本次已无法确证「是这 6 万次请求导致的封禁」，但该形态是典型会被风控命中的模式，必须消除。

这四类恰好是 3.2 表中**走 push2 系域名**的那几类；`/detail` 走 `fund.eastmoney.com` 所以活着。影响面比前端报的更大（见 §4.1）。

## 5. 最终方案

### 5.1 选型结论

用户决策（2026-10-13）：**方案 A —— 换源到新浪，接口契约不变**。
理由：新浪接口免费、已实测可达且数据为当日实时；东财 push2 属于网页端非公开接口，没有付费放行通道；付费的 Choice 数据产品对个人团队成本不合适。

### 5.2 数据源替换映射（新浪接口均已实测）

| 用途 | 原（东财，被拒） | 新（新浪，实测可用） | 实测结果 |
|---|---|---|---|
| 全市场快照 | `ak.fund_etf_spot_em()` | `ak.fund_etf_category_sina(symbol="ETF基金")` | 1696 只；10 次连续调用全部成功，单次 3.96–5.97s；512890 返回 `最新价 1.230 / 涨跌幅 +1.821% / 昨收 1.208`，与日K 校验一致 |
| 日 K | `ak.fund_etf_hist_em(period=daily)` | `ak.fund_etf_hist_sina(symbol="sh512890")` | 1870 根；5 只样本（588000/159915/513100/159998/510300）全部可用 |
| 分时（分钟） | `ak.fund_etf_hist_min_em` | `ak.stock_zh_a_minute(symbol, period="1")` | 1970 根滚动窗口，最新一根 `2026-10-13 11:20`；当日 110 条（09:30–11:20，条数与时间轴吻合） |
| 周/月 K | `fund_etf_hist_em(period=weekly/monthly)` | **日线重采样**（新浪无周/月线接口） | 代码推导，见 §5.4 |

`/detail` 保持不变——它走的 `fund_overview_em` / `fund_open_fund_info_em` 生产可达，本次不碰。

### 5.3 字段可得性对照（新浪 vs 原契约）

**行情快照**（`MarketData` / `_format_spot_data`）。新浪列表列为：`代码 名称 最新价 涨跌额 涨跌幅 买入 卖出 昨收 今开 最高 最低 成交量 成交额`。

| 契约字段 | 新浪来源 |
|---|---|
| `code` `name` `price` `change` `change_pct` `prev_close` `open` `high` `low` `volume` `amount` | ✅ 直接对应 |
| `bid_price` `ask_price` | ✅ ← `买入` / `卖出` |
| `amplitude` 振幅 | ✅ **可计算**：`(high - low) / prev_close × 100` |
| `data_date` | ✅ 取本次快照的北京日期 |
| `turnover_rate` 换手率 | ❌ 无来源 → `0.0` |
| `volume_ratio` 量比 | ❌ → `0.0` |
| `outer_vol` `inner_vol` `order_ratio` 外盘/内盘/委比 | ❌ → `0.0` |
| `main_inflow` `main_inflow_pct` 主力净流入 | ❌ → `0.0` |
| `latest_shares` `float_mv` `total_mv` 份额/市值 | ❌ → `0.0` |
| `update_time` | ❌ → 空串 |

**K 线**（`KlineData`）：新浪日K 列为 `date open high low close volume amount postVol postAmt`。

| 契约字段 | 新浪来源 |
|---|---|
| `date` `open` `high` `low` `close` `volume` `amount` | ✅ 直接对应 |
| `change` `change_pct` | ✅ **可计算**：与上一根 `close` 比较（首根为 0） |
| `amplitude` | ✅ **可计算**：`(high - low) / 上一根 close × 100` |
| `turnover_rate` | ❌ 无来源 → `0.0` |

**分时**（`IntradayPoint`）：`time price avg_price volume amount change_pct` — 新浪分钟接口 `day open high low close volume amount` 全部可映射；`time` 取 `day` 的 `HH:MM`；`avg_price` 沿用现有 `amount/volume` 口径；`change_pct` 改为**相对昨收**（现状是相对当日首点，见 §5.4 第 4 条）。

**⚠️ 直接后果（必须让前端知晓）**：`/money-flow/*`（资金流向）在新浪源下**全部为 0，接口失去意义**；`/ranking?sort_by=turnover_rate` 会因字段为 0 自动降级为按 `change_pct` 排序（`finance_api_service.py:318` 的既有降级逻辑）。

### 5.4 实现要点（逐条对应现有代码）

1. **代码前缀映射**：新浪代码形如 `sh512890` / `sz159915`，而 `_spot_dict` 的键与 `query_spot(fund_code)` 的入参都是**裸 6 位代码**。`_rebuild_spot_dict` 建键时必须剥掉 `sh`/`sz` 前缀；同时保留完整代码，供 K 线/分时接口使用（新浪 K 线接口需要 `sh`/`sz` 前缀）。需要一个 `512890 → sh512890` 的推导函数（`5/6` 开头 → `sh`，`1/0/3` 开头 → `sz`）。

2. **K 线列名差异化 + 缓存隔离**：现有 `_load_kline_cache` 直接存取**上游原始 DataFrame**（`:911-937`）。换源后若命中 `/tmp/etf_kline_cache` 里遗留的东财列名缓存，会按 `df['日期']` 取值而 KeyError。
   → 改为**先归一化再缓存**：新增 `_normalize_kline(df, source)`，统一产出内部列名（`date/open/close/high/low/volume/amount/change/change_pct/amplitude/turnover_rate`）；缓存只读归一化后的结果，并在文件名中带源标识（如 `512890_daily_sina.json`），避免新旧缓存串味。

3. **周/月线重采样**：新浪只有日线 → 用 pandas `resample('W-FRI')` / `resample('ME')`（`date` 升序、已按日索引）聚合 `open=first, high=max, low=min, close=last, volume=sum, amount=sum`，再按 §5.3 重算 `change/change_pct/amplitude`。**注意**：重采样必须在**取数之后、日期过滤与 limit 之前**做，否则 `limit` 语义会错。

4. **分时只取当日**：新浪 `stock_zh_a_minute` 返回约 1970 根的**滚动窗口（跨多个交易日）**，直接返回会让分时图画成十几天。必须按「今天（北京日期）」过滤 `day` 前缀，并对非交易日/停牌返回空。
   同时把 `change_pct` 口径从「相对当日首点」改为**「相对昨收」**（昨收取自快照的 `prev_close`，或日K 倒数第二根 `close`）——原口径下分时图的涨跌幅与行情页对不上，属于既有缺陷。
   现有 `_generate_intraday_fallback()`（模拟分时，`:984-1050`）**保留不动**，作为当日无数据时的降级。

5. **失败退避与熔断（并入本次范围，理由见下）**：`refresh_spot_cache()` 增加类级状态 `_consecutive_failures` / `_next_retry_at`：
   - 成功 → 计数清零；
   - 失败 → 计数 +1，退避 `min(30 × 2^(n-1), 1800)` 秒并写入 `_next_retry_at`；`refresh_spot_cache()` 开头若 `now < _next_retry_at` 直接返回 `False`（不发起请求）。
   - 效果：单次失败 30s 后重试（与现状一致），连续失败逐步退避到最长 30 分钟；非交易时段且缓存为空时不再每 30 秒空转。
   **为什么并入本次范围**：本次故障的直接致因是「源不可达 + 无退避重试」，若不修，换源后一旦新浪也被拒会 1:1 重演同一事故；且它不依赖任何其它改动即可独立完成。

6. **不改动的部分**：所有 `/api/market/*` 路由与响应模型、`/detail` 的取数逻辑、`_generate_intraday_fallback`、`query_money_flow*` 的字段结构（只改数据来源为空的问题）。

### 5.5 上线与回滚

### 9.2 实现中偏离原方案的地方（及原因）

1. **K 线缓存的日期格式（原方案漏项，实测发现）**
   缓存走 `to_json` → `read_json` 后，`date` 列被 pandas 还原成 `Timestamp`，`str()` 得到 `"2026-10-12 00:00:00"`；而未命中缓存时是 `"2026-10-12"`。
   → **同一接口会因「命中/未命中缓存」返回两种日期格式**（旧东财实现同样如此，属既有缺陷）。已在 `_load_kline_cache()` 里统一回 `%Y-%m-%d`，并加单测锁住。
2. **周/月线日期用「区间末日」标会标出未来日期（原方案漏项，实测发现）**
   原方案写的是 `resample('W-FRI')`/`resample('ME')` 取区间标签，实测当天（10-13）周线标成 `2026-10-16`（还没到的周五）、月线标成 `2026-10-31`。
   → 前端按日期过滤或画时间轴会把它当越界数据。已改为**取区间内最后一个实际交易日**（同 Yahoo 等主流源），当日周线/月线都标 `2026-10-12`。
3. **日线归一化时显式按日期升序排序**：重采样与「相对前一根」的涨跌幅都依赖升序，上游顺序不保证，加一道保险。
