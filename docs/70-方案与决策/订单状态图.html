底色区分「方向归属」：蓝＝买入专用、绿＝卖出专用、灰＝共用、红色虚线斜纹＝未使用。 「终态」是叠加标记而非独立底色：在方向色基础上加深填充、加双边框与右上角「终」角标，覆盖 completed / settled / rejected / cancelled 四个不可逆状态（它们本身也属于某个方向桶）。 箭头配色：灰＝共用主链，蓝＝买入分支，绿＝卖出分支；虚线细线为标签引线。胶囊框 [新建订单] 为入口，不是状态；reserved 为孤立节点，无任何迁移边。

审阅注记

  1. 业务阶段必需：赎回确认与到账之间存在真实时间差；用户侧「在途金额」、account_snapshots.settling_cash 聚合、reconcile_orders 对账都依赖它。依据 docs/10-需求/订单确认.md §2.1、§2.9 与 Q4 决策（2026-10-30「确认只生成应收，到账日再进 cash」）。
  2. 派生状态物化：trade_orders 已有 settle_date（应到账日）与 settled_at（实际到账时间）。settling 等价于 direction='sell' AND settle_date IS NOT NULL AND settled_at IS NULL；settled 等价于 settled_at IS NOT NULL。同一事实存了两处。
  3. 买卖不对称 + 文档偏差：买入终态是 completed，卖出终态是 settled，卖出从不经过 completed（代码为 processing → settling）；但文档 §2.1 画的是「（赎回）completed → settling → settled」，与实现不符。
  4. 枚举不干净：reserved 从未使用；status 列默认值是 'completed'（老系统「下单即建仓」的历史遗留）。
建议，未定稿
5. 可选改进：卖出确认后统一为 completed，「在途」由 settled_at IS NULL 表达，去掉 settling/settled 两个枚举值；代价是用户侧展示、快照聚合、对账的查询条件都要从 status='settling' 改为 settled_at IS NULL AND net_amount IS NOT NULL。
