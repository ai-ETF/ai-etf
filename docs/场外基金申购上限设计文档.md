## 1. 背景

**本设计的目标**：让「限大额」基金进入白名单，同时把它的额度边界如实建模，使模拟盘的成交/拒单与真实世界一致。

---

## 2. 术语：「限大额」的真实语义

天天基金申购状态字段的取值与含义：

| 状态 | 含义 | 能否交易 |
|---|---|---|
| `开放申购` | 正常开放 | ✅ 可买，无上限 |
| `限大额` | **开放申购 + 单日累计申购上限** | ✅ 可买，但受上限约束 |
| `暂停申购` | 停止接受申购 | ❌ |
| `封闭期` / `认购期` | 不在开放期 | ❌ |

**关键点一：「额」是「单日累计」，不是单笔。**

**关键点二：「单日」= 证券交易日（T 日），不是日历自然日。**

- **T 日 = 申请被受理的交易日**。收盘（15:00）之后提交的申请，T 日顺延到下一个交易日；
- **非交易日（周末、法定节假日）提交的申请不会即时受理**，平台只是**预存**申请，
  全部归集到**节后第一个交易日**统一受理，**全部算作那一个 T 日**。

这也决定了实现分两步走的原因 —— 见第 5、6 节。

## 3. 数据来源（实测结论）

两个数据源分工明确 —— **上限来自移动端接口，申购状态来自 jjfl HTML 页**：

| 字段 | 来源 | 实测值（012348，限大额） | 实测值（110020，开放申购） | 本项目是否采用 |
|---|---|---|---|---|
| `MAXSG` | 移动端 `FundMNBasicInformation` | `1000` | `100000000000` | ✅ **单日累计申购上限（元）** |
| `SHORTNAME` / `FTYPE` / `INDEXNAME` / `INDEXCODE` | 同上 | — | — | ✅ 基金名称/类型/跟踪标的（供风险分类） |
| `SGZT` | 同上 | `限大额` | `开放申购` | ❌ **未采用**（见下方提示） |
| `SGZTMARK` | 同上 | `限大额(单日累计购买上限1000元。)` | — | ❌ 未采用 |
| `MINSG` | 同上 | `10` | `10` | ❌ 未采用 |
| 申购状态 | **jjfl 页「交易状态」小节** | `限大额` | `开放申购` | ✅ 落库为 `subscribe_status` |
| 申购起点 | jjfl 页「申购与赎回金额」小节 | `10.00元` | `10.00元` | ✅ 落库为 `min_purchase_amount` |

> ⚠️ **易错点**：`SGZT` 的值与 jjfl 页「申购状态」实测一致，但本项目取的是**后者**
> —— 见 `fund_fee_source.fetch_jjfl()` 中解析「交易状态」小节的
> `out["subscribe_status"] = kv.get("申购状态", "")`。
> 移动端接口那条路只取了 `MAXSG` 与名称/类型/跟踪标的，**没有读取 `SGZT`**。
> 因此排查「某只基金的申购状态不对」时，要看 jjfl 页的解析结果，而不是移动端接口。
>
> `SGZTMARK` 是给用户看的人类可读说明（如「限大额(单日累计购买上限1000元。)」），
> 目前未落库；若前端想要更友好的限购文案，这是个现成来源。

**两个要点：**

1. **哨兵值**：开放申购基金 `MAXSG` 返回 `100000000000`（1000 亿），表示「无限额」。
   解析时用**阈值**判定（`>= 1e10` 视为无限额），而不是等值比较 ——
   哨兵值本身没有语义，被调整成别的数也不该让逻辑失效。
2. **零额外请求**：两个数据源都是本项目**本来就在抓**的（移动端接口取名称/类型，
   jjfl 页取费率分档与申购起点），上限与状态都是顺带解析出来的，不增加抓取请求数。

作为交叉验证，jjfl 页面（`https://fundf10.eastmoney.com/jjfl_{code}.html`）
的「申购与赎回金额」小节也有结构化行：

```
申购起点 10.00元    定投起点 10.00元    日累计申购限额 1000.00元
首次购买 10.00元    追加购买 10.00元    持仓上限 无限额
```

> 注意最后一项「持仓上限」是**另一个概念**（见第 7 节），不要与日累计申购限额混淆。

## 4. 数据链路（已实现）：状态与上限落库 + 交易侧校验

### 4.1 数据模型

两个迁移：

`20261002045009_add_fund_max_purchase_amount.sql`：

```sql
ALTER TABLE "public"."fund_fee_rules"
  ADD COLUMN IF NOT EXISTS "max_purchase_amount" numeric(18,2);
```

- 类型与 `min_purchase_amount numeric(18,2)` 一致
- **允许 NULL**（无默认值）—— 对开放申购基金，NULL 表示**无限额**

`20261002065555_add_fund_subscribe_status.sql`：

```sql
ALTER TABLE "public"."fund_fee_rules"
  ADD COLUMN IF NOT EXISTS "subscribe_status" text;
```

在原来数据库的基础上加上两列：

- `subscribe_status` ：写入基金真实的申购状态
- `max_purchase_amount`：单日购入上限，允许`NULL`，`NULL`则表示为开放申购的基金，无限额

`subscribe_status` 是 5.5 的修复基础：状态落库后，同步就能如实反映「基金已转暂停申购」，
而不必靠删行（删行会打断持有者的赎回链路）。

### 4.2 抓取与解析

`server/services/fund_fee_source.py`：

```python
UNLIMITED_MAX_SG_THRESHOLD = 1e10

def parse_max_purchase_amount(value) -> Optional[float]:
    """移动端 MAXSG -> 单日累计申购上限（元）。None = 无限额。"""
    if value is None:
        return None
    try:
        amount = float(str(value).strip())
    except (TypeError, ValueError):
        return None
    if amount <= 0 or amount >= UNLIMITED_MAX_SG_THRESHOLD:
        return None
    return _amount(amount)
```

`fetch_basic_info()` 的返回值新增 `max_purchase_amount` 键。

### 4.3 写入侧：状态一律如实落库

`server/services/fund_catalog_sync.py`：

```python
# 状态解析不出来 = 这次抓取不可信，整只跳过（fail-closed）。
# 与「暂停申购」不同：那种是抓到了真实状态，如实落库即可。
status = (jjfl.get("subscribe_status") or "").strip()
if not status:
    logger.warning(f"{code} 未取到申购状态，跳过（不写入白名单）")
    return None
```

**关键变化：写入门槛从「状态可申购」改为「状态可解析」。**
暂停申购 / 封闭期 / 认购期的基金现在也会写入 `fund_fee_rules`，
`build_fee_rule()` 把 `subscribe_status` 与 `max_purchase_amount` 一并落库，
能不能买改由**交易侧**判定（4.4）。

`build_fee_rule()` 的 fail-closed 收敛点仍在费率分档（缺分档即拒绝写库），
上限解析失败不再拒绝写入，见 5.2。

### 4.4 交易校验

`server/services/portfolio_service.py` 的 `apply_purchase()`：

```python
# 申购状态把关：白名单里的基金不一定都能买 —— 同步会把「暂停申购」
# 「封闭期」等状态如实落库（这样它们仍可赎回，且状态可查询），
# 能不能买由这里判定。
# NULL 是迁移前的存量行（没有状态字段），按开放申购兼容，不拦。
subscribe_status = rule.get("subscribe_status")
if subscribe_status and subscribe_status not in PURCHASABLE_SUBSCRIBE_STATUSES:
    return {
        "success": False,
        "message": f"该基金当前「{subscribe_status}」，暂不接受申购（已持有份额仍可赎回）",
        "data": None,
    }
```

随后是最低金额与单日累计上限校验（同上，紧接其后、**取净值与冻结资金之前**）：

```python
# 2. 校验申购金额上下限（均从 rule 中直接读取）
min_amount = Decimal(str(_require_rule_field(rule, fund_code, "min_purchase_amount")))
if amount < min_amount:
    return {"success": False,
            "message": f"申购金额 {float(amount):.2f} 元低于最低申购金额 {float(min_amount):.2f} 元",
            "data": None}

# 单日累计申购上限（「限大额」基金），NULL = 无限额。
# 语义是「同一 T 日累计」，因此必须聚合该 T 日已提交的申购金额 ——
# 只校验单笔会让用户拆成多笔小额绕过上限。
max_amount = rule.get("max_purchase_amount")
if subscribe_status == LIMITED_SUBSCRIBE_STATUS and max_amount is None:
    # 「限大额」却没有上限值 = 同步时没抓到 MAXSG，限额未知。
    # 此时 NULL 不能解释成「无限额」—— 那等于把限购当成随便买。
    logger.error(f"基金 {fund_code} 状态为限大额但缺少单日申购上限，拒绝申购")
    return {
        "success": False,
        "message": "该基金限额信息暂不可用（同步未取到单日申购上限），暂不接受申购",
        "data": None,
    }
if max_amount is not None:
    limit = Decimal(str(max_amount))
    used = self._sum_t_day_purchase(user_id, fund_code, actual_confirm)
    if used + amount > limit:
        return {
            "success": False,
            "message": f"本交易日已申购 {float(used):.2f} 元，本次申购 {float(amount):.2f} 元，"
                       f"合计超过该基金单日累计申购上限 {float(limit):.2f} 元",
            "data": None,
        }
```

「已用额度」的聚合口径（分组键、计入哪些状态、为什么不必新增列）见第 6 章。

**校验放置在冻结资金之前**是有意的：被拒的单不产生任何副作用（不冻结、不落库），与现有最低金额校验、余额校验的位置策略一致。

### 4.5 边界语义

| 校验项 | 触发条件 | 与边界的比较 |
|---|---|---|
| 申购状态 | 非空 且 ∉ {开放申购, 限大额} | NULL（存量行）→ **放行** |
| 限额未知 | 状态=限大额 且 上限 IS NULL | 上限缺失 → **拒绝**（不能当无限额） |
| 最低申购金额 | `amount < min_purchase_amount` | 恰好等于 → **放行** |
| 单日累计申购上限 | `已用 + amount > max_purchase_amount` | 恰好用满 → **放行** |

两者互补：规则表述分别是「不低于」与「不超过」，因此都是**闭区间**。
这一点有专门的单元测试覆盖（`test_申购_恰好等于上限时放行`、`test_申购_同一交易日累计刚好用满放行`）。

## 6. 日累计聚合（已实现）

### 6.1 「日」的口径：T 日

**结论：按 T 日聚合**（理由见第 2 节）。候选口径对比：

| 口径 | 定义 | 评价 |
|---|---|---|
| **T 日**（采用） | 申请被受理的交易日；收盘后 / 非交易日顺延 | ✅ 与基金公司一致 |
| 自然日 | `created_at` 的北京日历日 | ❌ **错的**。节假日里下的多笔会被判成不同日子，限额失效 |
| 确认日 | 申请确认日（T+N） | ❌ 语义混乱，且 N 因基金而异 |

#### 6.1.1 关键实现事实：T 日未落库，但可由 `confirm_date` 等价分组

现状（`portfolio_service.apply_purchase()`）**已经算出了 T 日**，只是没有落库：

```python
# 局部变量 confirm_date 实际是 T 日 —— 命名有误导性
if self._is_trading_day(now.date()) and self._is_before_cutoff(now):
    confirm_date = now.date()                            # T 日 = 今天
else:
    confirm_date = self._next_trading_day(now.date())    # T 日 = 下一交易日

actual_confirm = confirm_date
for _ in range(confirm_delay):
    actual_confirm = self._next_trading_day(actual_confirm)   # 确认日 = T 日 + N
```

而落库时写入的是 **`actual_confirm`（确认日）**，不是 T 日：

```python
self._write_trade_order(..., confirm_date=actual_confirm.isoformat())
```

**但这不需要加列。** 对**同一只基金**而言 `confirm_delay` 是常数，
映射「T 日 → confirm_date」是 N 次 `_next_trading_day()`，严格单调 ⇒ **双射**：

> 两笔订单属于同一 T 日 ⟺ 它们的 `confirm_date` 相同（同基金前提下）

所以按 `confirm_date` 相等聚合，与按 T 日聚合**完全等价**。

`confirm_date` 在订单确认流程中**从不被改写**（失败路径只更新
`status` / `reject_reason` / `updated_at`），因此是稳定的分组键。

**边界验证：**

```
用户 10/1（节假日）下单    → 非交易日   → T 日 = 10/8 → confirm_date = 10/9
用户 10/3（节假日）下单    → 非交易日   → T 日 = 10/8 → confirm_date = 10/9
用户 10/8 09:00（交易日）  → T 日 = 10/8              → confirm_date = 10/9
                            → 三笔 confirm_date 相同 → 正确聚为一组（累计）

用户 10/8 16:00（收盘后）  → T 日 = 10/9              → confirm_date = 10/10
                            → 与上面三笔正确分开
```

> **更干净的做法**是给 `trade_orders` 加一列显式存 T 日，可读性更好。
> 但那需要迁移，且**存量数据无法准确回填**（只能靠确认日反推，还得依赖当时的
> `confirm_delay`）。**当前判定为不值得**，用 `confirm_date` 等价分组即可。
> ⚠️ 若日后 `confirm_delay` 变成「按日可变」，这个双射关系会失效，
> 届时**必须**改为显式存储 T 日。

### 6.2 计入范围

真实语义是「**同一 T 日内已提交**的申购申请金额累计」——已撤销、已被拒的申请不占用额度。

`trade_orders.status` 的合法取值由 CHECK 约束定义
（`trade_orders_status_check`，见基线迁移第 621 行）：

```
pending-待确认 | completed-已完成 | cancelled-已撤销 | rejected-已拒绝 | reserved-预约待执行
```

据此确定计入范围：

| 订单状态 | 是否计入 | 理由 |
|---|---|---|
| `pending`（待确认） | ✅ **必须计入** | 已提交待受理；不计入则可连续下多笔 pending 单绕过上限 |
| `completed`（已完成） | ✅ 计入 | 已受理确认 |
| `rejected`（已拒绝） | ❌ 不计入 | 被拒的申请不占用额度 |
| `cancelled`（已撤销） | ❌ 不计入 | 撤销后额度释放 |
| `reserved`（预约待执行） | ❌ 不计入 | 尚未提交，不产生申请 |
| 校验失败被拒的单 | — | **根本不落库**，天然不计入（见下） |

补充事实：`apply_purchase()` 在金额校验失败时**直接返回错误、不写 `trade_orders`**。
因此「被下限 / 上限 / 余额拦下的单」不会污染累计值，无需额外过滤条件。

> ✅ **附带发现（既有 bug，非本设计引入）已修复**：`confirm_pending_orders()` 的失败分支
> 原先写 `status = "failed"`，但 **`failed` 不在上述合法取值中** —— UPDATE 违反 CHECK
> 约束抛错、又被 `except Exception: pass` 吞掉，订单永远停留在 `pending`，每轮确认都重试、
> 一直占着该 T 日的额度，本金还会因为在确认开头就解冻而凭空消失。
> 现已改为落 `rejected`（约束内取值）并退回本金，详见第 8.2 节。

**筛选条件**（按 T 日分组 ⇒ 用 `confirm_date` 等值匹配本次订单的确认日）：

```
user_id       = 当前用户
AND fund_code = 当前基金
AND direction = 'buy'
AND status    IN ('pending', 'completed')
AND confirm_date = <本次订单的 actual_confirm>
```

注意这里**不使用 `created_at`** —— 按提交时刻分组正是 6.1 中「自然日」的错误做法，
会在节假日场景下把同一 T 日的多笔申请错误地拆成多组。

### 6.3 查询与实现

在 `apply_purchase()` 中，4.4 节的单笔校验已替换为**同 T 日累计**校验。
位置仍在第 2 步（金额校验处）—— 此时第 1 步已经算出 `actual_confirm`，可直接使用。

```python
# 单日累计申购上限（「限大额」基金），NULL = 无限额。
# 语义是「同一 T 日累计」，因此必须聚合该 T 日已提交的申购金额 ——
# 只校验单笔会让用户拆成多笔小额绕过上限。
max_amount = rule.get("max_purchase_amount")
if subscribe_status == LIMITED_SUBSCRIBE_STATUS and max_amount is None:
    # 「限大额」却没有上限值 = 同步时没抓到 MAXSG，限额未知。
    # 此时 NULL 不能解释成「无限额」—— 那等于把限购当成随便买。
    logger.error(f"基金 {fund_code} 状态为限大额但缺少单日申购上限，拒绝申购")
    return {
        "success": False,
        "message": "该基金限额信息暂不可用（同步未取到单日申购上限），暂不接受申购",
        "data": None,
    }
if max_amount is not None:
    limit = Decimal(str(max_amount))
    used = self._sum_t_day_purchase(user_id, fund_code, actual_confirm)
    if used + amount > limit:
        return {
            "success": False,
            "message": f"本交易日已申购 {float(used):.2f} 元，本次申购 {float(amount):.2f} 元，"
                       f"合计超过该基金单日累计申购上限 {float(limit):.2f} 元",
            "data": None,
        }
```

统计函数用一次查询把该 T 日的订单金额拉回本地求和：

```python
def _sum_t_day_purchase(self, user_id: str, fund_code: str,
                        confirm_date: date) -> Decimal:
    """统计该用户对该基金在「同一 T 日」已提交的累计申购金额（元）。

    为什么用 confirm_date 分组而不是存一列 T 日：同一基金下 confirm_delay 是常量，
    「T 日 → 确认日」是套用 N 次 _next_trading_day()、严格单调，故两笔属于同一 T 日
    ⟺ 确认日相同 —— 按确认日等值匹配与按 T 日聚合完全等价，无需新增列。
    （若日后 confirm_delay 变成按日可变，这个双射会失效，届时必须显式存 T 日。）

    只计入 pending / completed：已撤销、已拒的申请不占用额度。
    查询异常直接上抛（fail-closed）—— 算不出已用额度时宁可拒单，也不能放行。
    """
    resp = (self.client.table("trade_orders")
            .select("amount")
            .eq("user_id", user_id)
            .eq("fund_code", fund_code)
            .eq("direction", "buy")
            .in_("status", ["pending", "completed"])
            .eq("confirm_date", confirm_date.isoformat())
            .execute())
    return sum((Decimal(str(r["amount"])) for r in (resp.data or [])), Decimal("0"))
```

> **异常路径是 fail-closed**：聚合查询报错会向上抛，被 `apply_purchase` 外层
> `except` 捕获并返回失败单。这是有意的 —— 算不出已用额度时放行等于把限购关掉。
> 该检查位于**冻结资金之前**，因此失败单不产生任何副作用。

> PostgREST 不直接支持 `SUM()` 聚合（需 RPC）。单只基金单个 T 日的订单量很小
> （单人模拟盘通常个位数），拉回金额列本地求和完全可接受；
> 若未来量大，再改成 `CREATE FUNCTION` + `.rpc()` 做服务端聚合。

### 6.4 边界情况

- **上限为 NULL**：不校验（开放申购基金）。
- **上限被同步调小**：假设某 T 日已买入 1000 元，随后基金把上限调到 500。
  此时该 T 日已用（1000）已超新上限，**当天任何后续申购都会被拒**
  （`同T日已用 + amount > 500`）。符合直觉，无需特例处理。
- **上限被同步调大 / 放开**：累计仍从该 T 日已用金额起算，行为自然。
- **T 日切换点**：不在零点整，而在「交易日 15:00」与「非交易日」两个边界上，
  由 `_is_trading_day()` + `_is_before_cutoff()` 共同决定。`_is_trading_day()`
  用的是 akshare 真实交易日历（`server/services/trading_calendar.py`，见 8.1），
  **自动识别节假日**、按日缓存；每次请求实时计算，无需定时任务。
- **连续长假**：假期内所有申请归集到同一个 T 日，累计值在节后第一个交易日集中生效。
  这是**正确行为**（见第 2 节），不是缺陷。
- **刚好用满**：该 T 日已申购 600，上限 1000，再下 400 → `600 + 400 <= 1000` 放行；
  再来一笔 1 元 → 拒。边界为闭区间（与 4.5 节一致）。
- **时区**：`_is_trading_day()` / `_is_before_cutoff()` 均基于北京时间（`BEIJING_TZ`），
  与 T 日口径一致。

## 7. 相关但不同的概念：「持仓上限」

jjfl 页面的「申购与赎回金额」小节还有一行 **`持仓上限`**（012348 实测为「无限额」），
语义是**单账户持有该基金的总市值上限**，与「单日累计申购限额」是两个独立约束：

| 约束 | 维度 | 数据来源 | 当前状态 |
|---|---|---|---|
| 单日累计申购上限 | 同一 T 日的**流量**（买入金额） | `MAXSG`（移动端接口） | ✅ 已实现（同 T 日累计） |
| 持仓上限 | 账户**存量**（持有市值） | 仅 jjfl 页面 HTML，移动端**无对应字段** | ❌ 未支持 |

若日后需要支持持仓上限，只能解析 jjfl 页面 HTML（移动端接口的完整字段清单里没有），
会引入 HTML 解析的脆弱性。**当前判定为不值得做**：绝大多数基金为「无限额」，
收益低而维护成本高。此处记录，避免日后重复调研。

## 8. 附带发现（既有问题，均非本设计引入）

排查限期功能的过程中撞到两个既有缺陷，与申购上限无直接关系，但都会影响本文档的
实现正确性，故一并记录。

### 8.1 `_is_trading_time()` 不识别节假日 —— ✅ 已修复

项目里原本有两个语义相近、实现不同的函数：

| 函数 | 位置 | 判断依据 | 认节假日？ | 用途 |
|---|---|---|---|---|
| `_is_trading_day(d)` | `portfolio_service.py` | `ak.tool_trade_date_hist_sina()` 真实交易日历 | ✅ | **申购确认日、赎回到账日推算（T 日口径的基础）** |
| `_is_trading_time()` | `spot_cache_scheduler.py` | 工作日 + 9:30–15:00 | ❌ | 行情缓存刷新开关 |

**交易相关的 `_is_trading_day()` 是正确的**（认节假日），因此本设计的 T 日口径
（6.1.1）建立在可靠的基础上 —— 这是好消息。

但 `_is_trading_time()` 只看时刻与星期，在**法定节假日中的工作日**（如国庆假期内
恰逢周四的 10/1）会误判为交易时段，导致行情缓存在非交易日继续刷新。影响仅限于多余的
行情请求，**不涉及交易正确性**。

**修复**（已实施）：把交易日历收敛为**全项目唯一来源** `server/services/trading_calendar.py`，
从根上消除「两套日历互相不一致」：

| 函数 | 修复后的形态 |
|---|---|
| `_is_trading_time()` | **已删除**。调用方 `finance_api_service.refresh_spot_cache()` 改为直接调用 `trading_calendar.is_trading_time(trading_calendar.beijing_now())` —— 该函数只剩这一处调用，留一层同名包装只是多一次无意义的跳转 |
| `_is_trading_day(d)` | 保留（`PortfolioService._is_trading_day`），改为**委托** `trading_calendar.is_trading_day(d)`：它被 `apply_purchase` / `confirm_pending_orders` / `_next_trading_day` 等 3 处调用、5 处测试打桩，是 T 日口径的稳定接缝，删掉它要改的面比收益大 |

| 能力 | 实现 |
|---|---|
| 日历来源 | `ak.tool_trade_date_hist_sina()`（唯一一处） |
| 缓存 | 按**北京日期**缓存整份日历，一天只抓一次 —— 30 秒一次的行情轮询因此不产生额外请求 |
| 抓取失败 | 沿用上一次成功的副本（日历覆盖全年，旧副本仍有效），且不推进缓存日期以便下次重试 |
| 从未抓到过 | 退化为 `weekday() < 5`（与修复前行为一致，宁可多刷行情也不要误判休市） |

顺带修掉一个性能问题：`_is_trading_day()` 原先**每次调用都请求一次新浪日历**，而
`_next_trading_day()` 是在循环里调它的（一次最多 14 次网络请求），`apply_purchase`
又会多次调用 `_next_trading_day`。现在这些调用共享同一份当日缓存。

测试：全部集中在 `tests/unit/server/services/test_trading_calendar.py`（19 例：时段边界、
国庆假期、假期中的工作日、周末、时区换算、按日缓存、抓取失败降级）。原先
`test_spot_cache_scheduler.py` 的 7 例与新增的假期用例重复，随 `_is_trading_time()` 一并删除。
注意 `trading_calendar` 是模块级缓存，`tests/unit/conftest.py` 里加了 autouse 夹具在
每个用例前后清空，避免用例之间互相污染。

### 8.2 `trade_orders.status = "failed"` 违反 CHECK 约束 —— ✅ 已修复

`confirm_pending_orders()` 的失败分支原先这样写：

```python
try:
    self.client.table("trade_orders").update({
        "status": "failed",              # ← 不在 CHECK 允许的取值内
        "reject_reason": str(e)[:200],
        "updated_at": _now_iso(),
    }).eq("id", order["id"]).execute()
except Exception:
    pass                                 # ← 违反约束抛出的异常被静默吞掉
```

而 `trade_orders_status_check`（基线迁移第 621 行）只允许
`pending` / `completed` / `cancelled` / `rejected` / `reserved`，**没有 `failed`**。

**后果**：确认失败时该 UPDATE 必然报错 → 被 `except Exception: pass` 吞掉 →
订单**永远停留在 `pending`**。连锁影响：

- 每次 `confirm_pending_orders()` 都会重新捞出这条订单、再次失败（死循环重试）
- 这条订单一直占着它所在 T 日的申购额度（6.2 的规则把 `pending` 计入），
  等于永久吃掉用户当天的限额
- **本金凭空消失**：下单时 `cash -= amount` / `frozen_cash += amount`，
  而确认流程的第一步就是解冻（只减 `frozen_cash`，不加回 `cash`）；
  一旦后续步骤失败，这笔钱既不在现金、也不在冻结、更没有持仓。
  （初版分析写的「冻结资金也不会释放」是错的 —— 实际情况相反，是**已经解冻但没退回**，
  比锁在冻结里更糟。）

**修复**（已实施）：

1. `status` 改用约束内的 `rejected`，并把 `except Exception: pass` 换成
   `logger.exception(...)` —— 后者正是让这个 bug 隐藏至今的原因；
   终态写库与原因记录收进 `_reject_order()`。
2. **买单失败必须退款**：新增 `_refund_rejected_buy()`，把本金退回可用现金。
   这不是可选项 —— 订单既然落终态不再重试，不退款就等于确认失败必丢本金。
   它**只加 `cash`、不再动 `frozen_cash`**：一个账户的 `frozen_cash` 是所有挂单
   共用的一笔汇总，解冻已在确认流程开头做过，再减一次会扣到**其他 pending 订单**的
   冻结资金上。
3. **先落终态、再退款**：顺序反过来，万一终态写库失败，就会出现「本金已退、
   订单仍是 `pending`」——下一轮重试会用退回来的钱再建一次仓（凭空多出持仓）。
4. 卖单不做退款补偿：卖单的钱从未离开现金（份额只在确认时才被扣）。
   失败点在动份额之前（无持仓 / 取不到净值 / 缺赎回费率）时，落 `rejected` 即可。

**已知残留（非事务）**：确认过程由多次独立的 PostgREST 写操作组成，跨表事务无法在此实现。
若失败发生在「持仓已写入」之后、「流水/订单更新」之前，退款会与已建仓位同时存在
（用户占便宜）。此处按「宁可退回本金，也不让本金消失」取舍；根治需把整段确认逻辑
放进一个数据库函数（RPC）里以事务方式执行 —— 属另一项改造，不在本次范围内。

**回归防护**：单测替身 `FakeQuery` 现在**镜像了 CHECK 约束**
（`_CHECK_CONSTRAINTS`），写入 `failed` 这类非法取值会直接抛错。这个 bug 当初能活下来，
正是因为替身什么状态都收 —— 现在这条路径在单测里就能被拦住。

> 说明：本设计的 6.2 计入规则已按**约束内的合法取值**编写，
> 不依赖 `failed` 这个实际写不进去的状态；改用 `rejected` 后，
> 「确认失败的订单」也自动纳入「`rejected` 不计入」这条规则，额度随之释放。
