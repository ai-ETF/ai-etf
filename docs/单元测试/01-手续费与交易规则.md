# 01-手续费与交易规则

**被测模块**：`server/services/fund_fee_service.py`
**测试文件**：`tests/unit/server/services/test_fund_fee_service.py`
**测试方法**：依赖注入（`rule=` 参数 / 替换 `svc._client`）+ 内存替身 `FakeClient`；全程不联网、不连 Supabase
**费率样本**：取自真实配置 `docs/legacy_sql/fund_fee_rules_seed.sql`（110020 A 类、001595 C 类）

## 功能

场外基金申赎费率的计算与规则查询：决定用户申购/赎回时**收多少手续费、多少金额真正用于买卖份额**。是资金计算正确性的核心，算错会直接导致份额、持仓、收益、快照全线错误。

## 业务场景 / 预期结果 / 测试结果

### 一、`_match_purchase_tier` —— 申购金额落在哪一档（10 例）

**业务场景**：场外基金申购费按金额分档，金额越大费率越低；超过最高分界点后按笔收固定费用。用户输入的金额要能唯一确定一个档位。

**预期结果**

| 场景 | 预期 |
|------|------|
| 小额申购 | 命中第一档费率 |
| 金额恰好等于分界点（`inclusive` 缺省） | `amount < tier.amount` 不成立，落到**下一档** |
| 金额恰好等于分界点（`inclusive=true`） | 命中**该档** |
| 超过所有金额分界点 | 命中**无 `amount` 的兜底档**（固定费） |
| 全部档位都不带 `amount`（C 类全免） | 直接返回该档，费率为 0 |
| 无兜底档且金额超界 | 返回金额最大的档 |
| 档位乱序传入 | 内部排序，结果不受传入顺序影响 |
| **档位列表为空** | **抛 `ValueError`**（修复项，见下）——不再猜一个 0.0015 的默认费率 |

**测试结果**：10 例全部通过。

### 二、`calc_purchase_fee` —— 多少钱交费、多少钱买基金（10 例）

**业务场景**：用户输入的是「我要花多少钱」，系统需按**外扣法**反算——手续费从这笔钱里扣，剩下的才是净申购金额，T+1 确认时用净额 ÷ 净值折算份额。

**预期结果**

| 场景 | 预期 |
|------|------|
| 比例费率档 | 净额 = 金额 ÷ (1 + 费率)；费用 = 金额 − 净额；均四舍五入到分 |
| 固定费用档（如 ≥1000 万每笔 1000 元） | 费用 = 固定值，净额 = 金额 − 固定值 |
| `fixed_fee` 与 `rate` 并存 | **`fixed_fee` 优先**，完全不看 `rate` |
| C 类份额 | 费率 0，全额买入 |
| 档位为 JSON 字符串 | 自动解析后正常匹配 |
| 基金不在白名单（`rule=None`） | 返回 `None`，拒绝交易 |
| **档位缺失 / 为空列表 / 为空 JSON 字符串** | **返回 `None`，拒绝**（修复项，见下）——不再套用 0.0015 默认费率 |

> 实测样本：申购 10000 元 → 费用 11.99 元、净额 9988.01 元；申购 1500 万元 → 费用 1000 元、净额 14999000 元。

**测试结果**：10 例全部通过。

### 三、`calc_redemption_fee` —— 按持有天数收赎回费（13 例）

**业务场景**：持有时间越短费率越高，鼓励长期持有；超过一定天数（通常 2 年）免赎回费。持有天数按确认日起算。

**预期结果**

| 场景 | 预期（以 110020 档位 7天1.5% / 365天0.5% / 730天0.25% / ≥730天0 为例） |
|------|------|
| 持有 3 天 | 1.5% |
| 持有 100 天 | 0.5% |
| 持有恰好 7 天 | 非 inclusive 档不命中，落到 365 天档 |
| 持有恰好 365 天 | 落到 730 天档 |
| 持有恰好 730 天 | inclusive 兜底档命中，免赎回费 |
| 持有超过 730 天 | 无档位命中，费率为零 |
| 金额含小数 | 结果四舍五入到分 |
| 档位为字典形式 `{"tiers": [...]}` | 取其中 `tiers` 字段 |
| 档位为 JSON 字符串 | 自动解析 |
| **档位缺失 / 为空 / 类型不可识别** | **返回 `None`，拒绝**（修复项，见下） |

**测试结果**：13 例全部通过。

### 四、规则查询与白名单校验（18 例）

| 单元 | 业务场景 | 预期结果 | 测试结果 |
|------|------|------|:---:|
| `is_supported` | 白名单 = `fund_fee_rules` 表中有记录的基金 | 命中 → `True`；未命中 / 查询异常 → `False` | 3 例通过 |
| `get_fee_rule` | 单基金费率查询 | 命中返回规则行；无记录 / 抛异常 / 数据库未配置 → `None` | 4 例通过 |
| `get_fee_rules_batch` | 批量查询（订单确认时预加载） | 返回 `{code: rule}`；入参**去重后才查库**；空列表不查库；查不到的基金**不出现**；脏数据行（缺 `fund_code`）跳过；异常 / 未配置 → `{}` | 7 例通过 |
| `get_min_purchase_amount` | 起购金额 | 返回配置值；**字段缺失 → 抛 `ValueError`**；**配置为 0 表示无门槛，原样返回 `0.0`**；基金不支持 → 抛 `ValueError` | 4 例通过 |
| `get_confirm_delay` | 申购确认延迟 T+N | 返回配置值；**字段缺失 → 抛 `ValueError`**（不再默认 T+1）；配置为 0 保留 0；基金不支持 → 抛 `ValueError` | 4 例通过 |
| `get_redeem_settle_delay` | 赎回到账延迟 T+N | 返回配置值；**字段缺失 → 抛 `ValueError`**（不再默认 T+3）；配置为 0 保留 0；基金不支持 → 抛 `ValueError` | 4 例通过 |
| `get_fund_name` | 基金名称 | 返回配置值；字段缺失 / 基金不支持 → `None`（名称仅用于展示，不属于资金计算，保留兜底） | 3 例通过 |

> **统一口径**：费率与天数类字段一律「缺失即报错」，不用默认值兜底。`0` 是合法配置值（如无门槛起购、T+0），与「缺失」严格区分。
>
> 这四个 getter 目前**无生产调用方**（生产代码在 `portfolio_service` 内联读取同一批字段），本次一并修改以保证口径一致。

## 代码变更记录

本次测试发现并修复 **1 类资金安全缺陷及其同类隐患**，改动经人工批准，共涉及 2 个文件。

**统一原则**：规则缺失/不完整时**直接暴露错误**，不用默认值兜底。
理由：走默认最大的问题是**发现不了错误**——配错会被静默变成一个看似合理的数字，交易照常完成。
`portfolio_service.py:36-37` 的货基收益早已采用同一口径（「获取失败时直接抛错，不做任何兜底默认值」），本次是将该口径推广到费率与天数字段。

### 1. 赎回费按「免手续费」放行（真实可达 + 影响资金）

| 文件 | 位置 | 改动 |
|------|------|------|
| `server/services/fund_fee_service.py` | `calc_redemption_fee` | `redemption_fee_tiers` 为 `None` 或空列表时，由返回 `0.0`（= 免赎回费放行）改为返回 `None`（拒绝） |
| `server/services/portfolio_service.py` | `_confirm_one_order` 赎回分支 | 赎回费为 `None` 时由「就地置 0」改为 `raise RuntimeError`，使拒绝真正生效（异常由 `confirm_pending_orders` 捕获并把订单标记为 `failed`） |

**修复理由**：模块 docstring 明确「不支持默认费率兜底 —— 交易规则不能靠猜」，但赎回侧在规则缺失时会按**免手续费**放行，与申购侧「查不到即拒绝」语义相反。且仅改 `fund_fee_service` 无效——调用方会把 `None` 静默转回 `0`，故两处一并修改。

### 2. 申购费静默套用 0.0015 默认费率（真实可达：该列可空）

`purchase_fee_tiers` 是 `fund_fee_rules` 表中**唯一可空且无默认值**的费率列
（`supabase/migrations/20260819113859_remote_schema.sql:414`），而旧的兜底列
`purchase_fee_rate` 已在 `docs/legacy_sql/drop_purchase_fee_rate.sql` 中删除。
一旦该列为 `NULL`，旧实现会拿 0.0015 把钱算完。

| 文件 | 位置 | 改动 |
|------|------|------|
| `server/services/fund_fee_service.py` | `calc_purchase_fee` | `purchase_fee_tiers` 缺失/为空时，由套用 0.0015 改为返回 `None`（拒绝） |
| `server/services/fund_fee_service.py` | `_match_purchase_tier` | 收到空档位时，由返回 `{"rate": 0.0015}` 改为抛 `ValueError` |

### 3. 延迟天数与起购金额的静默默认值（防御性加固）

`confirm_delay` / `redeem_settle_delay` / `min_purchase_amount` 三列在数据库层均为
`NOT NULL` 且带默认值（`remote_schema.sql:404,411,412`），字段缺失在生产环境**不可达**，
本次属防御性加固。

| 文件 | 位置 | 改动 |
|------|------|------|
| `server/services/fund_fee_service.py` | `get_confirm_delay` / `get_redeem_settle_delay` / `get_min_purchase_amount` | 新增 `_require_rule_field`，字段缺失或基金不支持时抛 `ValueError`；`0` 视为合法值原样返回 |
| `server/services/portfolio_service.py` | 新增模块级 `_require_rule_field`，替换 `apply_purchase` 的 `confirm_delay` / `min_purchase_amount` 与 `apply_redeem` 的 `redeem_settle_delay` 三处内联默认值 | 缺失即 `raise RuntimeError`，不再默认 T+1 / T+3 / 10 元 |

> 注：`get_min_purchase_amount` 原先用 `or 10.0`，会把配置为 `0`（无门槛）误判为缺失而返回 10 元；
> 新实现以「键是否存在 / 值是否为 `None`」判定缺失，`0` 得到保留。
