# 文档规范

## 1. 分类原则

文档按**用途**分类，不按业务功能分类。同一篇文档只能回答一种问题：要做什么、怎么做、怎么操作、怎么验证、为什么这么选。

- 新业务域只在 `20-设计/` 下增加子目录。
- 顶层目录固定为 9 个，不因新功能新增。确需新增时，先在 `70-方案与决策/` 写决策文档，并同步修改 `docs/README.md`。
- 分类有歧义时，按「读者拿它来做什么」判断，不按标题里的字眼判断。

## 2. 目录与数量约束

- 路径格式：`docs/<顶层>/<业务域>/<文件>.md`，`docs/` 下目录深度最多 2 层。
- 单个目录的 Markdown 不超过 15 篇；超出时按子域拆一层。
- 不设子目录 README。`docs/README.md` 是唯一入口、分类说明和查找指南。
- `docs/` 根目录除 `README.md` 外不放文档。

## 3. 命名

- 文件名只写主题，不带类型后缀。「设计文档 / 方案 / 指南 / 手册 / 评估 / 开发文档」由所在目录表达。
- 需要阅读顺序的系列用 `NN-主题.md`，如 `50-测试/单元测试/01-手续费与交易规则.md`。
- 时间点文档用 `YYYY-MM-DD-主题.md`：快照、事故、决策记录。现状类文档必须带月份前缀，让过期可见。
- 禁用词：最终、最新、新版、旧版、副本、v2、final、tmp、待整理。
- 分隔符统一用 `-`，文件名不用空格。
- 一个主题只保留一篇 `active` 文档。新版本直接改原文件，不新建 `-v2` 或「最终版」；旧内容移到 `90-归档/` 并建立前后关联。

## 4. frontmatter

每篇文档（`README.md` 除外）开头必须有 frontmatter：

```yaml
---
id: "20-设计/行情/行情数据源"
title: "【暂缓】场内基金行情数据源"
status: active
owner: sing
updated: 2026-10-18
tags: ["设计", "行情"]
supersedes: []
superseded_by: null
---
```

| 字段 | 说明 |
|---|---|
| `id` | 相对 `docs/` 的路径（不含 `.md`），全局唯一；跨文档引用优先用它 |
| `title` | 人类可读标题 |
| `status` | `draft` / `active` / `deprecated` |
| `owner` | 负责人 |
| `updated` | 最后实质性修改日期，格式 `YYYY-MM-DD` |
| `tags` | 检索标签，至少包含文档类型或业务域 |
| `supersedes` | 本文替代的旧文档 id |
| `superseded_by` | 替代本文的新文档 id；`deprecated` 时填写 |

## 5. 生命周期与归档

| 状态 | 含义 | 位置 |
|---|---|---|
| `draft` | 未定稿，可能还会大改 | 正式目录 |
| `active` | 当前有效版本 | 正式目录 |
| `deprecated` | 已失效或被替代 | 必须移到 `90-归档/YYYY/` |

归档时保留文件名，不删除内容；在原主题的相关文档里用 `superseded_by` 建立指向。归档文档不进 `docs/README.md` 的常用目录说明。

## 6. 校验

提交前运行：

```bash
python3 docs/00-协作规范/scripts/doc_lint.py
```

校验内容包括：顶层目录白名单、目录深度、单目录文件数、文件名禁用词、frontmatter 必填字段与状态合法性、`id`/`title` 唯一性、归档位置、相对链接有效性。
