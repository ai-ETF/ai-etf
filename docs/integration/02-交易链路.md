# 02-交易链路

**被测模块**：`server/services/portfolio_service.py`、`fund_fee_service.py`、`fund_catalog_sync.py`、`risk_service.py`、`watchlist_service.py`
**测试文件**：`tests/integration/server/services/test_portfolio_trade_flow.py`、`test_fund_fee_rules_seed.py`、`test_fund_catalog_sync.py`、`test_risk_profile_flow.py`、`test_watchlist_persistence.py`
**测试方法**：本地 Supabase 栈 + 21 条真实种子费率规则 + 合成 `user_id`（无外键表）/ 真实 auth 用户（有外键表）+ `time_machine` 冻结时钟 + 外部依赖替身（`_get_nav`、`fetch_jjfl`、`fetch_basic_info`）+ 定向清理

## 功能

这是「钱算得对不对、数据写得对不对」的核心层。服务层直接连真实 Postgres，验证的是**数据库约束、触发器、跨表一致性**，这些是单元测试替身模拟不出来的：

- 申购冻结 → 确认解冻建仓 → 赎回扣仓入账，跨 `accounts` / `positions` / `trade_orders` / `trade_flow` 四表的资金流转；
- 费率规则的档位匹配（外扣法、固定费用兜底、赎回持有天数）；
- 白名单批量同步的幂等、数据不完整时的拒写、状态变化（暂停申购 / 限大额）的落库与交易侧拦截；
- 风险问卷 → 画像的三表 upsert；
- 自选股的增删查清与多用户隔离。

> **时间冻结**：交易链路有「15:00 截止」「T+1 确认」等规则，用例用 `time_machine.travel()` 把时钟固定在 2026-09-14（周一）14:00 提交、2026-09-15 14:00 确认。这套时钟是确定性的，不依赖真实日期。
>
> **最近一次全量实测（2026-10-17，改用例后）**：`poetry run pytest -m integration tests/integration` → 选中 90 条，**87 通过 / 3 失败 / 0 跳过，315.23 秒**。剩 3 条全是基金详情接口 500（PR #18 带来的真 bug，非环境问题）。

## 业务场景 / 预期结果 / 测试结果

### 一、交易主链路（6 例）

**业务场景**：用户 1000 元申购一只场外基金，次日确认；随后全部赎回。每一步都要保证「四张表对得上、钱不多不少」。

**预期结果**

| 场景 | 预期 |
|------|------|
| 申购 1000 元 | 返回 `pending`；`accounts.cash` 100000→99000；`frozen_cash` 0→1000；`trade_orders` 1 条 `pending`/`buy` |
| 确认（T+1） | `processed=1`；`frozen_cash` 归零；`positions` 1 条且份额 > 0；`trade_flow` 1 条 `buy`；订单 `completed` |
| 申购确认后资金守恒 | 现金 + 冻结 + 持仓市值 ≈ 100000 − 申购费 1.20 元（允许 ±0.05） |
| 全部赎回并确认 | `positions` 清空；现金大于赎回前（净额 = 份额×净值 − 1.5% 赎回费） |
| 确认时取不到净值 | 订单落 `rejected`（CHECK 约束内的合法值），`reject_reason` 含「确认失败」；本金退回、冻结归零；不建仓 |
| 申购不在白名单的基金 | `success=False`，文案含「不支持」，不写任何表 |

**测试结果**：6 例全部通过。

### 二、费率规则（9 例）

**业务场景**：费率不是写死在代码里的，而是从 `fund_fee_rules` 表读；读不到规则必须拒绝交易，绝不用默认费率兜底。

**预期结果**

| 场景 | 预期 |
|------|------|
| 种子数据 | `fund_fee_rules` ≥ 20 条 |
| 查 110020 | 命中，基金名/类型/份额类别正确 |
| 查 999999 | 返回 `None`，`is_supported()` 为 `False` |
| 批量查（含重复 + 不存在） | 结果键只有存在的基金，重复自动去重 |
| C 类 001595 申购 1000 元 | 申购费 0，净额 1000 |
| A 类 110020 申购 10000 元 | 外扣法：费 11.99、净额 9988.01（±0.01） |
| 申购 2000 万元 | 所有金额档都没命中 → 固定费用 1000 元 |
| 赎回 1000 元，持有 3 / 30 天 | 分别按 1.5% / 0.5% → 15.0 / 5.0 |
| 最低申购金额 | 110020、001595 均为 10 元 |

**测试结果**：9 例全部通过。

### 三、白名单批量同步（16 例）

**业务场景**：定时任务从外部数据源抓取基金费率与基础信息，写入 `fund_fee_rules` / `fund_risk_profiles`。真实抓取由单元测试覆盖解析规则；这里用录制成同样形态的替身数据，只验证**落库、幂等、以及交易侧如何使用这些数据**。

#### 3.1 落库与数据完整性（5 例）

| 场景 | 预期 |
|------|------|
| 同步 3 只（1 只缺分档） | `synced=2`、`skipped=1`；费率/风险分档、T+1 / T+3、风险标签全部正确 |
| QDII（纳斯达克） | `confirm_delay=2`、`redeem_settle_delay=7`、`market_score=3` |
| 申购/赎回分档为空 | 费率与风险**都不写库**（宁可不支持，也不用默认费率兜底） |
| 基金转为「暂停申购」后再同步 | 仍然写入，`subscribe_status='暂停申购'` 如实落库 |
| 暂停申购的基金 | 目录里查得到、能赎回；但交易侧申购被拒，文案含「暂停申购」 |

#### 3.2 限大额（5 例）

| 场景 | 预期 |
|------|------|
| 「限大额」基金同步 | 落库为可交易状态，`max_purchase_amount` 随行写入 |
| 「开放申购」基金 | 上限为 `NULL`（无限额） |
| 限大额但取不到上限 | 仍写库留痕（可查/可赎），交易侧拒绝申购，文案含「限额信息暂不可用」 |
| 单笔下 5000 元（上限 1000） | 交易侧拒绝，文案含「超过该基金单日累计申购上限」 |
| 同一 T 日先买 600、再买 500 | 第二笔被拒，文案含「本交易日已申购 600.00 元」；被拒的一笔不落库（只有 1 条 pending） |

#### 3.3 幂等与白名单不丢失（3 例）

| 场景 | 预期 |
|------|------|
| 同一基金同步两次，第二次费率变了 | 不新增行；`purchase_fee_tiers` 被覆盖为新费率 |
| 名称筛选一无所获（改名导致） | 同步目标数 == 现有白名单数，一只都不丢 |
| 名称发现 1 只新基金 | 目标数 = 白名单 + 1；新基金真的被抓取，白名单每一只也都在抓取队列里 |

#### 3.4 同步结果可被交易链路直接使用（3 例）

| 场景 | 预期 |
|------|------|
| 同步后查目录（关键词「测试沪深」） | 查到 T90001，带 `risk_level` / `confirm_delay` |
| 同步后查详情 | 赎回分档、风险标签正确 |
| 同步进来的新基金直接申购 | 白名单放行；申购费 11.99、赎回费 15.0，无需改任何交易代码 |

**测试结果**：16 例全部通过（`test_限大额基金超上限申购被拒` 已于 2026-10-17 改用合成 UUID）。

### 四、风险画像（5 例）

**业务场景**：用户答 5 道风险题，系统算画像并落三张表；重复提交是覆盖，不是追加。

**预期结果**

| 场景 | 预期 |
|------|------|
| 读取当前问卷 | 版本 `v1.0`，5 道题 |
| 全选 A 提交 | `conservative`；`user_risk_answers` 与 `user_risk_profiles` 各 1 条 |
| 全选 C 提交 | `aggressive` |
| 全选 B 后查询最新画像 | `moderate` |
| 提交 A 再提交 C | 两表仍各 1 条，最终画像为 `aggressive`（upsert 覆盖） |

**测试结果**：5 例全部通过。

### 五、自选股持久化（7 例）

**业务场景**：自选股的增删查清必须真的落到 `watchlist` 表；重复添加要拒；不同用户之间不能串数据。

**预期结果**

| 场景 | 预期 |
|------|------|
| 添加 510300 | 成功，读回基金代码与名称一致 |
| 重复添加同一只 | `success=False`，文案含「已」 |
| 删除已存在的 | 成功，表里剩 0 行 |
| 删除不存在的 | `success=False` |
| 列表（`include_quote=False`） | 2 条，代码集合正确 |
| 清空 | `removed_count=2`，表里 0 行 |
| 两个用户各加同一只 | 各自列表只有自己的 1 条；测试结束定向清理另一个用户 |

**测试结果**：7 例全部通过。
