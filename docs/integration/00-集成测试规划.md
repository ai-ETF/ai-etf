## 二、模块清单与优先级

排序依据：**交互边界价值 × 可测性 × 外部依赖风险**。原则是把「不依赖网络、不依赖 LLM 的真实 DB 边界」先做完。

### P0 — 真实数据库边界（无网络、无 LLM）

| # | 模块 | 为什么是最高优先级 |
|---|------|------------------|
| 1 | 存储层 ↔ Postgres + pgvector：`EmbeddingRepo` / `Retriever` / `ChatRepo` / `DocumentRepo` | pgvector 的 `<=>` 距离、`match_chunks` / `match_chunks_fts` 两个 RPC、ivfflat 索引、`to_tsvector('simple')` 的中文分词效果——**只有连真库才能验证**，单测的 `FakeClient` 全部绕过了 |
| 2 | 交易链路 ↔ Postgres（多表一致性）：申购 → 确认 → 赎回 → 流水/快照 | 资金正确性是项目第一风险。`_confirm_one_order` 跨 `accounts`→`positions`→`trade_flow`→`trade_orders` **无 DB 事务**，靠手动补偿；补偿逻辑在真实 CHECK/NOT NULL 约束下是否成立，FakeClient 测不出来 |
| 3 | 风险测评 ↔ Postgres：问卷 → 答案 → 画像 | 三表状态机 + `user_risk_profiles` upsert 语义 + `risk_label` 迁移列 |
| 4 | 自选股 / 费率 ↔ Postgres | `watchlist` 唯一约束的真实行为；`fund_fee_rules` **21 条真实种子**的档位匹配 |

## 三、组件间交互边界

> 「边界」= 两个组件之间的**契约**。单测验证了一侧的假设，集成测试验证**两侧假设是否兼容**。

### P0-1 存储层 ↔ pgvector

| 边界 | 契约要点 | 单测为何覆盖不到 |
|------|---------|----------------|
| `Embedder` ↔ `document_chunks.embedding` | 768 维 `vector(768)` 写入不被拒；`SETTINGS.EMBED_DIM` 与表定义一致 | FakeClient 不校验维度 |
| `EmbeddingRepo.match_by_vector` ↔ RPC `match_chunks` | 返回字段名（`id`/`content`/`similarity`/`document_id`）、排序方向、`match_count` 语义、`1-(embedding<=>q)` 的实际取值范围 | FakeClient 是自实现的，**契约是猜的** |
| `EmbeddingRepo.match_by_keywords` ↔ RPC `match_chunks_fts` | `to_tsvector('simple',...)` 对**中文**的分词行为、`websearch_to_tsquery` 的语法容错 | 同上；中文 FTS 只能实测 |
| `Retriever.retrieve` ↔ 双路融合 | 稠密+稀疏结果去重/加权后的顺序；RPC 不可用时降级到 `text_search` → `ilike` 的**真实**可达性 | 降级链在真库上才有意义 |
| `ChatRepo` ↔ 触发器 | 删 `chats` → `trigger_delete_messages` → `trigger_delete_message_chunks` 级联；删 `messages` → `message_chunks` 级联 | FakeClient 无触发器语义 |
| `DocumentRepo` ↔ 外键 | 子表写入依赖父记录存在；`ON DELETE CASCADE` 行为 | 同上 |

### P0-2 交易链路 ↔ Postgres

| 边界 | 契约要点 |
|------|---------|
| `apply_purchase` ↔ `accounts` + `trade_orders` | 冻结资金后订单插入失败时，**手动补偿回滚**在真实约束下是否成立 |
| `_confirm_one_order` ↔ 4 张表 | 申购确认（`accounts` 解冻 → `positions` upsert → `trade_flow` → `trade_orders.status`）与赎回确认的中途失败最终一致性 |
| `_next_trading_day` / `_is_before_cutoff` ↔ `confirm_date` | 落库值与业务预期一致 |
| `credit_money_fund_income` ↔ `accrued_income` / `principal_reinvest` | 两次迁移新增列的真实读写；`numeric(18,2)` 精度 |
| `take_snapshot` / `get_daily_returns` ↔ `account_snapshots` | 唯一约束与日期语义 |
| `delete_account` ↔ RPC `purge_user_data` | **单事务删 13 张表**：删完逐表断言无残留（最值得做的一条） |

### P0-3 / P0-4 风险测评、自选股、费率

- `risk_questionnaires` → `user_risk_answers` → `user_risk_profiles`：提交 → 算分 → 等级 → 画像 upsert（重复提交应为 UPDATE 而非 INSERT）；`risk_label` 实际写入。
- `watchlist` 同用户同基金重复添加：真库返回错误还是静默。
- `fund_fee_rules` 21 条真实规则的档位匹配（`_match_purchase_tier` 的 `inclusive` 边界能否命中真实数据）。

### P1-5 API 纵向切片

`Authorization: Bearer <自签JWT>` → `get_current_user` → 路由 → 服务 → 真库 → Pydantic 响应模型。重点验证**跨层字段名/类型一致性**（如 DB 返回的 datetime 字符串 vs Pydantic `datetime` 字段）——这是单测最容易漏、真库最容易炸的地方。

### P1-6 行情 ↔ AKShare

`_format_spot_data` 的列名映射 ↔ AKShare 真实返回；K 线文件缓存（`/tmp/etf_kline_cache`，TTL 86400s）读写；`portfolio_service._get_nav` / `_is_trading_day` 的 AKShare 依赖。

> ⚠️ **货基万份收益走 `urllib` 直连 `api.fund.eastmoney.com`，不走 akshare**（[server/services/portfolio_service.py:291-298](../../server/services/portfolio_service.py#L291-L298)）——容易被误当成 AKShare 一起 mock 掉，需单独拦截。

### P1-7 调度器

`lifespan` → `start_scheduler()` → 3 个 job 注册（`IntervalTrigger(30s)` / `Cron 15:37 mon-fri` / `Cron 00:05`）→ `shutdown_scheduler()` 无残留。**必须断言测试结束后没有存活的调度器**——否则 30s 一次的 AKShare 拉取会持续污染后续测试。

### P2-8 / P2-9 / P2-10 图与 RAG

- 图：`ainvoke` 下 state 完整流转；节点内 `_get_rule_agent()` / `_get_format_agent()` 惰性单例；LLM tool-calling 路径与规则快速通道的**分支覆盖**（`comparison`/`factual_query` 走规则通道提前 return，不触发 LLM）。
- RAG：真实嵌入（离线）→ 检索 → `reranker is None` 降级 → `build_prompt` 输出含检索文本。
- LLM：`astream_text` 对真实流式 chunk 的归一化（`str` / `list` / thinking 三种形态）。

## 四、集成测试策略

### 4.1 判定原则

> **跨进程/跨语言/跨引擎的边界用真实依赖；不可控的第三方用录制回放；不确定性的东西（时间、随机、LLM 采样）用注入。**

| 依赖 | 策略 | 理由 |
|------|------|------|
| Supabase / Postgres / pgvector | ✅ **真实** | 这就是被验证的边界本身，mock 掉即退化为单测 |
| AKShare（HTTP） | 🎬 **录制回放** | 真实列名/类型是契约，但数据是活的、不可复现 |
| eastmoney 万份收益（urllib） | 🎬 录制回放 | 同上，且不走 akshare，需单独拦 |
| 本地嵌入模型 | ✅ **真实**（`TRANSFORMERS_OFFLINE=1`） | 仓库自带、确定性、无需网络 |
| Reranker | ⚠️ **降级为 `None`** | 模型下不动；生效路径归 `eval` |
| LLM (Anthropic) | 🎭 **假 LLM**（默认）/ ✅ 真实（`eval`） | 采样不可复现，不进主干 CI |
| 时钟 | 🧊 **冻结/注入** | 交易时段、15:00 截止、持有天数、确认日 |
| APScheduler | ✅ 真实对象，**手动触发** job | 验证注册与关闭，不等真实时钟 |

### 4.2 数据库与容器管理

- **形态**：`supabase start` 本地栈，测试连 `http://127.0.0.1:54321`，用本地 `service_role` key。
- **重置粒度**：
  - **session 级**：每个 run 前 `supabase db reset`（重放迁移 + `seed.sql`）。
  - **test 级**：每个测试用唯一合成 `user_id` 隔离；teardown 按 `user_id` 定向清理（可复用 `purge_user_data` RPC）。
- **为什么不用事务回滚**：应用走 PostgREST（HTTP），每条语句独立连接，测试进程持有的 DB 事务包不住 HTTP 请求。改成 `CREATE SCHEMA` + `search_path` 切换也不行——PostgREST 的 schema 白名单是静态配置。**故采用合成 UUID + 定向清理**（决策 D3）。
- **清理失败必须抛错**：teardown 中任何清理异常都要 `raise`，不得 `except: pass`。宁可测试红，不留脏数据。

### 4.3 外部 API 隔离

- **AKShare**：**录制样本 DataFrame + 种入类级缓存**（而非 vcrpy HTTP 录制）。原因：`FinanceApiService` 的行情查询走**类级内存缓存 `_spot_dict`**（由 `refresh_spot_cache` 拉全量 `fund_etf_spot_em` 后 `_format_spot_data` 构建），查询本身不再发 HTTP。故阶段 2 实际做法是——录制一次真实 `fund_etf_spot_em` 前 50 行 DataFrame 存 `tests/integration/fixtures/akshare/spot_sample.pkl`，测试用 `FinanceApiService._rebuild_spot_dict(df)` 种入缓存后打路由，离线回放、验证真实中文列名→英文字段的映射契约。
- **LLM**：`monkeypatch.setattr("server.llm._llm_instance", FakeLLM())`——`get_llm()` 是模块级惰性单例，是最干净的注入点。
- **嵌入模型**：`TRANSFORMERS_OFFLINE=1` + `HF_HUB_OFFLINE=1`，强制走 `local_models/`。
- **出网守卫（关键）**：`tests/integration/conftest.py` 加 autouse fixture 禁用 socket 出网（白名单 localhost + 测试库域名），**防止漏网的测试偷偷打真实 AKShare / LLM / 生产库**。

### 4.4 测试数据准备与清理

- **造数**：`tests/integration/_utils/data_factory.py`，`uuid4()` 生成合成 `user_id`。
  - ⚠️ **FK 全貌（阶段 1 实测修正）**：`user_id` 是否可合成取决于表是否有外键到 `auth.users`——
    - **无 FK（可用合成 UUID）**：`accounts` / `watchlist` / `positions` / `trade_orders` / `trade_flow` / `account_snapshots` / `fund_fee_rules`（配置表）等交易相关表；
    - **有 FK 到 `auth.users`（必须真实 auth 用户）**：`chats` / `documents` / `files` / `messages` / `user_allocations` / `user_risk_answers` / `user_risk_profiles`（共 7 张，见迁移 L1137/1152/1162/1200/1210/1215/1220）。
  - 有 FK 的表用 `supabase_client.auth.admin.create_user(...)` 创建真实用户（`email_confirm=True` 免邮件确认），teardown 顺序：先 `purge_user_data` 删业务数据、再 `admin.delete_user` 删 auth 用户（否则 FK 约束拦截）。
- **鉴权**：`_utils/auth.py` 的 `mint_token(user_id)`，用 `SETTINGS.SUPABASE_JWT_SECRET` 自签 HS256 + `aud="authenticated"`，直接覆盖所有 `Depends(get_current_user)` 路由。
- **种子数据**：走 `supabase/seed.sql`，**不在测试里硬编码**——否则又变成「自己造数据自己验证」。
- **防误连生产库**：conftest 启动时断言 `SUPABASE_URL` 指向 localhost（或显式声明的测试项目 ref），否则 `pytest.exit`。这是 R1 的兜底。

## 八、CI 运行方式

### 8.1 先补 pytest 默认隔离（当前缺口）

```toml
# pyproject.toml
[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["."]
addopts = "-m 'not integration and not eval'"   # ← 默认只跑快的
markers = [
  "unit: 单元测试（默认运行，禁网、禁外部 IO）",
  "integration: 集成测试（需本地 Supabase，默认不跑）",
  "integration_db: 仅需数据库，无网络（阶段 1）",
  "integration_net: 需录制回放/真实网络（阶段 2）",
  "eval: LLM/评测类测试（需真实模型或录制回放，默认不跑）",
]
```

### 8.2 分组

| 组 | 命令 | 预算 | 触发 | 阻断 |
|---|------|------|------|------|
| 快（单元） | `pytest -m unit` | ~15s | 每个 PR / push | ✅ 零容忍 |
| 中（DB 集成） | `pytest -m integration_db` | 1–3 min | 每个 PR，起 supabase 本地栈 | ✅ 零容忍 |
| 慢（网络/回放） | `pytest -m integration_net` | 3–8 min | PR 打标 / 合入 main | ⚠️ 允许 1 次重试，仍失败则阻断 |
| 评价（LLM） | `pytest -m eval` | 5–20 min | nightly / 手动 | ❌ 不阻断，仅出报告 |

### 8.3 CI 环境要点

- 集成 job 需 Docker → 拉镜像可能需配镜像加速器（§5.2）。这是 CI 上的第一个坑。
- `SUPABASE_URL` 用 CI secrets 指向测试库，**绝不指向生产 ref**；配合 conftest 的库目标断言做双保险。
- 覆盖率：单测与集成**分开出报告再合并**（`coverage combine`），否则集成覆盖率会掩盖单测盲区。
- 失败阈值：不设「覆盖率 ≥ X%」硬门槛（会诱导写垃圾测试），改为**关键模块清单式门槛**——`portfolio_service` / `embedding_repo` / `retriever` 必须有集成用例，缺失则在 CI 中断言失败。

## 附录：阶段 1 实测发现

### A. 出网守卫需在 `socket.socket.connect` 层拦截

初版守卫 patch `socket.create_connection`，实测 **akshare 绕过了它**（真实联网返回净值 1.839）。根因：akshare 的 HTTP 客户端走了更底层的 `socket.socket().connect()`。已改为在 `socket.socket.connect` 层拦截，覆盖 requests/httpx/urllib/akshare 全部客户端。

### B. 交易确认存在 DivisionByZero 隐患（真实 bug，待修）

**触发链**：
1. [apply_purchase](../../server/services/portfolio_service.py#L607) 写 pending 订单时 `price` 硬编码为 `Decimal("0")`（份额/价格确认时才填）；
2. 确认时 [_confirm_one_order](../../server/services/portfolio_service.py#L1080) 调 `_get_nav` 取净值，失败则回退 `nav = price`（即 0）；
3. [L1094](../../server/services/portfolio_service.py#L1094) `actual_qty = net_amount / nav` → `Decimal.DivisionByZero`。

**触发条件**：akshare 不可用（`_get_nav` 返回 None）时，任何 pending 订单确认都会崩，订单被标记 `failed`。生产环境 akshare 通常可用，故未暴露；但网络抖动/限流时会触发。

**当前测试处置**：`test_portfolio_trade_flow.py` 用 fixture mock `_get_nav` 返回固定净值，隔离此外部依赖后验证资金流转本身。**建议后续修**：apply_purchase 把传入的 `price` 写入订单，或确认时 `price==0` 时拒绝确认并明确报错（而非除零）。

### C. `user_id` 外键全貌（已并入 §4.4）

7 张用户数据表（chats/documents/files/messages/user_allocations/user_risk_answers/user_risk_profiles）有 FK 到 `auth.users`，需真实 auth 用户；交易表（accounts/positions/trade_orders/trade_flow/account_snapshots/watchlist）无 FK，合成 UUID 即可。

### D. 中文 FTS 检索失效（`match_chunks_fts` 用 `simple` 配置）

实测 `to_tsvector('simple', '本基金主要投资于大盘蓝筹股，跟踪沪深300指数')` → 只有两个 token：`'本基金主要投资于大盘蓝筹股'` 和 `'跟踪沪深300指数'`。PostgreSQL default parser **对中文完全不切分**，数字嵌入中文串也不分离，导致 `match_chunks_fts`（及客户端 `text_search`）对中文内容检索**全部返回空**，`match_by_keywords` 对中文关键词命中率为 0。

且 `embedding_repo.match_by_keywords` 的 ilike 降级仅在 FTS **抛异常**时触发，FTS 对中文「返回空但不报错」→ 不降级 ilike → 中文稀疏检索彻底失效。

**当前测试处置**：`test_embedding_repo_pgvector.py` 用英文 content 验证 FTS 检索本身可用（英文可被 simple 配置切分）。**若要支持中文检索**，需引入 zhparser / pg_jieba 扩展或应用层预分词——属后续增强，不在本次集成测试范围。

### E. 本地嵌入模型缺 tokenizer 文件

`local_models/text2vec-base-chinese/` 此前缺 `vocab.txt` / `tokenizer_config.json` / `special_tokens_map.json` / `sentence_bert_config.json` 四个文件，导致 `Embedder` 抛 `Unrecognized processing class`。已从本地 HF cache（`~/.cache/huggingface/hub/models--shibing624--text2vec-base-chinese/`）补全。

⚠️ 该目录被 `.gitignore` 忽略、不入库；**CI / 新环境需同样补全这四个文件**（或改 `embedder.py` 优先回退到 HF cache），否则 P0-1 / P2 的嵌入相关测试会失败。

### F. `sign_up` 用户 `admin.delete_user` 报「User not allowed」

实测（阶段 2 secure-chat E2E）：`supabase.auth.sign_up` 创建的用户，`auth.admin.delete_user` 会抛 `AuthApiError: User not allowed`；而 `admin.create_user` 创建的用户则能正常删除。二者在 `auth.users` 表里字段一致（都 confirmed、非匿名）。

影响：`auth_service.delete_account` 的「删账号」步骤用 `admin.delete_user`，对 sign_up 注册的用户可能同样报错 → 注销账号功能或受影响。**当前测试处置**：register 测试的 teardown 改用 SQL 直删（先 `auth.identities` 后 `auth.users`）。**待确认**：这是本地 gotrue 的行为还是生产同样存在，需在生产环境验证 delete_account 对 sign_up 用户是否可用。

### G. `sign_up` 自动设置 client session，污染 service_role → authenticated（触发 RLS）

`supabase-py` 的 `client.auth.sign_up`（auto-confirm 模式）会**自动设置该 client 的 session**，把 client 从 service_role 身份切成已登录用户的 authenticated 身份。此后同一个 client 的 `table().insert()` 等操作不再走 service_role（不绕过 RLS），对 `watchlist`/`positions` 等「只 ENABLE RLS、无 POLICY」的表会抛 `new row violates row-level security policy`（42501）。

**测试影响与处置**：`supabase_client` 是 session 级共享 fixture，若被 register 测试的 sign_up 污染，后续测试全部触发 RLS。故 `api_client` fixture 改为**每个测试新建独立 service_role client**（不共享 `supabase_client`），隔离 sign_up 的污染。

### H. secure-chat E2E 偶发 ERROR（低概率，已加缓解）

完整跑（50+ 测试）时 `test_secure_chat_e2e` 偶发（约 1/8 概率）4 例全部 ERROR，但单跑 / 目录跑稳定通过；重试循环 4 次未复现。判定为 gotrue `sign_up` 或 `sql_delete_auth_user` 的 docker exec 偶发（资源竞争 / 响应慢）。已加缓解：`sql_delete_auth_user` 加 3 次重试 + 30s 超时。若 CI 仍偶发，优先查 gotrue 容器日志与 docker exec 超时。

### I. `handle_question` RAG 路径的 B3 类遗漏（已修）

P2-9 RAG 端到端测试暴露：`DecisionResult` 是 dataclass，但 RAG 路径里还有多处把它当 dict 访问——`qa_service.py:507` 的 `decision["top_k"]`（B3 首修时漏掉）、`prompt_builder.py` 的 `decision.get("intent"/"output_format")` ×4。均已改为属性访问。**这印证 handle_question 的 RAG 分支此前从未被真正执行过**（server 内无调用方，F1），所以这些 bug 一直潜伏。

### J. reranker 降级 `None` 时 RAG 检索被整体拒识

`_rerank_and_select` 在 `reranker=None` 时回退 `candidate_chunks[:top_k]`（不重排），但 `_check_rejection` 用 `rerank_score`（此时恒 0）与阈值 0.2 比较 → `0 < 0.2` → 判「不相关」，走 `_handle_no_results` 返回引导/拒识。**即 reranker 不可用（HF 不可达）时，RAG 检索结果会被整体拒识，实际不可用**。P2-9 测试用 mock reranker（predict 返回 0.9）绕过。**待确认**：这是有意设计（宁可拒识不错答）还是需在 reranker=None 时跳过阈值检查。
