# 04-行情与定时任务

**被测模块**：`server/api/market.py`、`server/services/finance_api_service.py`、`server/services/spot_cache_scheduler.py`
**测试文件**：`tests/integration/server/api/test_market_e2e.py`、`tests/integration/server/jobs/test_scheduler_jobs.py`
**测试方法**：行情用**录制的真实 AKShare 样本**（`tests/integration/fixtures/akshare/spot_sample.pkl`）种入类级缓存离线回放；定时任务用 `time_machine` 冻结时钟 + 类级 mock `_get_nav`；全程出网守卫拦截外部请求

## 功能

1. **行情 API**：把外部数据源的原始数据（中文列名 DataFrame）变成接口标准字段，再经缓存与路由返回。真实抓取由单元测试覆盖解析规则；这里验证「样本 → 列名映射 → 缓存 → HTTP 响应」这条链。
2. **定时任务**：APScheduler 里的「确认 pending 订单」和「启动补偿」两个任务，直接调用任务函数，验证 `pending → completed + 建仓` 的真实数据库流转。

> 为什么要冻结时钟：订单落库时 `confirm_date = 受理日 + confirm_delay(1)`。任务只处理 `confirm_date <= today` 的订单，不把时钟推到次日就什么都不会发生。

## 业务场景 / 预期结果 / 测试结果

### 一、行情 API（3 例）

**业务场景**：小程序行情页查询单只 ETF、涨幅榜。数据源返回的是中文列名，服务层需要映射成 `code/name/price/change_pct` 等标准字段。

| 场景 | 预期 |
|------|------|
| 查 588710 | 200；`data` 非空；`code=588710`；含 `name` / `price` / `change_pct`，`price` 是数值 |
| 查不存在的 999999 | 200，响应里 `error` 非空（这是本接口约定的失败形态，不是 404） |
| 涨幅榜 `top_n=10, order=desc` | 200；`total > 0`；`len(items) == total`；每项含 `code` / `change_pct` |

**测试结果**：3 例全部通过。

### 二、调度任务（3 例）

**业务场景**：用户周一 14:00 申购，周二 14:00 由定时任务确认；以及服务重启时的补偿任务要能捞起遗漏的订单。

| 场景 | 预期 |
|------|------|
| 确认任务：周一申购 → 周二直调 `_confirm_pending_orders_job()` | 订单 `completed`；`positions` 1 条且份额 > 0 |
| 启动补偿：同一时序直调 `_startup_pending_compensation()` | 订单 `completed`；`positions` 1 条 |
| 没有任何 pending 订单时跑确认任务 | 不抛异常（`processed=0` 场景） |

> 补偿任务虽然 `skip_trading_day_check=True`，但仍要求 `confirm_date <= today`，所以时钟同样要推到确认日，否则什么都不会发生。

**测试结果**：3 例全部通过。

## 覆盖边界

- 行情只回放「已经录好的那一刻」的样本，**不验证数据源实时可用性**；东财/ AKShare 接口变化不会让这层变红，只会在单元测试的解析用例里暴露。
- 行情缓存刷新任务本身（`start_scheduler`）在 API 测试里被替换成空函数，避免测试启动时打外网；调度器的**其他** job（如行情刷新）没有集成用例。
- 定时任务没有覆盖「重复执行同一条订单」的幂等场景，靠数据库状态筛选兜底。
