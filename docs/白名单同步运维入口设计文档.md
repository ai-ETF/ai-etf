# 白名单运维入口设计文档

> 主题：为「场外基金白名单同步」补一个可手动触发的运维入口，并修复使其无法跑完的写入缺陷。
> 相关联文档：[场外基金申购上限设计文档](./场外基金申购上限设计文档.md)（同步链路的业务语义、白名单口径在该文）。

## 1. 背景与术语

| 术语 | 含义 |
|---|---|
| 白名单 | `fund_fee_rules` 表（配套 `fund_risk_profiles`）。表里有记录 = 系统支持该基金交易 |
| 同步 | `FundCatalogSync.run()`：全量发现候选基金 → 逐只抓天天基金页面 → 幂等 upsert 两张表 |
| flush | `run()` 内每攒够 `UPSERT_BATCH_SIZE=50` 行就批量写一次库，如果出现失败，则降级一行一行写入数据库 |
| fail-closed | 规则缺失/不可信时**拒绝写入**，不用默认值兜底。本模块既定原则（见同步模块 docstring 与旧设计文档第 4 节） |

**需求**：以后运维能随时手动刷新白名单，不必依赖次日 02:17 的定时任务。

## 2. 当前实现

### 运维入口

新增 `server/scripts/sync_fund_catalog.py`（目录需补 `__init__.py` 以支持 `-m` 调用）：

```bash
cd /root/ai-etf && .venv/bin/python -m server.scripts.sync_fund_catalog [选项]
```

| 选项                    | 说明                                                      |
| ----------------------- | --------------------------------------------------------- |
| `--limit N`             | 只处理前 N 只（试跑用，如 `--limit 5`）                   |
| `--codes 110020,000071` | 只处理指定基金代码                                        |
| `--interval S`          | 逐只抓取间隔秒数，默认沿用 `DEFAULT_REQUEST_INTERVAL=0.3` |
| `--dry-run`             | 抓取并组装，但**不写库**                                  |

- 脚本自行 `load_dotenv(项目根/.env)`（`load_dotenv` 默认不覆盖已有环境变量，本地开发亦安全）；
- 结束打印 `run()` 的统计 dict，并据此决定退出码：`0` 全部成功；`1` 有坏行或异常；`2` 未取到同步锁（已有同步在跑）；
- 服务端用法：`setsid nohup … > /tmp/fund_sync.log 2>&1 < /dev/null &` 可脱离 SSH 会话。


## 3. 发现的问题

- **统计口径**：`run()` 在 `_flush` **之前**就累加 `stats["synced"]`（`:320`），若 flush 失败，已写与未写的行在统计上无法区分。本次因引入逐行降级而顺带修正（见 4.2）。
- **部分批次已落库**：PostgREST 的单次批 upsert 是原子的，但**先前批次已成功写入且不回滚**。崩在第 50 只时，前 49 只并未写库（首次 flush 就失败），但更大规模故障时会留下半新半旧的数据。

## 4. 设计方案

### 4.1 并发锁

`fund_catalog_sync.py` 暴露 `sync_lock()` 上下文管理器（`fcntl.flock` 非阻塞独占，锁文件 `/tmp/fund_catalog_sync.lock`），**CLI 与定时任务共用**：

- CLI：拿不到锁 → 打印提示并以退出码 `2` 结束（不排队）；
- 定时任务（`_fund_catalog_sync_job`）：拿不到锁 → 记 `WARNING` 并跳过本轮（说明有手工同步在跑），不抛异常。

### 4.2 本次明确不做

| 不做的事 | 理由 |
|---|---|
| HTTP 管理端点（L2） | 代码库当前**完全没有「管理员」概念**，需先定义谁算管理员；且新增一个能触发重负载抓取 + 写库的公开接口是新攻击面。运维实际经 SSH 操作，CLI 已够用。需要时再议（Q2） |
| 任务化 + 状态落库（L3） | 需建表 + 迁移 + 重构调度，超出「便于运维」的即时需求（Q3） |
| 定时任务改写为独立进程 / systemd timer | 现状进程内调度可用，无证据表明需要改动 |

## 5. 测试策略

沿用 `tests/unit/server/services/test_fund_catalog_sync.py` 既有约定（纯函数直测 + 假客户端替身，不联网、不连 Supabase）：

| 用例 | 断言 |
|---|---|
| 销售服务费率缺失 → 落 0.0 | `build_fee_rule` 返回行中该字段为 `0.0`，且行**不为 None** |
| 申购起点缺失 → 跳过该基金 | 返回 `None`（不写库） |
| 管理费/托管费缺失 → 跳过该基金 | 返回 `None` |
| 批次写入失败 → 降级逐行，坏行计入 failed | 假客户端对整批抛错、对单行选择性抛错时，`stats["failed"]` 正确、好行仍写入、`codes` 不含坏行 |
| 费率行失败 → 不写其风险画像 | 假客户端记录中该 code 只出现在失败的费率行尝试里 |
| CLI 参数解析与锁语义 | `--limit` / `--codes` / `--dry-run` 生效；锁被占用时退出码 2 |
| 锁可重入/释放 | 退出上下文后锁可再次获取 |

集成测试（`tests/integration/…`）按需补充，需本地 Supabase 环境。

###  与设计稿的偏差

- 4.2 原写「`synced` 只在写入成功后累加」，实现改为「收集时累加、flush 失败时回退」—— 对外可观测结果一致，但不改原设计（避免把统计搬到 flush 后导致进度日志口径变化）。已就地更正 4.2 措辞。
