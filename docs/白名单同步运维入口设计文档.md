# 白名单同步运维入口设计文档

> 主题：为「场外基金白名单同步」补一个可手动触发的运维入口，并修复使其无法跑完的写入缺陷。
> 相关联文档：[场外基金申购上限设计文档](./场外基金申购上限设计文档.md)（同步链路的业务语义、白名单口径在该文）。

## 1. 背景与术语

| 术语 | 含义 |
|---|---|
| 白名单 | `fund_fee_rules` 表（配套 `fund_risk_profiles`）。表里有记录 = 系统支持该基金交易 |
| 同步 | `FundCatalogSync.run()`：全量发现候选基金 → 逐只抓天天基金页面 → 幂等 upsert 两张表 |
| flush | `run()` 内每攒够 `UPSERT_BATCH_SIZE=50` 行就批量写一次库 |
| fail-closed | 规则缺失/不可信时**拒绝写入**，不用默认值兜底。本模块既定原则（见同步模块 docstring 与旧设计文档第 4 节） |

**需求**：以后运维能随时手动刷新白名单，不必依赖次日 02:17 的定时任务。

## 2. 当前实现

| 环节 | 位置 |
|---|---|
| 定时任务（唯一入口） | `server/services/spot_cache_scheduler.py:64` `_fund_catalog_sync_job`，注册于 `:133`（`CronTrigger(hour=2, minute=17)`，`misfire_grace_time=7200`） |
| 全量同步主循环 | `server/services/fund_catalog_sync.py:276` `run()` |
| 抓取间隔 / 批大小 | `server/services/fund_catalog_sync.py:68` `DEFAULT_REQUEST_INTERVAL=0.3`、`:69` `UPSERT_BATCH_SIZE=50` |
| 落库行组装 | `server/services/fund_catalog_sync.py:95` `build_fee_rule()`，字段在 `:114-133` |
| 批量写入 | `server/services/fund_catalog_sync.py:344` `_flush()` |
| 费率解析 | `server/services/fund_fee_source.py:293`（销售服务费率）、`:64` `_pct()` |
| 表结构 | `docs/legacy_sql/migrate_v2_off_exchange.sql:139-150` |

表结构关键约束（`fund_fee_rules`，均为 `NOT NULL`）：

```sql
management_fee_rate    DECIMAL(6,4) NOT NULL DEFAULT 0.015
custody_fee_rate       DECIMAL(6,4) NOT NULL DEFAULT 0.0025
min_purchase_amount    DECIMAL(18,2) NOT NULL DEFAULT 10.00
sales_service_fee_rate DECIMAL(6,4) NOT NULL DEFAULT 0.0000   -- 注释：A类=0，C类通常0.2%~0.4%
```

## 3. 发现的问题

### 3.1 P1（阻塞）写入 NULL 触发 NOT NULL 约束，整轮同步崩溃

**实测证据**（2026-10-03 17:03 在生产服务器手工触发全量同步）：

```
postgrest.exceptions.APIError: {'message': 'null value in column "sales_service_fee_rate"
of relation "fund_fee_rules" violates not-null constraint', 'code': '23502',
'details': 'Failing row contains (..., 001241, 国寿安保中证500ETF联接, ... null, 开放申购)'}
```

崩在第 50 只 —— 正是第一次 flush。

**成因链**：

1. 天天基金购买信息页对部分基金**没有「销售服务费率」行**（A 类通常如此），`_pct()`（`fund_fee_source.py:64`）对空文本返回 `None`；
2. `build_fee_rule()` 用 `jjfl.get("sales_service_fee_rate")` 原样取值（`fund_catalog_sync.py:120`），得到 `None`；
3. 该值被**显式**写入 upsert，显式 `NULL` 会**覆盖掉列 DEFAULT**，于是撞上 `NOT NULL`；
4. `_flush()` 的异常向上抛穿 `run()`，**整个任务终止**。

**缺失面实测**（取首次 flush 的那 50 只，抓取失败 0 只）：

| NOT NULL 列 | 为 `None` 的只数 |
|---|---|
| `management_fee_rate` | 0 / 50 |
| `custody_fee_rate` | 0 / 50 |
| `sales_service_fee_rate` | **2 / 50（4%）** |
| `min_purchase_amount` | **1 / 50（2%）** |

**影响推论**：按 50 条一批，单批至少命中一条坏行的概率极高 → **全量同步实际上永远跑不完**。这意味着 02:17 的定时任务自落地起就是坏的，只是因为服务从未重启注册过该任务而没暴露（详见未解决问题表 Q5）。

### 3.2 P2 脆弱点：单条坏数据拖垮整轮

`_flush()`（`:344`）批量 upsert 失败即抛异常，`run()` 未捕获 → 整轮中止，**已抓取的待写批次全部丢弃**。即使修好 3.1 的两个字段，以后任何页面改版引入新的脏数据（新字段、新格式）都会重演。运维最需要的是「一轮跑完 + 坏行单独列出」，而不是整轮归零。

### 3.3 P3 无运维入口

想立刻刷新白名单，只能在服务器上手工拼一次性命令，且必须自己记得 `load_dotenv('.env')`（生产环境变量由 `server/app.py` 的 `load_dotenv` 注入，systemd 未配置 `EnvironmentFiles`），否则报「未设置SUPABASE_URL环境变量」直接失败。

### 3.4 P4 无并发保护

`_fund_catalog_sync_job`（`spot_cache_scheduler.py:64`）与 `FundCatalogSync` 内部**都没有任何锁**。加了手动入口后，「手动跑」与「02:17 定时跑」重叠写同一批 `fund_code` 的可能性显著上升。两个进程各自 upsert，会互相覆盖且无法察觉。

### 3.5 附带发现（本次不处理，仅记录）

- **统计口径**：`run()` 在 `_flush` **之前**就累加 `stats["synced"]`（`:320`），若 flush 失败，已写与未写的行在统计上无法区分。本次因引入逐行降级而顺带修正（见 4.2）。
- **部分批次已落库**：PostgREST 的单次批 upsert 是原子的，但**先前批次已成功写入且不回滚**。崩在第 50 只时，前 49 只并未写库（首次 flush 就失败），但更大规模故障时会留下半新半旧的数据。

## 4. 设计方案（已由用户拍板）

### 4.1 NOT NULL 空值策略 —— **方案 A：按语义区分**

| 字段 | 缺失（`None`）时 | 依据 |
|---|---|---|
| `sales_service_fee_rate` | 落 **0.0** | 列注释即「A类=0」；A 类不收取销售服务费是**业务事实**，不是猜测 |
| `min_purchase_amount` | **跳过该基金**（fail-closed） | 申购起点是真实交易规则，页面缺失即不可信；按 DEFAULT 写 10 元等于把起购金额猜小，纯猜 |
| `management_fee_rate` | **跳过该基金**（fail-closed） | 实测 0/50 缺失；真缺了属于页面结构异常，按「不可信」处理 |
| `custody_fee_rate` | **跳过该基金**（fail-closed） | 同上 |

> 被跳过的基金**不写库**，因此**存量行不受影响**（不会把已支持的基金从白名单挤掉，也不会被写成空值）。跳过原因逐条写日志。

**已否决的备选**：
- 全部回落到列 DEFAULT：改动最小，但会让 `min_purchase_amount` 按 10 元入库，与「交易规则不能靠猜」冲突。
- 两者都跳过：白名单会少约 4%（≈90 只），且这些基金即便页面正常也永远刷不进来。

### 4.2 `_flush()` 降级为逐行写入

- 批次 upsert 失败 → **降级为逐行 upsert**，坏行单独捕获、计入 `stats["failed"]` 并记 `ERROR` 日志（含 `fund_code` 与数据库报错信息）；
- 成功的行照常计入 `synced`，**整轮不再中止**；
- `stats` 口径修正：坏行在 flush 时**从 `synced` 回退**并改计 `failed`，同时从 `codes` 中移除（对应 3.5）；
- 风险画像表同样处理；**费率行写失败则该基金的风险画像不写**（避免出现无费率规则的风险画像）。

### 4.3 CLI 运维入口（L1）

新增 `server/scripts/sync_fund_catalog.py`（目录需补 `__init__.py` 以支持 `-m` 调用）：

```bash
cd /root/ai-etf && .venv/bin/python -m server.scripts.sync_fund_catalog [选项]
```

| 选项 | 说明 |
|---|---|
| `--limit N` | 只处理前 N 只（试跑用，如 `--limit 5`） |
| `--codes 110020,000071` | 只处理指定基金代码 |
| `--interval S` | 逐只抓取间隔秒数，默认沿用 `DEFAULT_REQUEST_INTERVAL=0.3` |
| `--dry-run` | 抓取并组装，但**不写库** |

- 脚本自行 `load_dotenv(项目根/.env)`（`load_dotenv` 默认不覆盖已有环境变量，本地开发亦安全）；
- 结束打印 `run()` 的统计 dict，并据此决定退出码：`0` 全部成功；`1` 有坏行或异常；`2` 未取到同步锁（已有同步在跑）；
- 服务端用法：`setsid nohup … > /tmp/fund_sync.log 2>&1 < /dev/null &` 可脱离 SSH 会话。

### 4.4 并发锁

`fund_catalog_sync.py` 暴露 `sync_lock()` 上下文管理器（`fcntl.flock` 非阻塞独占，锁文件 `/tmp/fund_catalog_sync.lock`），**CLI 与定时任务共用**：

- CLI：拿不到锁 → 打印提示并以退出码 `2` 结束（不排队）；
- 定时任务（`_fund_catalog_sync_job`）：拿不到锁 → 记 `WARNING` 并跳过本轮（说明有手工同步在跑），不抛异常。

### 4.5 本次明确不做

| 不做的事 | 理由 |
|---|---|
| HTTP 管理端点（L2） | 代码库当前**完全没有「管理员」概念**，需先定义谁算管理员；且新增一个能触发重负载抓取 + 写库的公开接口是新攻击面。运维实际经 SSH 操作，CLI 已够用。需要时再议（Q2） |
| 任务化 + 状态落库（L3） | 需建表 + 迁移 + 重构调度，超出「便于运维」的即时需求（Q3） |
| 定时任务改写为独立进程 / systemd timer | 现状进程内调度可用，无证据表明需要改动 |
