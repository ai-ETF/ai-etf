# 数据库规范化设计学习与现状评估

> 目的：梳理关系数据库规范化理论（1NF / 2NF / 3NF / BCNF），并据此对当前 AI-ETF 项目的数据库做一次**只评估、不修改**的体检。
>
> 评估对象：AI-ETF 项目数据库（Supabase / PostgreSQL）。

## 评估方法与数据来源（重要）

这次评估**直接连接了线上 Supabase 库**（用项目里的 `.env` 服务密钥），不是只看 SQL 文件。具体做了三件事：

1. 拉取 PostgREST 的 OpenAPI 结构描述（`/rest/v1/`），得到**线上真实**的表、列、类型、主键、外键；
2. 查询了若干张表的**真实数据**，核实枚举取值和分布；
3. 再回头和仓库里的 `sql/*.sql`、`server/types/supabase.ts` 交叉比对。

结论先说：**线上库的结构和仓库里的 SQL 脚本、类型文件三者已经对不上了**（详见第四节）。所以本评估以**线上真实库为准**，凡是"脚本里写了但线上没有"的地方会特别标注。

局限说明：PostgREST 的 OpenAPI 能拿到列/类型/主键/外键，但**拿不到 UNIQUE 约束、CHECK 约束和索引**。这三类信息我只能依据 SQL 脚本推断，已在下文标注。

## 一、规范化理论学习成果

关系数据库规范化的核心思想是：**消除冗余、避免异常**。所谓"异常"（anomaly）指三类：

| 异常类型 | 含义 | 通俗解释 |
|---------|------|---------|
| 更新异常 | 改一处要同时改多处 | 基金改名后要改 4 张表 |
| 插入异常 | 想存一部分数据必须先造出另一部分 | 想记录基金费率，必须先有用户持仓 |
| 删除异常 | 删一部分数据会连带丢另一部分 | 删掉最后一个持仓，基金基础信息也没了 |

范式是一层层递进的约束，每一级解决上一级遗留的问题：

### 1. 第一范式（1NF）—— 原子性
**规则**：每列都必须是不可再分的原子值，不允许"一个字段塞数组/对象/逗号分隔列表"这种重复组。

反例（重复组）：
```
purchase_fee_tiers = [{"amount":1000000,"rate":0.0015}, {"amount":10000000,"rate":0.0012}]
```
严格说这是重复组，违反 1NF，应拆成子表 `fund_fee_tiers(fund_code, amount, rate)`。

**但**：PostgreSQL 的 JSONB 是被广泛接受的"务实偏离"。当数组永远整体读写、从不用 SQL 查询/约束其中某个元素时，用 JSONB 反而更简洁。所以 JSONB 用得好是"合理的反范式化"，用不好才是"1NF 违规"。

### 2. 第二范式（2NF）—— 消除部分依赖
**规则**：满足 1NF 后，非主键列必须**完全依赖整个主键**，不能只依赖主键的一部分。**只对复合主键有意义**。

反例：`order_items(order_id, fund_code, fund_name)`，主键 `(order_id, fund_code)`。`fund_name` 只依赖 `fund_code`、不依赖 `order_id` —— 这是"部分依赖"。解法：把 `fund_name` 抽到独立基金主表。

### 3. 第三范式（3NF）—— 消除传递依赖
**规则**：满足 2NF 后，非主键列之间不能有依赖；每个非主键列都必须**直接**依赖主键，不能"拐弯"。

反例（本项目的头号问题）：
```
positions.id  →  positions.fund_code  →  positions.fund_name
```
`fund_name` 依赖 `fund_code` 这个非主键列，属于传递依赖。解法：`fund_name` 只存一份（基金主表），其余表只存 `fund_code` 外键。

### 4. Boyce-Codd 范式（BCNF）—— 3NF 加强版
**规则**：任何"能决定其他列"的组合（决定因素）都必须是候选键。绝大多数 3NF 设计天然满足 BCNF。本项目对标到 3NF 即可。

### 5. 第四/第五范式（4NF / 5NF）—— 简要提及
- 4NF 消除**多值依赖**（一个主键关联多个相互独立的多值属性，如"一个人会多种技能 + 说多门语言"），避免笛卡尔积爆炸；
- 5NF 消除**连接依赖**，日常业务几乎用不到。

### 6. 反范式化（Denormalization）—— 规范化的另一面
规范化不是越高越好。以下场景**应当**主动反规范化（有意识、有理由的冗余）：
- **快照/报表**：把某时刻计算结果落库，避免每次重算（如本项目 `account_snapshots`）；
- **读多写少的冗余列**：为省一次 JOIN 而冗余一个字段；
- **灵活 schema**：字段结构不固定时用 JSONB（如各表的 `metadata`）。

**关键区别**：规范化消除的冗余是"无意的、会引发异常"；反规范化的冗余是"有意的、被文档和代码保护"的。下文按这个标准区分"问题"与"合理取舍"。

## 三、逐域评估

### 3.1 交易域：规范化问题最集中，且缺外键

这一组是**手写 SQL** 建出来、又经历了十余个增量 `ALTER` 补丁的表，问题最集中。

#### 🔴 问题 1：`fund_name` 在 4 张表里冗余（3NF / BCNF 违规）

线上实测，`fund_name` 同时存在于 `positions`、`trade_orders`、`trade_flow`、`watchlist` 四张表，而基金主数据在 `fund_fee_rules`（`fund_code` 唯一）。这是典型传递依赖：`表.id → fund_code → fund_name`。

后果：
- **更新异常**：基金更名要同步改 4 张表，漏一张就数据不一致；
- **一致性负担**：`cleanup_old_fund_codes.sql` 里为换基金代码，要手工 `DELETE` 主表再检查 3 张关联表，正是这个冗余带来的额外维护成本。

建议方向：`fund_name` 只保留在 `fund_fee_rules`，其余表只存 `fund_code`，展示时 JOIN 或应用层缓存。

#### 🔴 问题 2：`trade_flow` 缺 `order_id`，字段大量重复

线上实测 `trade_flow` 有 11 列：`user_id / fund_code / fund_name / direction / amount / price / quantity / fee / trade_pnl / trade_time / id`，**没有 `order_id` 指向 `trade_orders`**，却把可由订单推导的字段几乎重复了一遍。

后果：
- 无法从一笔成交反查是哪个委托（对账/审计困难）；
- 委托信息变更后流水不跟着变，两份数据可能对不上。

建议方向：`trade_flow` 增加 `order_id → trade_orders.id`；`direction / fund_name` 等可由订单推导的字段明确取舍（`user_id / fund_code` 做查询索引可保留，`fund_name` 应去掉）。

#### 🔴 问题 3：交易域整体没有外键约束（线上实测确认）

线上实测：`positions / trade_orders / trade_flow / watchlist / fund_fee_rules / accounts / account_snapshots` 这 7 张表**一张都没有外键**。而 RAG 域、风险域的 8 张表外键齐全（见 3.2 / 3.3）。

后果：`positions.fund_code` 可能指向 `fund_fee_rules` 里根本不存在的基金（孤儿数据），数据库层完全无法阻止脏数据，只能靠应用代码保证。目前抽查没发现孤儿（见下），但这是"靠运气+靠应用"维持的一致性，不是结构上的保证。

说明：`user_id → auth.users` 不做外键是 Supabase 惯例（`auth.users` 在独立 schema），可理解；但 `fund_code → fund_fee_rules.fund_code` 这种**库内**引用，建议补外键。

#### 🟡 问题 4：`fund_fee_rules` 用 JSONB 存费率档位（1NF 的务实偏离）

线上实测 `purchase_fee_tiers`、`redemption_fee_tiers` 是 JSONB 数组（重复组），严格说违反 1NF。属**可接受的务实偏离**，因为档位总是整体读写、从不用 SQL 单独查某一档。需注意两点：

1. **两个档位列的约束不一致**：线上 `redemption_fee_tiers` 是 `NOT NULL`，`purchase_fee_tiers` 却是**可空**（`NULL` 表示"退回单费率"的兼容逻辑）。这种"一个必填、一个可空"的差异，会让算费逻辑出现分支，建议统一。
2. 档位结构没有数据库层约束，JSON 格式错了只能靠应用层兜；若将来要做"按持有天数/金额实时算费并统计"，应拆成独立 `fund_fee_tiers` 子表。

#### 🟡 问题 5：`trade_orders.fund_type` 冗余 + 取值与主表不一致（线上实测）

`trade_orders` 加了 `fund_type` 列，这个值本应由 `fund_code` 决定（主表 `fund_fee_rules.fund_type` 已有），又是一处传递依赖。更严重的是**取值对不上**：

- 线上 `fund_fee_rules.fund_type` 全部是 **`of`**（21 行，见下）；
- 线上 `trade_orders.fund_type` 全部是 **`otf`**（23 行）。

同一个"场外基金"概念，两张表用了两个不同的字符串（`of` vs `otf`），这是**已经在线上数据里发生了的枚举漂移**，不只是脚本层面的隐患。

#### 🟢 做得好的地方
- 全表统一代理主键 `UUID`，主键设计一致；
- `account_snapshots` 是**正确使用反范式化**的范例：把每日总资产/盈亏/收益率快照落库，属刻意的"快照表"；
- 索引充分（`idx_positions_user`、`idx_trade_flow_user_time` 等，依据 SQL 脚本）；
- 全表有 `COMMENT ON` 注释，文档习惯好。

### 3.2 RAG 域：规范化做得最好

这组是最新、质量最高的表，**线上实测外键齐全、中间表规范**：

- `message_chunks` 是标准**多对多中间表**，用 `message_id + chunk_id` 两个外键正确表达"一条消息引用多个切片"，完全符合 3NF，教材级正确示范；
- `chats → messages → message_chunks` 三层主从用外键串起来，配合 `triggers_cascade.sql` 级联删除，删会话能正确清理下游。

**小瑕疵**：
- 🟡 `messages.user_id` 冗余：可由 `chat_id → chats.user_id` 推导（传递依赖），且线上已设为**可空**。保留多半为查询方便，属可接受冗余，但应意识到它是冗余的。
- 🟡 `document_chunks.document_type` 冗余：`documents` 已有 `doc_type`，切片上的 `document_type` 是从文档继承的（传递依赖）。留它是为了让 `match_chunks_fts` 少一次 JOIN，属"为查询性能的合理反范式化"，可接受但需注明。

### 3.3 风险测评/资产配置域：结构正确，JSONB 使用偏重

**线上实测外键齐全**（`answers → questionnaire`、`profiles → answers`、`allocations → model`），关系建模正确。

**需注意**：
- 🟡 `risk_questionnaires.questions` 用 JSONB 存整张问卷（题目数组），是重复组，严格违反 1NF。问卷结构固定后若要按题统计，需拆 `questions` / `options` 子表。
- 🟡 `user_risk_profiles.dimension_scores`、`weighted_scores`、`ai_summary` 用 JSONB 存结构化评分。这些是"AI 算出、结构随模型版本变化"的数据，用 JSONB 灵活承载合理；而关键字段（`risk_level`、`total_score`、`confidence_score`）已抽成独立列，这个"半结构化 + 关键列"的做法是对的。
- 🟢 用了真正的 Postgres ENUM（`risk_level`、`profile_source`），比交易域的"VARCHAR + CHECK"更规范、更自文档化。

### 3.4 系统域：结构简单

`ai_requests`、`market_indicators` 都是扁平表，无冗余。仅一点：
- 🟡 `ai_requests.status` 用 `text` 且无 CHECK 约束（线上实测 `status` 是 `text`），取值不受控，建议加 CHECK 或用 ENUM。

## 四、线上核实发现：schema 漂移（比范式更紧急）

交叉比对"线上库 / `sql/*.sql` / `server/types/supabase.ts`"后，发现三者已经脱节。这是当前最该先处理的问题，也正好呼应组长想用 Supabase migration 规范流程的目标。具体证据：

### 4.1 类型文件 `supabase.ts` 严重过时
`server/types/supabase.ts`（`supabase gen types` 生成）与线上真实结构差异很大，例如：

| 表 | `supabase.ts` 里的样子（旧） | 线上真实（新） |
|----|------------------------------|----------------|
| `accounts` | 无 `frozen_cash` | 有 `frozen_cash`、`auto_invest_enabled`、`auto_invest_reserve` |
| `positions` | 无 `available_date` | 有 `available_date`、`confirm_date` |
| `trade_orders` | 无 `confirm_date`、`fund_type` | 有 `confirm_date`、`fund_type` |
| `fund_fee_rules` | 旧平铺列 `purchase_fee_rate`、`redemption_fee_rate_7d/30d/1y/over1y` | 已改为 `purchase_fee_tiers`、`redemption_fee_tiers` JSONB，且旧列已删除 |
| `trade_flow` | 无 `trade_pnl` | 有 `trade_pnl` |

也就是说：**线上库已经跑完了大部分 `alter_*.sql`，但类型文件没跟着重新生成**，导致前端/服务端的类型和真实库脱节。

### 4.2 有些脚本线上没有执行——分两类

交叉比对发现部分脚本在线上"查无此列/查无此数据"，但性质不同：

**有意未执行（不是 bug，是预留/暂缓）：**
- `alter_fund_fee_rules_t0.sql` 加的 `is_t0` 列，线上没有——这是**有意不执行**的预留迁移。`is_t0` 是场内 ETF 的"T+0 回转"标记，而当前系统只做场外基金、直接拦截场内 ETF 交易（`portfolio_service.py`），且 512890/510300 都是 T+1 的股票型 ETF，暂时用不上。
- `migrate_all_tables.sql` / `fund_fee_rules_seed.sql` 想塞入的场内 ETF（512890、510300）线上也没有——同样是**暂缓上线**：当前阶段只跑场外基金，尚未引入场内 ETF 品种。

**真正的漂移（需要处理）：**
- `supabase.ts` 与线上结构脱节（见 4.1）；
- `trade_orders.fund_type` 与主表的 `of`/`otf` 取值分叉（见 4.3，已有修复脚本 `alter_trade_orders_fund_type_fix.sql`）。

### 4.3 线上真实数据里已经存在取值不一致
- `fund_fee_rules.fund_type` = `of`（21 行全是场外基金）；
- `trade_orders.fund_type` = `otf`（23 行全是 `otf`）。

需要说明的是：主表 `fund_fee_rules` 其实**已经被清理统一成 `of`**（说明之前做过一次 `otf→of` 的修复），但 `trade_orders.fund_type` 是**另一张表里的独立列**（由 `alter_trade_orders_reserved.sql` 新增，`DEFAULT 'otf'` + `CHECK (fund_type IN ('otf','etf'))`），那次清理没覆盖到它，于是 23 行仍是 `otf`。

这恰恰是"冗余列引发更新异常"的活例子：`trade_orders.fund_type` 本可从 `fund_code` join 主表得到，主表改了、冗余副本没同步，就出现"主表 `of`、副本 `otf`"的分叉。而且因为这一列带着自己的 `CHECK ('otf','etf')`，要把它改成 `of` 还得先改约束——是典型的多步手工修复，正是散落 `ALTER` 脚本 + 手工在 SQL Editor 执行、没有单一真相来源的后果。

### 4.4 数据规模（供参考）
线上当前是开发/演示数据，量很小：`fund_fee_rules` 21 行、`trade_orders` 23 行、`trade_flow` 22 行、`positions` 4 行。交易集中在 4 个基金代码（000071、000198、001595、110020），抽查未发现孤儿 `fund_code`——但这是"靠应用+运气"维持的，不是结构保证。

## 六、改进建议（仅建议，未做任何修改）

按优先级排序：

### 1. 先重建迁移的"唯一真相来源"（呼应组长目标，最高优先级）
- 把散落的 `sql/*.sql` 收拢为 Supabase 版本化 migration（`supabase/migrations/<timestamp>_xxx.sql`），一条 migration 一个变更，按序执行、可回滚、可追溯；
- 每次 migration 后用 `supabase gen types` 重新生成 `supabase.ts`，保证类型文件和库结构一致；
- 用 `supabase db diff` / `db lint` 持续比对"脚本声明结构"与"线上实际结构"，尽早暴露漂移。

### 2. 统一 `fund_type` 取值（先止血）
- 定死一个值域（`of` 还是 `otf`，全项目统一），把 `trade_orders` 里那 23 行 `otf` 刷成和主表一致，并加单处定义的 CHECK 或 ENUM，杜绝再漂移。

### 3. 消除 `fund_name` 冗余（性价比最高的规范化动作）
- `fund_name` 只存 `fund_fee_rules`，其余表只留 `fund_code`，并给 `fund_code` 加外键；展示层 JOIN 主表或应用层缓存。

### 4. 补交易域外键、明确 `trade_flow` 与 `trade_orders` 关系
- `trade_flow` 加 `order_id → trade_orders.id`；
- `positions / trade_orders / trade_flow / watchlist.fund_code → fund_fee_rules.fund_code` 加外键；
- 加外键前先清理已有孤儿数据（`cleanup_old_fund_codes.sql` 已暴露过这类风险）。

### 5. 明确"JSONB 是刻意反范式化"的边界
- 费率档位、问卷、评分等 JSONB 字段，在注释/文档里标注"为什么用 JSONB、何时该拆表"，把"有意冗余"和"无意冗余"区分开。

---

## 七、结论

一句话总结：**这个数据库整体方向是对的——主键统一、关键自然键有 UNIQUE、RAG 域和风险域的外键与中间表很规范、快照表用对了反范式化；主要短板集中在手写的交易域**，表现为 `fund_name` 四处冗余（3NF/BCNF 违规）、全组缺外键、`trade_flow` 与订单脱钩，以及更底层的**迁移流程失控导致的 schema 漂移**——线上数据里 `fund_type` 已经出现 `of`/`otf` 两种写法，类型文件也严重过时。

按投入产出比，最值得先做两件事：**① 用 Supabase 版本化 migration 重建唯一真相来源；② 统一 `fund_type` 取值并清掉 `fund_name` 冗余、补外键。** 完成后，数据库规范程度会从"能跑但靠人工维持一致"提升到"结构上杜绝异常"。
