## 0. 目标与结论

把订单确认从「多表多次写、靠异常补偿、依附抓取任务」改为：

> **纯读库、可重入、单笔原子、资金守恒、调度独立。**

### 0.1 七条结论

1. **一笔订单的确认 = 一个数据库事务**（PL/pgSQL RPC）。解冻、建仓、建 lot、写流水、改订单、退尾差在同一事务内完成，失败整体回滚。
2. **确认只读 DB**：净值取 `fund_nav`（货基恒 1.0000），不触网、不 repair、不依赖交易日历。
3. **订单级认领 + 租约**：`pending → processing` 是带 `processing_at/processing_by` 的原子认领；租约超时由回收 RPC 放回 `pending` 或转 `manual_review`。
4. **批次级单飞**：`confirm_runs` 的「运行中唯一」约束 + advisory lock，覆盖多实例/多 worker。
5. **资金/份额原子增减**：`cash = cash ± x`、`frozen_cash = frozen_cash ± x`、`quantity = quantity ± x` 全部在 SQL 内完成，应用层不再读改写。
6. **lot + FIFO + 赎回到账**：`position_lots` 是持仓的事实来源，`positions` 是由 lot 汇总的读模型；卖出生成 `settling` 应收，`settle_date` 到账再进 `cash`。
7. **下单侧也必须原子化**：冻结资金 + 写订单、校验可赎份额 + 写卖单同样走 RPC。否则确认侧的资金守恒不成立（见 §3.4）。

### 0.2 本期不做

- 基金公司的真实「部分确认」、外部资金对账、税费/分红/份额折算、实时估值。
- 外部告警平台接入（本期用 ERROR 日志 + 对账/巡检脚本）。
- 前端页面改造（API 只做兼容追加）。

### 1.2 术语

| 术语 | 含义 | 落库位置 |
|---|---|---|
| 受理日 `accepted_date` | 订单被受理的交易日 T。15:00 前为当日，否则顺延到下一交易日。**也是买/卖单的成交净值日** | `trade_orders.accepted_date` |
| 份额确认日 `confirm_date` | 份额登记（到账）的日期。买单 = T + `confirm_delay` 个交易日；卖单 = T。**只决定份额何时可见，不决定成交价** | `trade_orders.confirm_date` |
| 到账日 `settle_date` | 赎回资金进入可用现金的日期 = T + `redeem_settle_delay` 个交易日 | `trade_orders.settle_date` |
| 可赎回日 `available_date` | 该批份额最早可赎回的日期 = 份额确认日 + `redeem_available_delay` 个交易日 | `trade_orders.available_date`、`position_lots.available_date` |
| 批次净值日 `nav_date` | 形成该 lot 的买单的**成交净值日** = 该买单的 `accepted_date`（不是 `confirm_date`） | `position_lots.nav_date` |
| 实际确认时间 | 跑批真正执行确认的时刻，仅审计/排查 | `trade_orders.processed_at` |
| 实际到账时间 | 应收转为现金的时刻 | `trade_orders.settled_at` |
| Lot | 一笔买入（或期初、货基收益）形成的持仓批次，用于 FIFO、持有期费用和未来部分确认 | `position_lots` |
| 认领 | 用 CAS 把 `pending` 改成 `processing` 并记录 worker/租约 | `trade_orders.processing_*` |
| 租约 | `processing` 的有效期，超时后可被回收 | `processing_at` + 配置 |
| 单飞 | 同一时刻只允许一个确认批次或净值同步执行 | `confirm_runs` |
| 四态 | `OK` / `NOT_YET_PUBLISHED` / `FETCH_FAILED` / `NO_NAV` | `NavLookupStatus` |

> **命名修正（2026-10-30）**：需求文档里的 `trade_date` 同时指「订单受理日」和「lot 的净值日」。
> 本文落库时拆成两个名字：订单受理日用 `accepted_date`，lot 的净值日用 `nav_date`，避免同名不同义。
> 语义不变；需求文档 §2.5/§6.2 的 `trade_date` 分别对应这两列。
>
> **口径修正（2026-10-30，方案 A）**：早期草稿把买单的成交净值日取成 `confirm_date`（T+`confirm_delay`），
> 相当于晚 1~2 个交易日定价，与真实代销「申购按申请日 T 的净值成交，T+N 只是份额确认」不一致。
> 现改为：**成交净值日 = 受理日 `accepted_date`**，`confirm_date` 退化为份额到账日。
> 影响：买单价 = T 日净值、lot 的 `nav_date` = T、持有期比原来多算 1 天（更接近真实）；
> 确认时点不变（仍等 `confirm_date` 到期），但要求 T 日净值已公布，否则 `nav_unavailable` 等下轮。

## 3. 最终方案

### 3.1 状态机

```
pending ──claim──► processing ──成功(buy)──► completed
   ▲                   │
   │                   ├──成功(sell)──► settling ──到账──► settled
   │                   ├──业务拒单──► rejected（同事务补偿）
   │                   └──需人工──► manual_review ──人工重排──► pending
   │
   └──租约回收─────────┘
```

| 当前状态 | 允许的下一状态 | 触发 |
|---|---|---|
| `pending` | `processing` | 认领 |
| `pending` | `cancelled` | 用户/系统撤单（本期不开放） |
| `pending` | `rejected` | 业务拒单 |
| `pending` | `manual_review` | 数据不一致/需人工 |
| `processing` | `completed` | 买入确认成功 |
| `processing` | `settling` | 卖出确认成功 |
| `processing` | `pending` | 租约回收 |
| `processing` | `rejected` | 业务拒单 |
| `processing` | `manual_review` | 数据不一致 |
| `settling` | `settled` | 到账 |
| `manual_review` | `pending` | 管理员重排（RPC） |
| `completed` / `rejected` / `cancelled` / `settled` | 不可再迁移 | — |

规则：

- 所有迁移只允许通过 §3.6 的 RPC 完成；应用层不得直接 `UPDATE trade_orders SET status=...`。
- 终态不可逆由数据库触发器 `enforce_order_status_transition` 兜底（§3.3.7）。触发器在灰度稳定后单独迁移上线，避免旧代码 `pending → completed` 被误伤。
- `manual_review` 不是终态：管理员可用 `requeue_manual_review_order` 放回 `pending`（本期提供脚本，见 §3.11）。

### 3.2 时间口径

| 字段 | 含义 | 写入时机 | 计算 |
|---|---|---|---|
| `trade_orders.accepted_date` | 受理日 T，**也是成交净值日** | 下单 | 15:00 前且交易日 = 当日；否则下一交易日 |
| `trade_orders.confirm_date` | 份额确认（到账）日 | 下单 | 买：T + `confirm_delay` 个交易日；卖：T |
| `trade_orders.settle_date` | 赎回到账日 | 下单（卖单） | T + `redeem_settle_delay` 个交易日；非交易日顺延 |
| `trade_orders.available_date` | 该批份额可赎回日 | 下单（买单） | `confirm_date` + `redeem_available_delay` 个交易日 |
| `position_lots.nav_date` | lot 的成交净值日 | 确认/迁移/收益 | 买单 `accepted_date`；期初用 `positions.confirm_date`；货基收益用入账日 |
| `position_lots.available_date` | lot 的可赎回日 | 确认/迁移/收益 | 买单 `trade_orders.available_date`；期初用 `positions.available_date`；收益用入账日 |
| `trade_orders.processed_at` | 实际跑批时间 | 确认 | `now()` |
| `trade_orders.settled_at` | 实际到账时间 | 到账 | `now()` |

规则：

1. **确认路径不查日历**。买单的 `available_date` 在下单时算好并落到订单；确认时 RPC 直接写 lot，不再调 `_next_trading_day`。卖单的 `settle_date` 同样在下单时算好。
2. **lot 的持有天数** = 卖出订单的 `accepted_date` − `lot.nav_date`（两者都是成交净值日），不能用跑批日。这样延迟确认不会改变持有期。
   > 卖单的 `confirm_date` 与 `accepted_date` 恒等，用 `accepted_date` 只是让「持有期 = 两个成交净值日之差」在读代码时不产生歧义。
3. **可赎回份额** = `SUM(lot.remaining_qty WHERE available_date <= accepted_date)` − 已提交未完成的卖单份额。
4. **单日申购额度**按 `accepted_date` 聚合，不再用 `confirm_date` 反推。
5. 所有日期按 `Asia/Shanghai` 解释；数据库用 `date` / `timestamptz`，应用层不依赖服务器本地时区。
6. 存量订单的 `accepted_date/settle_date/available_date` 由一次性脚本（§3.15）补齐；脚本无法可靠反推时，宁可留在 `manual_review`，不用猜测值。
7. **成交净值只认 `accepted_date`**。扫描仍按 `confirm_date <= today`（份额到账日没到就不确认），但取价、写 lot、算份额一律用 `accepted_date` 的净值；该日净值未公布 → `NOT_YET_PUBLISHED`，订单保持 `pending` 等下一轮，**不得**改用邻近交易日的净值顶替。

示例：

| 场景 | accepted_date | confirm_date | settle_date | available_date | lot.nav_date |
|---|---|---|---|---|---|
| 周一 14:00 买 A（confirm_delay=1，available_delay=2） | 周一 | 周二 | — | 周四 | **周一**（T 日净值） |
| 周一 15:30 买 A | 周二 | 周三 | — | 周五 | **周二**（T 日净值） |
| 周一 14:00 卖 A（redeem_settle_delay=2） | 周一 | 周一 | 周三 | — | — |
| 周一 15:30 卖 A | 周二 | 周二 | 周四 | — | — |
| 周五 14:00 卖 A | 周五 | 周五 | 下周二 | — | — |

### 3.7 费用快照与舍入

#### 3.7.1 快照内容

下单时把 `fund_catalog` 的确认所需字段写入 `trade_orders.fee_rule_snapshot`：

```json
{
  "rule_updated_at": "2026-10-30T12:00:00+08:00",
  "fund_type": "of",
  "share_class": "A",
  "subscribe_status": "开放申购",
  "confirm_delay": 1,
  "redeem_settle_delay": 2,
  "redeem_available_delay": 2,
  "min_purchase_amount": 10.00,
  "max_purchase_amount": null,
  "purchase_fee_tiers": [ ... ],
  "redemption_fee_tiers": [ ... ],
  "management_fee_rate": 0.0150,
  "custody_fee_rate": 0.0025,
  "sales_service_fee_rate": 0.0000
}
```

- 键名与 `fund_catalog` 一致，`FundFeeService.calc_purchase_fee/calc_redemption_fee` 可直接把快照当 `rule` 传入。
- 确认时**只读快照**，不再查 `fund_catalog`。规则后续变更不影响已受理订单。
- 存量 pending 订单由迁移脚本从当前规则回填；回填不到 → 确认时 `manual_review`，`code='FEE_SNAPSHOT_MISSING'`。

#### 3.7.2 买入

```
fee = calc_purchase_fee(fund_code, amount, rule=snapshot)   # 外扣法/固定费，保留 2 位
net = amount - fee                                          # 必须严格等于，不再单独 round net
qty = floor(net / nav, 2)                           # 向下取整
residual = ROUND(net - qty * nav, 2)                # 2 位；不足一分的差额是不可避免的舍入残差
cash += residual
amount == net + fee
net ≈ qty * nav + residual                          # 允许 ≤0.01 的舍入残差
```

- 现有 `FundFeeService.calc_purchase_fee` 返回 `round(net,2)`，可能与 `amount - fee` 差 0.01。实现阶段改为 `net = amount - fee`，并用单测锁定 `amount == net + fee`。
- 份额向下取整保证 `residual >= 0`；如果业务坚持四舍五入，`residual` 可能为负，必须从 `cash` 扣且不允许扣成负数（见 §7 U1）。

#### 3.7.3 卖出

```
gross = ROUND(quantity * nav, 2)                    # 总赎回金额
每段 lot：
  hold_days = order.accepted_date - lot.nav_date   # 两个成交净值日之差；卖单 confirm_date == accepted_date
  fee_i = calc_redemption_fee(fund_code, quantity_i * nav, hold_days, rule=snapshot)
  cost_i = lot.remaining_cost * quantity_i / lot.remaining_qty   # 按份额比例消耗成本
fee = SUM(fee_i)
cost = SUM(cost_i)
net = gross - fee
amount = gross（落订单/流水）
net_amount = net
trade_pnl = gross - fee - cost                       # 汇总口径，避免逐段舍入残差
```

- 费用按段分别计算后汇总；每段 `fee_i` 保留 2 位。总费用是各段之和，不再对总额二次舍入。
- `cost_i` 按 lot 的剩余成本比例消耗，避免部分赎回时成本漂移。**记账以 RPC 在锁内重算的结果为准**（§3.6.4 第 6 步）；应用层算出的 `cost/pnl` 只用于预估。
- 货基：`cost_i` 即消耗的本金；`trade_pnl` 含累计收益（gross 含收益，cost 是本金）。


### 3.8 FIFO、lot 与持仓汇总（导航）

- **卖出批次**：按 `nav_date, created_at, id` 先进先出消耗 lot，只消耗最早的可用批次（RPC 见《实现方案》§3.6.4，计划算法见 §3.8.1）。
- **持有期限**：按 lot 的成交净值日（买入受理日 T）到卖出订单受理日 T′ 计算，不再使用聚合持仓被覆盖的 `confirm_date`（口径见 §3.2 规则 2、§3.7.3）。
- **期初 lot**：存量持仓迁移生成，`nav_date` 用 `positions.confirm_date` 近似（迁移见《实现方案》§3.8.2）。
- **持仓汇总**：`position_lots` 是持仓的事实来源，`positions` 只是由它汇总出的读模型（汇总规则见《数据结构》§3.8.3）。

### 3.9 赎回到账与在途资金

1. 下单：`settle_date = T + redeem_settle_delay 个交易日`，落库。
2. 确认：卖单只扣 lot、写流水、订单进入 `settling`；**不动 `cash`**。
3. 到账：`settle_redeem_order` 在 `settle_date <= today` 时把 `net_amount` 加进 `cash`，订单 `settled`。
4. 确认晚于 `settle_date`：确认成功后立即在同一轮调用 `settle_redeem_order`，只入账一次。
5. 到账任务：每轮确认批次末尾执行 `settle_due_redemptions(today)`；也可由兜底窗口独立触发。查询 `status='settling' AND settle_date <= today`，逐笔调用 RPC。
6. 用户侧展示：
   - `cash`：可用现金。
   - `frozen_cash`：待确认买单冻结。
   - `settling_cash`（新增）：在途赎回款 = `SUM(net_amount) WHERE status='settling'`。
   - `total_assets = cash + frozen_cash + settling_cash + position_value`。
7. `account_snapshots` 增加 `settling_cash numeric(18,2) default 0`；`take_snapshot` 写入。存量快照该列为 0，不回填。
8. `AccountSummaryResponse` 追加 `settling_cash`，旧字段不变。
9. `positions` 已扣减卖出份额，`settling_cash` 补上在途应收，避免总资产在确认到到账之间凭空下降。

### 3.10 货基特殊规则

货基 `000198` 的所有特判收敛到 `server/services/money_fund_policy.py`：

| 规则 | 实现 |
|---|---|
| 净值恒 1.0000 | `MoneyFundPolicy.nav(code)`；确认 RPC 对 000198 不查 `fund_nav` |
| 买入 | `net_amount` 全部计入本金；lot `cost_price=1`、`remaining_cost=net_amount` |
| 每日收益 | `credit_money_fund_income_atomic` 生成 `source='income'` lot；`cost_price=0`、`remaining_cost=0`；只增份额，不改本金 |
| 卖出 | 按 FIFO 消耗 lot；`cost_i` 即消耗本金；`pnl_i` 含累计收益；比例核减不再在应用层读改写 |
| 自动申购 | `_auto_invest_money_fund` 仍生成 pending 订单，走统一 `confirm_buy_order`；不在自动申购里直接建仓 |
| 申购费 | 快照里通常为 0；按快照计算，不特判 |
| 可赎回日 | 由 `redeem_available_delay` 决定；默认 2（见 §7 U8） |

- 收益任务仍从上游取万份收益（可以触网），但写份额必须走 RPC；单仓失败不影响其他用户。
- 收益 RPC 的幂等键是 `(user_id, fund_code, 'income', income_date)`；同日重跑不会重复入账。
- `positions.principal` 由 lot 的 `SUM(remaining_cost)` 维护；收益 lot 成本 0，因此本金不变。
- `positions.cost_price` 货基恒 1.0000，不按 `cost/qty` 计算。
