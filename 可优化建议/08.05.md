## 2. 性能优化：get_fee_rule 重复查询

### 问题

`confirm_pending_orders()` 批量确认时，每笔订单独立调用 `get_fee_rule()`，造成 N 次远程查询（N=订单数）。假如 50 笔订单涉及 8 只基金，8 只需查 50 次，浪费 42 次网络往返。

### 解决方案

在 `confirm_pending_orders()` 入口处，收集所有 pending 订单的 `fund_code` 去重，一次批量查询全部费率规则到 dict，然后逐单确认时从 dict 取 rule。N 笔 M 只基金的场景从 N 次远程查询降为 **1 次**。

### 实现文件

- `server/services/fund_fee_service.py` — 新增 `get_fee_rules_batch(codes)` 方法，使用 `in_("fund_code", codes)` 批量查询
- `server/services/portfolio_service.py` — `confirm_pending_orders` 循环前预加载 `rules_map`，传入 `_confirm_one_order(rule=rule)`
- `_confirm_one_order` 增加 `rule` 参数，传入则直接使用，不传则回退到单独查询

## 3. C 类基金的 purchase_fee_tiers 魔法数字 + A 类 inclusive 冗余

### 问题一：C 类 999999999

C 类基金申购费全免，之前用 `{"amount": 999999999, "rate": 0.0000, "inclusive": true}` 表示"任何金额费率都是 0"。`999999999` 是硬编码魔法数字。

### 问题二：A 类最后一档 amount + inclusive 多余

A 类基金最后一档（固定费兜底）用了 `{"amount": 10000000, "rate": 0, "fixed_fee": 1000, "inclusive": true}`，其中 `amount` 和 `inclusive` 没有实际意义——兜底档本身就是"前面都不命中时自动选中"，不需要边界值。

### 解决方案

`_match_purchase_tier()` 增加对"无 `amount` 字段"的支持：档位 dict 中没有 `amount` 键 → 匹配所有金额，直接返回。

- **C 类**：`[{"rate": 0.0}]`（无 amount，匹配所有金额）
- **A 类**：最后一档去掉 `amount` 和 `inclusive`，如 `{"rate": 0, "fixed_fee": 1000}`

### 实现文件

- `server/services/fund_fee_service.py` — `_match_purchase_tier` 增加 `universal_tiers` 优先返回逻辑
- `sql/fund_fee_rules_seed.sql` — 8 只 C 类 + 12 只 A 类全部更新
- 数据库 — 执行了 UPDATE 同步 A 类 purchase_fee_tiers

### 设计原则

| 字段 | 使用场景 | 说明 |
|------|---------|------|
| 无 `amount` | 申购费最后一档兜底 | 匹配所有金额，不需要 inclusive |
| 有 `amount`，无 `inclusive` | 申购费金额分档 | `申购金额 < amount` 时命中 |
| `inclusive: true` | 仅赎回费最后一档 | 有真实天数边界（如 ≥730天），需要 `hold_days ≤ days` |

### Bug 修复（2026-08-05 测试发现）

`_match_purchase_tier` 初始版本有 bug：无 `amount` 的兜底档位被**优先**返回（`universal_tiers[0]`），而不是作为兜底。导致 A 类基金申购 1000 元时直接匹配兜底档 `fixed_fee=1000`，申购费算成 1000 元而非正确的 1.20 元。

**修复**：调整为"金额档位优先匹配，全部不命中后再兜底"：

```
1. 分离 amount_tiers 和 universal_tiers
2. 先遍历 amount_tiers 按 < 比较匹配
3. 全部不命中 → 返回 universal_tiers[0]（兜底）
4. 无 amount_tiers → 直接返回 universal_tiers[0]（如 C 类）
```

## portfolio_service 专项审查（2026-08-05）

> 由代码审查代理深度分析，共发现 29 个问题，以下是**严重和高风险项**。

### 🔴 严重（数据正确性 Bug）

#### A. 冻结资金后写订单失败 → 资金永久冻结

`apply_purchase` 先更新账户（冻结资金），再调用 `_write_trade_order`。但 `_write_trade_order` 内部吞掉所有异常（`except Exception: logger.error`），不向上抛出。如果写订单失败，函数继续返回 `success=True`，资金已冻结但没有对应订单，钱永久卡在 `frozen_cash`。

#### B. 确认确认失败时 `frozen_cash` 未释放

`_confirm_one_order` buy 分支：NAV 获取、费用计算、持仓查询都在解冻资金**之前**。这些步骤中任何异常都会跳到 outer handler 标记订单为 `failed`，但 `frozen_cash` 从未释放。用户资金永久锁定。

#### C. 卖出确认时先入账后扣持仓 → 可能凭空多钱

Sell 分支先 `UPDATE accounts SET cash = cash + net_amount`，再 `UPDATE positions SET quantity = new_qty`。如果现金入账成功但持仓扣减失败，用户拿到钱但份额没扣。

#### D. 持有天数用最后确认日覆盖，非 FIFO

赎回费计算用 `position["confirm_date"]`，但这个值每次申购确认都会覆盖。用户累计买入 3 次（持有 30 天、10 天、1 天），最后一次确认把 `confirm_date` 更新为今天 → 赎回费全部按持有 1 天算 → 多收赎回费。这是**财务正确性 bug**。

### 🟠 高优先级

#### E. 竞态：冻结资金并发确认 → 数值漂移

`_confirm_one_order` 读 `frozen_cash` → 计算 `new_frozen = frozen_cash - amount` → 写回。如果两个确认同时执行，第二个写回会覆盖第一个的修改，`frozen_cash` 漂移。

#### F. 竞态：首次访问创建重复账户

`_ensure_account` 先 SELECT 再 INSERT。两个并发首次请求都查到空 → 都 INSERT。如果没有 UNIQUE 约束，创建重复账户。有约束则第二个报错崩溃。

#### G. 竞态：申购现金检查非原子

先读 `cash`，检查够不够，再减。两个并发申购都能通过检查，但扣完后总支出超过 `cash`，账户变负数。

#### H. 卖出到账日期错误

赎回现金在 `confirm_date`（T+1）就入账，但合同规定 `settle_date`（T+3 到 T+7）。现金提前了 2-6 个交易日可用。

#### I. `trade_pnl` 计算后被丢弃

Sell 确认时算了 `trade_pnl`（净收入 - 成本基础），只打印日志，从未写入数据库。用户和前端都看不到实际盈亏。

#### J. `_get_nav` 精度双转换损失

`Decimal(str(float(nav)))` — numpy float → Python float → str → Decimal，中间 `float` 有精度损失。直接用 `Decimal(str(nav))` 避免。此模式在全文件出现 ~20 次。
