# Vibe Coding 协作协议

> **最高原则：让设计、代码实现和人的决策始终显式同步。**
> 同步三者的媒介，是一份人和 AI 都能看、都能改的**开发文档**。
> 说白了：**AI 不能只在自己脑子里开发。**

**边界**：`CLAUDE.md` 的红线（禁读 `.env`、禁 pip、不直接改环境、不打基线迁移、不在 dev 分支
开发、`.gitignore` 只能追加）优先于本协议任何一条。

下面标出六个**关键转折点**，到了那里必须做某件事；其余怎么发挥不限。

---

## 六个转折点

```
① 用户提出业务需求   →  先读现状相关实现，不直接改代码
② 准备动手写代码     →  必须先有文档（规则 2）
③ 存在明显的方案取舍  →  编号选项 + 代价 + 推荐，交人拍板（规则 3）
④ 实现中推翻原设计   →  先改文档，再改代码（规则 4）
⑤ 撞上范围外的问题   →  默认只记录，不顺手修（规则 5）
⑥ 完成一轮修改       →  会话汇报 + 回填文档真实状态（规则 6）
```

---

## 规则 1：业务需求先分析，后实现

用户提出业务需求时**不直接改代码**。先读完与需求相关的现状，再提方案。分析至少覆盖：

- 现有业务流程与关键代码（**指向 `文件:行号`**）
- 依赖关系与已有约束（配置、数据源、接口契约、schema）
- **需求与现状之间的差距**——差在哪一步、为什么现有实现撑不住

* 结论必须可复核：文件:行号、实测样本、命令与输出。**禁止「应该没问题」。**
* 外部数据源/接口的结论**一律实测**：字段名、取值、边界、失败形态。
* 量级问题用**抽样实测**回答，例如「2286 只候选 → 随机抽 40 只得到开放申购 87.5% /
  限大额 5% / 暂停申购 5% / 认购期 2.5% → 落库负担可忽略」，而不是凭感觉说「这点量没关系」。
* 读代码用 CodeGraph（`codegraph_explore`）优先于 grep 和逐个读文件。
* **人否决过的动作不要绕道重试**（例：被拒绝的联网探测）。改为换口径或直接提问。
* 开工对齐话术按 `CLAUDE.md` 的沟通规范（复述理解 / 获取的信息 / 假设），不在此重复。

---

## 规则 2：文档是本次开发的共享事实源

**路径**：`docs/<主题>设计文档.md`（沿用仓库惯例）。

**最低章节**（缺一不可）：

背景与术语 · 当前实现/业务逻辑 · 发现的问题 · 设计方案/最终方案 · 测试策略 · 未解决问题表

**按需增补**：由于不同的设计文件会涉及到的内容不同，所以你可以按需增加章节

**「详细」不等于「字多」**：优先保证**完整、具体、可追溯**，不为追求简短而省略影响理解
和决策的信息。

> ❌ 差的详细：本系统采用数据库。数据库是一种用于持久化数据的软件……
>
> ✅ 好的详细：当前 `TradeService.buy()` 调用 `check_whitelist()` 检查
> `config/funds.json`，该文件包含 20 支基金代码；通过检查后，再从 `fund_fee.json`
> 按基金代码读申购费率。因此**仅扩展白名单无法完成需求**，费率数据覆盖范围也是当前限制之一。

### 未解决问题表（固定字段）

这张表是**范围防火墙**：它让 AI 记下「我看见了，但现在不该顺手做」。

| ID | 问题（指向章节） | 与当前需求关系 | 是否阻塞 | 当前处理 |
|---|---|---|---|---|
| Q1 | 部分基金缺少赎回费率 | 直接相关 | 是 | ⏳ 待决策 |
| Q2 | 旧代码存在重复查询 | 附带发现 | 否 | ⏸ 暂不处理 |
| Q3 | 日志格式不统一 | 无直接关系 | 否 | ⏸ 暂不处理 |

| 状态 | 含义 |
|---|---|
| ✅ 已修复 | 代码 + 测试 + 文档三处都已回填 |
| ⚠️ 未修复 | 已知有害，待处理（**写清后果**） |
| ⏳ 待定 | 等人决策 |
| ⏸ 接受不修 | **必须写清为什么接受** |

* 这张表是本项目**唯一的 backlog**：人按编号下任务（「…… 修复这个 BUG」），
  AI 完成后把 ⚠️ 改成 ✅ 并写明改法。

## 规则 3：涉及明显成本取舍时，把选择权交给人

存在多个**不同量级、复杂度或成本**的合理方案时，不要自行选择。给出：

**编号选项 + 各自代价 + AI 推荐及理由**，由用户拍板。

例如 `L1 最小修改 / L2 较完整 / L3 长期方案`。**AI 可以有推荐，但不能替用户做成本、
复杂度和范围上的最终取舍。**

---

## 规则 4：设计变化必须先进入文档

实现过程中发现原设计不成立、已有假设错误，或需要明显改变原方案：

> **先改文档，再改代码。**

不允许 AI 在实现中**默默**改变架构、业务语义或方案，然后事后才告知。这条保证：

```
AI 脑中的方案  =  文档中的方案  =  正在实现的方案
```

至少尽量保持三者一致。

---

## 规则 5：不擅自扩大范围

做 A 时发现 B 的既有缺陷，若 B 不是完成 A 的必要条件——**不顺手改，也不丢弃**：
记入文档「附带发现」和/或未解决问题表，继续当前任务。

只有以下情况才处理 B，且**仍需说明它为什么进入了本次范围**：

- 不解决 B 就无法完成 A；
- B 会导致本次实现明显错误；
- B 带来严重的数据、安全或兼容风险。

---

## 规则 6：每轮实现都必须回填文档

每完成一个阶段，做两件事：

**会话**——简要汇报做了什么，重点说清楚逻辑。


**文档**——更新真实实现状态：

```text
实际修改 / 新发现 / 已解决问题 / 未解决问题 / 测试结果
```

* 文档不能停留在「开发前的设计稿」，应始终尽量反映**当前代码真实状态**。
* 每轮给出**命令 + 结果**：`poetry run pytest tests/unit -q → 521 passed`。
  **跑不了就说跑不了**（例：「集成测试需本地 Supabase 容器，当前环境没有 → 未运行」），
  绝不用「应该能过」代替结果。
* **残留必须写进文档和报告**：写明取舍理由与根治方向，标为已知残留。
* **原文档写错了就显式纠正**（写明原判断错在哪），不要静默覆盖。
