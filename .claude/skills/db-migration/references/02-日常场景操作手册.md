# 数据库迁移 · 日常场景操作手册

> 本文档为 skill 内副本，源文件：`docs/数据库迁移-日常场景操作手册.md`
>
> 前置知识（迁移机制、目录、环境要求）见 [01-工作流基础.md](01-工作流基础.md)。

## 场景速查表

| 我想做什么 | 做法 | 是否写迁移 |
|---|---|---|
| 建新表 / 加列 / 改列类型 / 加索引 | 迁移文件 `CREATE/ALTER` → `db push` | ✅ 是 |
| 新增 RLS 策略 / 函数 / 枚举 | 迁移文件 → `db push` | ✅ 是 |
| 新增**基础数据**（费率规则、风险等级、配置字典） | 迁移文件 `INSERT` → `db push` | ✅ 是 |
| 修改 / 清理**基础数据** | 迁移文件 `UPDATE/DELETE` → `db push` | ✅ 是 |
| 用户业务数据（交易、持仓、聊天、快照） | 应用运行时用 Supabase 客户端写入 | ❌ 否 |
| 在网页端改了**表结构** | `db diff` 反推成迁移（需 Docker） | ✅ 必须补 |
| 在网页端手工修了**几行数据** | 一般不需要迁移（见场景 6） | 视情况 |
| 结构变了，同步类型 | `gen types typescript` + Python 字段核对 | — |

> 判断一份数据该不该进迁移，一句话：**「配置型、所有环境都应有、代码逻辑依赖」的基础数据走迁移；「运行时、用户产生、环境相关」的业务数据不走迁移。**

---

## 通用步骤（每次变更后必做）

```
① supabase migration new <描述>
② 编辑 supabase/migrations/{时间戳}_{描述}.sql   # 写 CREATE / ALTER / INSERT ...
③ supabase db push --linked                     # 应用到远端
④ supabase migration list --linked              # 校验 Local │ Deployed 两列对齐
⑤ 同步类型定义                                   # 见「场景 7」
```

## 场景 1：创建新表 / 新结构

适合：新业务需要一张新表、新的枚举类型、新函数等。

```bash
supabase migration new create_fund_nav
```

编辑生成的 `supabase/migrations/{时间戳}_create_fund_nav.sql`：

```sql
CREATE TABLE public.fund_nav (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  fund_code text NOT NULL REFERENCES public.funds(code),
  nav_date date NOT NULL,
  nav numeric(10, 4) NOT NULL,
  created_at timestamptz DEFAULT now(),
  UNIQUE (fund_code, nav_date)
);
ALTER TABLE public.fund_nav ENABLE ROW LEVEL SECURITY;
```

然后按「通用步骤」③④⑤ 执行。

要点：

- 新表默认开启 **RLS**（`ENABLE ROW LEVEL SECURITY`），再加策略；参考 [docs/legacy_sql/rls_policies.sql](../../docs/legacy_sql/rls_policies.sql) 的写法。
- 主键默认 `uuid PRIMARY KEY DEFAULT gen_random_uuid()`（与现有表一致），`created_at` 用 `now()` 默认值。

## 场景 2：修改已有表（加列 / 改类型 / 加索引 / 改名）

适合：给 `trade_orders` 加字段、给 `fund_fee_rules` 改列类型等。

```bash
supabase migration new alter_trade_orders_add_exec_price
```

编辑迁移文件：

```sql
-- 加列
ALTER TABLE public.trade_orders
  ADD COLUMN exec_price numeric(10, 4);

-- 加索引
CREATE INDEX idx_trade_orders_user_created ON public.trade_orders (user_id, created_at DESC);
```

要点：

- **加列时尽量给默认值或允许 NULL**，避免存量数据写入失败。
- 改列类型（`ALTER COLUMN ... TYPE`）如果涉及存量数据转换，写清 `USING` 子句并先在本地验证。
- **绝不要修改已 push 的迁移文件**；即使改错了，也新建一个迁移来修正，保证历史可追溯。

## 场景 3：新增基础数据（种子数据）

适合：`fund_fee_rules` 费率规则、`fund_risk_levels` 风险等级、问卷、枚举配置等。

```bash
supabase migration new seed_fund_fee_rules
```

编辑迁移文件：

```sql
INSERT INTO public.fund_fee_rules
  (fund_code, fund_name, fund_type, purchase_fee_rate, management_fee_rate, custody_fee_rate)
VALUES
  ('000001', '华夏成长混合', '混合型', 0.0015, 0.015, 0.002),
  ('000002', '易方达蓝筹精选', '混合型', 0.0015, 0.015, 0.002)
ON CONFLICT (fund_code) DO UPDATE SET
  purchase_fee_rate = EXCLUDED.purchase_fee_rate,
  management_fee_rate = EXCLUDED.management_fee_rate,
  custody_fee_rate = EXCLUDED.custody_fee_rate;
```

要点：

- **务必带 `ON CONFLICT`**（幂等）：同一迁移在测试/生产重复执行不会报错，数据以最新为准。
- 迁移文件用相对路径**不引用其他文件**，自成一体可重复执行。

## 场景 4：修改 / 清理基础数据

适合：费率调整、修正某条配置、清理废弃的基础数据。

```bash
supabase migration new update_fund_fee_rules_2026
```

```sql
-- 修改
UPDATE public.fund_fee_rules
SET purchase_fee_rate = 0.001
WHERE fund_code = '000001';

-- 清理（仅限基础数据，绝不删用户业务数据）
DELETE FROM public.fund_fee_rules
WHERE fund_code IN ('ZZZZZZ');  -- 已废弃的旧代码
```

要点：`DELETE` 只用于基础数据；用户业务数据（交易/持仓）的清理不在迁移里做。

## 场景 5：用户业务数据（不走迁移）

**这一类数据永远不写进迁移文件**：

- 交易订单 `trade_orders`、持仓 `positions`、交易流水 `trade_flow`
- 聊天 `chats` / `messages` / `document_chunks`
- 账户快照 `account_snapshots`

它们由应用运行时通过 Supabase Python 客户端写入（`.from(...).insert(...)` / `.rpc(...)`），天然不属于"数据库结构"。

为什么不能走迁移：

- 迁移是**结构+共享数据**的变更日志，每条迁移对所有环境只执行一次；
- 业务数据量大会拖慢 `db push`，且迁移里带用户隐私数据也不安全。

**调试例外**：网页端可以浏览/手改这些数据（修脏数据、测试），**无需迁移**；改了就改了，属于环境本地状态。

## 场景 6：在网页端修改之后的操作

网页端（Dashboard / SQL Editor）能直接改数据库，但会绕过迁移历史。按改动类型区分处理：

### 6a. 网页端改了**表结构**（DDL）—— 必须补迁移

网页上加了列/改了类型后，本地迁移历史完全不知道。**下次 push 其它迁移前，先把网页改动反推成迁移：**

```bash
# 需要 Docker（shadow 数据库对比）
supabase db diff --linked --use-migra -f describe_change
```

生成 `supabase/migrations/{时间戳}_describe_change.sql`，人工核对后 `db push --linked`。

> 无 Docker 环境：对照网页改动**手工写一条等价迁移**（场景 1/2 的写法），效果一样。
> `db diff` 输出的噪音（CHECK 重建、CRLF 函数体差异）属正常，核对后剔除即可。

### 6b. 网页端改了**数据**（DML）

- 基础数据 → 按场景 3/4 补一条 INSERT/UPDATE 迁移，保证其它环境一致。
- 用户业务数据 → **不补迁移**（见场景 5）。

### 6c. 判断当前有没有"漂移"

```bash
supabase migration list --linked   # Local │ Deployed 两列不对齐 = 历史错位
supabase db diff --linked          # 输出非空 = 远端 schema 与迁移不符（需 Docker）
```

若历史错位（如误删迁移文件、远端被手工改），用：

```bash
supabase migration repair --status reverted <版本> --linked
```

## 场景 7：结构变更后的类型同步

数据库结构变了，**前端 TS 类型必须重新生成**，Python 代码也要人工核对字段。

### 7a. 前端 TypeScript 类型（`server/types/supabase.ts`）

```bash
supabase gen types typescript --project-id "wiynpkkfsiiqnofhifhs" > server/types/supabase.ts
```

不需要 Docker、不依赖本地 `supabase link`，直接用 project-ref 读远端 schema 生成，覆盖仓库内的类型文件 `server/types/supabase.ts`。每次场景 1/2/6a 之后都执行一次。

### 7b. Python 侧核对清单（无自动生成，人工检查）

- 代码里 `.insert({...})` / `.select(...)` / `.eq(...)` 的**字段名**是否与新 schema 一致（改名/加列最易漏）；
- `server/models/` 中镜像表行的 Pydantic/dataclass 字段是否需要同步；
- 新表/新列被代码读取时，查询结果 dict 的键是否正确。

## 常见问题（FAQ）

| 现象 | 处理 |
|---|---|
| `db push` 报列已存在/类型冲突 | 之前网页端改过结构没同步 → 按场景 6a 用 `db diff` 对比，剔除冲突的重复迁移 |
| `migration list` 两列不对齐 | 用 `migration repair` 对齐（见 6c） |
| 改错了已推送的迁移 | 不改旧文件，新建一条迁移修正 |
| 想把某环境的数据搬到别处 | `supabase db dump --linked --data-only`（仅数据） |
| 临时查/改数据 | `supabase db query --linked "SELECT 1"` |

## 禁止事项

- ❌ 直接在 `supabase/migrations/` 基线（`20260819113859_remote_schema.sql`）上增量修改
- ❌ 修改已 push 的迁移文件（一律新建迁移）
- ❌ 使用 `_run_sql.py` / `sql/` 目录手工执行 SQL（已废弃）
- ❌ 把用户业务数据写进迁移文件
