## 一、为什么必须用一次性账号

交易链路的断言依赖**精确数值**，这些数值来自一个恒定的起点：

| 量 | 值 | 来源 |
|---|---|---|
| 初始现金 | `INITIAL_CASH = 100000.00` | `server/services/portfolio_service.py` |
| 冻结资金 | `0`（新用户无 pending 订单） | — |
| 持仓数 | `0` | — |
| 流水数 | `0` | — |

**起点为什么是干净的**：`auto_invest_enabled` 的默认值是 `false`，所以新用户不会被自动申购货币基金 → 不会有隐藏的持仓和流水。

**所以**：如果复用固定账号，第一次跑完冻结资金变成 1000，第二次跑断言 `frozen_cash == 1000.00` 就挂了。用例会**永久变红**，而原因是测试设计问题不是代码问题。

> ⚠️ 这个设计的隐含依赖：**`auto_invest_enabled` 的默认值和 `INITIAL_CASH` 一旦被改动，夹具设计就要跟着改**。改这两个值时请同步检查 E2E 用例。

**账号命名**：`e2e<unixts>@ai-etf.xyz`，密码满足前端校验（≥8 位）。

## 二、夹具脚本的接口设计

三个子命令，全部**走 HTTP**：

```bash
python docs/e2e/scripts/e2e_fixture.py register              # 注册，输出 {email, password, token}
python docs/e2e/scripts/e2e_fixture.py token <email> <pw>    # 取 token（供交叉断言）
python docs/e2e/scripts/e2e_fixture.py cleanup <tok> <pw>    # 调 delete-account 清理
```

> **只有需要"回填状态"的用例（见第四节 4.2 第三类）才追加第四个改库子命令**（本项目对应 `backdate-order`）。**不要预先写没有用例会调的子命令** —— 特别是 `confirm-pending` 这类"看起来很顺手"的（它确认不了刚下的单，理由见第四节）。

**关键设计约束：夹具不得 `import server.*`。**
用 `httpx` 打 HTTP。理由是隔离：直接 import 后端模块会让夹具与被测服务**共享进程状态**（数据库连接、缓存、内存态的 token 黑名单），断言会被污染，而且"夹具通过但线上不通过"这类问题查不出来。

**默认地址** `http://localhost:8000`，用 `--api` 覆盖。

**为什么 `register` 交给夹具、而不是走 UI：**
被测端仍然走 **UI 登录**（这样登录页不被排除在覆盖外）。夹具只负责"把账号准备好并给我 token"。这样既保证起点干净，又不牺牲 UI 覆盖。

**夹具里用到的两个后端能力，都要注意它们的定位**：

| 接口 | 注意 |
|---|---|
| `POST /secure-chat/delete-account` | 前端**零调用** → 只能作夹具，不能作被测路径。需要密码。 |
| `POST /portfolio/confirm-pending` | 前端**零调用** → 只能作夹具。**⚠️ 它确认不了刚下的申购单**（买单落库的确认日 ≥ 次日）；但**赎单不一样**——交易日 15:00 前下的赎单确认日就是当天，它**确认得了**。本项目仍然不用它，理由见 4.3.1（前置须构造 + UI 无触发入口），不是"确认不了"。 |

## 三、交叉断言

**规则：涉及数值的用例，必须用夹具的 token 直连后端读真值，再比对 UI 文本。**

为什么不能只断言 UI：UI 上的数字来自后端，但如果前端算错了、或者用了缓存、或者展示的是上一轮的数据，只看 UI 是发现不了的。反向也一样（后端错了 UI 会如实展示错误）。**两边都读、互相印证**，才叫验证。

实现形态（伪代码）：

```js
// 1) UI 断言
expect(uiFrozenText).toContain('1000.00')

// 2) 后端真值（夹具 token）
const account = await fixtureApi.get('/api/portfolio/account', token)
expect(account.frozen_cash).toBe(1000.00)
expect(account.cash).toBe(99000.00)
expect(account.position_count).toBe(0)   // ⭐ 关键：pending 不建仓

// 3) UI 与真值一致
expect(uiFrozenText).toContain(account.frozen_cash.toFixed(2))
```

**哪些用例必须交叉断言**：所有涉及金额、份额、持仓数、流水数的；所有"某接口被调用了没有"的（例如重命名后标题是否真的落库 —— 历史上重命名 404 的 bug 就是"本地状态改了但后端没改"）。

## 四、状态可达性闸门（写用例前的必过关）

### 4.1 为什么要先问这一句

一条 E2E 用例 = 「操作 → 期望状态」。**如果那个"期望状态"在测试会话内根本不可达，这条用例就不是"偶尔红"，而是"永远红"** —— 而且它红得很有欺骗性：看起来像 bug，实际是你的设计错误。所以设计任何用例之前，先问：

> **这条用例要断言的状态，靠前端操作 + 合法接口，在这次会话内真的能到达吗？**

判断的落点是**状态机**，不是"今天是不是好日子"。很多不可达不是时间问题，是**业务流程本身需要多步异步环节**（确认、结算、审批、回调、第三方对账）。时间只是其中一种表现形式。

### 4.2 三类不可达，处置完全不同

| 类型 | 特征 | 处置 |
|---|---|---|
| **窗口期不可达** | 状态可达，但只在某时间/日期窗口内 | **加跳过守卫**，窗口外 `skip` 并标注原因（见 4.4） |
| **会话内永久不可达** | 需要跨会话的异步环节（T+N 确认、次日结算、外部回调） | **不要写这条用例**。把覆盖下沉给能冻结时钟/能直接造状态的层（后端集成测试、单测）；E2E 只覆盖"提交"这一半。⚠️ **必须逐分支判定**——同一功能的不同方向可能落库字段不同，一侧永久不可达、另一侧却有窗口（见 4.3 的第二个实例） |
| **接口可达，但只有夹具能走，UI 走不到** | 动作存在、端点存在，但**前端零调用 / UI 无入口** | 这**不算**"会话内可达"。用户路径不成立 → 按**需要构造状态**处理，用例里写明"该动作由夹具触发，不是用户操作" |
| **需要构造状态才可达** | 接口本身可用，但前置状态没法用公开操作造出来 | **回填状态**：夹具直连数据库把字段改成目标值，再驱动 UI。**必须在用例里注明"这条验证的是状态之后的表现，不验证状态本身如何产生"** |

判断顺序：**先试 1，再试 3，都不可行才判 2。** 别一上来就说"做不到"——回填状态能救回很多用例。

### 4.3 ⭐ 本项目的实例（曾经写错，值得记住）

**初版设计**：「申购 → 调 `confirm-pending` → 断言持仓出现该基金」，并加了时间门控「仅在交易日 00:00–14:59 可跑」。

**它是错的。** 代码事实（[portfolio_service.py:543-552](ai-etf/server/services/portfolio_service.py#L543-L552)）：

```python
if self._is_trading_day(...) and self._is_before_cutoff(...):
    confirm_date = now_beijing.date()            # 当日「受理」
else:
    confirm_date = self._next_trading_day(...)

actual_confirm = confirm_date
for _ in range(confirm_delay):                   # 110020 → confirm_delay = 1
    actual_confirm = self._next_trading_day(actual_confirm)
```

**落库的是 `actual_confirm`，不是 `confirm_date`**（[:610](ai-etf/server/services/portfolio_service.py#L610)）。而 `confirm-pending` 只确认 `confirm_date <= today`（[:990-996](ai-etf/server/services/portfolio_service.py#L990-L996)）。

→ 即使交易日 14:00 下单（受理日 = 当日），**持久化的确认日仍是下一个交易日**，`confirm-pending` 必然 `processed=0`。**这不是"窗口外不可跑"，是"任何时候都不可跑"** ——属于上表第二类。仓库自己的集成测试就是旁证：`tests/integration/server/jobs/test_scheduler_jobs.py` 用 `time_machine` 把时钟从周一 14:00 拨到周二才能确认。

**处置**：从 E2E 删除，覆盖交给已有的后端集成测试（那正是 `time_machine` 存在的意义）。P1 因此**零时钟依赖**。

**教训（这才是要带走的东西）**：
1. **看到"T+N"、"确认"、"结算"这类词，先算一遍落库字段，别只看第一层赋值。** 我当初就是只读了 `:543-548` 就下了结论。
2. **别用"时间门控"去救一条本质上需要跨会话的用例。** 门控只适用于"窗口内真的能跑"，不适用于"永远跑不了"。
3. **找现成的证据**：仓库里已有一个跨日测试 → 说明作者知道这件事需要冻结时钟 → 这条断言不该由 E2E 承担。

### 4.3.1 ⭐⭐ 第二个实例：修完上面之后，我又推广过头了（同一个坑的背面）

修完 4.3 之后，我把结论写成了"**任何时间、任何途径都无法在"下单当天"确认**"，并推广到"E2E 会话内永远走不到『已确认持仓』这个状态"。

**这两句又错了——它们只对买单成立。**

| | 受理日计算 | `confirm_delay` 循环 | **落库字段** | 结果 |
|---|---|---|---|---|
| **申购** `apply_purchase` | `:543-548` | ✅ `:550-552` | `actual_confirm`（**推进过**）`:610` | 确认日 ≥ 次日 → **当天不可确认** |
| **赎回** `apply_redeem` | `:715-718` | ❌ **无** | `confirm_date`（**未推进**）`:783` | 交易日 15:00 前 → 确认日 = 当天 → **当天可确认** |

`apply_redeem` 里那个 `for _ in range(redeem_delay)` 循环（`:773-775`）推的是**另一个变量 `settle_date`**，它只被拼进提示文案"将于 {settle_date} 到账（T+N）"（`:786`），**从不落库**。所以"T+3 到账"是话术，**实际入账时刻是确认日**——`_confirm_one_order` 的 sell 分支先扣份额（`:1245-1261`），紧接着就把 `new_cash = current_cash + net_amount` 写回 `cash`（`:1263-1277`），**没有第二个到账延迟**。

**旁证**：`tests/integration/server/services/test_portfolio_trade_flow.py:106-129` 在**同一个冻结时刻** `CONFIRM_DAY` 里完成赎回与确认——若赎单也要 T+N，这条测试写不出来。

**第二个坑的教训（比第一个更重要）**：

1. **可达性按「分支/方向」逐条判，不能按「功能」一刀切。** 申购与赎回在前端是同一套 UI、同一个 `pending` 概念、同一个 `confirm-pending` 端点，但**落库字段不同**，可达性就完全相反。
2. **一路跟到落库那一行。** 别停在"受理日算出来了"——两跳计算里，中间那个变量可能根本不落库。
3. **"造不出前置"和"永远确认不了"是两件事，别混成一句。** 本项目赎回前置确实要夹具构造（常规申购跨日；货基自动申购 `:129-160` 虽能立即确认但**前端零调用、UI 无入口**），但那是"需要构造状态"，不是"不可达"。
4. **反过来说：修完一个过度乐观的结论后，警惕过度悲观。** 第一次错在"没读到底就说能跑"，第二次错在"读到底了但把一条分支的结论外推到整个功能"。两次的根因是同一个：**结论的适用范围没有跟着证据走**。

### 4.4 窗口期不可达的守卫写法

```js
const canRun = await fixtureApi.isTradingDay() && new Date().getHours() < 15

;(canRun ? describe : describe.skip)('P1-x 需要窗口的用例', () => { ... })
```

**报告里必须显式标注 `SKIP(原因)`，不能记为 PASS。** 理由：`SKIP` 和 `PASS` 在报告里长得很像，混在一起会掩盖"这条用例从来没跑过"。

> 注意：`_is_trading_day` 依赖 `akshare` 的交易日历，失败时回落到 `weekday() < 5`。所以周末一定是非交易日，但工作日的节假日需要日历才能判准 —— 守卫要用后端的能力判，不要自己用 `weekday()` 判。

### 4.5 回填状态的写法与措辞

若要用 4.2 第三类处置，夹具需要一个"改库"子命令（本项目对应 `backdate-order`：把订单的 `confirm_date` 改成今天/昨天）。用例里**必须**写清边界：

> 本用例验证的是**「确认动作完成之后，UI 展示是否正确」**；「确认日算得对不对」由后端集成测试 `test_scheduler_jobs.py` 覆盖，本用例不重复。

## 五、断言写作规范

### 5.1 三条纪律

1. **每条断言都要写「依据」（file:line）。** 不能因为"代码看起来应该这样"就断言业务规则。
2. **负例必须断言到确切文案。** 后端的错误文案是产品语义的一部分。
3. **测试标的要选对。** 同一页面不同分支要求不同标的代码。

### 5.2 后端错误文案表（写负例时直接查这里）

| 触发 | 确切文案 |
|---|---|
| 标的在白名单外 | `暂不支持基金 {code} 的交易` |
| 场内 ETF | `场内 ETF 暂不支持交易，请使用场外开放式基金` |
| 低于最低申购额 | `申购金额 {amt:.2f} 元低于最低申购金额 {min:.2f} 元` |
| 现金不足 | `可用现金不足：需 {amt:.2f} 元，实际可用 {cash:.2f} 元` |
| 未持有 | `未持有基金 {code}，无法赎回` |
| pending 未确认 | `基金 {code} 存在待确认的申购订单，份额确认前无法赎回` |
| 申购成功 | `申购申请已提交（{当日\|下一交易日}受理），将于 {date} 确认份额（T+{n}），资金已冻结` |

### 5.3 测试标的的选择（**选错必然失败**）

| 用途 | 标的类型 | 为什么 |
|---|---|---|
| 申购 / 赎回 | **场外白名单**代码 | 只有白名单代码才渲染申购按钮 |
| 详情页行情 / K 线 / 自选 | **场内 ETF** 代码 | 详情页的 `quote` 与 `tradeable` **互斥**：白名单基金 `quote` 恒为 `null` → K 线接口**根本不会请求** |
| "场内 ETF 拦截"负例 | — | ⚠️ 前端不渲染申购按钮 → **前端不可达** → 只能做**接口级**用例，不能做 E2E 步骤 |

### 5.4 模板选择器

优先用 `id`：uni-app 的 `id` 会透传到 wxml。手写的 `class` 也会保留，所以 class 选择器**可用**，但以下情况必须用 `id`：① 同类元素有多个（消息气泡、列表项、Tab）；② class 名是动态拼接的。

**微信端硬限制**：不支持父子选择器、不能跨组件查询元素 → `id` 要加在**页面直接层级**的元素上。若目标元素在深层自定义组件里，把 `id` 加到它的外层容器。
