## 一、工具选型结论

**用 `@dcloudio/uni-automator` + jest。**

**决定性理由：它已经在 `application/package.json` 的 devDependencies 里了**，版本与其余 17 个 `@dcloudio/*` 包完全一致（随 uni-app 官方同步发布）。不需要引入任何第三方工具。

**另一个契合点**：它的 mock API 是 **`uni.` 前缀**（`mockUniMethod` / `callUniMethod`），而本项目代码里用的正是 `uni.showModal` / `uni.showToast` / `uni.setStorageSync` → **不用做 `wx.` ↔ `uni.` 适配**，桩的粒度与代码调用点一一对应。

**没选的，以及为什么**（细节见 `docs/e2e/04-工具选型.md`）：

| 方案 | 为什么不用 |
|---|---|
| `miniprogram-automator`（裸用） | 微信官方 SDK，**自 2023-11 停更**；2025 年在新版开发者工具下有 `launch()` spawn EINVAL 与 `Page.*` 协议族整族超时两处硬伤 |
| `Minium`（Python） | 唯一能塞进 pytest 栈的方案（同为 Python），但仍是 beta（`1.0.0b2`）、**URL 直装不走 PyPI**（与 poetry 规范冲突，只能装独立 venv）。**作为 Plan B 保留**：若 jest 27 在当前 Node 上跑不起来就切它 |
| 微信云测 | 每周 150 分钟免费、专有云 1600 元/台/月；**跑在云真机上、本机 CI 无法编排**，且会打到 `API_BASE` 配的后端（当前是生产）→ 等于对生产库做真实交易 |
| H5 端 + Playwright/Cypress 代跑 | ⭐ H5 与小程序是**两条不同代码路径**（H5 走 `fetch` + `ReadableStream`，小程序走 `uni.request` + `enableChunked` + `onChunkReceived`）。**风险最高的正是小程序那一支**，用 H5 跑等于把风险排除在覆盖外。可作补充，不可作替代 |

## 二、执行拓扑（WSL 的坑）

**实测事实**：本机是 WSL2（`uname -a` 显示 `microsoft-standard-WSL2`）；微信开发者工具是 Windows 应用（默认安装路径在 WSL 里查不到）。

**问题链条**：
1. uni-automator 对 mp-weixin 的处理是 **spawn 开发者工具的 `cli.bat`**，并通过 **WebSocket 连 `ws://127.0.0.1:9420`** 驱动它。
2. WSL2 的 localhost 转发是 **Windows → WSL 单向可用**。
3. devtools 的 9420 **只监听 Windows 侧 127.0.0.1** → **WSL 里的 jest 连不上**。

**→ 推荐拓扑**（业务代码全留 WSL，只有测试运行器在 Windows）：

```
┌─ WSL2 ─────────────────────────┐      ┌─ Windows ───────────────────────┐
│ 后端 uvicorn  :8000             │◄─────┤ 微信开发者工具 + cli.bat :9420   │
│ pytest / 契约测试 / fixture      │      │ jest + uni-automator            │
│ poetry / Node 22（开发用）       │      │ Node 16/18（E2E 专用，见第四节） │
└────────────────────────────────┘      └─────────────────────────────────┘
        ▲  Windows→WSL localhost 转发可用  ▲  同机 127.0.0.1 直连
```

- ✅ Windows → WSL 的 `http://localhost:8000` 可用 → 小程序能打到 WSL 里的后端。
- ❌ 反向不可用 → **jest 必须在 Windows 上运行**，`application` 仓库需要在 Windows 侧也有一份。
- 想在 WSL 里跑就得在 Windows 上做 `netsh portproxy` 转发 9420 → **不建议**（多一层会坏的环节）。

**区分两个端口**：**9420 是自动化端口**（automator 用）；**服务端口**（如 55975）用于 CLI 登录/预览/上传。在开发者工具「设置 → 安全设置 → 服务端口」里开启自动化测试。

## 三、jest 配置

`application/jest.e2e.config.js`（独立文件，不要和将来前端单测的 vitest 配置合并）：

```js
module.exports = {
  globalTeardown: '@dcloudio/uni-automator/dist/teardown.js',
  testEnvironment: '@dcloudio/uni-automator/dist/environment.js',
  testEnvironmentOptions: {
    compile: true,                 // 自动编译，不需要单独的 build 步骤
    'mp-weixin': {
      port: 9420,
      launch: true,
      teardown: 'disconnect',      // 保留 devtools，避免每轮冷启动 6~12s
      remote: false
      // executablePath: 自动查找失败时才填
    }
  },
  testTimeout: 30000,              // 全局；SSE 用例内部单独设 130000
  testMatch: ['<rootDir>/e2e/**/*.e2e.js'],
  watchPathIgnorePatterns: ['/node_modules/', '/dist/', '/.git/']
}
```

```jsonc
// package.json 追加（不要覆盖已有 script）
"scripts": {
  "test:e2e": "cross-env UNI_PLATFORM=mp-weixin jest -i --config jest.e2e.config.js"
}
```

**API 要点**：
- uni-automator 通过 `testEnvironment` **注入全局 `program` 对象**（不需要手动 launch）。
- 取页面：`program.currentPage()`；导航：`program.reLaunch(...)`。
- mock：`program.mockUniMethod('showModal', {...})` / `program.restoreUniMethod(...)`。
- 调 uni 方法：`program.callUniMethod('setStorageSync', ...)`。
- `program.evaluate` **仅在开发者工具模拟器可用**，且**无法闭包引用外部变量**。

**微信端硬限制**：
- **element 不能跨组件选择**，**不支持父子选择器** → `page.$('.a .b')` 无效，要分两次 `$`。
- 分包页面 `reLaunch` 后需 `await page.waitFor(7000)` 再取 `currentPage()`。**本项目未配置分包**（`pages.json` 无 `subPackages`），暂不受影响 —— 但改动 `pages.json` 时要留意。
- `testMatch` 必须与前端单测（vitest）**分开**，否则 `npm test` 会互相抢文件。

## 四、版本风险（可能推翻整条路线）

| 事实 | 后果 |
|---|---|
| uni-automator 要求 **jest ≤ 27.0.4**、`jest-environment-node ≤ 27.5.1` | 必须装 jest 27 |
| 本机 `node -v` = **v22.21.0** | **jest 27 官方支持的 Node 范围是 10/12/14/15/16**，**不含 22** |
| jest 27 的传递依赖在 Node 18+ 有已知告警/报错 | 可能启动即崩 |

**处置顺序**：
1. **先实测** Node 22 + jest 27 能否跑通（可能没事，只是不在支持列表内）。**这一步要在动手前做，不要等到写完用例才发现。**
2. 跑不通 → Windows 侧用 `nvm-windows` 装 **Node 16 或 18** 作 E2E 专用，与开发用的 Node 22 隔离。
3. 都不行 → 切 **Plan B（Minium）**。

**另一个已知故障族**（症状与处置）：
- `launch()` `spawn EINVAL`（Node 24 + Windows，BatBadBut 相关）→ 绕过 `.bat`，直接 spawn 同目录的 `node.exe + cli.js`。
- **`Page.*` 协议族整族超时**（`page.$` / `page.$$` / `page.data()` / `setData` / `tap` 全挂，但 `App.*` 与 `evaluate` 正常）→ 这是 **SDK 与开发者工具的版本错配**，处置是**换回已知可用的 devtools 版本**，不是改用例。
- **"亚秒级 launch 成功"是坏信号**：devtools 被 kill 后不会立即释放 9420，残留会话会让 `launch()` 在 0.4s 内假连上。正常冷启动需 **6.5–12.3 秒**。

## 七、与后端 pytest 栈的配合

选 uni-automator 就意味着**两套运行器**（这是它唯一的代价）：

| 受众 | 命令 |
|---|---|
| 后端 | `poetry run pytest`（含 L3 契约测试，marker `contract`） |
| 前端 | `npm run test:e2e` |

**桥接方式**：
1. **夹具复用后端能力**：`ai-etf/docs/e2e/scripts/e2e_fixture.py` 提供 `register` / `token` / `cleanup`，前端 E2E 通过 `execSync` 调用它 → 前端仓库不写任何后端逻辑。（**没有 `confirm-pending`**，理由见 [参考 02 §四](02-夹具与断言设计.md)。）
2. **交叉断言**：E2E 用夹具 token 直连后端读真值比对 UI，天然把两仓库串起来。
3. **统一用例编号**（`P1-03` 这种）：两套报告靠编号拼成一张总表。
4. **CI 编排**：L3 与 L4 分开 job，L4 需要 **Windows runner**。

**marker 约定**（后端）：现有 `addopts = "-m 'not integration and not eval'"` 是**黑名单**，所以新增的 `contract` marker 会**默认运行** —— 正合适，因为契约测试大多是静态断言（读 `app.routes` / `openapi.json`），不联网、不碰数据库。需要真实响应字节的那条（SSE 帧契约）复用已有的 `integration_net`（默认不跑）。**只新增一个 marker，不破坏现有体系。**
