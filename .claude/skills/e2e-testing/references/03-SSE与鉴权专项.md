## 一、SSE 流式接口

### 1.1 先接受能力边界

**小程序端的 SSE 无法在自动化里被直接观测。** 原因不是工具选得不好，是协议能力的边界：

`program` / `miniProgram` 的 API 全集是 **页面导航 / 元素查询与交互 / 页面数据读写 / 截图 / `callMethod` / `mockMethod` / `evaluate`** —— **没有网络拦截、没有响应监听、没有请求计数**。开发者工具本身有 Network 面板，但 automator 协议不暴露它。

**并且** `RequestTask.onChunkReceived` 的**回调时机、chunk 大小、是否合并小 chunk 全部由微信运行时决定**，不受你控制。

> 推论：**"必须收到 N 个 chunk"这类断言不可写。** 这是最反直觉的一点 —— 在小程序自动化里，"验证数据是分块到达的"这件事本身是不可靠的。硬写只会得到随机红绿的用例。

### 1.2 处置：三层各司其职

| 层 | 能拿到什么 | 断言什么 |
|---|---|---|
| **前端单测（核心）** | 人造的分块字节流 | ⭐ 把 3 字节中文**手动切成 2+1 两个 chunk**，断言输出无 `�`；emoji（4 字节）同理；非法字节 → `�`；有/无 `TextDecoder` 两条实现；`parseSSELine` 的 `done`（带 `chat_id`）/ `error` / 坏 JSON → `null` / 空行 |
| **契约测试（核心）** | 原始响应字节（httpx 直连） | `Content-Type: text/event-stream`；响应头有 `X-Session-ID`；帧格式严格 `data: {...}\n\n`，**无** `event:`/`id:`/`retry:`；至少 1 个 `token` 帧；**恰好 1 个**收尾 `done` 帧；中文以原始 UTF-8 出现（校验 `ensure_ascii=False`） |
| **E2E（只验用户可见结果）** | 只有 UI | 见下 |

**为什么单测必须做**：`createUtf8StreamDecoder` 存在的**唯一理由**就是"中文被切在两个 chunk 之间"。这个场景在 E2E 里**永远复现不了**（运行时不给你控制分块的机会），只能靠人造分块。这是全项目最值得写单测的一个函数。

> ⚠️ 该函数目前**内联在 `pages/index/index.vue` 里且未 export**，要单测必须先抽到 `src/utils/sse.ts`（纯搬运、不改逻辑）。这是需要**先征得同意**的生产代码改动。

### 1.3 E2E 层怎么断言

按可靠性排序：

| 手段 | 做法 | 评价 |
|---|---|---|
| ① **UI 文本采样**（推荐，无需钩子） | 发送后对 bot 气泡文本以 ~300ms 间隔采样 5 次，要求**至少出现 2 个互不相同的非空文本** | "流式"的弱证据，但能区分"流式"与"一次到位"。**不需要前端配合** |
| ② **后端交叉验证** | 发送后用夹具轮询 `GET /api/secure-chat/chats`，确认出现新会话且标题 == 问题前 20 字 + `...` | 验证 `done` 帧的 `chat_id` 确实被前端落地了 |
| ③ `evaluate` 读 store | 读 Pinia store 的状态 | 最精确，但 store 通常不在页面实例 `data` 上，需前端暴露测试钩子（如 `getApp().globalData.__chatStore`），**需先确认** |
| ❌ 监听网络 | — | automator 没有这个能力 |

### 1.4 ⚠️ 必须规避的假阳性

前端在出错时会把异常写进气泡：`抱歉，${message}。`

→ **任何"AI 有回复"的断言都必须排除以「抱歉，」开头的文本。**
否则 LLM 超时 / 报错会被判成成功 —— 这是 SSE 用例里最容易出现的假绿。

### 1.5 超时

前端自己设了首 token 65s / 总请求 120s 的超时。所以：
- 该用例的 `testTimeout` 至少 **130000**（jest 默认 5s，全局配置通常 30s）
- 它会**独自拖长整个 suite 2 分钟以上**
- 真实 LLM 有成本且非确定性 → 默认不建议进 CI

**让 P2 进 CI 的办法**（建议提给后端）：加一个 `E2E_MOCK_LLM` 开关，命中时把 SSE 换成**确定性内容**，但仍走真实的 `StreamingResponse` 与 `sse.py` 封装。收益：可进 CI、可断言内容而不只是结构、若 mock 故意分成多个小帧还能把"文本递增"这条弱证据变成强证据。
⚠️ 必须**仅在非生产可用**（参考 `_get_test_user` 的 `ENV != production` 保护写法）。

## 二、登录态过期与 401 跳转

### 2.1 必须测两个分支（代码路径完全不同）

| 分支 | 造状态的方法 | 触发点 | 特征 |
|---|---|---|---|
| **A 本地过期** | 篡改本地存储的过期时间为过去，**不动 token** | 本地校验失败，**不发任何 HTTP 请求** | 无网络往返 |
| **B 服务端 401** | **服务端撤销 token**（进黑名单），**保留本地存储不动** | 请求返回 401，走拦截器 | 有一次完整往返 |

**只覆盖一条会漏掉一半。** B 分支的关键设计是 **"服务端撤销 + 保留本地态"** —— 如果顺手把本地存储也清了，就会走成 A 分支，B 分支永远测不到。

### 2.2 本地过期分支的坑：三个条件

本地有效性校验通常是**三重**条件（`token 未过期` ∧ `本地 expireTime 未到` ∧ `expireTime <= loginTime + 1h`），第三个是**防篡改**的。

→ 所以篡改时**只改 expire_time 是不够的**（要同时满足"看起来已经过期"）。写用例前先读一遍校验函数的实现，不要凭"把时间改成过去就行"的直觉写。

### 2.3 必须显式断言"行情放行"这个例外

请求库对 `/api/market/` 有**特判放行**：未登录时行情接口**照常发请求、不跳转**，而其他受保护接口**必须**跳转。

**这是最容易让"401 该跳转"用例假绿的地方**：如果测试时恰好打的是行情接口，用例会"通过"，但受保护接口的跳转可能已经坏了。

→ 一条好的对比用例：
1. 清空本地登录态
2. 访问行情接口 → 断言**不跳转**且**有结果**
3. 访问受保护接口 → 断言**立即跳转**

①②③ 一起才固化住这条规则。

### 2.4 跳转断言的时序

跳转逻辑带**互斥锁 + 两段 `setTimeout`**（约 250ms + 300ms，为了等 toast 展示）。

→ 断言跳转要：
- **轮询等待**（`currentPage().path` 变成登录页），超时设 **3s**
- **不要**用固定 `sleep`，也不要在 200ms 内就断言（必然失败）

同时断言本地存储的 4 个 auth key 被清空。

### 2.5 原生弹窗/提示必须桩掉

`uni.showModal` / `uni.showToast` / `wx.showToast` 是**原生 UI**，读不到也驱动不了 → 用 `mockUniMethod`（uni-automator）或 `mockWxMethod`（miniprogram-automator）**捕获调用参数**再断言文案。

- 桩 `showToast` **不阻断后续逻辑**（跳转仍会执行），所以可以放心桩掉整个用例。
- 桩 `showModal` 时可以回填 `{confirm: true, content: '...'}` 来模拟用户确认与输入（重命名会用到 `editable: true`）。
- ⚠️ **若桩失败，先检查是否误入了 H5 分支**：这类代码常写成 `window.confirm` 优先、`uni.showModal` 兜底。小程序端 `window` 应为 undefined。

### 2.6 一个容易忽略的收尾用例

**过期后重新登录要验证"内存态已清空"**：重新登录同一账号后，首页不应残留上一个会话的消息/会话列表。这验证的是登录成功时的 store 重置逻辑，很容易被漏掉。

### 2.7 依赖提示

服务端登出的黑名单是**内存态** → 若后端进程在此期间重启，被撤销的 token 会"复活"，该用例会红。**用例说明里要写明**，本地跑时不要重启后端。
