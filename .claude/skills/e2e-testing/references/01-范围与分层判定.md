## 一、范围闸门的实操判法

### 1.1 怎么确认"前端真的有入口"

不要靠印象，靠搜索。在 `application/src/` 里搜后端路径片段：

```bash
cd application
grep -rn "portfolio/positions\|market/search\|secure-chat/chats" src/ --include=*.ts --include=*.vue
```

**关键陷阱：搜到 ≠ 有入口。** 本项目已知有三类"假入口"：

| 假入口类型 | 例子 | 怎么识破 |
|---|---|---|
| **空模块** | `src/api/modules/etf.ts`、`src/api/modules/user.ts`、`src/api/request.ts` 是 `export {}` | 文件里只有 `export {}` 就是没接线 |
| **死 composable** | `useEtf` / `usePortfolio` / `useRequest` / `useSupabaseAuth` 无人 import | `grep -rn "usePortfolio" src/` 看有没有调用方 |
| **修复落在死代码里** | `useMarketQuery.ts` 里改了 `limit` → `top_n`，但该文件无任何导入方 | 改了对线上毫无影响，对应接口**仍然**没有可用入口 |

→ 所以判据是：**该路径被至少一个"用户可达的页面/组件"实际调用**。

### 1.2 本项目的不测范围（改动前后都要确认）

| 范围 | 具体内容 | 处置 |
|---|---|---|
| 草稿代码 | `server/graphs/`、`server/agents/` 的 Agent 图与追问链 | 不分析、不测、不设计用例、不修 bug |
| 软工作业 | `server/api/upload.py`、`document_service`、`rag/`、`graphs/document/` | 同上 |
| 前端未接线的后端端点 | 19 个（见 `01-页面与API调用关系.md` §4.2） | 不做 E2E 步骤；接口级覆盖交给后端集成测试 |
| `X-User-Id` 开发端点 | 7 个（`/api/portfolio/test/*`） | 生产环境返回 404；生产下不可用。可作夹具，**不作被测路径** |
| 无前端入口的业务端点 | 含 `POST /secure-chat/delete-account`、`POST /portfolio/confirm-pending` 等 | **可作夹具，不作被测路径** |

> `delete-account` 特别容易踩：它在"要测"的业务范围内（注销功能），但前端**零调用**。所以它的覆盖方式是**接口级用例**，不是 E2E 步骤。

## 二、分层归属：完整判定表

判断顺序（从上往下，命中即停）：

1. **这条断言需要原始响应字节吗？**（帧格式、响应头、编码方式、字段名）
   → **契约测试**。只有这一层能拿到字节。
2. **这条断言能用人造输入在几秒内判完吗？**（纯函数、分块解码、TTL 计算、字符串映射）
   → **前端单测**。不需要开发者工具、不需要网络。
3. **这条断言是"拦截器 / 请求库 ↔ store"之间的交互吗？**（401 处理、token 注入、放行例外、竞态丢弃）
   → **前端集成测试**（mock `uni.*`）。不需要真实渲染。
4. **这条断言是"后端路由是否存在 / 参数名是否对齐 / 鉴权分级是否被改"吗？**
   → **契约测试**（静态读 `app.routes` / `openapi.json`，不联网）。
5. **剩下的、只能由"用户看见什么"来证明的** → **E2E**。

### 分层速查表

| 断言对象 | 层 | 本项目落点 |
|---|:---:|---|
| SSE 帧格式、`X-Session-ID` 响应头、`ensure_ascii=False` | 契约 | `tests/contract/`，marker `integration_net` |
| 前端调用点 ↔ 后端路由存在性 | 契约 | `tests/contract/`，marker `contract` |
| 鉴权分级不被误改（JWT/公开/`X-User-Id`） | 契约 | 同上 |
| `X-User-Id` 端点在 `ENV=production` 下 404 | 契约 | 同上（monkeypatch 环境变量） |
| 分块边界、UTF-8 被切断、JSON 解析失败 | 前端单测 | `src/utils/__tests__/sse.spec.ts` |
| JWT 解析、会话有效期 `min()` 三分支、防篡改条件 | 前端单测 | `src/utils/__tests__/auth.spec.ts` |
| 401 跳转、token 注入、行情放行、竞态丢弃 | 前端集成 | `request.integration.spec.ts` |
| 页面跳转、弹窗文案、列表更新、金额展示 | E2E | `application/e2e/` |

## 三、放错层的真实代价（案例）

**案例 A：把 SSE 帧格式放进 E2E。**
想断言"响应是流式的、有多个 token 帧"。但 automator 没有网络层 → 只能靠 UI 采样猜。结果是一条**随机红绿**的用例：LLM 快的时候 1 个 chunk 就结束，断言挂；慢的时候过。真实问题（分块解码）反而没被验证。

**案例 B：把"后端错误文案"放进单测。**
后端文案是产品语义（`可用现金不足：需 1000.00 元，实际可用 500.00 元`）。写在单测里会和后端实现耦合；放在 E2E 里断言 UI 上出现的完整文案才有意义。

**案例 C：把"路由存在性"放进 E2E。**
历史上 `PUT /api/secure-chat/chats/{chat_id}/title` 缺失导致重命名必 404。如果在 E2E 里发现，要跑完整的"发消息 → 开抽屉 → 点重命名 → 桩弹窗"才能暴露，几百秒；而在契约层是一行静态断言，几毫秒。

## 四、五个「看起来像 E2E 但不该做 E2E」的场景

1. **"验证接口返回的字段结构"** → 契约测试。E2E 拿不到响应体。
2. **"验证分块流式"** → 单测（人造分块）+ 契约（帧格式）。E2E 只能证明"用户最终看到了回复"。
3. **"验证某个前端未接线的功能"** → 接口级测试。前端没有入口，E2E 走不通。
4. **"验证 LLM 回答得对不对"** → 不属于 E2E 的职责。E2E 只断言结构与"没有走错误分支"（排除 `抱歉，` 前缀）。
5. **"验证金额算得对"** → 后端单测 / 集成测试算准确性；E2E 只验证金额**显示出来且与后端真值一致**（交叉断言）。
