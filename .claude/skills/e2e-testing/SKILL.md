# 端到端（E2E）测试 SOP

覆盖 `ai-etf`（FastAPI 后端）与 `application`（uni-app + Vue3 微信小程序）两个**独立 git 仓库**的 E2E 工作。

**完整规划文档在 `ai-etf/docs/e2e/`**（00 背景与范围边界 / 01 页面与 API 调用关系 / 02 核心路径与分层策略 / 03 用例清单 / 04 工具选型 / 05 执行计划 / 06 协作提示词与验收清单）。本 skill 是**执行这些文档时的规范**，不是它们的替代品 —— 具体某条用例的步骤与预期，去 03 查；环境与工具坑，去 04 查。

## 为什么需要这份 SOP

E2E 最容易犯的错不是"写不出来"，而是**写出一条永远绿（或永远红）的用例**：断言了一条前端根本走不到的链路、把 LLM 的随机回复写死、把 `SKIP` 当 `PASS` 上报。这些错不会报错，只会让整个测试体系失去可信度。下面每一步都是为了让这件事不发生。

---

## Step 0：范围闸门（**不通过就停下来问人，不要开始写**）

按顺序问三个问题，任何一个答"否"就不要写用例：

**① 这条链路用户真的走得通吗？**
前端有没有真实的调用点？本项目有 **19 个后端端点是前端零调用的**（清单见 `01-页面与API调用关系.md` §4.2）。为它们写 E2E 步骤必然跑不通 —— 它们只能做接口级测试。
判断方法：在 `application/src/` 里搜接口路径，确认有真实调用点，而不是只存在于死代码（如 `useMarketQuery.ts`、空的 `api/modules/*.ts`）。

**② 它属于"不测"的范围吗？**
两组内容被明确排除，**不要分析、不要测、不要设计用例、不要顺手修 bug**：
- **草稿代码**：`server/graphs/`、`server/agents/` 里的 Agent 图与追问链
- **软工作业**：文档上传 / 文档分析（`upload.py`、`document_service`、`rag/`、`graphs/document/`）

**③ 这个断言已经由更低层覆盖了吗？**
如果是，就不要放在 E2E 里 —— 见 Step 2。

## Step 1：确定路径与用例编号

从已定的 **5 条核心路径**里选，不要临时发明新路径（新路径需要先更新 `02-核心路径与分层策略.md`）：

| 路径 | 内容 | 优先级 |
|---|---|---|
| **P1** | 交易核心：持仓 → 申购（pending 语义）→ 赎回拦截 → 流水 | P0 |
| **P2** | AI 对话核心：发消息(SSE) → 会话列表 → 历史消息 → 重命名 → 删除 | P0 |
| **P3** | 行情 + 自选：搜索 → 详情/K线 → 加自选 → 移除 → 清空 | P1 |
| **P4** | 鉴权失效：本地过期分支 + 服务端 401 分支 | P0 |
| **P5** | 注册 + 风险测评 | P2 |

用例编号用 `P<路径号>-<两位序号>`（如 `P1-03`）。**编号必须与 `03-E2E用例清单.md` 一致** —— 两套报告（jest 与 pytest）靠它拼成一张总表。

## Step 2：分层归属判定（**本 SOP 最核心的一步**）

原则一句话：**把每一条断言下沉到"能拿到原始字节"的最低层，E2E 只验证用户看得见的东西。**

每写一条断言前，先问"我要证明的东西，在哪一层能拿到证据"：

| 要证明什么 | 放哪层 | 为什么 |
|---|---|---|
| 帧格式、响应头、UTF-8 编码方式 | **契约测试**（httpx 直连后端） | 只有这层能拿到**原始字节** |
| 分块边界、UTF-8 被切断、JSON 解析失败 | **前端单测**（人造分块喂给纯函数） | 分块时机由微信运行时决定，自动化里**不可控**（见 Step 5） |
| 纯函数、store 状态变更、有效期计算 | **前端单测** | 不需要开发者工具、不需要网络，几秒就能跑 |
| 401 拦截、token 注入、行情放行例外、竞态丢弃 | **前端集成测试**（mock `uni.*`） | 这些是"拦截器 ↔ 请求"的交互，不需要真实渲染 |
| 路由存在性、参数名对齐、鉴权分级 | **契约测试**（读 `app.routes` / `openapi.json`） | 静态可判，**不联网**，成本最低 |
| 页面跳转、弹窗文案、列表是否更新、用户最终看到什么 | **E2E** | 只有 UI 能证明 |

**E2E 里不要写这些断言**（写了就会得到随机红绿）：
- ❌ 流式的分块数量（`chunkCount > 1`）
- ❌ SSE 的帧格式细节
- ❌ LLM 回复的具体文本内容（非确定性）
- ❌ 精确到分的金额 —— 除非**同时**用夹具拿后端真值交叉验证
- ❌ "没有发出请求" —— automator 没有请求计数能力

## Step 3：夹具设计

**① 用一次性账号，不要用固定测试账号。**
每次运行前注册 `e2e<unixts>@ai-etf.xyz`。原因不是洁癖：交易相关断言依赖**精确数值**（`INITIAL_CASH = 100000.00`、`frozen_cash = 0`、`position_count = 0`），固定账号跑第二遍数值就变了，用例会永久变红。

**② 为什么新账号的起点是干净的**：`auto_invest_enabled` 默认 `false`，所以新用户不会被自动申购货基 → 无持仓、无订单、无流水。这个前提**一旦被改动，夹具设计就要跟着改**。

**③ 夹具走 HTTP，不要 import `server.*`。**
夹具脚本（`ai-etf/docs/e2e/scripts/e2e_fixture.py`）用 `httpx` 调接口。如果直接 import 后端模块，夹具会和被测服务共享进程状态（连接池、缓存、内存态黑名单），断言就被污染了。

**④ ⭐ 先过"状态可达性闸门"，再谈时间门控。**
在设计任何依赖某个状态出现的用例之前，先问：**这个状态靠前端操作 + 合法接口，在本次会话内真的能到达吗？**

三种答案，处置完全不同：

| | 处置 |
|---|---|
| 只在某时间窗口内可达 | 加**跳过守卫**，窗口外 `skip` 并写明原因（Step 6）。守卫要用后端能力判（`_is_trading_day` 依赖 `akshare` 日历），别自己用 `weekday()` |
| **会话内永久不可达**（需 T+N 确认、次日结算、外部回调等跨会话异步环节） | **不要写这条用例**。覆盖下沉给能冻结时钟的层（后端集成测试 / 单测）。⚠️ 判这一类**必须逐分支**——同一功能的不同方向可能落库字段不同，一侧不可达、另一侧却有窗口 |
| **接口可达，但那只是夹具能走，UI 走不到** | 这**不算**"会话内可达"。若 UI 上没有任何入口能触发该动作，用户路径就不成立 → 按**需要构造状态**处理，并在用例里写明"该动作由夹具触发，非用户操作" |
| 接口可用但前置状态造不出来 | **夹具回填状态**（直接改库字段），用例里注明"只验证状态之后的表现" |

**判断靠读状态机，不靠猜"今天是不是好日子"。** 本项目踩过**两次**这个坑，而且方向相反：

1. **读得不够深**：「申购 → 确认 → 持仓出现」曾被写成"仅交易日 00:00–14:59 可跑的时间门控用例"——**错**。落库的确认日 = 受理日**再加 `confirm_delay` 个交易日**（`110020` 的 `confirm_delay = 1`），刚下的单**当天永远确认不了**，属第二类，任何门控都救不回来。
2. **推广得太宽**：修完 ① 后把结论写成"**任何途径都无法在下单当天确认**"——**又错**。这句只对**买单**成立：`confirm_delay` 只出现在 `apply_purchase`；**赎回**走 `apply_redeem`，落库的是**未推进**的 `confirm_date`，交易日 15:00 前下单**当天就能确认**。

> **所以：可达性要按「分支/方向」逐条判，不能按「功能」一刀切。** 申购与赎回在前端是同一套 UI、同一个 `pending` 概念、同一个 `confirm-pending` 端点，但落库字段不同（`actual_confirm` vs `confirm_date`），可达性就完全相反。看到"同一个业务概念"就照搬同一个结论，正是第二个坑的根因。

**具体动作：一路跟到落库那一行，不要停在第一次赋值。** 这类计算常有"受理日 → 调整后确认日"两跳，而中间那个变量可能根本不落库（本项目赎回的 `settle_date` 就只用于拼提示文案，实际入账在确认日）。

> 一句话：**时间门控只适用于"窗口内真的能跑"，不适用于"永远跑不了"；而"永远跑不了"必须逐分支验证，不能从一个分支外推。** 看到 T+N / 确认 / 结算这类词，先算一遍最终落库的字段。详见 [参考 02 §四](references/02-夹具与断言设计.md)。

**⑤ 清理要配套。**
注册类用例每跑一次就真写一个 Supabase 用户 → 结束时调 `POST /api/secure-chat/delete-account`。注意这个接口**前端零调用**，所以它只能作夹具，**不能**设计成一条 E2E 路径。

**⑥ 交叉断言用夹具的 token。**
涉及数值的用例，用夹具拿到的 token 直连后端读真值，再比对 UI 文本。这是唯一能防住"UI 和后端一起错"的手段。

## Step 4：编写用例（固定模板）

每个用例都要有这六项，缺一不可：

```markdown
### P<路径>-<序号> <用例名>

| | |
|---|---|
| **前置** | 需要什么状态（账号、持仓、登录态） |
| **步骤** | 1. … 2. … （具体到元素与输入值） |
| **预期** | ① … ② … （可判定的结果，不是"正常显示"） |
| **交叉断言** | 用夹具 token 请求哪个接口，比对什么字段 |
| **依据** | 文件:行号 —— 这条断言的业务规则写在哪里 |
| **需确认** | 如果有，写清"缺什么信息、我的判断依据是什么" |
```

**三条断言纪律**：

1. **每条断言都要有「依据」（file:line）。** 不能因为"代码看起来应该这样"就断言业务规则。真实的例子：详情页的 `quote` 与 `tradeable` 是**互斥**的（白名单基金的 `quote` 恒为 `null`，导致 K 线接口根本不会被调用）—— 不知道这件事就会写出永远失败的用例。
2. **负例必须断言到确切文案。** 后端错误文案是产品语义的一部分（`基金 {code} 存在待确认的申购订单，份额确认前无法赎回`）。断言"出现了错误提示"是没有价值的。
3. **测试标的要选对。** 同一个页面里不同分支要求不同的标的代码：申购必须用**场外白名单**代码，K 线与行情必须用**场内 ETF** 代码。选错代码用例必挂 —— 写用例前先确认标的落在哪个分支。

**模板选择器**：优先 `id`（uni-app 的 `id` 会透传到 wxml）。注意微信小程序的硬限制：**不支持父子选择器**，**不能跨组件查询元素** → `id` 要加在**页面直接层级**的元素上。

## Step 5：两个专项

### 5.1 SSE 流式接口（首页 AI 对话）

**先接受一件事：小程序端的 SSE 无法在自动化里被直接观测。** automator 的 API 全集是"页面导航 / 元素查询交互 / 数据读写 / 截图 / mock / callMethod / evaluate"——**没有网络层**，抓不到帧。

而且 `RequestTask.onChunkReceived` 的**回调时机、chunk 大小、是否合并小 chunk 全由微信运行时决定**，不受你控制。所以"验证数据是分块到达的"这件事在小程序自动化里**做不到**。

**处置**：把协议断言下沉到两层 —— 单测喂人造分块（特别是"3 字节中文被切成 2+1"这个核心场景），契约测试用 httpx 断言帧格式与响应头。E2E 只做结构断言：非空、**不以「抱歉，」开头**、角色为 bot、文本采样出现 ≥2 个不同值（弱证据，但能区分流式与一次到位）。

> ⚠️ **必须规避的假阳性**：前端在出错时会把异常写进气泡（`抱歉，${message}。`）。任何"AI 有回复"的断言都要排除这个前缀，否则 LLM 超时会被判成成功。

### 5.2 登录态过期与 401 跳转

**必须分两个分支测，缺一不可**，因为它们的代码路径完全不同：

| 分支 | 怎么造状态 | 触发点 |
|---|---|---|
| **本地过期** | 篡改本地存储的 `expire_time` 为过去（**不动 token**） | 本地校验失败 → **不发请求**就跳转 |
| **服务端 401** | 服务端撤销 token（进黑名单），**保留本地存储不动** | 请求返回 401 → 走拦截器跳转 |

只覆盖一条会漏掉一半。**服务端分支的关键设计是"服务端撤销 + 保留本地态"** —— 如果顺手把本地存储也清了，就会走成本地过期分支，测不到 401。

另外**必须显式断言"行情接口放行未登录"这个例外**：未登录时 `/api/market/` 不跳转、正常返回，而其他受保护接口必须跳转。这是最容易让"401 该跳转"用例假绿的地方。

**断言跳转要给足时间**：跳转逻辑带互斥锁 + 两段 `setTimeout`（约 250ms + 300ms），所以要等待 ≥600ms，用**轮询**而不是固定 `sleep`。

**原生弹窗要桩掉**：`uni.showModal` / `uni.showToast` / `wx.showToast` 是原生 UI，读不到也驱动不了 → 用 `mockUniMethod`（uni-automator）/ `mockWxMethod` 捕获调用参数。**若桩失败，先检查是否误入了 H5 分支**（代码里常常是 `window.confirm` 优先、`uni.showModal` 兜底）。

## Step 6：结果上报（三态，**不许合并**）

| 结果 | 含义 |
|---|---|
| `PASS` | 真通过 |
| `FAIL` | 真失败 |
| `SKIP(原因)` | **不可判定** —— 时间窗口外 / 真实 LLM 成本 / 环境未就绪 |
| `N/A(不可达)` | **设计阶段就判定该状态会话内不可达、故不写此用例** —— 必须在文档里写明它被下沉到哪一层（例：确认后建仓 → 后端集成测试 `test_scheduler_jobs.py`）。**这是与 SKIP 不同的第四种结局**：SKIP 是"用例存在但这次没跑"，N/A 是"这条用例就不该存在" |

**绝不能把 `SKIP` 当 `PASS` 上报。** 这会掩盖"某条用例从来没跑过"这个事实 —— 而"从来没跑过"和"通过"在报告里长得很像，是测试体系失效的最常见方式。

**金丝雀检查（每条核心路径至少做一次）**：故意把对应的后端规则改坏 → 用例**必须变红** → 恢复。
不做这一步，你无法区分"用例通过了"和"用例根本不会失败"。目前已知的金丝雀：交易链路的 pending 语义、鉴权链路的两条分支、契约测试的路由存在性。

**报告里要写清每条用例的**：编号、结果、耗时、SKIP 原因（如果有）、以及它依赖的外部条件（时钟 / 网络 / 真实 LLM）。

## 红线

1. **发现缺陷只登记，不顺手修。** 包括看起来"顺手就能改"的（例如某个跳转用了 `uni.switchTab` 而项目没有 tabBar 配置）。修了会让用例的「依据」失准。
2. **不擅自改生产代码。** 涉及范围：前端 `src/**`（除测试配置）、后端 `server/**`。改动前先问人，并说明最小改动方案。
3. **不确定就标「需确认」** —— 写清缺什么信息、你的判断依据。**不要编。**
4. **不自己换技术方案。** 工具选型的结论在 `04-工具选型.md`，换方案要人拍板。
5. **不为了"跑绿"而放宽断言。** 用例红的时候先确认是用例错了还是代码错了。
6. **测试标的、账号、断言文案都要有依据**，不能凭直觉。
7. **不碰 `supabase/`、不读 `.env` 内容**（只看 key 名）、后端依赖用 poetry 不用 pip。
8. **不直接改 `dev` 分支，不擅自 commit / push。**
9. **这份 skill 在两个仓库各存一份，内容必须逐字节一致。** 真源是 `ai-etf` 那份（`docs/e2e/00–06` 在 ai-etf，skill 由它派生）。要改就**两边一起改**，并在 `ai-etf` 跑
   `docs/e2e/scripts/sync_e2e_skill.sh`（`--check` 只校验、不写入）。
   只改一份**不会报错**——但会让前端和后端"都按规范做了"却对不上，这是最难查的一类问题。若你只有其中一个仓库的权限，**在交付说明里写明"另一份需要同步"**。
