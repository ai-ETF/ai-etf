# 单元测试 SOP

### Step 1：确定测试目标

* **测试模块名称**
* **模块功能或具体测试场景**

AI 根据提供的信息定位需要测试的代码。

---

### Step 2：代码检查与预期行为

AI 分析被测代码是否满足单元测试的前提条件，包括依赖注入等。

单测须**禁网、禁外部 IO**（不连数据库、不调真实外部服务），与 `pyproject.toml` 中 `unit` marker 的「禁网、禁外部 IO」口径一致；需要联网/连库的路径用替身（Fake/Stub）隔离。

* 如果不符合：提出最小修改方案，**待人批准后再修改代码**。
* 如果符合：无需说明此部分，直接进入下一步。

随后，AI 根据代码涉及的**实际业务环境**，编写本次测试的预期行为（正常、异常、边界），并据此规划数据集：

* **正常场景至少 2 组正确数据**：两组应覆盖不同的取值、字段组合或上游格式差异（例如不同日期区间、不同基金类型、不同返回结构），不能是同一组样本改个名字。
* **错误场景**：非法输入、缺失字段、上游错误码、格式漂移等，验证失败分类与异常信息。
* **边界场景**：空集合、单元素、最大/最小边界、日期临界（含/不含端点）、数值精度、可选字段缺失等。

> AI 不能因为代码看起来应该如此，就擅自定义业务规则。
> 如果代码行为无法判断，或存在多个合理的业务预期，应向人询问。

---

### Step 3：编写测试代码

根据已确定的测试预期编写测试代码。

**测试数据集要求：**

* **正确数据至少 2 组**，各组覆盖点不同（见 Step 2），并在注释或命名中说明它代表哪类真实样本。
* **必须包含错误输入与边界情况的用例**，不能只测 happy path。
* 断言要落到具体值或失败类型上，避免只断言「不抛异常」「结果非空」这类空泛条件。
* 样本尽量内联在测试文件中（或沉淀为 fixture），保证测试可独立运行、可追溯。

测试代码必须符合 **AAA（Arrange-Act-Assert）** 原则：

* **Arrange**：准备测试数据和测试环境
* **Act**：执行被测功能
* **Assert**：验证实际结果是否符合预期

测试代码中的头部注释需说明：

* **模块名称**
* **所测功能**
* **使用的测试方法**

---

### Step 4：提出测试数据集建议

测试完成后，AI 需结合被测代码的**真实上游特征**，给出可执行的数据集改进建议：

* 现有样本还没覆盖到的真实数据形态（例如历史兼容格式、上游异常字段、极值）；
* 哪些样本适合沉淀为固定 fixture，哪些需要定期用真实数据回放校验；
* 建议新增的样本及其预期断言，说明「补什么数据、覆盖什么行为、为什么需要」。

建议要具体到数据和行为，不要泛泛而谈「提高覆盖率」。

---

### Step 5：生成测试结果文档

测试完成后，生成一份测试结果文件，记录：

```
## <测试模块名称>

**功能** : 

### 测试数据集

| 数据组 | 覆盖场景 | 预期 |
| ------ | -------- | ---- |
|        |          |      |

### 业务场景

### 预期结果

### 测试结果

### 数据集建议

```
