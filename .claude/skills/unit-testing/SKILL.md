# 单元测试 SOP（人机协作）

一段固定分工：**人出题与验收，AI 检查 / 改造 / 写测 / 体检**。目标是让任意新模块都能稳定补上单测，且人不需要掌握 pytest 细节。

## 分工总览

| 环节 | 谁 | 要做什么 |
|---|---|---|
| 1 出题 | 人 | 给三要素：**被测模块 / 被测功能 / 预期结果**，并授权改动范围 |
| 2 代码体检 | AI | 依赖注入检查：找出该单元所有"外部依赖"，逐条判定是否可注入 |
| 3 改造决策 | AI→人 | AI 判定是否需要改生产代码并给出最小方案与理由；**人拍板后才动手** |
| 4 写测 | AI | 按纪律写单测、跑 pytest 到全绿 |
| 5 体检与汇报 | AI | 覆盖率体检、盲区分析、结果汇报 |
| 6 收尾 | 人 | review diff，决定 commit / 合并 |

## 人的部分（出题与验收——不懂 pytest 也没关系）

每轮开始时，人提供或确认以下 4 点：

1. **被测模块**：给文件路径（例：`server/auth/token_store.py`）。
2. **被测功能**：用大白话讲这段代码负责什么（例："登出/注销后把 token 记入黑名单，并判断它还能不能用"）。
3. **预期结果**：关键输入 → 期望输出，写成列表或表格（例："已撤销且未到期的 token → 返回 True；已过期的 → 返回 False 并被清理"）。
4. **改动授权**：是否允许改生产代码。默认只允许"**行为不变的最小改动**"（加可选参数 / 抽小函数），不允许顺手重构无关代码。

结束前：review AI 给的 diff 与汇报（改动文件、为什么行为不变、覆盖与盲区），再由人决定是否 commit。

## AI 的部分（五步）

### 步骤 1 · 代码体检（依赖注入检查）

- 用 codegraph 或读源码，列出该单元的全部**外部依赖**，归到四类：外部服务（LLM / Supabase / 行情源 / embedder）、时钟与随机（`time.time` / `datetime.now` / `random`）、配置值（`SETTINGS.xxx`）、文件 IO。
- 输出一张 **DI 判定表**：

| 外部依赖 | 现状调用点 | 是否已可注入 | 判定 |
|---|---|---|---|
| 例：时钟 `time.time` | `token_store.is_revoked` 内部硬编码 | 否 | 不符合 |

- **判定口径**：依赖从参数/构造传入 → ✅ 符合；函数内部硬编码抓全局（`get_llm()`/`get_supabase()`/`time.time()`/`SETTINGS.xxx`）→ ❌ 不符合。纯第三方离线库（如 `pyjwt` 本地解密）不算外部逻辑，无需替换。

### 步骤 2 · 改造决策（先讲清逻辑，等人拍板）

- 对每个不符合项给出**最小改动方案**，优先"**可选参数 + 生产默认值**"注入：在函数签名加可选参数，`None` 时走真实默认（例：`is_revoked(token, now=None)` → `None` 时取 `time.time()`）。
- 必须说明：改了哪里、为什么行为不变、现有生产调用点为何无需改（它们省略新参数即走默认）。
- **涉及金额 / 费率等关键计算**：先加"特征测试"锁定当前行为，再改代码。
- ⚠️ **不在未确认前改生产代码**；改动须等人在上一步输出中同意。

### 步骤 3 · 编写测试（单一职责纪律）

- 目录：`tests/unit/<server 下路径镜像>`（例：`tests/unit/server/auth/test_token_store.py`）。
- 一个测试类/函数只测**一个被测单元、一种行为**；Arrange–Act–Assert；断言可观察结果，不锁内部实现。
- **禁网、禁真实模型/DB/akshare、禁读 `.env`**；外部一律用替身（FakeLLM、Fake 客户端、注入固定时钟）。
- 异步被测函数用例加 `@pytest.mark.asyncio`。
- 金额断言用"双层"：字符串容错（`0.50%` / `0.5%` 均过）但数值精确。

### 步骤 4 · 跑到全绿

- 跑 `poetry run pytest -v`，迭代到全绿；顺手清掉**测试自身造成**的告警（如 pyjwt 要求密钥 ≥32 字节）。

### 步骤 5 · 覆盖率体检与汇报

- **节奏**：平时开发不开覆盖率（有开销）；合并前 / 给新模块补完测试后跑一次：
  `poetry run pytest --cov=<模块路径> ...`
- **解读**：`Stmts` 语句条数 / `Miss` 未被任何测试执行到的条数 / `Cover%` = 被执行比例。
- 对每个低覆盖模块判断盲区性质：是**故意不测的接缝**（真实接线、真模型工厂，应允许低覆盖并说明）还是**遗漏的分支**（需补测）。
- **汇报格式**（给真人看的）：
  - 结果：几个用例绿 / 耗时
  - 改动：改了哪些生产文件、为什么行为不变、调用点为何无需改
  - 覆盖率：各模块数字 + 盲区是否合理
  - 遗留：剩余告警 / 需要人拍板的事项

## 常用命令速查

```bash
poetry add --group dev pytest-asyncio pytest-cov   # 一次性装测试依赖（禁 pip）
poetry run pytest -v                               # 平时跑（快）
poetry run pytest -q                               # 安静模式
poetry run pytest --cov=server.llm -q              # 覆盖率体检（合并前用）
```

## 红线（任何情况不得违反）

- ❌ 单元测试不碰真实 IO：不联网、不调真 LLM/DB/akshare、不触发模型下载；不 import 整台 app（`server/__init__.py` 已惰性化，勿回退成 `from .app import app`，否则单测会被迫加载 torch 且 `--cov` 崩）。
- ❌ 生产代码改动必须**行为不变**、先讲清逻辑、经人同意；不顺手重构无关代码。
- ❌ 不把根目录遗留的 `test_qa.py` / `test_intent.py`（直连生产 + 真模型）当作单测基线。
- ❌ 覆盖率"高"≠"好"：100% 也可能什么都没验出来；盲区要逐个判断是"故意"还是"遗漏"。
- ❌ 项目规范：用 poetry 管理依赖、开发前拉远程、在新建分支上开发（不在 dev/已开发分支直接改）。

## 仓库内已有范例（对照用）

`test/unit-pilot` 分支已完成第一轮试点（认证 + LLM 流式归一），可作套路模板：

- `tests/unit/server/test_llm.py` — `astream_text` 流式归一（含防线上"推理模型流式崩溃"的回归用例）
- `tests/unit/server/auth/test_token_store.py` — 撤销黑名单（时钟经可选参数 `now` 注入）
- `tests/unit/server/auth/test_jwt_handler.py` — JWT 本地校验（secret 经可选参数注入，用同一 secret 自签造数据）

生产侧落地了两类最小改动：`is_revoked(token, now=None)`、`verify_supabase_token(token, secret=None)`（默认 `None` → 走真实默认），并把 `server/__init__.py` 改惰性导入。最终 12 passed、覆盖率 93%。
